## High

### H-1 · Покрытие Nansen переобещает то, что транспорт не умеет
`packages/core/src/adapters/nansen/index.ts:87,99,114,385` · `endpoints.ts:19`
**Найдено:** logic (H-1) + security (L-1) — `corroborated`, эскалации нет (одна модель, один механизм).

В задаче 006-9 `chainSupport()` подключён к спеке (17/25/25 сетей), но **транспорт не расширен**:
`isNansenChain()` по-прежнему `=== 'ethereum' || === 'solana'` и используется в `fetch()`.
Вендорский токен `chain.vendors['nansen']` читается **только** в предикате (`:385`) и никогда не
уходит в запрос — туда идёт наш слаг (`bsc` вместо `bnb`).

**Сценарий:** `onchain_token_risk({chain:'bsc'})` → схема OK → гейт покрытия «покрыто» →
`fetch()` бросает `invalid args` → ловится в `adapters/registry.ts` → **`CapabilityUnavailableError`**,
то есть *повторяемый* класс ошибки для постоянного условия. Агент ретраит бесконечно. Параллельно
`onchain_list_chains({capability:'token.risk'})` рекламирует ~24 сети, из которых работают 2.

**Деньги в безопасности — проверено критиком и подтверждено чтением:** throw происходит в
`validateArgs` **до** `gate.ensureBudget`, поэтому кредиты не резервируются и HTTP не идёт.

**Отягчающее:** мой собственный тест `test/nansen-coverage.test.ts:69-70` фиксирует это
переобещание **как правильное поведение**.

**Что делать:** либо расширить транспорт (заменить `NansenChain` на реестр и отправлять
`chain.vendors['nansen']`), либо сузить `chainSupport` обратно до двух сетей до этого момента.
Не отгружать предикат, который `fetch()` не может исполнить. Нужен инвариантный тест: для каждого
слага из `chainsFor(cap)` платной способности `fetch()` не должен бросать `invalid args`.

### H-2 · `.max(64)` не обрывает `superRefine` → неограниченный Левенштейн
`packages/core/src/chain/input-schema.ts:36-51` · `registry-core.ts:128-144,226-237`
**Найдено:** perf (H-2) + security (H-1) — `corroborated`, эскалации нет (один механизм).

**Измерено оркестратором** (`ChainInputSchema.safeParse('z'.repeat(N))`):

| N | время | результат |
| --- | --- | --- |
| 64 | 9.8 мс | отвергнут |
| 2 000 | 46.4 мс | отвергнут |
| 20 000 | **416.2 мс** | отвергнут |

Линейно по длине входа. В zod 4 `too_big` ставит `continue: true`, поэтому `superRefine`
выполняется на строке любой длины и уходит в Левенштейн по ~1300 кандидатам, аллоцируя новый
массив на каждой внешней итерации. 1 МБ ≈ секунды-минуты полной блокировки однопоточного
stdio-сервера — при том что запрос заведомо невалиден.

**Этот же класс дефекта проект уже закрыл** в `chain/address.ts:60` (`MAX_DECODABLE_ADDRESS_LENGTH`
перед base58) и компенсирует на четырёх `address`-путях (`get-token.ts:50-53` и др.). Для `chain`
компенсации нет ни одной. Существующий тест `chain-input-schema.test.ts:81-84` называется «bounds
the input length before doing any registry work», но проверяет только `success === false` — что
работа пропущена, он не утверждает.

**Что делать:** первой строкой `superRefine` — `if (raw.length > 64) return;`; плюс
`if (needle.length > 64) return [];` в `suggest()`; предвычислить `normalizeKey(candidate)` в
`buildIndexes`. Тест: `expect(elapsed(() => safeParse('x'.repeat(100_000)))).toBeLessThan(50)`.

### H-4 · Реестр пересобирается на каждый вызов инструмента
`packages/core/src/chain/input-schema.ts:70-72` + 8 хендлеров
**Найдено:** perf (H-1, стоимость) + logic (M-4, корректность) — **разные механизмы в одной точке**.

**Измерено оркестратором:**

```
loadChainRegistry() мемоизирован = false
build                              = 0.69 мс
canonicalizeChain('ethereum')      = 0.55 мс     ← так зовут все 8 хендлеров
canonicalizeChain('ethereum', reg) = 0.0001 мс   ← ×5500
```

Полный zod-разбор 458 строк + 4 индекса ради одного `Map.get`, на каждый запрос. На cache-hit —
пути, ради скорости которого весь кеш и существует — накладные расходы превышают полезную работу.
Плюс 8 удерживаемых экземпляров реестра (5 адаптеров + `CapabilityRegistry` + `ChainInputSchema` +
legacy-мост в `address.ts`), из них 5 строятся подряд на старте.

**Второй механизм (logic M-4):** хендлер канонизирует по *отгруженному* снапшоту, а гейт резолвит
по `ctx.registry.getChainRegistry()`. При инжекции своего реестра (документировано как
поддерживаемое) это два разных словаря.

> **Отклонение от правила эскалации Phase 2, п.3.** Разные механизмы в одной точке дают +1, что
> подняло бы находку до Critical. Не поднимаю: корректностная половина требует DI-пути, которым
> продовая сборка не пользуется (`mcp-server` всегда конструирует адаптеры без `chains`). Останется
> High; станет Critical, если кто-то начнёт инжектить свой реестр.

**Что делать:** `canonicalizeChain(input.chain, ctx.registry.getChainRegistry())` в хендлерах —
это чинит обе половины разом; либо мемоизировать дефолт в `registry.ts` (построенный реестр —
чистая функция от константы сборки, это не то изменяемое состояние, что запрещает §8).

## Medium

**M-1 · `nativeSymbol` — листинговый токен, а не газовый.** `scripts/sync-chain-registry.ts:363`
берёт `dl.tokenSymbol ?? eip.nativeCurrency.symbol`. В отгруженных данных: `op-mainnet → OP`,
`arbitrum → ARB`, `gnosis → GNO` — все трое платят газ в ETH/xDAI. Инвертировать приоритет для
EVM. **Чинить до H-3**, иначе фикс H-3 заменит один неверный символ другим.

**M-2 · 7 описаний инструментов всё ещё «on ethereum or solana».** Проверено: 7 файлов. Енум из
458 значений убран ради экономии ~7.8k токенов, и теперь **описание — единственный сигнал о сетях,
который модель видит при маршрутизации**. Оно описывает мир до TASK-006. Главная способность
задачи невидима её единственному потребителю. `chain-tvl.ts:71-73` сделан правильно — образец.

**M-3 · `rpcHosts: []` уводит запрос на хосты Ethereum.** `rpc-evm/index.ts:135-137`: пустой
массив проходит и `chainSupport` (`!== null`), и схему загрузки (`z.array(...).nullable()`), затем
`chainHosts.length > 0` ложно → fallback на `HOSTS`/`ENDPOINTS` Ethereum. Баланс чужой сети,
схема-валидный и закешированный. Латентно (в данных 439 × `null` + 19 курированных, нулей нет), но
`[]` — ровно то, что куратор напишет для «искал, не нашёл». Фикс: `.min(1)` в схеме + убрать
fallback (комментарий рядом уже утверждает, что ветка недостижима — пусть бросает).

**M-4 · URL CoinGecko без `encodeURIComponent`.** `coingecko/index.ts:124` — ни `platformId`, ни
`normalizedAddress` не кодируются (сравнить: `defillama:172`, `dexscreener:109` кодируют). Для
`bitcoin` (`family: other`, `vendors.coingecko: "ordinals"`) `normalizeAddress` возвращает вход
дословно, а `isValidAddress` принимает любые 1–128 символов ⇒ `address: '../../../simple/price?ids=x'`
перенаправляет запрос на другой эндпоинт вендора с приложенным API-ключом. Не SSRF (хост в
шаблоне), но forgery внутри вендорского API.

**M-5 · `isCovered` игнорирует `deprecated`, `chainsFor`/`list` — учитывают.** `coverage.ts:55-63`.
Депрекированная сеть проходит гейт и доходит до реального (возможно платного) `fetch()`, но в
списке «Available on:» и в `onchain_list_chains` её нет. Два представления одной матрицы
расходятся — ровно то, ради чего покрытие делалось производным.

**M-6 · Неограниченный вендорский текст в контекст модели.** `types/token.ts:16-17`,
`types/pool.ts:12-15` без `.max()`; M2-путь Nansen закрыт (`nansen/normalize.ts:16-40`), M1-пути —
нет. Pre-existing, но TASK-006 расширил `pairs.new`/`token.price` с 2 сетей до 458 — на длинном
хвосте адверсариальные `name`/`symbol` становятся рутиной. Цель эскалации — 100cr-tier

Плюс `new-pairs.ts:29` — `limit` без `.max()`.

**M-7 · `NANSEN_EXHAUSTIVE_LABELS_CHAINS` объявлен, но не применяется.** `chain-coverage.ts:93`
читается только генератором и тестом. Докстринг обещает отказ «до эскалации на 100cr» — такого

**M-8 · `onchain_list_chains` пересчитывает константный ответ.** `list-chains.ts:79-111`: результат —

## Перекрытия

| Находка | Критики | Механизм | Решение |
| --- | --- | --- | --- |
| H-1 | logic + security | один (предикат ≠ транспорт) | `corroborated`, severity = max = High, **эскалации нет** |
| H-2 | perf + security | один (non-aborting zod → O(L×1300)) | `corroborated`, severity = max = High, **эскалации нет** |
| H-4 | perf + logic | **разные** (стоимость vs расхождение словарей) | правило даёт +1 → Critical; **оставлено High**, обоснование в карточке |
| L-2 | logic + security | один | `corroborated`, Low |

Тег `corroborated` означает слабый положительный сигнал: находка пережила смену персоны и промпта,
но критики на одной модели ошибаются одинаково примерно в 60% случаев — это **не** независимое
подтверждение. Поэтому все четыре High были перепроверены оркестратором отдельно; три из четырёх
подтверждены измерением или чтением кода, четвёртая (H-3) — чтением.

## Что критики проверили и признали чистым

- **SSRF-периметр, половина генератора:** `rpcHosts` читается и переносится, никогда не
  присваивается; кандидаты только в отчёт. Все 19 курированных строк — публичные `https://`.
- **Гейт покрытия выше бюджета:** подтверждено. Непокрытая/неизвестная сеть не вызывает
  резервирования кредитов; даже H-1 бросает до `ensureBudget`.
- **Секреты:** ключ кеша — `sha256({capability, canonicalize(args)})` с null-prototype
  аккумулятором, `env` рядом не читается; `NANSEN_API_KEY` редактируется **до** усечения тела
  ошибки; `safeFetch` срезает `authorization|api-?key` на cross-host редиректе.
- **Изоляция dev-скриптов:** ни один `src/` не импортирует `scripts/`.
- **Отказ загрузки реестра:** `.min(1)` на `chains`, `.strict()` на обеих схемах (JSON-ключ
  `__proto__` = ошибка загрузки, не загрязнение), `'data' in deps` вместо `??`. Ни один путь не
  деградирует в пустой реестр.

## Рекомендуемый порядок

1. **H-2** — однострочный guard, снимает удалённую блокировку сервера.
2. **M-1 → H-3** — именно в этом порядке: сначала источник символа, потом его использование.
3. **H-1** — решить: расширить транспорт или сузить предикат. Плюс инвариантный тест
   «покрыто ⇒ `fetch()` не бросает `invalid args`».
4. **H-4** — одна строка в 8 хендлерах, чинит и стоимость, и расхождение словарей.
5. **M-2** — описания инструментов; дёшево и возвращает видимость главной способности задачи.
6. Остальное — по усмотрению.

### Что изменилось за пределами списка находок

- **Реестр перегенерирован живьём** (`syncedAt` 2026-07-26): 63 строки поменяли `nativeSymbol`,
  добавлена колонка `nativeDecimals`, `hyperliquid-l1` и `mantra` потеряли алиасы, унаследованные
  от тестнет-строк. TVL-значения дрейфанули у 314 строк — обычный вендорский дрейф, снапшот на то
  и «as of sync». Повторный прогон генератора — байт-в-байт, детерминизм сохранён.
- **Новая колонка `nativeDecimals`** — расширение схемы, которого в отчёте не было. Обосновано
  тем, что H-3 называет ОБА литерала (`symbol: 'ETH', decimals: 18`), а 29 сетей каталога
  EIP-155 не 18-десятичные.
- **Не тронуто:** `adapter.capabilities()` всё ещё несёт устаревшие литералы `chains: ['ethereum']`
  у части адаптеров. Роутинг их не читает (маршрутизация идёт по `providers.config.ts` и
  `chainSupport`), в отчёте они не значатся — менять означало бы правку тестов без изменения
  поведения. Отмечено как расхождение, а не исправлено.
