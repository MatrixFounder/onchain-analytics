# Задача 014.06: `UserStore` и `TokenStore` — интерфейсы и стабы `[STUB]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети
- UC-3 — оператор запускает локально

<!-- contract:goal -->

## Цель задачи

Объявить типы личности и наборы методов хранилищ пользователей и токенов в пакете `mcp-server`.
Стабы возвращают фиксированные значения; тесты проверяют форму и проходят на стабах.

**Why пакет `mcp-server`, а не `core`.** `security.md` §7.5.1: проверки живут в пакете `mcp-server`,
рядом с транспортом, которому они нужны. `packages/core` не получает знания о токенах, ролях и
заголовках. SQL, называющий таблицы личности, пишется из того же пакета.

**Why задача не создаёт таблиц.** Объявление таблиц — задачи 014-35 (Postgres) и 014-36 (SQLite).
Здесь объявляется форма доступа к ним.

## Описание изменений

### Новые файлы

- `packages/mcp-server/src/auth/identity-types.ts` — `Role`, `User`, `ApiToken`, `TokenLookupRow`,
  `AccessAuditEntry`
- `packages/mcp-server/test/identity-store-contracts.test.ts` — тесты формы

### Изменения в существующих файлах

Оба файла заведены задачей 014-02 как интерфейс со стабом. Текущая задача объявляет их методы.

**Файл `packages/mcp-server/src/auth/user-store.ts`:**
- Объявить `createUser`, `findUser`, `listUsers`

**Файл `packages/mcp-server/src/auth/token-store.ts`:**
- Объявить `issue(userId, accessProfileId): Promise<{ token: string; prefix: string }>`
- Объявить `lookup(presented): Promise<TokenLookupRow | null>`
- Объявить `revoke(tokenId, actorId): Promise<void>`
- Объявить `appendAudit(entry): Promise<void>`

**Why `issue` принимает профиль доступа.** Колонка `api_tokens.access_profile_id` объявлена
`NOT NULL` с внешним ключом на `access_profiles` (`data-model.md` §4.5.4). Выпуск без профиля не
имеет строки, которую можно вставить.

### Форма значений

Типы объявляются под колонки `data-model.md` §4.5.3, §4.5.4 и §4.5.5 и канон DB-SCHEMA §1:

| Значение | Форма | Колонка |
| :--- | :--- | :--- |
| роль | `'admin'` \| `'user'` | `users.role` |
| статус пользователя | `'active'` \| `'suspended'` | `users.status` |
| статус токена | `'active'` \| `'revoked'` | `api_tokens.status` |
| идентификатор | ULID строкой, генерирует приложение | `id` каждой из трёх таблиц |
| время | целое epoch-ms UTC | `created_at`, `updated_at`, `expires_at`, `revoked_at`, `ts` |
| дайджест | 64 hex-символа в нижнем регистре | `api_tokens.token_hash` |
| префикс | видимая часть, `UNIQUE`, не короче 8 символов | `api_tokens.prefix` |
| адрес | приведён к нижнему регистру до вставки | `users.email` |
| действие журнала | пять значений `CHECK` из §4.5.5 | `access_audit.action` |

**Why адрес приводит к нижнему регистру писатель.** Ни один из двух движков не складывает регистр в
`UNIQUE`-индексе по умолчанию, поэтому `A@x` и `a@x` завелись бы как два разных человека
(`data-model.md` §4.5.3).

**Why идентификатор генерирует приложение.** Форма едет на два движка, поэтому серверное умолчание
не может владеть идентификатором (`data-model.md` §4.5.2, канон §1.3).

### Что возвращает `lookup`

Семь значений чтения аутентификации `data-model.md` §4.5.4: `t.id`, `t.status`, `t.expires_at`,
`t.access_profile_id`, `u.id`, `u.role`, `u.status`. Предикат живости в запрос не входит.

**Why предикат живости не в `WHERE`.** Запрос, вернувший ноль строк, не отличает неизвестный токен
от отозванного. R-26 нужен класс отказа, а R-31 отрисовывает его дважды (`data-model.md` §4.5.4).

### Соответствие ролей принципалам

Роль `admin` — операторский принципал `ADR-002` D8. Роль `user` — клиентский. Роль живёт на
пользователе, а не на токене.

**Why роль живёт на пользователе.** Видимость `_meta.budget` — функция роли принципала (R-6.1). Два
токена одного человека иначе разошлись бы в том, что этот человек видит (`data-model.md` §4.5.3).

**Why роль не несёт числа** (R-15.3b). Различие лимитов выражается тем, на какой профиль доступа
ссылается токен. Один механизм, а не два (`security.md` §7.5.3).

### Где канон побеждает образец

Образец — `n8n-lazy-loading-skills`, файл `sql/010_identity_tables.sql`. `data-model.md` §4.5.2
называет пять колонок, в которых побеждает канон DB-SCHEMA §1:

| Образец | Здесь |
| :--- | :--- |
| `uuid DEFAULT gen_random_uuid()` | `TEXT` ULID, генерирует приложение |
| `timestamptz DEFAULT now()` | `INTEGER` epoch-ms UTC |
| `token_hash bytea` | `TEXT`, sha256 в нижнем регистре hex |
| `scopes text[]` | не переносится: сужение живёт на профиле доступа |
| `id bigserial` в журнале | `TEXT` ULID |

Образец переносится без изменений в пяти пунктах: проверка роли `admin | user`, проверка статуса
`active | suspended`, видимый `prefix` рядом с дайджестом, минимальная длина префикса 8 и защита
журнала от правки задним числом.

### Что не меняется

- `packages/core` не получает ни типа токена, ни типа роли, ни типа заголовка
- Строки не удаляются: отзыв доступа — `status = 'suspended'` плюс отзыв токена (§4.5.3)
- `createServer` сохраняет форму `createServer(deps: CreateServerDeps): McpServer`

## Тест-кейсы

### Модульные тесты
1. **TC-UNIT-01:** стабы реализуют объявленные интерфейсы
   - Входные данные: вызов каждого метода стаба
   - Ожидаемый результат: компиляция проходит, метод возвращает объявленную форму
2. **TC-UNIT-02:** тип роли допускает два значения и отвергает третье
   - Входные данные: присваивание `'owner'` под `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает присваивание
3. **TC-UNIT-03:** `issue` объявлен возвращающим значение токена и префикс раздельно
   - Входные данные: вызов стаба с идентификаторами пользователя и профиля
   - Ожидаемый результат: результат несёт две строки, `token` и `prefix`
4. **TC-UNIT-04:** `lookup` возвращает семь значений чтения §4.5.4
   - Входные данные: стаб, отдающий строку активного токена
   - Ожидаемый результат: статус токена и статус пользователя доступны раздельно
5. **TC-UNIT-05:** тип `ApiToken` не объявляет поля со значением токена
   - Входные данные: чтение `row.token` под `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает чтение
6. **TC-UNIT-06:** поля времени объявлены числом epoch-ms
   - Входные данные: строка ISO в поле `createdAt` под `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает присваивание
7. **TC-UNIT-07:** запись журнала допускает пять действий §4.5.5 и отвергает шестое
   - Входные данные: `'token.rotate'` в поле `action` под `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает присваивание
8. **TC-UNIT-08:** два токена одного пользователя ссылаются на разные профили и дают разные лимиты
   - Входные данные: стаб `lookup` с двумя строками одного `u.id`, `access_profile_id` = `'P1'` и
     `'P2'`; стаб читателя профилей с `rateLimitPerMin` 10 для `'P1'` и 100 для `'P2'`
   - Ожидаемый результат: прочитанные лимиты 10 и 100 различны, `u.role` в обеих строках равны
     (R-15.3b)
9. **TC-UNIT-09:** тип пользователя не несёт числа лимита
   - Входные данные: чтение `user.rateLimitPerMin` и `user.creditsBalanceRaw` под
     `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает оба чтения (R-15.3b)

## Примечания

Стаб `issue` возвращает фиксированную пару. CSPRNG, дайджест с перцем, отзыв и защиту журнала
вводит задача 014-07; до неё стаб не должен попадать в путь запуска сетевого профиля.

Задача не создаёт ни одной таблицы: объявление в Postgres — 014-35, в SQLite — 014-36, засев первого
администратора — 014-37.

Журнал `access_audit` достигается методом `appendAudit` хранилища токенов. Словарь действий объявлен
в `data-model.md` §4.5.5; правило на удаление и триггер на обновление ставят миграции.
