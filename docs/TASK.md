## 1. Контекст и цель

`onchain-intel` закрыл M1 (4 free MCP-tools, двухуровневый кеш, 9 адаптеров, $0 трат). M2 — первый
**платный** срез: агент должен отвечать на вопрос «куда идут умные деньги» через Nansen, при этом
бюджет кредитов управляется явно и проверяемо, а движок остаётся полностью функциональным без
единого платного ключа (M1-путь не деградирует).

**Живой пробник 2026-07-23 (`GET /api/v1/account`, 0 кредитов) изменил вводные ROADMAP:** аккаунт
на плане **`free`**, `credits_remaining: 100` — **не** Pro $49, как предполагал ROADMAP при
написании. Это не блокирует задачу — наоборот, даёт настоящий, а не смоделированный тест-кейс для
budget-guard (см. UC-3).

### Решения, зафиксированные владельцем на кикоффе 2026-07-23 — не пересматриваются в этой задаче

1. **Проектируем для ОБОИХ планов (`free` и `Pro`) одновременно.** Budget-guard выводит лимиты
   **только** из живого `GET /api/v1/account` (`plan`, `credits_remaining`) и из заголовков ответа
   `X-Nansen-Credits-Used`/`X-Nansen-Credits-Remaining` — **никогда** из захардкоженной
   costs-таблицы и **никогда** из захардкоженного предположения о плане. Апгрейд плана — **zero
   code change**.
2. **Интеграционная поверхность — REST API, не официальный MCP-сервер Nansen**
   (`mcp.nansen.ai/ra/mcp`, 37 tools). Причины, зафиксированные здесь как решение, а не открытый
   вопрос: (a) несколько MCP-tools явно возвращают **markdown-текст** («Returns: ... as markdown»,
   пробник) — непригодно как источник для канонической zod-нормализации (D5); (b) проксирование
   стороннего MCP-сервера обошло бы **наш собственный** кеш (D6), budget-guard, SSRF-гейт (§7.2
   ARCHITECTURE) и rate-limiter — архитектурная дыра, не экономия. MCP-эндпоинт Nansen остаётся
   задокументирован как ручной/exploratory инструмент (для дев-проб), в движок не встраивается. По
   той же логике из скоупа исключены REST-эндпоинты `/api/v1/agent/fast` и `/api/v1/agent/expert`
   (см. openapi.json) — оба возвращают потоковый natural-language ответ AI-агента, не структурные
   данные, нормализовать в canonical zod нечего.
3. **Bitquery — вне скоупа M2 (YAGNI).** ROADMAP называет его опциональным; ключа нет, живого
   пробника не было. Явно откладывается (§4), а не «забывается» — не изобретаем для него требований.
4. **Бюджет живой верификации самой сборки M2 ≤ ~30 кредитов суммарно** — не оценка, а конкретный
   план по статически задокументированной в спеке цене (`credit_cost_table`, x-credit-cost, все
   74 операции — task-reviewer C1, 2026-07-23):
   `GET /api/v1/account` (0) + `POST /api/v1/search/general` (0) + `POST /api/v1/smart-money/netflow`
   (5) + `POST /api/v1/tgm/holders` (5) + `POST /api/v1/tgm/indicators` (5) +
   `POST /api/v1/tgm/token-information` (1) ≈ **16 кредитов** — укладывается в ≤30 с запасом на один
   повтор при сбое записи. **Эскалация владельца плана не нужна**: exit-критерий #1 ROADMAP
   («smart-money-запрос отдаёт метки+потоки») закрывается живьём на текущем `free`-балансе (100cr)
   без апгрейда. Фикстуры пишутся **один раз** и коммитятся — повторные прогоны `pnpm test`/CI
   тратят **0** кредитов (D11, тот же контракт, что и M1); поскольку цена вызова уже известна
   статически из спеки (C1, см. R-37), фикстурам не нужно её открывать — они валидируют только
   нормализацию и post-call reconciliation (R-38). Это жёсткое ограничение самой Development-фазы,
   отслеживается наравне с продуктовыми требованиями (см. R-44, UC-8).
5. **`premium_labels=true` стоит 150 кредитов/вызов** (документировано в спеке для эндпоинтов
   `/tgm/holders`, `/tgm/pnl-leaderboard`, `/tgm/perp-pnl-leaderboard`, `/perp-leaderboard`) —
   больше, чем весь остаточный баланс free-плана (100). Это настоящий, не смоделированный
   отказ-кейс для budget-guard (UC-3) — используется буквально, не изобретается.

**Что уже существует и НЕ является предметом этой задачи:** `packages/core` (M1) — 9 адаптеров,
канонические типы `Token`/`Wallet`/`Balance`/`Pool`/`OHLCV`/`Snapshot`, `CapabilityRegistry`,
двухуровневый кеш (`providers`/`cache_entries`), SSRF-гейт, rate-limiter. M2 **расширяет** этот
пакет — десятый адаптер, три новых канонических типа, новая `usage`-таблица в той же кеш-БД (уже
зарезервировано её forward-compat комментарием в `packages/core/src/cache/ddl.ts`, не требует
миграции существующих таблиц) — не переписывает M1.

## 2. Use Cases

### UC-1: Оператор настраивает `NANSEN_API_KEY` и агент запрашивает smart-money flows по токену

**Actors:** Claude Code (host), MCP-сервер `onchain-intel`, Nansen REST API.
**Preconditions:** `NANSEN_API_KEY` задан и валиден; `isAvailable()` адаптера `nansen` возвращает
`{ok: true}`; дневной остаток бюджета положителен.
**Main Scenario:**

1. Агент вызывает `onchain_smart_money_flows({ chain, tokenAddress })`.
2. Cache lookup — miss (первый вызов).
3. Budget-guard **атомарно** (в одной транзакции) читает накопленный расход бакета и **резервирует**
   точную цену `costOf()` из статической `credit_cost_table` в `usage` (R-34a/R-37) — проходит.
4. Адаптер `nansen` шлёт REST-запрос (`apiKey`-заголовок, не Bearer) на `api.nansen.ai`.
5. Ответ нормализуется в канонический тип (условно `SmartMoneyFlow[]`), провайдер-DTO не протекает
   наружу.
6. Из заголовков ответа читаются `X-Nansen-Credits-Used`/`X-Nansen-Credits-Remaining` — поверх
   резервации записывается **подписанная дельта** (`фактический − зарезервированный`, R-34b/R-38)
   тем же аддитивным upsert. Это **НЕ** замещающая запись: аддитивный upsert + повторная запись
   полной фактической стоимости дали бы двойной учёт.
7. Результат кешируется (TTL по типу данных, как M1 D6) и возвращается вызывающему.

**Alternative Scenarios:**

- **A1 (повторный вызов в пределах TTL):** cache hit — шаги 3–6 не выполняются, платный вызов не
  происходит (см. UC-5 отдельно — это критичный по деньгам путь, не только по латентности).

**Postconditions:** `usage`-таблица отражает реальный расход; кеш содержит свежую запись;
`_meta.cache`/аналог budget-видимости присутствует в ответе tool (контракт — Architecture-фаза, но
факт видимости — обязателен, см. R-41).
**Acceptance Criteria:** см. §6, R-29/R-31/R-36/R-38/R-41.

### UC-2: `NANSEN_API_KEY` не задан — M2-tools деградируют явно, M1 не затронут

**Actors:** Claude Code, MCP-сервер.
**Preconditions:** `.env` не содержит `NANSEN_API_KEY` (или пуст).
**Main Scenario:**

1. Агент вызывает любой из трёх новых tools.
2. `nansen.isAvailable()` возвращает `{ok: false, reason: 'needs NANSEN_API_KEY'}` **до** попытки
   сети (R-24-паттерн из M1, не новый механизм).
3. Tool возвращает `isError: true` с понятной причиной (без утечки значений секретов), сервер не
   падает.

**Alternative Scenarios:**

- **A1:** тот же вызов, но `onchain_ping` и 4 M1-tools (`onchain_get_token`,
  `onchain_wallet_balances`, `onchain_new_pairs`, `onchain_protocol_tvl`) в той же сессии продолжают
  отвечать нормально — регрессия M1 недопустима (существующий тест-сьют 287 остаётся зелёным).

**Postconditions:** движок полностью функционален на $0; ни один M2-код-путь не исполняется.
**Acceptance Criteria:** R-29 (isAvailable), R-40 (регрессия), unit-тест на пустой `.env` (тот же
паттерн, что M1 UC-1).

### UC-3: Budget-guard отказывает в непосильном платном вызове (150cr против 100cr баланса)

**Actors:** Claude Code, MCP-сервер, budget-guard (внутренний компонент, не внешний actor).
**Preconditions:** план `free`, живой `credits_remaining: 100` (подтверждено пробником); запрошена
операция, чья документированная стоимость (`premium_labels=true` на одном из четырёх эндпоинтов,
150cr) превышает остаток.
**Main Scenario:**

1. Агент вызывает `onchain_smart_money_flows` или `onchain_entity_label` с параметром,
   транслирующимся в `premium_labels=true` на `POST /api/v1/tgm/holders` — общий источник данных
   обоих tools (R-41/R-42, §3); это конкретный, не гипотетический триггер (снимает прежнюю
   неопределённость об «точном мэппинге»).
2. Cache lookup — miss.
3. Budget-guard вычисляет требуемую стоимость (150) и текущий остаток (100 или меньше) — **до**
   какого-либо сетевого вызова.
4. 150 > остаток → guard отказывает: **ни одного** байта не уходит в сеть к Nansen (проверяемо в
   тесте — spy на `fetch`/`safeFetch` не вызван ни разу).
5. Tool возвращает `isError: true` со структурированной причиной («insufficient budget: need 150,
   have ≤100»), без утечки значения ключа.

**Alternative Scenarios:**

- **A1 (баланс когда-нибудь окажется ≥150, напр. план апгрейднут на Pro):** тот же путь пропускает
  guard и делает реальный вызов — **без изменения кода**, только потому что живой
  `credits_remaining` теперь другой (доказывает решение владельца п.1 §1).

**Postconditions:** `usage` не изменился (вызова не было — нечего реконсилировать); баланс
`credits_remaining`, наблюдаемый через `/account`, не тронут.
**Acceptance Criteria:** R-36/R-37 — один из **двух** реальных, не смоделированных отказ-кейсов,
использованных в задаче (§1 п.5; второй — 100cr-эскалация `onchain_entity_label`, R-42);
вместе они закрывают exit-критерий ROADMAP «budget-guard реально режет при достижении лимита
(тест)».

### UC-4: Бюджет исчерпывается в середине сессии (накопительный расход)

**Actors:** Claude Code, MCP-сервер.
**Preconditions:** несколько разных (по нормализованным args → разные cache-ключи) платных вызовов
подряд в одной сессии, каждый дёшев по отдельности, но их сумма приближается к остатку.
**Main Scenario:**

1. Вызов 1 — costOf() ≪ потолок бакета → проходит, `usage` увеличивается на фактически потраченное
   (аддитивно — см. R-34 нюанс про «прибавочный», а не «перезаписывающий» upsert).
2. Вызов 2 (другие args, другой cache-ключ) — снова проходит, `usage` продолжает расти.
3. Вызов N — накопленный `usage` за бакет + `costOf()` превышает **выведенный потолок бакета**
   (R-35/R-36; потолок фиксируется на старте бакета либо пересчитывается как
   `live_remaining + usage_since_bucket_start`) **ЛИБО** `costOf()` превышает живой остаток
   (hard-ограничитель) → guard отказывает **до** сети, как в UC-3.

   > ⚠️ **Ловушка двойного счёта (не реализовывать наивно):** сравнивать накопленный `usage`
   > с **текущим** живым остатком **запрещено** — `X-Nansen-Credits-Remaining` уже уменьшен на
   > этот самый расход. Наивная формула `usage + costOf() > live_remaining` вдвое урезает
   > доступный бюджет: при 100cr и вызовах по 5cr она откажет на k=10 (`usage`=50,
   > `live_remaining`=50), хотя реально доступно 20 вызовов.

**Alternative Scenarios:**

- **A1:** между вызовами 1 и N кто-то извне (тот же ключ, другой процесс) тоже тратит бюджет —
  локальный `usage`-счётчик может разойтись с реальным `credits_remaining`; см. UC-6 (402 от
  вендора) как страхующий путь именно для этого расхождения.

**Postconditions:** `usage` содержит N-1 успешных записей, N-я операция не оставила следа (не было
вызова).
**Acceptance Criteria:** R-34 (накопительный upsert), R-37 (гейт видит накопленный расход, а не
только стоимость текущего вызова).

### UC-5: Cache hit полностью избегает платного вызова

**Actors:** Claude Code, MCP-сервер.
**Preconditions:** предыдущий вызов с теми же нормализованными args уже закеширован и TTL не истёк.
**Main Scenario:**

1. Повторный вызов — cache lookup **до** budget-guard (порядок операций фиксируется как
   требование, не деталь реализации — иначе кеш-хит по ошибке всё равно блокировался бы
   исчерпанным бюджетом).
2. Hit → результат возвращается немедленно; budget-guard, costOf(), сетевой вызов — не исполняются
   вовсе.

**Postconditions:** `usage` не изменился; latency низкая (как в M1 UC-3).
**Acceptance Criteria:** R-37 (явно фиксирует порядок: cache-miss — необходимое условие для входа в
budget-gate), regression-тест на существующий `TwoLevelStore` не меняет своего контракта.

### UC-6: Nansen отвечает `402 Payment Required` посреди сессии

**Actors:** MCP-сервер, Nansen REST API.
**Preconditions:** локальный `usage`-учёт по какой-то причине разошёлся с реальным состоянием на
стороне Nansen (гонка, внешнее списание, drift) — редкий, но реальный путь (см. openapi.json:
`402` документирован как `PaymentRequiredError` для платных операций).
**Main Scenario:**

1. Локальный gate пропустил вызов (по своим данным бюджет есть).
2. Nansen возвращает `402`.
3. Адаптер трактует это как авторитетный сигнал «бюджета фактически нет **сейчас**» — не крашит
   процесс, возвращает понятную причину, и (по возможности) синхронизирует локальное состояние
   ближайшим дешёвым `GET /api/v1/account` (0 кредитов) вместо того, чтобы доверять устаревшему
   локальному счётчику до следующего успешного вызова.

**Postconditions:** ошибка дошла до вызывающего как явный `isError`, не как необработанное
исключение; сервер продолжает обслуживать остальные tools.
**Acceptance Criteria:** R-38 (реконсиляция также обрабатывает неуспешный, но информативный ответ,
не только 2xx).

### UC-7: Nansen отвечает `429 Too Many Requests`

**Actors:** MCP-сервер, Nansen REST API.
**Preconditions:** локальный token-bucket (по образцу M1 `throttle()`) сконфигурирован
консервативнее **всех четырёх** документированных лимитов (`x-ratelimit-limit-second: 150`,
`x-ratelimit-limit-minute: 3000`, `x-ratelimit-limit-credit-fails-minute: 10`,
**`x-ratelimit-limit: 15`** — пробник; окно последнего не подтверждено, калибровать по нему как
по самому строгому, пока не измерено — R-29), но возможен всплеск/рассинхрон.
**Main Scenario:**

1. Ответ `429` с заголовком `retry-after`.
2. Адаптер не повторяет вызов молча и бесконтрольно — либо явная ошибка с причиной («rate limited,
   retry after Ns»), либо один ограниченный retry с уважением `retry-after` (точный выбор —
   Architecture-фаза; это НЕ registry hot-swap fallback, т.к. у платных M2-capability нет
   альтернативного free-адаптера — единственный источник исчерпан).

**Postconditions:** ни одного «тихого» бесконечного цикла ретраев; ошибка видна вызывающему.
**Acceptance Criteria:** R-29 (rate-limit конфиг), сопровождающий unit-тест на 429-путь.

### UC-8: Контрактные тесты гоняются в CI с нулевым живым расходом

**Actors:** CI, разработчик.
**Preconditions:** фикстуры для `nansen`-адаптера записаны один раз вручную (dev-скрипт, аналог
`record-fixture.mjs` M1) и закоммичены вместе с evidence-файлами (реально наблюдённые поля +
**реально наблюдённый `X-Nansen-Credits-Used`** для каждого нового эндпоинта).
**Main Scenario:**

1. `pnpm test` в CI/локально гоняет golden-нормализацию против фикстур — 0 сетевых вызовов, 0
   потраченных кредитов.
2. Тесты на оба отказ-кейса (UC-3's 150cr и R-42's 100cr) тоже не требуют живого вызова — они
   проверяют арифметику guard'а против статической `credit_cost_table` (150 > 100, 100 ≥ остаток),
   а не реальный HTTP-запрос к Nansen (C1).

**Postconditions:** конкретный план живого расхода всей Development-фазы M2 (запись фикстур +

**≤ 30 кредитов**, зафиксирован в evidence-файлах рядом с фикстурами (§1 п.4).
**Acceptance Criteria:** R-44, Live-verification (§6).

### UC-9: Апгрейд плана `free → Pro` не требует изменения кода

**Actors:** оператор (человек), MCP-сервер.
**Preconditions:** оператор поменял подписку на стороне Nansen (вне движка).
**Main Scenario:**

1. Следующий вызов budget-guard читает живой `/api/v1/account` (или недавние response-заголовки) —
   видит `plan: "pro"`, новый `credits_remaining`.
2. Лимиты, ранее блокировавшие 150cr-вызов (UC-3), теперь пропускают его — без единого изменения в
   `providers.config.ts`, коде адаптера или деплое.

**Postconditions:** доказывает решение владельца §1 п.1 буквально, не декларативно.
**Acceptance Criteria:** R-36 (тест подставляет фикстуру аккаунта с другим планом/остатком —
поведение гейта меняется только от данных, не от кода).

## 3. В рамках задачи (In Scope)

- **Адаптер `nansen`** (десятый в `adapterRegistrations`, тот же паттерн `ProviderAdapter`, что и
  девять M1-адаптеров): REST, host `api.nansen.ai`, заголовок `apiKey` (НЕ `Authorization: Bearer`),
  `isAvailable()` по наличию `NANSEN_API_KEY`, rate-limit конфиг консервативнее документированных
  вендором порогов.
- **Три новых capability** (рабочие имена, финализирует Architect) — источники и точная цена по
  `credit_cost_table` (x-credit-cost, статически задокументировано, C1-ревью — НЕ гадание):
  - **smart-money flows:** `POST /api/v1/smart-money/netflow` (5cr free/pro, MVP-источник);
    опционально `holdings`/`dex-trades` той же ценовой категории (5cr) как более богатые
    представления; `POST /api/v1/tgm/holders` (5cr) — holder-адреса + метки + балансы одним
    вызовом, общий источник с меткой-способностью ниже (закрывает exit-критерий #1 «метки+потоки»
    дёшево, см. R-41/R-42).
  - **метки адреса/сущности:** дефолт (0cr) — `POST /api/v1/search/general` (поиск по
    имени/символу/адресу) + `POST /api/v1/search/entity-name` (резолвер имя→entity_name);
    токен-scoped обогащение (5cr, общий с выше) — `POST /api/v1/tgm/holders`; явная opt-in
    эскалация (100cr free/pro — весь free-баланс!, budget-gated) — `POST /api/v1/profiler/address/labels`;
    `POST /api/v1/profiler/address/premium-labels` (500cr) вне досягаемости текущего плана, не
    проектируется как активная фича M2 (см. R-42, §7 OQ-4).
  - **риск/скор токена:** `POST /api/v1/tgm/indicators` (5cr, risk/reward-индикаторы) +
    `POST /api/v1/tgm/token-information` (1cr, метаданные).
    Из всех перечисленных эндпоинтов **POST с JSON-телом** — все, кроме `GET /api/v1/account`
    (см. R-29 — влияет на форму `fetch()`, fixture-recorder, redirect-обработку).
- **Три канонических zod-типа** (D5-расширение, рабочие имена `SmartMoneyFlow`, `EntityLabel`,
  `TokenRiskScore`): provider DTO не протекает наружу — тот же anti-corruption-паттерн, что
  `Token`/`Wallet`/`Pool` в M1.
- **`usage`-таблица** в существующей кеш-БД (`DATA_DIR/cache.sqlite3`) — DB-SCHEMA-CONCEPT §1
  portable-типы, FK на существующий `providers`-реестр (без миграции `providers`/`cache_entries`,
  как уже спроектировано в `packages/core/src/cache/ddl.ts`).
- **`BudgetStore`-репозиторий** (имя буквально из ADR-001 D6/DB-SCHEMA-CONCEPT §1.9 — «паттерн
  `CacheStore`/`BudgetStore`») — engine-swap-safe интерфейс, тот же принцип, что `CacheStore` в M1.
- **Pre-call budget gate:** отказ до сетевого вызова при недостатке бюджета (не после).
- **Post-call reconciliation:** запись фактического расхода из `X-Nansen-Credits-Used`/
  `X-Nansen-Credits-Remaining` в `usage`.
- **Дневной потолок, выводимый из живых данных** (не хардкод): `GET /api/v1/account` (0 кредитов)
  - заголовки ответов — единственные источники истины для остатка/плана.
- **Singleflight-коалессинг** для одновременных идентичных платных запросов (не двойной расход на
  гонке двух одинаковых in-flight вызовов) — явно триажировано в M2 из адверсариального хвоста M1
  (`docs/BACKLOG.md`, 2026-07-23: «singleflight coalescing (fits budget-guard — paid-call dedup)»).
- **Явная деградация** при отсутствующем ключе/исчерпанном бюджете — R-24-паттерн M1, не новый
  механизм; остальной движок (onchain_ping + 4 M1-tools) не затрагивается.
- **MCP-tools:** `onchain_smart_money_flows`, `onchain_entity_label`, `onchain_token_risk`.
- **Контрактные тесты на записанных один раз фикстурах** (D11) + evidence-файлы с реально
  наблюдённым `X-Nansen-Credits-Used` на момент записи.
- **Секретная дисциплина** для `NANSEN_API_KEY`: не логируется, не входит в `args_hash` кеш-ключа,
  снимается при cross-host редиректе (переиспользование существующего `SENSITIVE_HEADER_RE` из
  `safeFetch`, M1).
- **`EnvSchema` + `.env.example` + `docs/architectures/interfaces.md` §5.3** синхронизация: ключ
  уже зарезервирован в `.env.example` (M2+ секция) — задача переводит его в раздел «код читает
  сейчас» и добавляет `NANSEN_API_KEY` в `EnvSchema` (опционально, как все M1-ключи, D10).
- **(Опортунистически, не блокирует acceptance M2)** два carry-over пункта из M1-триажа 2026-07-23
  в `docs/BACKLOG.md`, не завязанные на Nansen: `safeFetch` streaming byte-cap для
  chunked/no-Content-Length ответов; точный парсинг lamports для Solana-кошельков >~9.007M SOL
  (MAX_SAFE_INTEGER-обрыв). См. §4 — почему они помечены Should/не-MVP.

## 4. Вне рамок (Out of Scope) — явно

- **Bitquery-адаптер** — ROADMAP помечает его опциональным, ключа нет, живого пробника не было
  (§1 п.3). Явный YAGNI-отказ, не забытая строка.
- **Официальный MCP-сервер Nansen как интеграционная поверхность** (`mcp.nansen.ai/ra/mcp`) —
  решение §1 п.2; остаётся ручным/exploratory инструментом, в движок не встраивается.
- **`/api/v1/agent/fast`, `/api/v1/agent/expert`** — потоковый natural-language ответ AI-агента, не
  структурные данные; не входят в 3 tools (§1 п.2). Отдельно: ADR-001 D6 упоминает «Nansen Agent
  Expert 750cr/вызов» как исходный (июнь 2026, до подписания) драйвер решения о кеше/бюджете —
  **число подтверждено** сгенерированной из спеки `credit_cost_table` (`x-credit-cost`:
  `/agent/expert` = 750cr free/pro, `/agent/fast` = 200cr free/pro; task-reviewer C2, 2026-07-23) —
  оба эндпоинта всё равно вне скоупа M2 независимо от точной цены (natural-language output, не
  структурные данные для canonical zod).
- **Live-запрос Dune (`token.holders`)** — M1-архитектура (§3.2 system-architecture.md) явно
  анонсировала `onchain_token_risk` как «первого потребителя» Dune-запроса, отложенного из M1.
  **Эта задача не подтверждает это ожидание**: кандидат-источники риска токена, зафиксированные в
  §1/§3 выше — Nansen `/tgm/indicators` + `/tgm/token-information`, не Dune. Оживление
  `dune`-адаптера (`isAvailable()` по-прежнему безусловно `false`) остаётся отдельным, не
  затронутым этой задачей пунктом — явное решение, не молчаливое расхождение с M1-документом. Если
  Architect всё же захочет Dune как дополнительный источник holder-концентрации — это отдельное
  расширение скоупа, не подразумеваемое здесь (решение уже принято, открытого вопроса не требует).
- **Явное отклонение от буквального текста ROADMAP §M2 (семантика «деградации»).** ROADMAP говорит
  буквально «отказ/**деградация на free-провайдера** при превышении» — т.е. предполагает
  registry-уровня fallback на другой (бесплатный) адаптер, как M1's hot-swap `dash-platform` ⇄
  `platform-explorer` (R-11). **Эта задача намеренно реинтерпретирует критерий**: ни для одной из
  трёх M2-способностей нет бесплатного provider-эквивалента с тем же смыслом данных (никто, кроме
  Nansen, не отдаёт smart-money net-flow/labels/risk-score) — молчаливая подмена на семантически
  другие бесплатные данные была бы хуже громкой явной ошибки. «Деградация» в R-40 означает: явный
  `isError` при отсутствии ключа **или** исчерпанном бюджете + остальной движок (`onchain_ping` +
  4 M1-tools) продолжает работать без изменений — тот же R-24-паттерн M1, не registry-level
  hot-swap. Явное, обоснованное решение, не молчаливое расхождение с ROADMAP (трассировка — §6).
- **M3 целиком:** watchlists, планировщик (`croner`), правила/алерты, Telegram-нотификации (D9) —
  budget-guard в M2 ограничивается **stderr**-уровня предупреждением при приближении к потолку
  (то же место, что M1 cache-метрики), не новым notification-каналом.
- **Поглощение снапшоттера** (n8n → движок) — остаётся M3, не трогается этой задачей.
- **Streamable HTTP MCP-транспорт** — M6; M2 остаётся stdio-only, как M0/M1.
- **ERC-20/SPL enrichment `onchain_wallet_balances`** — существующий M1-backlog work-item, не
  относится к платному слою.
- **Полная фикстура/тест по всем 75 REST-путям Nansen** — только ~6–8 эндпоинтов, реально стоящих
  за тремя tools + `/account`, интегрируются и фикстурируются (§1 п.4, бюджет ≤30cr).
- **Решение об апгрейде подписки на Pro** — бизнес-решение владельца, не предмет этой инженерной
  задачи; движок обязан корректно работать на текущем `free` плане и оставаться корректным без
  изменений кода при апгрейде (UC-9), но сам апгрейд эта задача не инициирует.
- Два carry-over M1-пункта из §3 (safeFetch chunked byte-cap, Solana >9M SOL lamports) **не входят
  в критерии приёмки этой задачи** — подхватываются оппортунистически, если у Planner есть запас в
  атомарной нарезке; явно НЕ трассируются к exit-критериям ROADMAP §M2 (см. §6).

## 7. Open Questions

Блокирующих вопросов для старта Architecture-фазы нет. Зафиксированы как **неблокирующие**, но
требующие решения до соответствующей атомарной задачи:

- **OQ-1 — cadence сброса `credits_remaining` у Nansen.** Живой `/account` отдаёт только текущий
  остаток, без явного поля периода/сброса (пробник 2026-07-23 не содержит такого поля). ADR-001 D6
  предполагает именно «дневной» потолок (`usage(provider, day, credits_used)`) — R-36 уже
  фиксирует, что day-бакет служит **собственным pacing-инструментом**, а не отражением вендорского
  цикла, но точную формулу «сколько можно потратить сегодня» (весь live-остаток целиком? остаток /
  оставшиеся дни месяца? фиксированный self-imposed cap?) решает Architect.

  > ⚠️ **Обязательное ограничение любой выбранной формулы:** сравнивать накопленный `usage`
  > с **текущим** (уже уменьшенным на этот расход) live-остатком **запрещено** — это двойной
  > счёт, вдвое урезающий бюджет (разбор — UC-4, шаг 3).

- **OQ-2 — где именно живёт pre-call gate.** Внутри `CapabilityRegistry.resolve()` (единая точка
  для любого будущего платного адаптера) vs обёртка конкретно вокруг `nansen`. Требование (R-37)
  фиксирует **поведение** (отказ до сети, после cache-miss), не место в коде. **Не вариант** — гейт
  «на уровне MCP tool-хендлера»: `CapabilityRegistry.resolve()` сам владеет cache lookup, значит
  гейт на уровне хендлера неизбежно выполнялся бы **до** cache lookup, нарушая обязательный порядок
  R-37 и ломая UC-5 (кеш-хит без сети) — жизнеспособно только если хендлер сам делает cache lookup
  в обход `resolve()`, что не предусмотрено M1-архитектурой (M-5 review, task-reviewer 2026-07-23).
- **OQ-3 — chain-scope трёх новых capability.** Nansen поддерживает ~32 сети (пробник,
  `supported_chains_mcp`); M1-tools узили до ethereum+solana ради простоты acceptance. Стоит ли
  M2-tools ограничивать тем же подмножеством (согласованность с M1) или расширять — именно широкое
  покрытие сетей и есть часть премиальной ценности Nansen? Решение — Architect/Planner.
- **OQ-4 — стоит ли на Pro-плане поднимать дефолт эскалации `onchain_entity_label`.** Обе цены
  (`/profiler/address/labels` = 100cr, `/profiler/address/premium-labels` = 500cr) теперь
  **документированы статически** (`credit_cost_table`, C1/C2-ревью) — прежняя неопределённость
  «сколько это стоит» снята. Дефолт R-42 (`search/general`+`tgm/holders`, эскалация — explicit
  opt-in) выбран для `free`-плана, где 100cr — весь баланс. На `Pro`-плане, где эти суммы менее
  ощутимы, стоит ли автоматически поднимать дефолт до `/profiler/address/labels` (или даже
  `/premium-labels`), или opt-in-флаг остаётся explicit независимо от плана? `costOf()`-таблица
  (R-37) уже знает точную цену для обоих планов — вопрос чисто UX/дефолт-политики, не технической
  осуществимости. Решение — Architect/Planner.
- **OQ-5 — нужен ли самостоятельный env-оверрайд потолка** (например, опциональный
  `NANSEN_DAILY_CREDIT_CAP` — «не тратить больше N кредитов/день, даже если вендор позволяет
  больше»)? Решение владельца §1 п.1 говорит «выводить лимиты из живых данных, не хардкодить» — это
  не запрещает **дополнительный** самостоятельный potолок поверх live-остатка (как минимум двух
  чисел), но и не требует его явно. Architect решает, вводить ли эту ручку в M2 или оставить на
  потом.
