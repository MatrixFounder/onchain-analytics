# Directory: packages/core/

## Purpose

`@onchain-intel/core` — the M1 library package (ARCHITECTURE.md §3.1/§3.2, D5/D12 "packages/core
split"): canonical zod domain types (`Token`, `Wallet`/`Balance`, `Pool`, `OHLCV`, `Snapshot`,
`ChainSchema`), the chain/address normalization module (`normalizeAddress`/`isValidAddress`) —
both task 003-1, R-1/R-2 — the hot-swappable provider-adapter contour: `ProviderAdapter`/
`CapabilityRegistry`/`CacheStore` seam (`src/adapters/*`), the declarative `providers.config.ts` (9
adapter registrations + capability routes, copied literally from ARCHITECTURE.md §3.2), the SSRF
gate + rate-limiter + canonical args-hash (`src/net/*`) — all task 003-2, R-3/R-4/R-25/R-26 — and,
added this task (003-3, R-13/R-14/R-15), the real two-level cache (`src/cache/*`): `lru-cache` hot
layer + `better-sqlite3` persistent layer in `DATA_DIR`, implementing the exact `CacheStore`
interface 003-2 defined, plus hit/miss stats. Consumed by `@onchain-intel/mcp-server` via a
`workspace:*` dependency (declared task 003-1; not yet imported — that starts at task
003-6/003-7). **Task 003-4 (R-5/R-6/R-7) added the first three LIVE provider adapters** —
`coingecko`, `dexscreener`, `defillama` (`src/adapters/<id>/index.ts`), each a factory function
implementing `ProviderAdapter` for real, plus their committed fixtures + golden `normalize()`
tests. **Task 003-5 (R-8..R-12) completes the full nine-adapter set**: `rpc-evm`/`rpc-solana`
(LIVE JSON-RPC native-balance adapters, OQ-1 resolved), `platform-explorer` (LIVE REST, the only
live Dash source in M1 + its own history method), `dash-platform` (interface + fixture-contract
only, F-3 — `isAvailable()` unconditionally `false`), `dune` (interface/config-stub, R-8 amended
scope — no live call/fixture/test beyond registration+availability), and `pg-history` (optional
read-only Postgres history adapter over the new `src/pg/read-client.ts`, `pg` dependency). All
nine `providers.config.ts` ids now have a matching real `ProviderAdapter` factory. The cache
itself is real as of task 003-3, but nothing in this package constructs one by default yet:
`CapabilityRegistry`'s constructor still defaults to `PassthroughCacheStore` (unchanged, see
`src/adapters/cache-store.ts` below) — wiring `createCacheStore()` and all nine adapters into a
real `CapabilityRegistry` instance is `mcp-server`'s bootstrap responsibility (tasks 003-6/003-7),
not this package's.

### Build choice: plain `tsc`, no tsup (ARCHITECTURE.md §3.1/§3.2/§6.4)

This package's `build` script is `tsc -p tsconfig.build.json` — a single `tsc` invocation emits
both `.js` (NodeNext-native ESM output) and `.d.ts` for every file under `src/` in one step (see
the `dist/` file list below). This is a deliberate architectural decision (not a shortcut): the
`mcp-server` package needs tsup/esbuild only because it has a `bin` entry that must be bundled into
a single executable file, and separately hit an upstream tsup/rollup-plugin-dts bug when it tried
to have tsup also emit declarations (`baseUrl` injection crashes under both TS6 and TS7 — see
`packages/mcp-server/.AGENTS.md`'s `tsup.config.ts` note for the full empirical writeup), which is
why `mcp-server`'s build is a two-step `tsup && tsc --emitDeclarationOnly`. `packages/core` has no
`bin`, needs no bundling, and NodeNext's own module resolution is sufficient at runtime for a
library consumed only via `workspace:*` — so it sidesteps that whole bug class entirely rather than
reproducing it in a second package. Verified: `pnpm -r build` builds `core` (plain `tsc`) before
`mcp-server` (tsup+tsc) via pnpm's default topological ordering (`mcp-server`'s `workspace:*`
dependency on `@onchain-intel/core`) — confirmed by output ordering in a live `pnpm -r build` run,
not assumed.

`dist/` after a build: `index.{js,d.ts}`, `chain/{address,registry,errors}.{js,d.ts}` **plus the
copied `chain/registry.data.json`** (TASK-006), `types/{chain,token,wallet,
pool,ohlcv,snapshot,index}.{js,d.ts}` — an exact mirror of `src/`, nothing from `test/`.

### src/chain/address.ts

`normalizeAddress(chain, raw): string` / `isValidAddress(chain, raw): boolean`
(ARCHITECTURE.md §3.2/§4.1, reviewer note — the mandatory single point of address canonicalization
used by both MCP-tool input `superRefine`s and adapters before building a cache key):

- **`ethereum`:** canonical form is the **EIP-55 checksum**, never lowercase (ADR-001 D5). Algorithm:
  strip an optional `0x`/`0X` prefix, validate the remaining 40 characters are hex
  (`/^[0-9a-fA-F]{40}$/`), lowercase them, hash that lowercase hex **string** with `keccak_256`
  (`@noble/hashes/sha3.js` — accepts a `string | Uint8Array` directly, no manual `TextEncoder`
  needed), then for each hex digit of the lowercased address: digits (`0`-`9`) pass through
  unchanged, letters (`a`-`f`) are upper-cased iff the corresponding hex nibble of the hash (same
  character index) is `>= 8`. This is a pure function of the address bytes — `normalizeAddress`
  applied to any input case (all-lower, all-upper, already-checksummed, or an arbitrary mix)
  produces the identical output, proven in `test/chain-address.test.ts`. `isValidAddress` for
  ethereum only checks the hex-format contract (length + charset) — it does **not** additionally
  require the input's _own_ casing to already be a correct checksum (that would make
  `isValidAddress` reject perfectly normalizable lowercase input, contradicting the "any case in"
  contract).
- **`solana`:** canonical form is the input **as-is** — base58 is case-sensitive (unlike hex),
  so lowercasing would corrupt the address rather than canonicalize it. Validation: `bs58.decode`
  succeeds (any character outside the base58 alphabet — `0`, `O`, `I`, `l` are excluded — throws,
  caught and turned into `false`/a thrown `Error`) **and** the decoded byte length is exactly 32
  (a raw ed25519 pubkey, no version/checksum byte, unlike Bitcoin-style base58check).
- **`dash`:** not implemented in M1 (ARCHITECTURE.md §4.1 — `dash-platform` emits `Snapshot`, not
  `Wallet`/`Balance`, so there's nothing here to normalize/validate yet). `isValidAddress('dash',
*)` unconditionally returns `false`; `normalizeAddress('dash', *)` unconditionally throws. This
  mirrors the `dash-platform` adapter's own `isAvailable()` contract (§3.2: unconditionally
  unavailable in M1, not "unavailable if unreachable") — both are explicit, not silently-broken,
  M1 boundaries.

`normalizeAddress` throws (never returns a sentinel) on invalid/unsupported input — the contract
documented in ARCHITECTURE.md §3.2: "невалидный вход → бросок, ловится вызывающим
`superRefine`/адаптером". No custom `Error` subclass was introduced (Zero-Dependency /
no-speculative-complexity — a plain `Error` with a descriptive, value-free message is sufficient
for this task's scope; callers that need typed error handling can add a subclass when they
actually need to branch on it).

**TASK-006 (task 006-3, R-55): dispatch is by `family`, not by chain name.** `switch (chain)` over
`'ethereum' | 'solana' | 'dash'` became `switch (familyOf(chain))`. The `evm` and `svm` branch
bodies are byte-for-byte what they were — what changed is their reach: one `evm` branch now serves
all 288 EVM chains in the registry.

- **Signature:** `AddressChain = Pick<ChainInfo,'family'> | Chain`. The bare-string arm is a
  **migration bridge removed in task 006-6** (`LEGACY_CHAIN_FAMILY`): ~20 call sites still pass a
  chain string until adapters/tools resolve the registry themselves (006-5/006-6). The alternative
  — keep branching on chain NAME so nothing breaks — is the coupling this task exists to remove.
- **A family with no validator ACCEPTS, it does not refuse** (R-55c): `move`/`cosmos`/`utxo`/
  `other` return the input unchanged and validate only "non-empty and within
  `MAX_DECODABLE_ADDRESS_LENGTH`". Refusing would mean "unsupported until someone writes a parser".
  Stated price: without canonicalization the cache key is built from the raw string, so the same
  address in different case yields TWO cache entries — lost cache efficiency, never lost
  correctness. Writing a real validator becomes a priority when a PAID provider appears on such a
  family, because only then does the split cost money (OQ-1).
- **CHANGED EXPECTATION, named deliberately:** `dash` used to be hardcoded to reject
  (`isValidAddress → false`, `normalizeAddress` threw). It is now `family: 'other'` and therefore
  accepted as-is. Nothing on a live path changes: no MCP tool ever accepted `dash` (their enum was
  `ethereum|solana`), and `dash-platform` emits `Snapshot`, not `Wallet`/`Balance`. Two test cases
  were rewritten for this; every EIP-55/base58 case is untouched (53 insertions, 5 deletions).

### src/chain/registry-core.ts + src/chain/registry.ts + src/chain/registry.data.json + src/chain/errors.ts (new, TASK-006 task 006-1/006-2, R-48/R-60)

The chain registry — the single source of truth about chains (ARCHITECTURE.md §3.2 "Модуль
`src/chain/registry.ts`", data-model.md §4.1/§4.2.1). Before it, the engine's chain vocabulary was
`z.enum(['ethereum','solana','dash'])` duplicated across five layers; a chain is now a **row**, so
adding one is a data edit rather than a code change in five places.

- **`loadChainRegistry(deps?): ChainRegistry`** — a **factory, never a module singleton** (same
  convention as `CapabilityRegistry`/`SqliteCacheStore`, ARCHITECTURE.md §8). `deps.data` injects a
  synthetic registry document for tests.
  - **`'data' in deps`, NOT `deps.data ?? registryData`.** `null ?? x` evaluates to `x`, so an
    explicit `{data: null}` would silently fall back to the SHIPPED registry — a test believing it
    ran on a synthetic document would exercise production data and pass for the wrong reason. Key
    absent ⇒ shipped snapshot; key present ⇒ use exactly that and fail loudly if unusable. This
    was a real defect caught by the Phase-2 test, not a hypothetical.
- **`ChainInfo`** — `caip2` (canonical CAIP-2 id, the only chain value that reaches a cache key or
  a route), `slug`, `name`, `family`, `aliases`, `nativeSymbol`, `vendors` (**naming only**, never
  coverage), `rpcHosts` (curated SSRF allowlist, `null` ⇒ honestly uncovered), `tvlUsdAtSync`
  (deliberately stale, only for `onchain_list_chains` ranking — never an answer to "what is the
  TVL"), `deprecated`.
- **Resolution order:** exact `caip2` → `slug` → `alias` → normalized (lowercase, `[^a-z0-9]`
  stripped). Pure and offline; a miss raises `UnknownChainError` carrying up to 3 Levenshtein
  candidates (distance ≤ 3), computed only at failure time so the O(n) walk never touches the hot
  path. Failing without a network call matters because a mistyped chain name is the most common way
  an agent misses on a PAID route.
- **Ambiguous fuzzy keys are dropped, not resolved.** If two chains normalize to the same key
  (`foo-bar` / `foo.bar`), that key is removed from the fuzzy index entirely: exact matches still
  work, and the ambiguous spelling fails loudly with candidates instead of silently picking
  whichever row was first.
- **Load-time validation (R-60c/d)** via zod + explicit invariant checks: unique `caip2`, unique
  `slug`, globally non-overlapping `aliases` (a chain MAY alias its own slug/caip2 — the shipped
  data does — but colliding with a _different_ chain is a load failure), CAIP-2 shape, non-empty
  `chains`. Any violation raises `ChainRegistryLoadError` **at load**, never at first request.
  **Degrading to an empty registry is forbidden**: it would turn every request into "unknown chain"
  while the process still looked healthy — a total outage wearing the costume of normal operation.
- **`registry.data.json` is a BUILD ARTIFACT, not a DB table and not a startup fetch**
  (data-model.md §4.2.1): the offline gate ("a full run makes zero network calls"), CI determinism,
  and reviewability of `rpcHosts` (SSRF surface, security.md §7.2.1) each independently forbid
  fetching it. Consequence stated openly: registry freshness is the OPERATOR's job — a new chain
  becomes available after the generator runs and the snapshot is committed (task 006-2).
  Currently a **3-row stub** (`ethereum`, `solana`, `dash`); the ~461-row production snapshot is
  generated by task 006-2. Data lives in its own `.json` so the large generated diff never mixes
  with logic diffs in review.
- **`tsconfig.json` gained `resolveJsonModule`** for this import (scoped to this package, not
  `tsconfig.base.json` — mcp-server has no JSON import). Under `NodeNext` the import must carry
  `with { type: 'json' }`; `tsc` copies the file into `dist/chain/`.
- **`errors.ts`** — `UnknownChainError` (`input`, `candidates`, `registrySize`) and
  `ChainRegistryLoadError`. Kept in their own module because task 006-4 adds
  `CapabilityNotCoveredOnChainError` beside them and both are imported by mcp-server tool handlers;
  a shared error module avoids a registry↔coverage cycle.

### scripts/sync-chain-registry.ts + test/fixtures/chain-registry*/ (new, TASK-006 task 006-2, R-49)

Regenerates `src/chain/registry.data.json` from three keyless catalogs (DeFiLlama `/v2/chains`,
CoinGecko `/asset_platforms`, `chainid.network`). **A dev script — nothing in `src/` may import
it**; a test asserts that isolation. Run it with `pnpm --filter @onchain-intel/core sync:chains`.

- **Join ladder, strongest key first.** (1) EIP-155 chain id present on both sides — unambiguous
  by construction; (2) `gecko_id` → exactly one `native_coin_id` platform; (3) ambiguous
  `gecko_id`, accepted only when exactly one candidate's name matches exactly; (4) bare name match
  across the catalog — **fuzzy, reported for human review**; else `null`. A final guard rejects any
  match whose `chain_identifier` contradicts DeFiLlama's `chainId`.
  - **Why the ladder exists (a real defect, not caution):** `native_coin_id` is NOT unique — 28
    native coins are shared by 109 platforms, because every L2 paying gas in ETH reports
    `native_coin_id: "ethereum"` (49 of them). The first naive implementation took the first hit
    and produced `ethereum → alienx`, `bsc → opbnb`, `solana → sonic-svm`,
    `bitcoin → trustless-computer` — i.e. token price/metadata lookups aimed at a different
    chain's platform. Silent data corruption, no crash. Adding the EVM-id rung cut fuzzy joins
    from 73 to 20 as a side effect.
- **Aliases are assigned in a SECOND pass**, after every slug is known. A single-pass check is
  order-dependent: a chain processed early could claim an alias that is the slug of a chain
  appearing later (`iota-evm` claiming `iota`), emitting a snapshot the loader rejects outright.
- **The generator validates its own output with `buildChainRegistry`** — the same validator the
  runtime uses — and refuses to write when it fails. This is why `registry-core.ts` exists
  separately from `registry.ts`: importing the loader directly would drag in the JSON file the
  generator is in the middle of producing, so deleting the snapshot would break the only tool that
  can regenerate it.
- **Curated columns are carried forward, never invented and never erased:** `rpcHosts` (task
  006-8, security.md §7.2.1) and `vendors.nansen` (task 006-9). `vendors.dexscreener` comes from
  an explicit OBSERVED list — DexScreener publishes no chain catalog, and a non-null value is what
  makes `chainSupport()` true, so guessing ids there would claim unverified coverage.
- **Determinism (R-49c):** rows sorted by `caip2`, fixed key order, and `syncedAt` advances only
  when the data actually changed — otherwise every sync would rewrite the file and produce a
  meaningless diff. Two consecutive runs are byte-identical; a test enforces it.
- **Failure is loud and total:** an unavailable catalog aborts without writing (a partial snapshot
  would pass validation and silently shrink the known world), and a chain that vanishes is kept
  with `deprecated: true` rather than deleted.
- Report sections: added / deprecated / changed / **ambiguous-or-rejected joins** / **fuzzy
  name-joins** / slug conflicts / dropped aliases / **RPC candidates** (proposed only — never
  written to `rpcHosts`).
- `src/chain/registry.data.json` is in **both** `.prettierignore` files: the generator owns its
  byte format, and prettier re-wrapping arrays would break the determinism guarantee every sync.

### src/adapters/types.ts (new, task 003-2, R-3)

The stable internal interfaces the rest of the provider-adapter contour depends on
(ARCHITECTURE.md §3.2, D4):

- `CapabilityDescriptor { id, chains? }` — a single routable data capability; `chains` narrows it
  to specific chains, omitted means chain-agnostic.
- `ProviderAdapter { id, capabilities(), costOf(), fetch(), normalize(), isAvailable()? }` — no
  concrete adapter implements this yet (003-4/003-5); `fetch()` returns `unknown` (a
  provider-specific raw shape, narrowed only inside that adapter's own `normalize()`) — the
  anti-corruption-layer contract: `CapabilityRegistry` never sees a raw provider DTO, only what
  `normalize()` produces. `isAvailable?()` is optional — an adapter with no env/key precondition
  (e.g. a keyless REST API) omits it and `CapabilityRegistry` treats that as "always available"
  (`??  { ok: true }` at the call site in `registry.ts`).

### src/chain/coverage.ts + CapabilityNotCoveredOnChainError (new, TASK-006 task 006-4, R-51)

Capability × chain coverage, **derived and never stored**:
`covered(cap, chain) := ∃ adapterId ∈ route(cap).adapterIds : adapter.chainSupport(chainInfo)`.
A stored matrix would have to be maintained in two places (registry AND each adapter) and would
diverge on the first edit; the derivation leaves the registry the single source of facts about a
chain and the adapter the single source of facts about itself. An adapter with no `chainSupport`
counts as not chain-bound and covers whatever its route covers — which is why adding this changed
no M1/M2 behaviour.

- **Gate position is the point, not the check itself.** `CapabilityRegistry.resolve()` runs it
  after the route is known but BEFORE `deriveArgsHash`, the cache read, `isAvailable()`, the budget
  gate and any HTTP. Widening the chain set from 2 to 458 multiplies the ways a caller can miss
  coverage; if a miss cost a credit reservation, the widening would itself become a way to spend
  money. Tests assert the negative directly: `fetch` never entered, `costOf` never called,
  `cache.get`/`cache.set` never touched, `globalThis.fetch` booby-trapped.
- **`CapabilityNotCoveredOnChainError` is deliberately NOT `CapabilityUnavailableError`.** "Not
  here and never will be" versus "could work — fix the key, or retry later" demand opposite
  reactions; collapsing them sends an agent retrying where retrying is pointless and giving up
  where a key would have sufficed. Both lists in the message come from the same two sources as the
  predicate, so they cannot drift from real behaviour, and both are truncated with a "+N more"
  suffix — an error meant to save a wasted call must not flood the model's context itself.
- **An unresolvable chain string leaves the gate inert.** Canonicalizing tool input is task 006-6's
  job at the boundary; `resolve()` must not start rejecting chains the pre-TASK-006 contract
  accepted.
- **`resolve(capability, chain: string, …)` — widened from the closed `Chain` enum** (as is
  `CapabilityUnavailableError.chain`). With the enum in place the gate was unreachable for any
  chain outside the original three, i.e. untestable and pointless. Every existing caller still
  compiles: the enum is a subset of `string`.
- `CapabilityRegistry` gained an optional 4th constructor arg (`chains: ChainRegistry | null`),
  defaulting to the shipped snapshot so production wiring cannot forget it, injectable so tests use
  a synthetic 3-chain registry. The `Coverage` instance is built lazily and memoized per instance —
  never a module singleton (§8).

### src/adapters/registry.ts (task 003-2, R-4/R-11/R-24 — completes 003-1's earlier stub)

`CapabilityUnavailableError extends Error { capability, chain, tried: CapabilityAttempt[] }` —
thrown when every adapter in a route's `adapterIds` was unavailable/failed, or no route matches
`(capability, chain)` at all (`tried: []` in that case). `CapabilityAttempt { adapterId, reason }`
records one skipped/failed attempt (R-24 explicit degradation — never a silent empty result).

`CapabilityRegistry` — constructor takes `(routes: CapabilityRoute[], adapters: Map<string,
ProviderAdapter>, cache: CacheStore = new PassthroughCacheStore())`; a factory, not a module
singleton (ARCHITECTURE.md §8, task reviewer note) — tests build their own small route tables +
mock-adapter Maps instead of importing the real `providers.config.ts` (which has no matching real
`ProviderAdapter` instances until 003-4/003-5).

`resolve(capability, chain, args)` algorithm (implemented this task, replacing 003-1's
`throw new Error('not implemented yet')` stub):

1. Find the route where `route.capability === capability` and (`route.chains` is unset or
   contains `chain`). No match → `CapabilityUnavailableError` with `tried: []`.
2. Compute `argsHash = deriveArgsHash(capability, args)` once per call (not per-adapter — the
   capability+args pair is the same regardless of which adapter ultimately serves it).
3. Walk `route.adapterIds` in order:
   - No `ProviderAdapter` registered for that id in the `adapters` Map → recorded as
     `{ adapterId, reason: 'no adapter registered for this id' }`, skip-to-next. This is the
     documented behavior for ids `providers.config.ts` names but no adapter implements yet (see
     that file's own docstring) — **not** a compile-time or runtime error in this package.
   - `adapter.isAvailable?.() ?? { ok: true }` reports `{ ok: false, reason }` → recorded, skip.
   - `cache.get(adapter.id, capability, argsHash)` hit → return
     `{ result: cached.value, source: adapter.id, cache: 'hit', ageMs: cached.ageMs }` immediately
     — `fetch`/`normalize` are never called on a hit.
   - Miss → `try { fetch → normalize → cache.set → return { result, source, cache: 'miss' } }
catch (error) { record { adapterId, reason: error.message }; continue to next adapterId }` —
     a throw from either `fetch()` or `normalize()` is caught and treated as a fallback trigger,
     never propagated as-is (R-11 hot-swap).
4. Every `adapterId` exhausted without a return → `CapabilityUnavailableError` with the full
   `tried` list.

Anti-corruption layer preserved: only `normalize()`'s return value is ever part of the resolved
`result` — the raw `fetch()` payload never escapes this method (asserted in
`test/registry.test.ts` via `result.result !== raw` object-identity check).

**Cache-fault resilience (adversarial cycle 1, findings A1/A2 — fix "A"):** `cache.get(...)` and
`cache.set(...)` each got their OWN try/catch, on top of everything above — a faulty `CacheStore`
is now always best-effort, never fatal. A `cache.get()` throw is caught, logged to stderr (one
line, `cache.get failed provider=... capability=...: <message>`), and treated exactly like a
plain miss — `resolve()` falls straight through to `fetch`/`normalize`. A `cache.set()` throw is
caught in its OWN try/catch NESTED INSIDE the `fetch`/`normalize` try block (deliberately not
sharing that block's catch, so it can never be recorded as a `tried` failure or trigger a
fallback to the next `adapterId`) — logged to stderr
(`cache.set failed provider=... capability=...: <message> — result still returned...`), and the
already-fetched/normalized `result` is still returned as a genuine `'miss'`. Two new
`test/registry.test.ts` cases (nested `describe('cache-fault resilience ...')`) inject a
`ThrowingCacheStore` whose `get()`/`set()` throw independently, asserting the successful
`fetch`/normalize result is still returned in both cases and that the matching stderr line was
written (`vi.spyOn(process.stderr, 'write')`).

### src/net/safe-fetch.ts (task 003-2, R-25 — the single point of outgoing HTTP)

`SsrfBlockedError extends Error { hostname }` — carries only the rejected hostname, never the full
URL/query (not a secret, but no reason to carry more than needed to diagnose a misconfigured
allowlist). `assertAllowedHost(hostname, allowlist)` — throws if `hostname` isn't in `allowlist`;
transport-agnostic (designed to also serve a future non-HTTP transport, e.g. `dash-platform`'s
deferred gRPC channel — ARCHITECTURE.md §7.3 — though only `safeFetch` calls it in M1).

`safeFetch(url, opts, allowlist, fetchImpl = fetch, options?: SafeFetchOptions)` — resolves the
target hostname and `assertAllowedHost`s it **before** any network attempt; calls `fetchImpl` with
`redirect: 'manual'`; on a 3xx response with a `Location` header, resolves that `Location` against
the current hop's URL (handles both absolute and relative redirects identically to a real
browser), re-checks **that** hostname against the same `allowlist` before following it, up to
`MAX_REDIRECTS = 3` hops — never trusts `Location` blindly (R-25/§7.3). `fetchImpl` is injectable
(defaults to the global `fetch`) specifically so `test/safe-fetch.test.ts` never touches the real
network — every test supplies a `vi.fn()` fake returning canned `Response`s per hop.

**Hardened (adversarial cycle 1, fix B — 3 findings):**

1. **Per-call timeout (B1):** every hop races `fetchImpl(...)` against
   `AbortSignal.timeout(options.timeoutMs ?? DEFAULT_TIMEOUT_MS)` (15s default) via a small
   `raceWithTimeout()` helper — on abort, rejects with a typed `SafeFetchTimeoutError` (never a raw
   `AbortError`), which lets a caller's own fallback loop (e.g. `rpc-evm`'s primary→secondary
   endpoint retry) advance instead of hanging forever. `raceWithTimeout()` attaches its own
   `signal.addEventListener('abort', ...)` rather than trusting `fetchImpl` alone to reject on
   abort — deliberate, so an injected TEST `fetchImpl` that never resolves (and never inspects its
   own `signal` argument) still times out, exactly like a real hung `fetch()` would. Verified
   empirically (a throwaway Node script, not committed) that `AbortSignal.timeout()`'s internal
   timer is unref'd — it never keeps a test process alive waiting for the default 15s to elapse.
2. **Response-size cap (B2):** `assertResponseSizeWithinCap()` checks the `Content-Length` header
   (when present) against `options.maxResponseBytes ?? DEFAULT_MAX_RESPONSE_BYTES` (10MB default)
   immediately after each hop resolves, BEFORE the caller ever reads the body — throws
   `SafeFetchResponseTooLargeError` if it's over. **Documented limitation, not silently claimed as
   full protection:** a response with NO `Content-Length` (e.g. chunked transfer-encoding) isn't
   capped mid-stream by this check; a true streaming byte-counter is explicitly out of this fix's
   scope (future hardening).
3. **Redirect hardening (B3):** a redirect `Location` resolving to a non-`https:` target is
   rejected outright (a plain `Error`, `/https/i`-matchable). A redirect `Location` resolving to a
   DIFFERENT hostname than the current hop strips `Authorization`/`*-api-key`-style headers
   (`SENSITIVE_HEADER_RE`, a case-insensitive substring match covering both `Authorization` and
   every adapter's own `x-...-api-key` header, e.g. coingecko's `x-cg-demo-api-key`) from the
   request before following it, via `stripCrossHostHeaders()` (normalizes through the `Headers` API
   so it works regardless of whether the caller passed a plain object, an array of pairs, or a
   `Headers` instance) — a SAME-host redirect keeps the original headers untouched.

`SafeFetchOptions { timeoutMs?, maxResponseBytes? }` — both optional, both default to the module
constants (`DEFAULT_TIMEOUT_MS`/`DEFAULT_MAX_RESPONSE_BYTES`); no adapter currently overrides
either. **TS note:** `stripCrossHostHeaders()`'s parameter is typed via the indexed-access type
`RequestInit['headers']`, not the bare `HeadersInit` name — `@types/node`'s bundled
`undici-types` declares `HeadersInit` as a plain module export, not an ambient global, so it
doesn't resolve under this package's `types: ["node"]` (no DOM lib) tsconfig; the indexed-access
form reaches the identical type through `RequestInit`, which IS declared globally.

`test/safe-fetch.test.ts` gained a new `describe('timeout + size-cap + redirect hardening ...')`
block (5 new tests): a never-resolving fake `fetchImpl` + a tiny `timeoutMs` rejects with
`SafeFetchTimeoutError`; an oversized `Content-Length` rejects with
`SafeFetchResponseTooLargeError` (and an in-cap one does NOT reject); a redirect to `http://`
rejects (`/https/i`); and a same-host-then-cross-host two-hop redirect chain asserts the fake
`fetchImpl`'s SECOND call still carries `Authorization`/`x-cg-demo-api-key` (hop 2, same host) while
the THIRD call has them stripped (hop 3, different host) but keeps `content-type`.

**Initial-URL https check (adversarial cycle 2, finding 4):** cycle 1's non-https rejection (B3)
only ever covered REDIRECT targets — the very first `url` argument itself had no such check at
all. `safeFetch` now resolves `new URL(url)` up front and throws (a plain `Error`, `/https/i`
matchable, mirroring the redirect-hop check's own error style) if its protocol isn't `https:`,
BEFORE any network attempt — symmetrical with the existing redirect-hop guard. One new
`test/safe-fetch.test.ts` case: a plain `http://` initial url rejects and `fetchImpl` is never
called at all.

### src/net/rate-limit.ts (task 003-2, R-26 — per-provider token bucket)

`TokenBucketConfig { capacity, refillPerSec }` (the shape of `providers.config.ts`'s `rateLimit`
field). `createThrottle(deps?: { now?, wait? })` builds an isolated `Throttle` function
(`(providerId, config) => Promise<void>`) with its own `Map<providerId, BucketState>` — a factory,
not a shared singleton (mirrors the Registry/CacheStore "factory, not singleton" principle). Each
call: refills the named provider's bucket by `elapsedSeconds * refillPerSec` (capped at
`capacity`) based on time since the bucket's last check, then either consumes one token
immediately or awaits `deficit / refillPerSec` seconds before proceeding. `deps.now`/`deps.wait`
are injectable (production default: real `Date.now`/`setTimeout`) precisely so
`test/rate-limit.test.ts` never spends real wall-clock time or touches a real timer — tests supply
a fake clock whose `wait()` just advances an in-test counter and resolves immediately. The
module-level `throttle` export (`= createThrottle()`) is the production singleton adapters will
call in 003-4/003-5 — in-memory, per-process, no persistence (M1 — one process, ARCHITECTURE.md §8).

**Concurrency-safe + reject-on-misconfiguration (adversarial cycle 1, fix C — 2 findings merged):**
the refill+consume+decide-whether-to-wait step is now entirely SYNCHRONOUS (no `await` before it
fully commits the bucket's new state), and `tokens` is allowed to go NEGATIVE (a backlog) and is
**never reset back to `0`** after a real wait resolves. The PREVIOUS code deferred its state commit
(`tokens = 0; lastRefillMs = now()`) until AFTER `await wait(waitMs)` resolved — two callers
arriving back-to-back while the first was still waiting both read the SAME pre-wait state and
computed the IDENTICAL `waitMs`, never spacing out. Leaving `tokens` negative and committing
synchronously means each subsequent caller's math immediately accounts for every still-outstanding
reservation ahead of it (verified empirically via a throwaway Node script, not committed, before
writing the real fix — JS's single-threaded execution model guarantees `N` concurrent
`throttle()` calls issued via `Promise.all([...])` run their synchronous prefixes back-to-back, in
order, with no interleaving, so no explicit queue/mutex object is needed). Separately,
`refillPerSec <= 0` now throws a typed `RateLimitRejectedError` immediately instead of computing
`waitMs = Number.POSITIVE_INFINITY` — that branch never actually hung forever: `setTimeout`'s own
documented clamping of an out-of-range delay (`> 2147483647` or `< 1`) down to `1` meant it
silently resolved almost immediately, defeating the rate limit with no signal anything was
misconfigured.

`test/rate-limit.test.ts` gained a new `describe('concurrency-safe token bucket ...')` block (3
new tests): 3 concurrent callers against a 1-capacity/2-per-second bucket (via
`Promise.all([throttle(...), throttle(...), throttle(...)])`, a FROZEN clock so `now()` never
advances on its own and `wait()` only records the requested duration — isolating the spacing logic
from the real-time-elapsed refill logic the pre-existing tests already cover via
`clock.advance()`) assert `waitCalls` is exactly `[500, 1000]`, never `[500, 500]`; plus
`refillPerSec: 0` and `refillPerSec: -1` each reject with `RateLimitRejectedError`.

**30s fairness cap (adversarial cycle 2, fix 7):** `RateLimitRejectedError` now carries a second
constructor argument (`reason: string`, alongside `providerId`) so the SAME typed error class
serves both of its trigger conditions with a distinct, accurate message — the pre-existing
misconfiguration branch (`refillPerSec <= 0`) and the new one: if the computed `waitMs` for a call
exceeds `MAX_WAIT_MS = 30_000`, `throttle()` rejects instead of actually awaiting that long
(`computed wait <n>ms exceeds the 30000ms fairness cap (saturated bucket)`) — a caller stuck
behind a severely backed-up bucket gets a fast, typed, actionable rejection instead of silently
blocking a request handler for up to (or beyond) 30 real seconds. The reserved token is REFUNDED
(`bucket.tokens += 1`) before this throw, since a rejected call never actually consumes its slot —
without the refund, a burst of rejected callers would permanently deepen the backlog for whoever
calls next. One new test: an artificially tiny `refillPerSec` (`0.001`) makes a 2nd call's computed
wait balloon into the hundreds-of-thousands-of-ms range, asserting the rejection is
`RateLimitRejectedError`, its message names the provider AND contains "saturat...", and
`clock.wait` is never actually called (never blocks).

**Saturation-refund regression coverage (post-M1 polish, cheap-fix backlog item 6):** the fix-7
refund itself (`bucket.tokens += 1` before the saturation throw) had no dedicated test proving
"no double-pay" across TWO consecutive rejections. New `test/rate-limit.test.ts` case: with a
frozen clock (zero elapsed time) and a tiny `refillPerSec`, a successful call followed by two
consecutive saturating (rejected) calls against the SAME bucket — both rejections' `RateLimitRejectedError` messages embed the identical computed `waitMs` (parsed out of the message
text), proving the 1st rejection's refund put the bucket back into the exact same state the 2nd
rejection computed from (a double-pay bug would have made the 2nd rejection's computed wait grow).
`clock.wait` is asserted never called across either attempt.

### src/net/args-hash.ts (task 003-2 — `cache_entries`' `args_hash`, ARCHITECTURE.md §7.2)

`canonicalize(value)` — recursively sorts object keys (arrays keep element order, only object
_keys_ are canonicalized; primitives pass through unchanged) so that `{chain, address}` and
`{address, chain}` — the same logical tool input, built in a different key order — produce
byte-identical `JSON.stringify` output. `deriveArgsHash(capability, args)` —
`sha256(hex(JSON.stringify({ capability, args: canonicalize(args) })))` via Node's built-in
`node:crypto` `createHash` (no new dependency). `args` **must always** be the normalized,
post-zod-validation, post-`normalizeAddress` tool input — **never** `process.env` or any secret
(D10/§7.2); folding `capability` into the hashed payload (not just a separate cache-key column)
prevents two different capabilities called with coincidentally-identical `args` from colliding.

  write can reference one as an FK target. `get()` selects by the UNIQUE key, treats `expires_at <=
now` as a miss **and deletes the stale row** (so it never shadows a later write); `set()` is
  `INSERT ... ON CONFLICT (provider, capability, args_hash) DO UPDATE SET value_json=excluded...,
created_at=excluded..., expires_at=excluded...` — an upsert, never `DO NOTHING` (DB-SCHEMA-CONCEPT
  §1.5 "aggregates" branch — a cache entry is a recomputable projection, not an append-only
  observation). **Opportunistic expired-row sweep (adversarial cycle 1, fix H):** every
  `sweepEveryNWrites`-th (constructor option, defaults to `DEFAULT_SWEEP_EVERY_N_WRITES = 50`)
  `set()` call runs `DELETE FROM cache_entries WHERE expires_at <= ?` via the existing
  `idx_cache_entries_expiry` index — counter-based (`writeCount`, instance-scoped), no timers/
  background jobs. **Documented M2 deferral, not silently done:** this is NOT a retention/size cap
  (no maximum row count or disk-size ceiling) — it only keeps rows that have already EXPIRED from
  lingering indefinitely between reads (`get()` already deletes a stale row on read, but a
  `(provider, capability, argsHash)` key that's never read again would otherwise sit forever).
  `test/cache.test.ts` forces `sweepEveryNWrites: 2` (rather than looping 50 times) to reach the
  sweep path deterministically: writes one entry, force-expires it via a second raw connection (the
  same white-box technique the pre-existing TTL-expiry test uses), then a 2nd `set()` on the SAME
  store crosses the threshold — asserts the expired row is gone and the fresh one remains.
  **Prepared statements (adversarial cycle 2, fix 5):** the four recurring statements
  (`get()`'s SELECT, `get()`'s stale-row DELETE, `set()`'s upsert INSERT, and
  `sweepExpired()`'s DELETE) are each `db.prepare()`d exactly ONCE, in the constructor, as private
  readonly fields — `get()`/`set()`/`sweepExpired()` now call `.get()`/`.run()` on those cached
  `Statement` objects instead of calling `this.db.prepare(...)` fresh on every single invocation
  (re-parsing/re-planning the identical SQL text every time). The one-time `bootstrapProviders`
  upsert (already called at most once per instance, from the constructor) is left as a local
  `prepare()` there rather than a fifth long-lived field — it was never re-prepared per-call to
  begin with. Purely a performance refactor — behavior is bit-for-bit identical, so no new test was
  added; the full existing `test/cache.test.ts` suite (unchanged) is the regression guard.
  **Leak-safe constructor (post-M1 polish, cheap-fix backlog item 4):** every step that runs AFTER
  the connection opens (PRAGMA/DDL exec, `bootstrapProviders`, the four statement `prepare()`
  calls above) is now wrapped in its own try/catch — a throw from any of them used to leak the
  already-opened `better-sqlite3` handle (nothing closed it before the exception propagated out of
  the constructor). Now: best-effort `db.close()` (swallowing any close-time error, which must never
  mask the ORIGINAL failure) before rethrowing the original error unchanged.
  `SqliteCacheStoreOptions` gained a TEST-ONLY seam, `postOpenTestHook?: () => void` (called as the
  very first post-open step) — never set by production code, exists solely so
  `test/cache.test.ts` can simulate an arbitrary post-open failure without needing a genuinely
  malformed DDL string or corrupt provider row. One new `test/cache.test.ts` case: a
  `postOpenTestHook` that throws makes the constructor rethrow that exact error AND asserts
  `Database.prototype.close` was called exactly once (`vi.spyOn`).
- **`two-level-store.ts`** — `TwoLevelStore implements CacheStore`: `get()` walks hot
  (`LruHotLayer`) → cold (injected persistent `CacheStore`) → miss; a cold hit is promoted into the
  hot layer with `ttlFor(capability) * 1000 - coldHit.ageMs` (the entry's REMAINING ttl); `set()`
  writes both layers (persistent first, then hot with the full capability ttl). Hit/miss stats +
  the stderr line are recorded **inside this class's `get()`**, not by an edit to
  `registry.ts` — see the section header above for why that's equivalent. `createCacheStore(options?)`
  factory: assembles a `SqliteCacheStore` (bootstrapped from `adapterRegistrations`, all 9, by
  default) wrapped in a `TwoLevelStore` — this is what a future `mcp-server` bootstrap (tasks
  003-6/003-7) constructs and injects as `CapabilityRegistry`'s third constructor argument in place
  of the default `PassthroughCacheStore`.

  **`ageMs` anchored across cold→hot promotion (adversarial cycle 2, fix 2):** `LruHotLayer.set()`
  gained a 6th, optional `createdAt` parameter (defaults to `Date.now()` for a genuinely fresh
  write); `TwoLevelStore`'s promotion path now passes `Date.now() - coldHit.ageMs` explicitly. The
  PREVIOUS code always stamped a promoted entry's `createdAt` as `Date.now()` (the promotion
  moment), so every subsequent HOT hit's `ageMs` reset to ~0 and stayed there until the entry
  naturally expired — silently under-reporting `_meta.cache.ageMs` to MCP tool callers for however
  long the value had ALREADY been sitting in the persistent layer. One new `test/cache.test.ts`
  case (in the `TwoLevelStore` describe block): a `FixedAgeCacheStore` test double whose `get()`
  always reports a fixed `ageMs` (5s) — after the first (`cold`) `get()` promotes it, a second
  (`hot`) `get()` asserts `ageMs >= 5000`, proving the age carried forward instead of resetting.

all dated 2026-07-22):**

- CoinGecko's `platform` path segment and `detail_platforms` key both equal the literal `Chain`
  string (`'ethereum'`/`'solana'`) — no translation table needed.
- **DexScreener has no keyless "list newest pairs for chain X" endpoint** — `/token-profiles/
latest/v1` and `/token-boosts/latest/v1` carry neither liquidity/volume data nor a chain filter.

  `GET /latest/dex/search?q=<query>`; querying by the target chain's own native asset symbol
  (`NATIVE_QUERY`: `ethereum→'ETH'`, `solana→'SOL'`) reliably surfaces that chain's pairs among the

**Value validation on `tvlUsd`/`totalTvlUsd` (adversarial cycle 2, finding 1b):** `normalize()` now
additionally rejects a non-finite or negative value for EITHER field (`!Number.isFinite(...) ||
... < 0`), throwing a clear `defillama.normalize: invalid tvl value(s) for chain <chain>
(tvlUsd=..., totalTvlUsd=...)` error — DISTINCT from the pre-existing "missing tvl series" error
(a genuinely absent series vs. a present-but-corrupt last point are different failure modes,
reported differently). This matters because a bad value here would otherwise have been cached as a
"successful" `ProtocolTvlResult` by `CapabilityRegistry.resolve()` BEFORE `onchain_protocol_tvl`'s
own output schema (`.nonnegative()`, `packages/mcp-server`) ever got a chance to reject it — an
adapter's own `normalize()` is the correct anti-corruption-layer boundary to catch this, not the
downstream tool's re-parse. Two new `test/defillama.contract.test.ts` cases (`describe('tvl value
validation ...')`): a `structuredClone`d fixture with the chain-scoped series' last point forced
negative, and the same for the top-level series — each asserts the documented error message.

`defillama`'s `normalize()` return shape (`ProtocolTvlResult`, exported from this module) is a
**plain TypeScript interface, not a zod schema** — ARCHITECTURE.md §3.2/§5.1 specifies this exact
`{protocol, chain, tvlUsd, totalTvlUsd, source, fetchedAt}` shape literally, not a reference to one
of the six canonical `types/*` schemas; introducing a new zod schema for it would be an
unrequested architectural addition (developer-guidelines §1.6) not asked for by this task.

**`fetch(cap, args)`/`normalize(cap, raw)` are written as object-literal properties with arrow
functions** (`fetch: async (cap, args) => {...}`), not ES2015 method shorthand
(`async fetch(cap, args) {...}`) — a deliberate style choice: method-shorthand syntax puts a bare
`fetch(` token in the source (preceded by whitespace, not a `.`), which is exactly the pattern the
task's "no bare `fetch(`" acceptance grep flags, even though it's a legitimate `ProviderAdapter`
interface-method declaration, not a raw network call. The arrow-function-property form
(`fetch:` — a colon, not an open-paren) is behaviourally identical (both satisfy the interface
structurally) and simply never produces that substring. Doc comments in these three files
similarly avoid ever writing `fetch()`/`fetch(` verbatim — described in prose as "the HTTP step"
instead (task instruction).

**`dexscreener.normalize()` — skip-and-log malformed pairs (adversarial cycle 1, fix G):**
previously a single malformed pair anywhere in a `/latest/dex/search` response batch made
`normalize()` throw, failing the ENTIRE `onchain_new_pairs` call even when most pairs were fine.
Now each candidate (post chain-filter/`limit`-slice) is validated INDEPENDENTLY — the existing
manual type-narrowing guard (unavoidable: the wire fields are `unknown`), followed by
`PoolSchema.safeParse(pool)` as the canonical contract check — and a malformed one is DROPPED
(counted), not thrown. A malformed count `> 0` writes ONE stderr summary line
(`dexscreener.normalize: skipped <n> malformed pair(s) of <total> for chain=<chain>`). Only when
EVERY candidate in the batch turns out malformed does this still throw (an empty `Pool[]` would
otherwise be indistinguishable from "no new pairs right now", a silent/misleading success — R-24's
explicit-degradation principle applied at this finer grain). `test/dexscreener.contract.test.ts`
gained a `describe('malformed pair handling ...')` block: one malformed pair among two returns the
well-formed subset (length 1) with the stderr summary line; a batch where the only candidate is
malformed throws.

Two more LIVE `ProviderAdapter` factories (`createRpcEvmAdapter`/`createRpcSolanaAdapter`), same
factory/DI convention as the 003-4 adapters (`fetchImpl?`/`now?`, no `env` — both keyless). Both
serve `wallet.balances.native` (one chain each) via JSON-RPC over HTTP (`fetch`-based, through

  HTTP step tries each `ENDPOINTS` entry in order, catching any failure (non-2xx or a thrown
  error) and moving to the next host, only throwing after all are exhausted — this is DIFFERENT
  from `CapabilityRegistry`'s cross-adapter fallback (R-11): `wallet.balances.native` on ethereum

  hex-wei `result` to an exact decimal string via `BigInt(...).toString(10)` — **never**

  `amountNum` is still populated as a documented lossy display projection.
- **`rpc-solana`**: `getBalance` JSON-RPC call, single confirmed live host
  `api.mainnet-beta.solana.com` (2026-07-22) — **no fallback host** in M1 (ARCHITECTURE.md §11: a

  hosts). **Documented vendor limitation** (not an engine bug): unlike `eth_getBalance`,
  Solana's `getBalance` wire response carries `result.value` as a JSON **number**, not a
  hex/decimal string — so a lamport balance above `Number.MAX_SAFE_INTEGER` (~9.007M SOL) has
  already lost precision by the time `response.json()` parses it, before this adapter ever sees
  it; `amountRaw` is still emitted as a string per convention, but merely reflects that
  already-lossy number for balances past that threshold. This is called out explicitly in the
  module's own docstring rather than silently accepted.

**Input hardening (adversarial cycle 1, fixes E/F) — both tightened the "raw wire value → exact
numeric string" boundary, never trusting the vendor response's shape blindly:**

- **`rpc-evm` (fix E):** the hex-balance guard is now `HEX_BALANCE_RE = /^0x[0-9a-fA-F]+$/`

- **`rpc-solana` (fix F):** `result.value` (lamports) is now validated as a non-negative SAFE

### rpcHosts + the SSRF perimeter (TASK-006 task 006-8, R-56) — security-critical

`rpc-evm` now takes BOTH its endpoint list and the allowlist it hands `safeFetch` from **this
chain's** `rpcHosts` row — per chain, never merged, so one chain's endpoint can never be used to
reach another's. `safeFetch` itself is untouched: only the SOURCE of the allowlist changed, not the
mechanism.

- **`rpcHosts` is the one registry column the generator may not fill.** `chainid.network` publishes
  RPC endpoints for 2660 chains; importing them would mean the set of hosts we make outgoing
  requests to is decided by a third party over the network. The generator only _proposes_
  candidates in its report (`row.rpcHosts` is read, never assigned — a test greps for it).
- **19 of 458 chains curated** (2026-07-26). Criterion: highest-TVL EVM chains for which
  `chainid.network` offers a keyless https endpoint; each probed with `eth_chainId`, and only those
  returning the EXPECTED chain id were admitted.
- **One candidate was rejected by hand, and it is the argument for the whole rule.**
  `hyperliquid-l1` (chainId 999): its only live candidate was `gwan-ssl.wandevs.org` — a **Wanchain**
  domain. chainId 999 is historically claimed by both chains, so `eth_chainId` returns exactly the
  expected value and **the automated check passes**. Hyperliquid balance queries would have been
  answered by Wanchain. A machine can verify "responded with the right chain id"; it cannot verify
  "is the right chain".

### src/pg/read-client.ts (new, task 003-5, R-12)

`createReadClient(deps?)` — a lazy, read-only Postgres client, used ONLY by
`adapters/pg-history/index.ts` (not a separate side-channel, F-2). `PgPoolLike`/`PgPoolCtor` are
a deliberately NARROW structural interface (just the one `query(text, values?)` method this module
actually calls) rather than importing `pg`'s full `Pool` type surface — this is what lets tests
inject a lightweight fake pool constructor that never opens a real socket (R-21). The real
`pg.Pool` is the production default, assigned via an explicit `as unknown as PgPoolCtor` cast at
the DI boundary (documented in-line: `Pool`'s actual `PoolConfig` constructor parameter is broader
than the narrow `{connectionString, options?}` shape this module ever passes it — the cast
documents that intentional narrowing rather than fighting structural variance). Behavior:

- **Lazy**: the underlying `Pool` is constructed on the FIRST `query()` call only — never at
  `createReadClient()`'s own call time, never at module load — and only once (a module-closure
  `pool` variable, reused across subsequent calls).
- **DSN never logged**: `isAvailable()` reports `{ok: false, reason: 'needs ONCHAIN_PG_URL'}`
  when `env.ONCHAIN_PG_URL` is absent — the reason string never contains the DSN value itself
  (D10/§7.2).
- **`search_path=onchain`** is set via the connection's own `options: '-c search_path=onchain'`
  (DB-SCHEMA-CONCEPT's Postgres schema-isolation convention — literal string present in source,
  the task's acceptance grep finds it verbatim).
- **SELECT-only, enforced twice**: a runtime regex guard (`/^\s*select\b/i`) rejects any
  non-`SELECT` statement BEFORE it ever reaches the pool — defense in depth alongside the
  code-review grep gate (R-27) this task's acceptance also runs; this module never issues a write
  statement regardless of the guard.

**Pool hardening (adversarial cycle 1, fix D — 2 findings, both against the underlying `pg.Pool`,
never exercised with a live PG connection, R-21):**

1. **`pool.on('error', ...)` attached immediately after `new PoolCtor(...)` (D1):** an IDLE
   connection in the pool erroring out is a `pg.Pool`-documented event, fired independently of any
   in-flight `query()` call — without this listener, Node treats an unhandled `'error'` event on an
   `EventEmitter` as an UNCAUGHT EXCEPTION and crashes the whole process, exactly what this
   optional, best-effort history source must never do. The handler only writes to stderr
   (`pg/read-client: idle pool error (connection details never logged): <message>`) and otherwise
   ignores it. `PgPoolLike.on` is OPTIONAL on the interface (`on?(...)`) — only the real `pg.Pool`
   and any fake that chooses to model it need to implement it; `read-client.ts` calls it as
   `pool.on?.('error', ...)`. Also new: `PgPoolCtor`'s config type gained
   `connectionTimeoutMillis?`/`max?`, and `createReadClient` now ALWAYS passes them explicitly
   (`DEFAULT_CONNECTION_TIMEOUT_MS = 10_000`, `DEFAULT_MAX_POOL_SIZE = 3`) — conservative sizing for
   an optional, single-adapter, read-only client, never left at `pg`'s own looser defaults.
2. **Sanitized query-failure messages (D2):** any failure from the actual `pool.query(...)` call
   (as opposed to the guard clauses above, which already throw their own safe, DSN-free messages)
   is now caught, logged to stderr with its FULL detail (which may embed the DSN's host/port/user,
   e.g. `pg`'s own "connection to server at ... failed" text), then rethrown as the single
   sanitized message `'pg-history: database unavailable'` (`SANITIZED_QUERY_FAILURE_MESSAGE`) —
   with `{ cause: error }` attached (satisfies this repo's `preserve-caught-error` ESLint rule and
   preserves the chain for local debugging; never read by anything in this codebase's own error
   handling, which only ever reads `.message`). The DSN's host/port/user never reach the caller —
   and, transitively, never reach an MCP client.

`test/pg-history.contract.test.ts` gained a `describe('pool hardening ...')` block (3 new tests,
plus the pre-existing "fetch() lazily constructs the pool" test's exact-equality assertion was
updated to include `connectionTimeoutMillis`/`max`): a `FakePool.emitError(...)` helper (a small
in-test `EventEmitter`-shaped extension of the existing mock, tracking registered `'error'`
listeners) proves an idle-connection error is logged and never throws; a second test asserts the
pool constructor call includes `connectionTimeoutMillis: 10_000, max: 3`; a third injects a
`FailingQueryPool` (deliberately WITHOUT an `on()` method, proving `read-client.ts` never assumes
it's present) whose `query()` always throws a DSN-shaped raw error, asserting the caller only ever
sees `'pg-history: database unavailable'` while the raw text reaches stderr only.

**Pool-construction hardening (post-M1 polish, cheap-fix backlog item 3):** `new PoolCtor(...)`
itself — a SYNCHRONOUS constructor call — sat OUTSIDE the D2 query-failure try/catch above, so a
throw from it (e.g. `pg` rejecting a malformed connection string) used to propagate its raw
message, potentially embedding the DSN's host/port/user, straight to the caller. Now wrapped in the
SAME sanitize-and-rethrow pattern as D2: the raw detail is logged to stderr only, and the caller
only ever sees the single sanitized `SANITIZED_QUERY_FAILURE_MESSAGE`, with `{ cause: error }`
attached (identical rationale to D2 — never read by this codebase's own error handling). One new
`test/pg-history.contract.test.ts` case: a `ThrowingPoolCtor` whose constructor throws a
DSN-bearing message — asserts the caller-visible error never contains the DSN/host fragment while
stderr does.

## Q-2 + `/vdd-multi` cycle 4 (2026-07-25) — `NANSEN_DAILY_CREDIT_CAP` gets a default, and five defects

**Q-2 (commit `15b8dfa`) — the key now has THREE states**, not "optional / absent":

- **unset** → the gate DERIVES a ceiling: `deriveDailyCap(bucketStartBalance)` =
  `max(30, floor(balance × 0.25))`, resolved once per day-bucket and pinned into
  `NansenAccountSnapshot.dailyCapForBucket`. The guard is therefore ON out of the box.
- **positive integer** → an explicit operator ceiling. Applied DIRECTLY, never routed through the
  snapshot (`capInForce()`): a configured cap must not be able to disappear because a snapshot
  predates it — in a snapshot, `undefined` is indistinguishable from "off".
- **`off`** (the literal word) → no self-imposed ceiling; the vendor remainder alone bounds spend
  (the pre-Q-2 behaviour). `0` stays INVALID on purpose: it is one typo from silently disabling a
  money guard, and semantically ought to mean "spend nothing".

Either way `effectiveCeilingFor()` still takes `min(vendorCeiling, cap)`, so a cap can only ever
narrow, never widen. The ceiling in force is announced on stderr once per bucket.

**Cycle-4 defects found and fixed** (three parallel critics + an RTM completeness audit; every fix
carries a regression test that was verified to FAIL without it):

- **L-1 · `smart-money.flows` corrupted every Solana address.** The DF-1 fix applied
  `.toLowerCase()` to `filters.token_address` unconditionally, but it was live-verified on EVM only.
  Base58 is case-sensitive as an ENCODING (`chain/address.ts`'s `normalizeSolanaAddress()` returns
  its input unchanged for exactly that reason), so the fold corrupted the mint rather than re-casing
  it — recreating the DF-1 tarpit (empty `data: []` → post-payment throw → nothing cached → 10cr per
  retry) on the one advertised chain nobody probed. The fold is now EVM-only.
- **L-2 · the derived cap could lock the whole paid layer out for a UTC day.** It was derived from
  the live (post-spend) remainder but compared against `used`, a cumulative bucket counter — two
  reference frames. The per-bucket pin hid it _within_ a process; the pin is in memory only, so a
  mid-day MCP-server restart re-derived from a smaller balance and refused every paid call for the
  rest of the day. Now derived from the same `usageAtObserve + creditsRemainingAtObserve` anchor
  `effectiveCeilingFor()` already rebases onto, so every cold start, resync and concurrent session
  agrees on the number.
- **S-1 · `/account.credits_remaining` was accepted on `typeof` alone.** `1e999` is valid JSON and
  parses to `Infinity`; the value got PINNED, the ceiling became unbounded, and every reservation
  was approved for the rest of the bucket — unrepairable by a later healthy resync. Now requires a
  non-negative safe integer, matching the discipline `reconcile.ts` already applied to the far less
  consequential credits-used header.
- **L-5 · a `null` element in any vendor array destroyed an already-paid response.** Every row guard
  is shaped `typeof row.field !== 'string'`, which is itself a throw when `row` is `null`. Cycles
  1–3 closed this class for oversized strings, wrong types and fractional numbers; it stayed open
  one level up, at the element. `isRecord()` now guards each mapper, degrading to dropping the one
  bad row.
- **L-3 + L-4 · the success-path ledger write could nullify a paid call.** `await reconcile(...)`

## L-1 + Q-4 (2026-07-25) — negative caching, and the sub-call we were paying for blind

**L-1 — `CapabilityRegistry.resolve()` now negative-caches deterministic failures.**

The old shape wrapped fetch+normalize in one `try`, and cached only after `normalize()` returned. So
every normalize throw discarded an already-fetched — on Nansen, already-PAID — response: nothing
cached, adapter recorded as failed, the caller's retry paying full price to be rejected identically.
10cr per `smart-money.flows` attempt, 100cr for the exhaustive `entity.labels` tier, on a loop with
no exit. The mechanism cost 35 real credits to discover (DF-1).

The split is the whole idea:

- **`fetch()` throws → never cached.** Transport, 429, 5xx, budget refusal — all transient. Caching
  that verdict turns a blip into a self-inflicted outage for the negative TTL.
- **`normalize()` throws → cached 60s.** Deterministic: the same body is rejected the same way, so
  a replay can only spend money to reach the same conclusion.

The caller's experience is unchanged — still `CapabilityUnavailableError`, never a fabricated empty
result. **That was deliberate**: DF-1 proved an empty vendor response can also mean _our_ request is
malformed, so returning an empty canonical object would turn that class of bug into a
plausible-looking cached answer. Request-shape assertions (`TC-UNIT-07`, the Solana case) are where
that gets caught; a runtime heuristic cannot.

Mechanics worth knowing before touching this:

- `CacheStore.set()` gained an optional `ttlSecondsOverride` — **one** call site uses it. Without
  it a negative would inherit the capability TTL (3600s for `entity.labels`).
- Expiry is checked against the entry's own embedded `expiresAtMs`, NOT the store's `ageMs`: the
  two-level store promotes cold hits into its hot layer using `ttlFor(capability)`, which is the
  wrong number for a negative.
- Cached reasons are surfaced with a `[cached negative]` suffix, so a just-fixed request bug does
  not look unfixed for a minute.

**Q-4 — `token.risk` now reads the sub-call it always paid for.**

`/tgm/token-information` was fetched, charged (1cr of 6) and discarded. Two options were open —
drop it or consume it — and the recorded fixtures decided it at zero credits: `/tgm/indicators`'
own `token_info` carries **three** fields, `/tgm/token-information` carries **~20**. R-43's
"(метаданные)" was right; the implementation was wrong. `TokenRiskScore` gained `deploymentDate`
(token age — kept as the vendor's raw string, never parsed: no timezone in the format),
`liquidityUsd`, `totalHolders`, `fdvUsd`, `circulatingSupply`, `totalSupply`, `name`, `symbol`.
`logo`/`website`/socials deliberately excluded — no risk signal, needless injection surface.

The two sub-responses are not equal in weight: a malformed `indicators` body stays fatal (it is the
substance), a malformed `token-information` body degrades to fields-absent (it is enrichment, and
throwing would re-enter the L-1 class on an already-paid 6cr call).

Price is unchanged at 6cr. This did not make the capability cheaper — it made the 6cr honest.

## `/vdd-multi` cycle 5 (2026-07-26) — the widening's own defects: coverage that over-promised, and labels that lied

The review of TASK-006 found four High defects, all introduced by that task. Each is a variant of
one mistake: **widening the chain set touched what the engine ADVERTISES without touching what it
can DO.**

**H-1 — `chainSupport()` was widened to Nansen's real coverage; the transport was not.**
Task 006-9 read 17/25/25 chains out of the committed OpenAPI spec, but `endpoints.ts` still typed
`chain` as `'ethereum' | 'solana'` and `index.ts` still sent OUR slug. So `token.risk({chain:'bsc'})`
passed the coverage gate, reached `fetch()`, and threw — and `registry.ts` turned that into
`CapabilityUnavailableError`, the class that means "retry". A permanent condition wearing a
retryable error's clothes: the agent loops forever, and on a paid route each loop is another
budget-gate entry. (Money was never at risk — the throw precedes `ensureBudget()`.)

The transport was widened rather than the predicate narrowed, because narrowing would have thrown
away the task's deliverable. Three consequences worth remembering:

- `NansenChain` (a literal union) became `NansenChainRef = {token, family}`. `token` is the
  VENDOR's chain name from `vendors.nansen` (`bnb`, not `bsc`) and is the only thing that goes on
  the wire; `family` is ours and decides `token_address` casing.
- The DF-1 casing rule is now keyed on **family**, not chain name — it was never per-chain, it was
  per-encoding: hex is case-insensitive (fold it, as the vendor's column requires), base58/bech32
  are not (folding corrupts the address). The `never` guard moved to `ChainFamily`, so a new family
  is still a compile error.
- `resolveVendorChain()` is now the single statement of coverage that both `chainSupport()` and
  `fetch()` read. It throws `CapabilityNotCoveredOnChainError`, and `registry.ts` **rethrows that
  class instead of folding it into `CapabilityUnavailableError`** — the error class is the fix.

`test/nansen-transport-coverage.test.ts` holds the invariant the review asked for: every slug the
matrix advertises must be a slug `fetch()` can build a request for. It is derived from the matrix,
so it cannot go stale the way a hand-listed set would.

**M-7, fixed alongside it.** `NANSEN_EXHAUSTIVE_LABELS_CHAINS` had been generated, documented as
refusing "before the 100cr escalation", and read by nobody: `chainSupport()` cannot see
`args.exhaustive`. It is now enforced in `validateArgs()`, before `ensureBudget()`. A money guard

**H-3 + M-1 — the balance label. Fix the source before the consumer.**

ethereum-only; wrong for 18 chains after 006-8. But the obvious fix — "read `chain.nativeSymbol`" —

ETHEREUM's endpoints — another chain's balance, cached and schema-valid. `[]` is exactly what a
curator writes for "looked, found none". Now `.min(1)` at load, and the fallback is gone: the
comment next to it already claimed the branch was unreachable, which is how it survived review.

**H-2 — `.max(64)` does not short-circuit `superRefine` in zod 4.** `too_big` is raised with
`continue: true`, so the refinement ran on strings of any length and walked ~1300 Levenshtein
candidates. Measured: 64 chars → 9.8 ms, 20 000 → 416 ms, linear. The guard is now the first line
of the refinement, plus a bounded Levenshtein with an O(1) length-difference bail and precomputed
candidate keys. The project had already closed this exact class in `chain/address.ts`
(`MAX_DECODABLE_ADDRESS_LENGTH` before an O(n²) base58 decode) and did not carry the lesson across.

**H-4 — the shipped registry is built once.** `loadChainRegistry()` memoizes the no-deps path; an
injected `data` is still built fresh every call. Not the mutable singleton §8 forbids — a memoized
pure function of a build constant. The handler half matters more than the cost: canonicalizing
against the shipped snapshot while the gate resolves against `ctx.registry` is two dictionaries for
one request.

**Smaller ones, same theme.** `isCovered()` now excludes deprecated chains (M-5 — the gate said
covered while every list said otherwise); `dune.chainSupport` returns false (L-10 — coverage does
not consult `isAvailable()`, so a permanently-unavailable adapter was advertising `token.holders`);
CoinGecko encodes its path segments (M-4 — `bitcoin` has no address validator, so
`'../../../simple/price?ids=x'` rewrote the request path with our API key attached); vendor-authored
symbols/names are truncated in `normalize()` with schema `.max()` as backstops (M-6 — truncate,
never reject, per the cycle-2 lesson: a parse throw discards a response already paid for);
`chain.tvl` shares one `/v2/chains` download across chains (L-9 — the engine cache is keyed per
chain and cannot deduplicate it).

## `/vdd-multi` cycle 6 (2026-07-27) — reviewing the fixes, and the trigger the task pulled without noticing

The second pass was aimed at cycle 5's own fixes — the freshest, least-reviewed code in the branch.
Two of the three top findings were about that code, one of them a straight regression. Read that as
a fact about review economics, not about cycle 5: **a fix is code, and code that has been reviewed
once has been reviewed once.**

**C-1 (Critical) — the widening opened PAID routes onto families we cannot validate addresses for.**
Seven Nansen-covered chains (`tron`, `ton`, `near`, `sui`, `starknet`, `sei`, `bitcoin`) are
`family: 'other'`, where `isValidAddress` accepts any 1–128-character string and `normalizeAddress`
returns its input verbatim. Three consequences at once, all costing money:

- a garbage `tokenAddress` passed the schema, passed the coverage gate and reserved credits — and
  every distinct garbage string is a distinct `deriveArgsHash`, so neither cache bounded the spend;
- two case variants of one REAL address were two cache entries, i.e. two charges;
- the DF-1 casing rule is unknown for those chains, so a legitimate call could return an empty body
  after payment, throw in `normalize`, and be paid for again on retry.

`chain/address.ts` had already written the rule down: a family without a validator is fine "until a
PAID provider appears on such a family, because only then does the split start costing money
(OQ-1)". TASK-006 pulled that trigger and nobody revisited OQ-1. The condition was stated correctly
and never checked — which is a more useful lesson than the bug.

Now `hasAddressValidator(family)` states the policy once, and `nansenServesChain()` requires it.
That predicate is read by `chainSupport`, by the transport, and by the error's "available on" list —
one statement, three readers, which is the shape cycle 5's H-1 was missing. **Stated cost:**
`entity.labels` 25→18, `token.risk` 24→18, `smart-money.flows` 17→16. `sei` is the strongest
candidate to come back (EVM-addressed in practice, filed under `other` only because no EIP-155
chain id joined) — but re-classifying it needs evidence, so it waits.

**H-1 — the twin nobody looked at.** Cycle 5 hardened `rpc-evm` (per-chain hosts, registry-derived
symbol/decimals) and left `rpc-solana` untouched: it advertised coverage for ANY svm chain with a
curated host while sending every request to `api.mainnet-beta.solana.com` and labelling the result
`SOL`/9. Latent today (solana is the only such row) and guaranteed the day a second SVM chain is
curated — which this branch exists to make a data edit. Its docstring even claimed it was "correct
by construction if another ever appears". **When a fix is about a class of defect, grep for the
class.**

`solana`'s row gained a curated `nativeDecimals: 9` — not a new claim, just the literal that had
been sitting in the adapter since M1, moved into data where the registry can own it.

**H-2 — a regression cycle 5 introduced.** Widening the transport to send Nansen's own chain token
left `mapSearchGeneral` still comparing the vendor's echoed `chain` against OUR slug. Identical for
`ethereum`/`solana`; different for every chain where the vocabularies diverge — so on ~20 chains
EVERY token row was dropped from a response already paid for. Non-empty, schema-valid, plausible,
missing half its data: the exact class this file's own comments say cost 20 live credits to
diagnose. `EntityLabelsFetchResult` now carries `vendorChain`, and the filter compares against it.

**The rest, by theme.**

- _A predicate and its transport must be one statement._ Both `rpc-solana` and `nansen` gained the
  `servesChain`-shaped single predicate `rpc-evm` already had.
- _An error must not assert what it did not compute._ `CapabilityNotCoveredOnChainError`'s
  `availableCapabilities` is now optional: `undefined` renders nothing, where a caller-supplied `[]`
  used to render "No capability is available on 'ton'" — false, and enough to talk an agent out of
  a call that would have worked.
- _Derived data from immutable inputs belongs to the process, not the request._ `coverage.ts` builds
  its route index once and memoizes both directions; the refusal path takes a bounded
  `servedSlugs(cap, limit)` instead of materialising ~450 slugs to render ten; `list()` matches
  against a precomputed per-row key.
- _The SSRF column is now validated, not merely non-empty._ `https:` only, no userinfo, no IP
  literal — a malformed entry is a load failure, the same class as a duplicate `caip2`. `hostOf`
  throws instead of returning the raw string, so the perimeter has no fail-open path left.
- _The generator reserves the previous snapshot's names BEFORE assigning slugs_ (cycle 5 reserved
  them after the main loop, which protected pass 2 only), and writes its report BEFORE the
  validation gate — a rejected run used to discard the one artifact that explains why.
- _Codegen validates vendor tokens instead of escaping them._ A chain token outside `[a-z0-9._-]`
  is a vendor-drift signal worth a human's attention, not something to quietly encode.

## SEC-1 (2026-07-27) — the daily cap was a damage ceiling; now there is also a brake

The budget guard was denominated in credits per UTC day and nothing bounded the RATE. The
per-provider throttle sustains ~5 paid calls/second ≈ 50 credits/second, so a 2500-credit daily cap
was consumable in under a minute. That was never an over-spend — the ceiling held, the reservation
stayed atomic, the vendor remainder still bound — but a day's entire authorized budget could be
gone before any human noticed, which for an operator is indistinguishable from a leak.

**`usage_window(provider, window_start, credits_used, updated_at)`** — the same additive counter as
`usage`, bucketed by 60 s. A separate table, not a `bucket_width` column: the day counter must keep
summing a day, and two widths in one column would make every existing SELECT ambiguous and force a
migration. Plain `CREATE TABLE IF NOT EXISTS`, same `providers` FK, nothing migrates.

Three things about it are load-bearing, and each was a constraint the issue set out:

- **It is checked and reserved inside the SAME transaction as the daily reservation.** Two
  processes sharing one `cache.sqlite3` would otherwise each pass their own window check against a
  stale read and both spend. `checkAndReserve` takes an optional `velocity: {windowStartMs,
ceiling}` — `BudgetStore` still only ever compares plain numbers and knows nothing about windows,
  minutes or credits, exactly as it knows nothing about `usageAtObserve`.
- **The state is in the ledger, not in memory.** An in-memory limiter is defeated by the same
  process restart that defeated Q-2's L-2.
- **The refusal names the velocity limit.** A rate refusal and a daily refusal call for opposite
  operator responses — wait out the window versus raise a ceiling — so an operator who cannot tell
  them apart fixes the wrong one. The message also states that the daily budget is NOT exhausted.

**The number:** `max(100, ceilingInForce / 20)` per 60 s. Derived rather than absolute for the same
reason `deriveDailyCap` is (owner decision #1: free and Pro, zero code change). The divisor 20 buys
~20 minutes before a day's budget is gone. The floor of 100 is the dearest single call
(`entity.labels` exhaustive) — a limit under one call's cost makes that capability impossible
rather than rate-limited, a worse failure than the one being prevented. Where the floor exceeds
what the daily cap allows, the daily cap binds first; the guards compose and the tighter wins.

**Two properties worth not re-deriving later:**

- The window is **tumbling, not sliding** — up to 2× the allowance across a boundary. Stated in the
  code, the issue and both READMEs rather than implied. A sliding window needs per-call history
  instead of one counter, and 2× does not undermine "buy a human time to notice". If it ever does,
  add a second, wider window; do not rewrite this one.
- **A refund goes back into the window the RESERVATION used**, threaded through `ensureBudget →
reconcile` exactly as `bucket` already was. Refunding into whatever window is current when a
  long call returns would credit a window that never spent — the one way a rate brake can hand a
  runaway loop extra headroom.

**Still open, and deliberately:** Q-3 — a 0-credit tier is unrefusable by ANY credit-denominated
limiter, this one included. Bounding it needs a call-denominated limit, which is a different
mechanism and a separate decision.

## Q-3 + RF-2 (2026-07-27) — a second denominator, and a provenance chain that cannot skip an edit

Two ledger entries closed together because each needed a MECHANISM rather than a patch, and each
had already stated in its own file what that mechanism had to be.

**Q-3 — the credit gate could never refuse a call that costs zero credits.** `entity.labels`' query
tier is priced `{free: 0, pro: 0}`, so `used + 0 > ceiling` is false for the entire life of any
bucket, under any cap, including a deliberately low one. Three review rounds hardened a guard that
structurally could not see this path. The calls are still two real HTTPS round trips against the
operator's account, each carrying up to 200 characters of free text — so every one is a fresh
`args_hash`, a guaranteed cache miss and a new row with an attacker-selectable key.

The fix is a different UNIT, not a tighter number: `usage_window` gained `calls_made` alongside
`credits_used`. Same row, same window, same transaction — a second table would mean a second read
and a second chance for the two to disagree.

Three things worth not re-deriving:

- **The default is FIXED (60/min) while the credit limits are derived.** That asymmetry is the one
  judgement call here. Credits are derived because `free` and `Pro` balances differ by orders of
  magnitude and owner decision #1 requires both to work unchanged. A call is a call on either plan —
  neither vendor rate limits nor cache-row pressure scales with the balance, so there is nothing to
  derive FROM.
- **A call is never refunded.** `recordDelta` passes `calls: 0`. The vendor round trip happened;
  letting reconciliation refund it would let cheap-then-refunded calls walk past the limit that
  exists to bound exactly that traffic.
- **Only two of the issue's three consequences are closed.** Vendor exposure and cache-row growth,
  yes (at 60/min against a 3600s TTL, rows settle at ~3600). _Price drift detectable in advance_ is
  NOT closed and cannot be by any pre-call gate — it stays `reconcile()`'s job. Said in the issue
  rather than quietly counted as fixed.

The column arrived after the table shipped, so `CREATE TABLE IF NOT EXISTS` does not add it:
`SqliteBudgetStore` checks `PRAGMA table_info` and issues `ALTER TABLE … ADD COLUMN`
(`USAGE_WINDOW_COLUMNS`). Idempotent per open, additive, no backfill — the "mechanical, not a
project" migration shape DB-SCHEMA-CONCEPT §1 requires, and the first time this repo has needed it.

**RF-2 — the golden-test SHA chain had a window in which it could not detect a silent edit.** The
mechanism failed structurally, not carelessly: it required a human to re-run `shasum` and paste the
result, and there is no way to test that a human remembered. Any fix ending in "remember to update
the hash" reproduces the break.

`docs/provenance.json` pins `path → sha256` for the golden test and all nine live-recorded Nansen
fixtures. `scripts/verify-provenance.mjs` recomputes and compares from three sources, and the
choice between them is the whole point:

- `worktree` — run by `packages/core/test/provenance.test.ts` on every `pnpm test`, so drift is
  caught seconds after the edit;
- `index` — run by `.githooks/pre-commit`, i.e. against what is actually being COMMITTED. The
  working tree and the index can differ, and that difference is exactly how the original break
  happened;
- `head` — after-the-fact audit.

**`--update` is in no gate, deliberately.** A check that silently re-recorded the hash it just found
wrong would be worse than no check — every silent edit would become a green build. Re-baselining
puts the edit and the new hash in the SAME diff, which is the property the hand-copied hash was
supposed to have.

**Stated bound on the guarantee:** git hooks are local. `--no-verify`, or a clone that never ran
`git config core.hooksPath .githooks`, bypasses the commit-time half. What survives is the test —
a bypassed commit lands red on the next run anyone does — and the manifest's absence from a diff
that touches a pinned file, which a reviewer can see. The mechanism makes a skipped update LOUD; it
does not make it impossible, and no local-only mechanism can. Files are listed explicitly rather
than globbed, so adding a live-recorded artefact to the pinned set is also a visible decision.

## TASK-007 (2026-07-27) — the free DEX-volume tier, and the size cap that was not one

Third capability on the keyless `defillama` adapter: `dex.volume.history`, from
`GET /overview/dexs/{chain}`. Three of this task's decisions came from a live probe run before the
design, not from the research write-up — each one changed the design.

### `src/adapters/defillama/dex-chains.ts` (GENERATED) + `scripts/gen-defillama-dex-chains.ts`

**`vendors.defillama` is the wrong predicate for this capability, and the gap is 184 chains.** That
registry column was populated from the vendor's TVL catalog (`/v2/chains`) and is non-null for all
458 rows. The vendor's DEX-volume dataset covers 287 chains (`allChains` in a live response), of
which 274 are ours. Reusing the TVL predicate would advertise the capability on 184 chains that have
no such data — TASK-006's H-1 defect class verbatim (coverage widened, transport not).

So `chainSupport(chain, capability)` branches: TVL capabilities keep `vendors.defillama != null`,
`dex.volume.history` requires membership in the generated list. `coversDexVolume()` is the ONE
predicate both the gate and the adapter's own argument validation call — an adapter that answers the
same question in two places eventually answers it two different ways.

The list is a build artifact for the three reasons the chain registry is one (offline gate, CI
determinism, reviewability), generated from committed raw evidence under
`docs/onchain-analytics/raw/`. The generator **refuses** rather than escapes a vendor name outside
`/^[A-Za-z0-9][A-Za-z0-9 ._-]*$/` (space is allowed — `OP Mainnet` is real; quote/backslash/newline
are not, because the value is interpolated into a committed `src/` module), refuses a list under 50
entries, and prints the 13 vendor chains our registry cannot map rather than hiding them.

### `src/adapters/defillama/index.ts` — `fetch`/`normalize` for `dex.volume.history`

- **URL.** `excludeTotalDataChartBreakdown=true` always (the breakdown is the 11.2× difference —
  18 MB vs 1.6 MB globally — and nothing reads it); `excludeTotalDataChart=true` additionally when
  `includeSeries: false`. No headers of any kind: the endpoint is keyless and must stay provably so.
- **Document cache per adapter INSTANCE** (never a module singleton). The vendor has no windowing
  parameter, so 30/90/365 days of one chain is one document — but `days` is part of `argsHash`, so
  the engine's own cache sees three unrelated keys and would download the same 250 KB three times.
  Keyed by `(vendorName, includeSeries)` because `includeSeries` changes the REQUEST; stores the
  PROMISE so concurrent callers share one flight; evicts on rejection so a blip is not remembered
  for an hour. `fetchedAt` is the DOCUMENT's timestamp — two TTL windows in series do not compose
  into one (vdd-multi cycle 6, M-1).
- **`normalize()` verifies the response's `chain` echo first.** Forced by measured behaviour: the
  path is name-tolerant (`op-mainnet`/`optimism`/`OP Mainnet` → one document), an unknown chain
  answers **HTTP 500** (not 404), and a chain outside the active set answers **HTTP 200 with zeros
  and a narrower key set**. Without the check, "served a different chain" and "this chain has no
  volume" are the same observation — and the wrong document gets cached under our slug.
- **Units and refusals.** Vendor `date` is unix SECONDS → `ts = date*1000`, epoch-ms UTC
  (DB-SCHEMA §1.2). An implausible timestamp drops its point (a decoding question about one point);
  a non-finite or negative volume throws BEFORE the cache write (the document is not what we think
  it is). Aggregates are `number | null` — never `0` for a key the vendor omitted, which would be a
  fabricated measurement.
- **`gapDays` counts, it never stitches.** An interpolated point is a number nobody measured, and
  dropping the count makes an incomplete answer look complete.
- **The truncation flag is a granularity-drift guard, and the obvious version of it is dead code.**
  The window is `args.days` long and `days` is bounded, so a separate "max points" constant could
  never fire — a daily series in an N-day window has at most N points by construction. What CAN
  exceed it is the vendor switching to sub-daily points or emitting duplicates under an unchanged
  endpoint; that is what the cap catches, and `truncated` therefore keeps meaning "you did not get
  what you asked for" instead of being set by ordinary windowing.
- **No vendor free text reaches the result.** The document carries 151 protocol cards with
  `name`/`category`/`methodology`/`logo` — third-party-editable strings. None is read; `chain`/`name`
  come from our registry and `source` is a literal. A test asserts a planted injection string cannot
  appear in the serialized output.

### `src/net/safe-fetch.ts` — the response-size cap became real (closes R-47 item 1)

The cap read the advertised `Content-Length` and returned early when the header was absent. That is
the common case, not the exotic one: **`api.llama.fi` sends no `Content-Length` on any response**
(HTTP/2 + Cloudflare, measured 2026-07-27), so the cap was inert on a host this package already
called on two capabilities and was about to call on a third. `capResponseStream()` now counts bytes
off `response.body` when no header is present and **cancels the upstream reader** on overflow —
stopping the transfer, not merely declining to look at it. Status/statusText/headers are carried
over verbatim so every existing caller behaves identically, and a response that DOES advertise a
length still takes the cheaper header path untouched.

The error surfaces where the body is READ, inside the calling adapter's `fetch()`. That placement is
correct rather than incidental: `CapabilityRegistry` treats a `fetch()` throw as "try the next
adapter" and deliberately does NOT negative-cache it — an oversized response is a transport
condition, not the deterministic `normalize()` verdict negative caching exists for.

### `src/providers.config.ts` — `defillama` rate limit raised to `{capacity: 10, refillPerSec: 5}`

The old `{5, 1}` was OUR brake, not the vendor's: the vendor publishes no numeric limit, and a live
cache-busted probe took 40 concurrent origin requests with 40/40 HTTP 200 and zero 429s. At 1
token/s a ten-chain sweep spent ~5 s asleep in our own limiter and a wider one crossed
`MAX_WAIT_MS = 30_000` and began throwing. One bucket serves all three defillama capabilities, so
raising it can only speed the two existing paths up.
