# Задача 015.03: Postgres-миграция T-015 — `client_usage`, `usage.calls_made`, гранты и дом леджера

## Связь со сценариями

- UC-1 — списание на границе тула независимо от исхода кеша (авторитетны строки Postgres, R-7.3)
- UC-6 шаг 2 — миграция применяется к новому контейнеру и создаёт тринадцатую таблицу пустой

<!-- contract:goal -->

## Цель задачи

Объявить на оси Postgres таблицу `onchain.client_usage`, колонку `onchain.usage.calls_made` и гранты
роли состояния так, чтобы форма леджера совпадала с формой оси SQLite, а дом леджера был назван до
первого запуска сетевого профиля.

**Why миграция идёт до интерфейса.** Ось хранилища выбирает реализацию репозитория. Интерфейс,
написанный до формы таблицы, переписывается на втором движке — прецедент T-014, задача 014-02.

**Why дом леджера решается здесь.** Ревью архитектуры раунда 2 (MAJOR-F) нашло две одинаково законные
трактовки того, где `client_usage` живёт между выкаткой T-015 и переездом. Обе исполнимы, и обе
несовместимы: одна отказывает каждому запросу сетевого профиля, вторая кладёт строки леджера под
удаление задачи 015-27.

### Форма `onchain.client_usage`

Тринадцать колонок по `data-model.md` §4.6.1, тип по карте `DB-SCHEMA-CONCEPT` §5: `TEXT` → `TEXT`,
`INTEGER` → `BIGINT`.

| Колонка             | Тип    | Пусто | Смысл                                                    |
| :------------------ | :----- | :---- | :------------------------------------------------------- |
| `id`                | TEXT   | нет   | ULID; объявлен `TEXT PRIMARY KEY NOT NULL` (§4.5.2a)     |
| `principal_id`      | TEXT   | нет   | `api_tokens.id` либо `local` — метка, не внешний ключ    |
| `access_profile_id` | TEXT   | да    | у локального принципала профиля доступа нет (R-7.5)      |
| `client_request_id` | TEXT   | нет   | значение клиента либо серверный `traceId`                |
| `tool`              | TEXT   | нет   | имя тула, известно в точке резерва всегда                |
| `capability`        | TEXT   | да    | СТАТИЧЕСКАЯ декларация тула, не разрешённое значение     |
| `price_raw`         | TEXT   | нет   | применённая цена, скопированная в момент резерва (R-4.5) |
| `state`             | TEXT   | нет   | `reserved`, `settled` либо `refunded`                    |
| `refund_reason`     | TEXT   | да    | имя класса либо `expired`; только при `state='refunded'` |
| `reserved_at`       | BIGINT | нет   | epoch-ms UTC, пишется один раз                           |
| `terminal_at`       | BIGINT | да    | epoch-ms UTC выхода из `reserved` — якорь ретенции       |
| `created_at`        | BIGINT | нет   | epoch-ms UTC                                             |
| `updated_at`        | BIGINT | нет   | epoch-ms UTC                                             |

Ключ дедупликации: `UNIQUE (principal_id, client_request_id)`.

Ограничения:

- `CHECK (state IN ('reserved','settled','refunded'))`
- `CHECK ((state = 'refunded') = (refund_reason IS NOT NULL))`
- `CHECK ((state = 'reserved') = (terminal_at IS NULL))`

Индексы:

- `idx_client_usage_principal (principal_id, reserved_at)` — периодный запрос по принципалу
- `idx_client_usage_terminal (terminal_at)` — ретенция и агрегат `sumSettled`
- `idx_client_usage_reserved (state, reserved_at)` — скан фоновой сверки

**Why в ключе дедупликации нет времени приёма** (AC-12, R-5.1). Ключ `request_trace` —
`(principal_id, client_request_id, received_at)` (`sql/migrations/002_t014_network_profile.sql:200`),
и время в нём стоит намеренно: ретрай пишет вторую строку следа. Ключ той же формы в леджере дал бы
второе списание на тот же ретрай.

**Why `price_raw` — `TEXT`, а не число** (AC-3, R-4.5). `DB-SCHEMA-CONCEPT` §1 называет кредиты
случаем, требующим строки. Та же форма уже у `access_profiles.credits_balance_raw`
(`packages/core/src/cache/ddl.ts:155`), поэтому резерв сравнивает два целых в строковой записи.

**Why `principal_id` не несёт `REFERENCES`.** У принципала локального профиля строки токена нет.
Внешний ключ отверг бы запись на транспорте, которому токен не нужен — то же решение, что уже принято
для `request_trace.principal_id`.

**Why `id` несёт `NOT NULL` рядом с `PRIMARY KEY`.** SQLite допускает `NULL` в такой колонке,
Postgres — нет (`data-model.md` §4.5.2a). Без этого слова две оси объявляют разное ограничение.

### Аддитивная колонка `onchain.usage.calls_made`

```
ALTER TABLE onchain.usage ADD COLUMN IF NOT EXISTS calls_made BIGINT NOT NULL DEFAULT 0;
```

Ограничение `CHECK (calls_made >= 0)` добавляется именованным табличным ограничением под охраной
запроса к `pg_constraint`: в Postgres 16 нет формы `ADD CONSTRAINT IF NOT EXISTS`, а файл обязан
переживать повторное применение.

**Why `DEFAULT 0` без бэкфилла.** Строка `usage`, предшествующая колонке, по построению не несёт
учтённых вызовов. Тот же приём уже применён к `usage_window.calls_made`
(`packages/core/src/cache/ddl.ts:344-349`).

**Why колонка, а не таблица.** Тот же провайдер, то же суточное окно, та же транзакция и одно чтение
строки вместо двух (`data-model.md` §4.6.3).

### Гранты роли состояния

```
GRANT SELECT, INSERT, UPDATE, DELETE ON onchain.client_usage TO :"STATE_ROLE";
```

Три запрещённые формы остаются запрещёнными: `GRANT … ON ALL TABLES`, `ALTER DEFAULT PRIVILEGES`,
`GRANT CREATE ON SCHEMA` роли состояния (`deployment.md` §10.5.1, §10.9.3).

**Why грант перечисляет таблицу поимённо.** `ALL TABLES IN SCHEMA onchain` покрыл бы три таблицы
снапшоттера, и эта граница — причина, по которой гранты вообще перечисляются
(`sql/migrations/002_t014_network_profile.sql:284-292`).

Роль читателя (`READ_ROLE`) в этом файле не участвует: новый контейнер не держит таблиц снапшоттера,
поэтому роли чтения там нет вовсе (`deployment.md` §10.9.2).

### CHECK формата на `credits_balance_raw` — MINOR-7 раунда 2

```
ALTER TABLE onchain.access_profiles ADD CONSTRAINT client_usage_balance_is_integer
  CHECK (credits_balance_raw IS NULL OR credits_balance_raw ~ '^-?[0-9]+$');
```

Ограничение добавляется под той же охраной `pg_constraint`, что и `CHECK (calls_made >= 0)`.

**Why ограничение нужно.** Проверка баланса — `credits_balance_raw::numeric >= $2::numeric`
(`data-model.md` §4.6.1). Значение `'NaN'` делает это условие истинным при любой цене, а результат
вычитания снова `'NaN'`: обслуживание идёт без единого отказа и без списания.

**Why ограничение объявлено только на оси Postgres.** Предикат несёт оператор `~`, которого в SQLite
нет. На оси SQLite арифметика идёт в `BigInt` (`data-model.md` §4.6.1), а `BigInt('NaN')` бросает,
поэтому отказ там уже существует по построению. Асимметрия записана тестом, а не оставлена молчаливой.

## Примечания

Ось SQLite — задача 015-02 (`packages/core/src/cache/ddl.ts`). В `packages/*/src` эта задача меняет
один файл — `packages/core/src/pg/state-client.ts`: перечень `STATE_TABLES` и его докстринг.

**Счётчик в докстринге правится тем же проходом, что имя.** Строка `:78` называет двенадцать таблиц
в двух строках над перечнем из тринадцати имён. Это тот же класс, что MINOR-6 раунда 2, — ложное
утверждение вплотную к правке. Соседний счётчик того же перечня — сообщение
