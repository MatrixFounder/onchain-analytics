# Задача 015.11: тотальность правила списания — перечень классов отказа, класс вне перечня, дедлайн и коалесценция

## Связь со сценариями

- UC-1 — списание на границе тула независимо от исхода кеша (A2, A3, A4)

<!-- contract:goal -->

## Цель задачи

Замкнуть правило списания над каждым исходом так, чтобы резерв получал терминальное состояние при
любом классе отказа, включая класс, которого сегодня не существует.

**Why тотальность проверяется отдельной задачей.** R-3 объявляет функцию тотальной над исходом и
над классом отказа. Тотальность — свойство перечня, а не одного вызова: её нельзя увидеть в тесте
на один класс.

**Why правило не ветвится на значение класса.** Ветвь по значению даёт классу, добавленному
завтра, проход мимо правила. Отсутствие ветви — то, что делает AC-35 следствием конструкции, а не
отдельного случая (`docs/architectures/system-architecture.md:4364` — подстрока `The rule does not
branch on`).

## Описание изменений

### Новые файлы

- `packages/mcp-server/test/billing-outcome-total.test.ts` — тесты этой задачи

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/tools/registry.ts`:**

- Причина возврата для `refund` берётся из `outcome.refusalClass`; при пустом значении
  подставляется объявленное умолчание, а не пустое
- Правило завершения читает только `outcome.ok`; сравнения с именем класса в нём нет

**Why умолчание причины обязательно.** Отказ может прийти без класса: сегодня строка следа
допускает пустое значение — `packages/mcp-server/src/tools/registry.ts:646` —
`refusalClass: outcome.ok ? null : (outcome.refusalClass ?? null),`. Леджер такого не допускает:
`docs/architectures/data-model.md:1765` — `CHECK ((state = 'refunded') = (refund_reason IS NOT
NULL)),`. Возврат с пустой причиной отверг бы сам движок.

**Why правило живёт в обёртке, а не в хранилище.** Хранилище исполняет условный `UPDATE` и о
классах отказа не знает. Транзакционную границу вызова владеет задача 015-10; здесь объявляется то,
какой исход какой вызов выбирает.

### Правило целиком

| Исход                                               | Вызов                 | Основание    |
| :-------------------------------------------------- | :-------------------- | :----------- |
| `outcome.ok === true`, `outcome='answer'`           | `settle` полной ценой | R-3.1        |
| `outcome.ok === true`, `outcome='partial_deadline'` | `settle` полной ценой | R-3.2        |
| `outcome.ok === false`, любой класс                 | `refund`              | R-3.3, R-3.4 |

Правило читает одно поле. Значение `refusalClass` попадает в причину возврата и в решение не
входит (`docs/architectures/system-architecture.md:4361` — подстрока `The mapping is R-3, restated
as one rule with one exception`).

### Перечень классов R-3.3 — данные теста, не ветви кода

Шесть классов названы спецификацией:

| Класс                             | Что даёт правило                  |
| :-------------------------------- | :-------------------------------- |
| `CapabilityUnavailableError`      | `refunded`                        |
| невалидный по контракту результат | `refunded`                        |
| `CapabilityDeadlineExceededError` | `refunded`                        |
| насыщение токен-бакета лимитера   | `refunded`                        |
| отказ гейта вызовов (R-11.4)      | `refunded`                        |
| `ClientCreditsExhaustedError`     | строки нет — резерв не создавался |

**Why шестая строка отличается от пяти остальных.** Исчерпание баланса обнаруживается внутри
`reserve()`, до появления строки, которую можно было бы вернуть
(`docs/architectures/system-architecture.md:4397` — подстрока `writes no row, even though
R-3.3`). Перечень R-3.3 читается как перечень ПРИЧИН отказа, не убегающих от правила `refunded`,
а не как утверждение, что каждая причина пишет строку и отменяет её.

**Why класс истёкшего ключа реплея в перечень не входит.** Резерва для него не существует: поиск
по `client_request_id` предшествует решению о резерве (R-3.5, R-5.7). Владелец окна — задача
015-08.

### Класс вне перечня (R-3.4, AC-35)

Синтетический класс, не входящий в перечень, проходит тот же путь и даёт три наблюдаемых следствия:

| Следствие                              | Где читается                                    |
| :------------------------------------- | :---------------------------------------------- |
| строка `client_usage` — `refunded`     | леджер                                          |
| `request_trace.refusal_class` заполнен | `packages/mcp-server/src/tools/registry.ts:646` |
| событие `tool.refused` выпущено        | `packages/mcp-server/src/tools/registry.ts:704` |

Координата события — `packages/mcp-server/src/tools/registry.ts:704` — `(await
ctx.diagnostics?.emit('tool.refused', {`.

Нового канала наблюдаемости задача не заводит: оба уже несут любой отказ тула (R-3.4).

### Полный ответ за потолком (R-3.2, AC-6)

`outcome='partial_deadline'` вычисляется из превышения потолка на успешном исходе:
`packages/mcp-server/src/tools/request-trace-row.ts:122` — `export function outcomeClassOf(ok:
boolean, overrunMs: number | undefined): RequestTraceOutcome {`, и значение объявлено третьим в
словаре — `packages/mcp-server/src/engine/request-trace-store.ts:38` —
`export const REQUEST_TRACE_OUTCOMES = ['answer', 'refusal', 'partial_deadline'] as const;`.

Списание идёт полной ценой: `outcome.ok` истинно, и правило второй ветви не имеет.

**Why это не «ответ с недостающими источниками».** Вторая половина `ADR-002` D4 п.5 отклонена
решением OD-4 (R-3.2). Класс означает полный ответ, отданный за объявленным потолком.

### Коалесцированный последователь (AC-7)

Списание идёт по ЗАПРОСУ, на обёртке тула — слоем выше свёртки одинаковых вендорских вызовов
внутри `resolve()` (`packages/core/src/adapters/nansen/singleflight.ts:40` — `const inFlight = new
Map<string, { promise: Promise<unknown>; shared?: S }>();`).

Ведущий и ведомый доходят до обёртки отдельными вызовами, каждый резервирует свою строку, оба
получают успешный исход. Один вендорский вызов даёт два списания.

Признак ведомого уже записывается следом запроса:
`packages/mcp-server/src/tools/request-trace-row.ts:111` —
`if (receipts.some((r) => r.kind === 'coalesced')) return 'coalesced';`.

**Why отдельной ветви для ведомого нет.** Свёртка невидима выше `resolve()` по построению. Ветвь
здесь описывала бы состояние, которого обёртка не наблюдает.

## Тест-кейсы

### Модульные тесты

1. **TC-UNIT-01 (AC-5):** каждый названный класс отказа переводит резерв в `refunded`
   - Входные данные: таблица из пяти классов R-3.3, пишущих строку, по одному прогону на класс
   - Ожидаемый результат: пять строк `state='refunded'`, `refund_reason` равен имени класса;
     падает при добавлении ветви по значению класса — красной становится одна строка таблицы
2. **TC-UNIT-02 (AC-5):** `ClientCreditsExhaustedError` строки не оставляет
   - Входные данные: отказ по балансу под `credits_mode='metered'`
   - Ожидаемый результат: в `client_usage` строки нет; ни `settle`, ни `refund` не вызваны
3. **TC-UNIT-03 (AC-6):** полный ответ за потолком списывается полной ценой
   - Входные данные: успешный исход с `overrunMs > 0`
   - Ожидаемый результат: `state='settled'`, списанная величина равна `price_raw` резерва;
     `request_trace.outcome='partial_deadline'`
4. **TC-UNIT-04 (AC-7):** один вендорский вызов даёт два списания
   - Входные данные: два запроса на одну способность с одинаковыми аргументами, свёрнутые
     singleflight в один вендорский вызов
   - Ожидаемый результат: две строки `settled`, каждая полной ценой; строка ведомого несёт
     `served_from='coalesced'`
5. **TC-UNIT-05 (AC-35):** синтетический неизвестный класс даёт `refunded`
   - Входные данные: отказ с именем класса, отсутствующим в перечне R-3.3
   - Ожидаемый результат: `state='refunded'`; `request_trace.refusal_class` равен этому имени;
     событие `tool.refused` выпущено
6. **TC-UNIT-06:** правило не ветвится на значение класса
   - Входные данные: два отказа с разными именами классов на одном туле
   - Ожидаемый результат: оба дают `refunded` одним и тем же путём; падает при внесении сравнения
     с именем класса в выражение выбора вызова
7. **TC-UNIT-07:** отказ без класса получает объявленное умолчание причины
   - Входные данные: отказ с пустым `refusalClass`
   - Ожидаемый результат: `state='refunded'`, `refund_reason` непуст; ограничение
     `CHECK ((state = 'refunded') = (refund_reason IS NOT NULL))` не нарушается
8. **TC-UNIT-08:** успешный исход без превышения потолка списывается тем же способом
   - Входные данные: успешный исход с пустым `overrunMs`
   - Ожидаемый результат: `state='settled'`; `request_trace.outcome='answer'`; величина та же, что
     в TC-UNIT-03

## Примечания

Этап: **Этап 3. Точка перехвата и терминальность резерва**. Проход: **impl**. Зависимость: 015-10
(транзакционная граница `settle`/`refund` и поздний исход).

Задача 015-09 создаёт резерв и рождает синтетический исход на отказе резерва; задача 015-10 владеет
переходом в терминальное состояние. Здесь проверяется, что переход накрывает КАЖДЫЙ исход.

`ClientCreditsExhaustedError` в фазе 0 не наблюдается на продуктивном трафике: единственный сеяный
профиль несёт `credits_mode='unlimited'` (R-6.2). Покрытие даёт тест.

Требования: R-3.1, R-3.2, R-3.3, R-3.4.
