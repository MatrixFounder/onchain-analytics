# Задача 014.35: Postgres-миграция — двенадцать таблиц, индексы, гранты, verify-гейт `[LOGIC]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети
- UC-2 — две сессии делят вендорскую квоту

## Цель задачи

Создать одну нумерованную миграцию Postgres: двенадцать таблиц движка в схеме `onchain`, их индексы,
непересекающиеся гранты двум ролям и verify-гейт с записью прогона.

**Why задача заведена отдельно.** `data-model.md` §4.4 называет пять обязательств T-014. Редакция 1
плана называла первое частично — восемь таблиц §4.5, — а четыре счётчика §4.2.4, гранты, verify-гейт
и seed админа исполнителя не получали. Задача 014-02 миграций не объявляет: она заводит интерфейсы
репозиториев и стабы.

### Состав миграции

Схемы файл не создаёт: `sql/migrations/001_init.sql:18` (`CREATE SCHEMA IF NOT EXISTS onchain;`) уже
создал её, и dev VM держит её сегодня. Оператор `CREATE SCHEMA` здесь ничего не добавил бы (§4.4).

Колонки, ключи и ограничения `CHECK` берутся из §4.5.3–§4.5.9 и §4.2 без изменений. Карта типов для

**Why счётчики попадают в тот же файл.** OQ-8 помещает данные времени выполнения сетевого профиля
только в Postgres (`docs/TASK.md:538`), а `docs/TASK.md:572` называет кеш по имени. Без этих четырёх
таблиц профиль `network` не имеет кеша и бюджетного гейта.

### Порядок создания и цели внешних ключей

- `onchain.providers` создаётся до `onchain.provider_buckets` (§4.5.6)
- `onchain.users` и `onchain.access_profiles` создаются до `onchain.api_tokens`
- Строка профиля `name = 'phase0-unlimited'` вставляется через `ON CONFLICT (name) DO NOTHING`, три
  режима лимитов — в неограниченном значении, `route_disclosure_mode = 'full'` (§4.5.3)
- Значение `id` этой строки — литеральная ULID, одна и та же в этом файле и в SQLite-объявлении
  задачи 014-36

**Why порядок назван условием.** `provider_buckets.provider` ссылается на `providers(id)`. Если
убрать `providers` из миграции, каждая запись лимитера станет отказом по внешнему ключу, и процесс
по R-7.7 деградирует до внутрипроцессной корзины навсегда (§4.5.6).

**Why идентификатор профиля — литерал, а не значение на движок.** Два движка, засеявших профиль
независимо, дадут два идентификатора для одной сущности. Тогда `access_profile_id` токена
разрешится на одном хосте и повиснет на другом (§4.5.3).

### Запрет изменения журнала

`onchain.access_audit` защищается парой из справочного проекта: правило `DO INSTEAD NOTHING` на
`DELETE` и триггер `BEFORE UPDATE`, поднимающий ошибку (§4.5.5).

**Why защита не входит в переносимую форму.** Снятие защиты не меняет ни одной колонки, поэтому
переезд между движками остаётся механическим (§4.5.5).

### Параметры применения и предусловия

Оба имени ролей приходят параметрами `psql` (`deployment.md` §10.4.2 шаг 2):

| Параметр     | Значение                                                                 | Кто задаёт           |
| :----------- | :----------------------------------------------------------------------- | :------------------- |
| `STATE_ROLE` | имя роли хранилища состояния; §10.5.4 называет `onchain_engine_state`    | владелец инсталляции |
| `READ_ROLE`  | имя read-роли инсталляции; `.env.example:118` показывает `readonly_user` | владелец инсталляции |

Команда применения (§10.4.2 шаг 2):

```bash
ssh vm 'docker exec -i supabase-db psql -qU supabase_admin -d postgres -v ON_ERROR_STOP=1 \
  -v STATE_ROLE=onchain_engine_state -v READ_ROLE=readonly_user' \
  < sql/migrations/002_t014_network_profile.sql
```

Файл открывается блоком предпроверки: на каждый параметр — `\if :{?STATE_ROLE}`, иначе `\echo` с
именем параметра и `\quit 1`. Блок стоит до первого оператора DDL, поэтому без любого из двух
параметров файл не применяется и ни одной таблицы не создаёт. В грантах имена подставляются формой
идентификатора `:"STATE_ROLE"` и `:"READ_ROLE"`.

**Why имена ролей приходят параметрами.** Оба имени локальны для инсталляции, и файл с зашитым именем
не является тем же файлом на следующем хосте (§10.4.2 шаг 2). Seed-миграция задачи 014-37 принимает
дайджест тем же способом.

**Why предпроверка стоит до DDL.** Незаданный параметр `psql` оставляет ссылку неразрешённой, и отказ
приходит на первом гранте — после создания двенадцати таблиц. Схема остаётся применённой наполовину и
разбирается вручную.

Предусловие: роль `STATE_ROLE` существует до применения файла — её создаёт шаг 1 §10.4.2, до
миграции. Read-роль появилась до T-014 и этим файлом не меняется (§10.5.1). Файл выдаёт гранты и не
создаёт ролей: пароль роли в репозиторий не попадает.

**Why роль создаётся до миграции.** `GRANT` называет грантополучателя, и отсутствующая роль прерывает
весь файл под `ON_ERROR_STOP=1`. Обратный порядок отказывает на гранте, уже создав таблицы
(§10.4.2 шаг 1).

### Гранты (`deployment.md` §10.5.1)

```sql
-- state role: the twelve engine tables of §4.4, enumerated one by one
GRANT USAGE ON SCHEMA onchain TO :"STATE_ROLE";
GRANT SELECT, INSERT, UPDATE, DELETE ON
  onchain.users, onchain.access_profiles, onchain.api_tokens, onchain.access_audit,
  onchain.provider_buckets, onchain.request_trace, onchain.diagnostics, onchain.retention_runs,
  onchain.providers, onchain.cache_entries, onchain.usage, onchain.usage_window
  TO :"STATE_ROLE";

-- read role: the three snapshotter tables, read only
GRANT USAGE ON SCHEMA onchain TO :"READ_ROLE";
GRANT SELECT ON onchain.assets, onchain.metrics, onchain.snapshots TO :"READ_ROLE";
```

`assets`, `metrics` и `snapshots` не встречаются ни в одном гранте state-роли. Двенадцать таблиц
движка не встречаются ни в одном гранте read-роли (§10.5.1).

Четыре формы запрещены, и в миграции нет ни одной из них. Первые три названы §10.5.1, четвёртая —
§4.4.

- `GRANT … ON ALL TABLES IN SCHEMA onchain TO :"STATE_ROLE"`
- `ALTER DEFAULT PRIVILEGES IN SCHEMA onchain GRANT … TO :"STATE_ROLE"`
- `GRANT CREATE ON SCHEMA onchain` любой из двух ролей
- `CREATE SCHEMA` в любом написании, включая `IF NOT EXISTS`

**Why двенадцать таблиц перечислены.** `ALL TABLES IN SCHEMA onchain` покрывает три таблицы
снапшоттера, а это та граница, ради которой гранты и существуют (§10.5.1).

**Why ни одна роль не получает `CREATE`.** Миграции применяются от `supabase_admin` (§10.4.2 шаг 2),
поэтому работающий процесс не добавляет таблиц в общую схему.

**Why `CREATE SCHEMA` запрещён, а не безвреден.** На хосте, где схемы нет, файл создал бы её и
завершился успехом, скрыв, что `001_init.sql` не применялся. Отказ на отсутствующей схеме называет
это состояние.

**Why гранта на последовательности нет.** Идентификаторы генерирует приложение, и ни одна таблица
§4.4 не имеет serial-значения по умолчанию (DB-SCHEMA §1).

**Why state-роль не может быть ролью `postgres`.** Замер 2026-08-13: роль `postgres` уже держит
`arwd` на трёх таблицах снапшоттера, а схема `onchain` несёт умолчательный ACL, выдающий `arwd` на
каждую новую таблицу той же роли (§4.4). Подключение хранилища состояния под `postgres`
восстанавливает путь записи, ради удаления которого гранты и написаны.

### Что гранты держат и чего не дают (`deployment.md` §10.5.2)

Оба отказа выносит сервер: Postgres отказывает в `SELECT` и в `INSERT`/`UPDATE`/`DELETE` на таблице,
на которую роль не держит привилегии.

Отказ держится при трёх условиях: роль не владеет такой таблицей, не является суперпользователем и не
наследует от роли, держащей привилегию.

Четыре вещи гранты не дают.

- Имена таблиц остаются видимыми: state-роль читает `pg_catalog` и видит, что `onchain.snapshots`
  существует и какие у неё колонки
- Оценки строк остаются видимыми: `pg_class.reltuples` читается для таблицы, чьи строки — нет
- Роль миграции не ограничена: `supabase_admin` применяет DDL §4.4, держа в схеме все привилегии
- Граница шириной в один оператор: позднейший `GRANT … ON ALL TABLES IN SCHEMA onchain` снимает её
  без ошибки

**Why последний пункт записан, а не устранён.** Процесс не наблюдает привилегию, выданную после
старта, поэтому набор грантов утверждается на установке — шагами 2 и 2a §10.4.2.

**Why граница связывает роль, а не процесс.** Движок продолжает законно читать `snapshots` по
`ONCHAIN_PG_URL` под read-ролью (§10.5.2, `security.md` §7).

### Замер до применения: текущий ACL read-роли

Read-роль появилась до T-014, а миграция выдаёт права и не отзывает их. Замер снимается до
применения (`deployment.md` §10.4.2 шаг 2a):

```sql
SELECT t.table_name,
       has_table_privilege('<read-role>', 'onchain.' || t.table_name, 'SELECT') AS may_select
  FROM information_schema.tables t
 WHERE t.table_schema = 'onchain'
 ORDER BY 2 DESC, 1;
SELECT defaclobjtype, defaclacl FROM pg_default_acl d
  JOIN pg_namespace n ON n.oid = d.defaclnamespace WHERE n.nspname = 'onchain';
```

Имя роли в этом запросе — то же значение, что уходит параметром `READ_ROLE`.

Постусловие: `may_select` истинно для `assets`, `metrics` и `snapshots` и ложно для любой другой
таблицы схемы. Любое истинное значение вне трёх отзывается до старта профиля. `pg_default_acl` не
несёт записи, которая выдала бы read-роли будущую таблицу движка.

Несущая проверка — отказ на `SELECT * FROM onchain.api_tokens` по `ONCHAIN_PG_URL`; два запроса выше
показывают оператору, что чинить.

**Why `has_table_privilege`, а не `information_schema.role_table_grants`.** Представление каталога
слепо к трём путям: к гранту на `PUBLIC`, к привилегии через членство в групповой роли и — по
собственному определению представления — к любому гранту, чьи роли не включены в текущей сессии.
Пустой результат оттуда означает «не найдено», а не «не выдано». Проект уже платил за трактовку
уверенного пустого ответа как безопасного (L-10).

**Why замер, а не только грант.** До T-014 таблицы движка лежали в другом пространстве имён, и
схемный `SELECT` на `onchain` до них не доставал. Общая схема убрала это разделение, и заменяет его
список грантов, который проверяет только этот шаг.

### Замер после применения: привилегии state-роли

Постусловие шага 2 §10.4.2 снимается по каждой из трёх таблиц снапшоттера:

```sql
SELECT t.table_name,
       has_table_privilege(:'STATE_ROLE', 'onchain.' || t.table_name, 'SELECT') AS may_select
  FROM information_schema.tables t
 WHERE t.table_schema = 'onchain'
   AND t.table_name IN ('assets', 'metrics', 'snapshots');
```

Постусловие: `may_select` ложно для всех трёх. Наблюдаемое поведение: `SELECT * FROM onchain.snapshots`
под state-ролью отказывает сообщением `permission denied for table snapshots`, а
`INSERT INTO onchain.request_trace …` проходит (§10.5.2).

**Why замер, а не только поведенческий тест.** Поведенческий тест называет одну таблицу и одну
привилегию. Шаг 2 §10.4.2 требует замера `has_table_privilege` по каждой из трёх таблиц, и других
мест проверки списка грантов нет.

### Проверка совпадения имён перед применением

Проверка повторяется против целевого сервера, потому что снапшоттер добавляет таблицы в `onchain`
без согласования с движком (§4.4, §10.5.3):

```sql
select c.relkind::text||' '||n.nspname||'.'||c.relname from pg_class c join pg_namespace n on n.oid=c.relnamespace where n.nspname like 'onchain%';
```

Замер 2026-08-13 дал три таблицы — `assets`, `metrics`, `snapshots` — и пять индексов: `assets_pkey`,
`metrics_pkey`, `snapshots_pkey`, `uq_snapshots_dedup`, `idx_snapshots_series` (§4.4). Ни одно из
двенадцати имён таблиц и ни одно из десяти имён индексов миграции в этих списках не встречается.

**Why считаются индексы, а не только таблицы.** Таблица и индекс занимают одно пространство имён
отношений на схему. Отдельная схема делала эту проверку избыточной, общая — нет (§4.4).

Четыре из пяти присутствующих имён — `assets_pkey`, `metrics_pkey`, `snapshots_pkey`,
`uq_snapshots_dedup` — даны конструктором от ограничений, а не объявлены. Такие индексы отдельного
сравнения не требуют: Postgres выводит их имя из таблицы (`users_pkey`, `api_tokens_token_hash_key`),
поэтому двенадцать различных имён таблиц дают различные имена производных индексов (§4.4).

### Verify-гейт миграции

Четыре утверждения, все — на пустых таблицах (§4.4 пункт 4):

1. Присутствие: двенадцать таблиц существуют в `onchain`, ни один объект не создан в `public`
2. Засеянные цели внешних ключей: строка `access_profiles` с `name = 'phase0-unlimited'` на месте;
   строки `providers` появляются загрузочным апсертом процесса до первого обращения лимитера (§4.5.6)
3. Ноль сирот: счёт строк с недостающей целью по каждой таблице с `REFERENCES` даёт ноль
4. Запись прогона: дата, хост и результат verify-гейта записываются в лог инсталляции (DB-SCHEMA §6)
   до шага 5 `deployment.md` §10.4.2 — до того, как профиль обслужит первый запрос

**Why гейт короче требований DB-SCHEMA §5.3.** Ничего не переносится, поэтому счёту строк и
`min`/`max(ts)` не с чем сравниваться. Проверка сирот остаётся: она единственная из §5.3 держится на
пустой таблице (§4.4).

**Why прогон записывается до первого запроса.** Незаписанный прогон неотличим от непроведённого, и
правило «ничего молча» требует записи объёма и результата.

      трёх и приложен к записи прогона

Задача 014-02 объявляет интерфейсы репозиториев и стабы под ними и не создаёт ни одной таблицы.
Единственный файл миграции Postgres для T-014 — этот; SQLite-объявление ведёт задача 014-36, засев

`data-model.md` §4.4 не называет индексов для группы счётчиков, а `packages/core/src/cache/ddl.ts:66`
объявляет `idx_cache_entries_expiry` в диалекте SQLite. Миграция следует §4.4; расхождение вынесено
оркестратору.

`deployment.md` §10.5.1 печатает грант с литеральным `onchain_engine_state` и заявляет, что документ
закрепляет имя только state-роли. §10.4.2 шаг 2 передаёт параметрами оба имени и ссылается на §10.5.1
как на основание. Задача следует §10.4.2. Расхождение вынесено оркестратору.

на шаг 2. Расхождение вынесено оркестратору.
