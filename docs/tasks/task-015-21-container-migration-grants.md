# Задача 015.21: [VM · аддитивно] миграция тринадцати таблиц, роль состояния и гранты на новом контейнере

## Связь со сценариями

- UC-6 — таблицы движка переезжают в выделенный контейнер Postgres на dev-VM, шаг 2

<!-- contract:goal -->

## Цель задачи

Создать на новом контейнере схему, роль состояния и гранты тринадцати таблиц движка так, чтобы
`may_select` под ролью состояния был истинен ровно для них и ложен для всего остального.

**Why тринадцать, а не двенадцать.** Двенадцать таблиц T-014 (`data-model.md` §4.5 и §4.2.4) плюс
`client_usage` (R-8.2). Леджер живёт только здесь — решение MAJOR-F раунда 2, принадлежащее задаче
015-03.

**Why пустые таблицы.** Перенос строк — отдельное обязательство R-8.11 и отдельная задача 015-23.
Миграция сама по себе создаёт таблицы пустыми
(`docs/architectures/deployment.md:794` — `#### 10.9.2. The migration, applied to an empty container
(R-8.2)`).

### Форма файла миграции

Паттерн — `sql/migrations/002_t014_network_profile.sql`, с пятью отличиями. Файл создаёт целевое
состояние целиком, а не паттерн плюс догадку читателя.

| Отличие                      | Как                                                                                                                  |
| :--------------------------- | :------------------------------------------------------------------------------------------------------------------- |
| один параметр вместо двух    | только `STATE_ROLE`; `READ_ROLE` не объявляется                                                                      |
| тринадцатая таблица          | `CREATE TABLE IF NOT EXISTS onchain.client_usage`                                                                    |
| суперпользователь применения | `postgres` образа, не `supabase_admin`                                                                               |
| колонка суточного счётчика   | `calls_made BIGINT NOT NULL DEFAULT 0` и `CHECK (calls_made >= 0)` внутри `CREATE TABLE onchain.usage`               |
| ограничение формата баланса  | именованное `CHECK (credits_balance_raw IS NULL OR credits_balance_raw ~ '^-?[0-9]+$')` на `onchain.access_profiles` |
| **создание схемы**           | `CREATE SCHEMA IF NOT EXISTS onchain;` — добавлено при исполнении 2026-08-28, см. ниже                               |

**Why шестое отличие добавлено при исполнении (2026-08-28).** Первая редакция таблицы называла пять
отличий. Файл 002 схему не создаёт намеренно: его собственный комментарий на строке 23 объясняет,
что `001_init.sql` на его цели уже отработал, и `CREATE SCHEMA` здесь скрыл бы факт, что не
отработал. Для нового контейнера это предусловие ложно — измерено перед применением: `pg_namespace`
содержал только `public`. Без `CREATE SCHEMA IF NOT EXISTS onchain;` файл 005 отказал бы на первой
же команде `CREATE TABLE onchain.…`. Буквальное прочтение «пять отличий и ничего больше» дало бы
миграцию, которую нельзя применить.

**Why охрана параметра не возвращает код отказа.** Форма `\quit 1` скопирована из файла 002 и на
обеих целевых версиях psql (15.8 и 16.13) печатает `extra argument "1" ignored` и возвращает ноль:
аргумент кода возврата появился в PostgreSQL 17. Скрипт при этом действительно встаёт до первой
команды DDL, поэтому свойство безопасности держится, а наблюдаемость отказа — нет. Дефект записан
как `L-28` и правится во всех пяти файлах разом, а не в этом одном.

**Why четвёртое отличие названо.** Файл 002 объявляет `onchain.usage` четырьмя колонками
(`sql/migrations/002_t014_network_profile.sql:63` — `CREATE TABLE IF NOT EXISTS onchain.usage (`), и
`calls_made` там нет: колонка есть только у `usage_window` (`:72`). Оператор задачи 015-14 на
контейнере без неё отказывает с `column "calls_made" does not exist`.

**Why пятое отличие названо.** Ограничение формата на `credits_balance_raw` вводит MINOR-7 раунда 2,
и объявляет его только файл 004. Значение `'NaN'` без него делает проверку баланса истинной при
любой цене.

**Why имена ограничений совпадают с именами файла 004.** Постусловие «применение 004 после 005
ничего не меняет» держится только тогда, когда охрана по `pg_constraint` находит уже созданное
ограничение под тем же именем.

**Why `READ_ROLE` отсутствует.** Роли чтения на этом контейнере нет по построению: снапшоттерских
таблиц он не держит, и грантить нечего (R-8.6, R-8.7).

Предпроверка параметра — та же форма, что уже несёт файл 002:
`sql/migrations/002_t014_network_profile.sql:29` — `\if :{?STATE_ROLE}`. Незаданный параметр
останавливает файл до первой команды DDL, а не после создания таблиц.

Команда применения — подача через стандартный ввод:

```bash
ssh vm 'docker exec -i <new-container> psql -qU postgres -d postgres -v ON_ERROR_STOP=1 \
  -v STATE_ROLE=onchain_engine_state' < sql/migrations/005_wi62_dedicated_container.sql
```

**Why через stdin, а не файлом внутри контейнера.** Skill `vm-deploy` требует `docker exec -i` с
подачей на стандартный ввод. Путь `-f /tmp/…` читает файловую систему контейнера и исполняет
устаревшую копию.

### Отношение к миграции 004

| Файл                               | Куда применяется                          | Что делает                                       |
| :--------------------------------- | :---------------------------------------- | :----------------------------------------------- |
| `004_t015_billing.sql` (015-03)    | база, уже несущая двенадцать таблиц T-014 | добавляет леджер, `calls_made` и два ограничения |
| `005_wi62_dedicated_container.sql` | новый пустой контейнер                    | создаёт все тринадцать сразу                     |

**В T-015 файл 004 не выходит на путь выкатки ни одного контейнера.** Единственная база с
двенадцатью таблицами — `supabase-db`, и решение MAJOR-F запрещает применять к ней миграцию T-015.
Новый контейнер получает 005.

**Оговорка: одно применение 004 в этапе всё же есть — проверочное.** TC-OPS-09 применяет
`sql/migrations/004_t015_billing.sql` к НОВОМУ контейнеру как проверку идемпотентности, после 005 и
без ожидания изменений. Это не путь выкатки: файл ничего не создаёт и ничего не меняет, а его вывод
и есть проверяемое утверждение. Формулировка приведена к редакции задачи 015-03
(`docs/tasks/task-015-03-pg-migration-billing.md` — таблица «Куда применяется миграция 004»), где
строка нового контейнера читается «только как проверка идемпотентности TC-OPS-09».

**Why оговорка записана, а не подразумевается.** Оператор, читающий предыдущий абзац буквально,
откажется исполнять собственный TC-OPS-09 этой задачи — то самое расхождение адресата, ради снятия
которого правка M-5 и делалась.

Оба файла идемпотентны. Постусловие: применение 004 после 005 ничего не меняет — оно и есть
TC-OPS-09, и оно верно только при пятиотличном 005.

**Why 004 всё же существует.** Он — аддитивный путь для базы, уже несущей двенадцать таблиц: его
исполнит следующий переезд или второй контейнер. 005 — создание с нуля. Слияние потребовало бы
одному файлу знать, в каком из двух состояний находится база.

**Why это записано здесь, а не только в 015-03.** Ревью плана нашло расхождение адресата между двумя
файлами задач. Адресата называет одно предложение, и оно стоит в обеих задачах дословно.

### Гранты

```sql
GRANT USAGE ON SCHEMA onchain TO :"STATE_ROLE";
GRANT SELECT, INSERT, UPDATE, DELETE ON
  onchain.users, onchain.access_profiles, onchain.api_tokens, onchain.access_audit,
  onchain.provider_buckets, onchain.request_trace, onchain.diagnostics, onchain.retention_runs,
  onchain.providers, onchain.cache_entries, onchain.usage, onchain.usage_window,
  onchain.client_usage
  TO :"STATE_ROLE";
```

Перечисление поимённо — та же форма, что уже несёт файл 002:
`sql/migrations/002_t014_network_profile.sql:289` — `GRANT SELECT, INSERT, UPDATE, DELETE ON`.

Три формы запрещены и в этом файле не встречаются
(`docs/architectures/deployment.md:830` — подстрока `The same three prohibited forms`):

- `GRANT … ON ALL TABLES IN SCHEMA onchain`
- `ALTER DEFAULT PRIVILEGES IN SCHEMA onchain GRANT …`
- `GRANT CREATE ON SCHEMA onchain` роли состояния

**Why перечисление, а не `ALL TABLES`.** Форма `ALL TABLES` накрывает и то, что появится в схеме
позже. Именно она — механизм, которым RISK-5 воспроизводит `SEC-2` на новом контейнере.

**Why роль состояния не получает `CREATE`.** Миграции применяет суперпользователь; работающий
процесс таблиц не создаёт.

### Перечень ролей — измеряется, а не предполагается (R-8.6)

Ролей на контейнере две: суперпользователь образа (`postgres`) и роль состояния, создаваемая
оператором до применения файла. Третьей роли не существует
(`docs/architectures/deployment.md:812` — подстрока `Which roles exist on this container, named
explicitly`).

Перечень снимается запросом, а не переписывается из этого документа:

```sql
SELECT rolname, rolsuper, rolcanlogin FROM pg_roles WHERE rolname NOT LIKE 'pg\_%' ORDER BY 1;
```

**Why суперпользователь исключён из постусловия AC-17.** Он держит все привилегии по построению
образа, и `may_select` для него истинен независимо от грантов. Постусловие формулируется над
ПРИКЛАДНЫМИ ролями — та же оговорка, что уже сделана для роли `authenticator` в §10.4.2.

### Verify-блок файла

Четыре запроса, исполняемые тем же файлом после `COMMIT`:

1. тринадцать таблиц существуют в схеме `onchain`; в `public` не создано ни одного объекта
2. `may_select` под ролью состояния по КАЖДОЙ таблице схемы — истина ровно для тринадцати
3. перечень ролей контейнера
4. `has_table_privilege` по каждой прикладной роли и каждой из тринадцати таблиц

**Why `has_table_privilege`, а не каталожное представление грантов.** Представление слепо к гранту
на `PUBLIC`, к привилегии через членство в групповой роли и к любому гранту, чьи роли не включены в
сессии. Пустой результат там означает «не найдено», а не «не выдано» — прецедент `L-10`. Та же
форма уже применена в файле 002: `sql/migrations/002_t014_network_profile.sql:353` —
`has_table_privilege(:'STATE_ROLE', 'onchain.' || t.table_name, 'SELECT') AS may_select`.

### Предусловие MAJOR-F, повторённое здесь

Миграция T-015 к контейнеру Supabase не применяется. Леджер живёт только на новом контейнере.

**Why повтор, а не ссылка.** Решение принадлежит задаче 015-03, но исполняет его оператор, читающий
этот файл. Утверждение, лежащее только в соседней задаче, до него не доходит. Строка леджера,
записанная в старый контейнер, исчезла бы в удалении задачи 015-27.

### Что эта задача не делает

- Не переносит ни одной строки — задача 015-23
- Не снимает verify-гейт переноса — задача 015-24
- Не переключает `ONCHAIN_STATE_PG_URL` — задача 015-25
- Не удаляет ничего в старом контейнере — задача 015-27
- Не трогает `assets`, `metrics`, `snapshots` и credential «Supabase DB» (R-8.3)

## Примечания

Этап: **Этап 6. Переезд таблиц движка на выделенный контейнер (dev-VM)**. Проход: **ops**.
Зависимости: 015-02 (форма `client_usage` на оси SQLite), 015-03 (та же форма на оси Postgres и
решение MAJOR-F), 015-20 (контейнер поднят).

**Операция аддитивна.** Существующий контейнер Supabase не правится. Подтверждения деструктивности
по skill `vm-deploy` эта задача не требует; его требует задача 015-27.

**Предусловие исполнения.** Роль состояния создаётся оператором ДО применения файла: `GRANT` называет
грантополучателя, и отсутствующая роль прерывает файл под `ON_ERROR_STOP=1` уже после создания
таблиц. Пароль роли задаёт оператор и в репозиторий он не попадает — то же разделение, что уже
записано в `docs/onchain-analytics/PROD-RUNBOOK.md:201` — подстрока `Split the creation from
the password`.

**Предусловие среды.** dev-VM обязана быть доступной. На момент планирования `ssh vm` отвечал
таймаутом устойчиво.

Проектные координаты: `docs/architectures/deployment.md:794` (§10.9.2, миграция) и
`docs/architectures/deployment.md:818` (§10.9.3, гранты).

Требования: R-8.2, R-8.5, R-8.6, R-8.7.
