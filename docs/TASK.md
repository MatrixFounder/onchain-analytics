**Зафиксированные отклонения от TASK/ARCHITECTURE:**

6. **`ChainInfo` получил колонку `nativeDecimals`** (постревью, H-3). Схема сети в

- `GET https://api.coingecko.com/api/v3/asset_platforms` — **461** платформа, keyless. Поля:

- `GET https://chainid.network/chains_mini.json` — **2660** EVM-сетей, keyless. Несёт `rpc[]` и

**Качество join'а между каталогами (измерено, не предположено):**

| Ключ join                                                | Совпадений     | Вердикт                                                      |
| -------------------------------------------------------- | -------------- | ------------------------------------------------------------ |
| `defillama.gecko_id` → `coingecko.native_coin_id`        | **235**        | Явный вендорский cross-reference — **основной ключ**         |
| нормализованное имя (`[^a-z0-9]` вырезано)               | 255            | Больше, но фаззи — **только fallback, с ручным ревью диффа** |
| `coingecko.chain_identifier` → `chainid.network.chainId` | **257 из 270** | Основной ключ для EVM-ветки                                  |

**Ключевой вывод, определяющий весь дизайн:** общего словаря сетей между вендорами **не
существует**. 461 ≠ 461: пересечение по именам — 255, по явному ключу — 235. Поэтому канонический
идентификатор сети должен быть **нашим**, а вендорские id — колонками маппинга, а не первичным
ключом.

## 1. Контекст и цель

### 1.1. Проблема

Движок сейчас жёстко ограничен двумя сетями — `ethereum` и `solana`. Это **не ограничение
провайдеров**: 4 из 5 наших адаптеров (DeFiLlama, CoinGecko, DexScreener, rpc-evm) покрывают
сотни сетей бесплатно и без нового провайдера. Ограничение — **наше собственное**, и оно
продублировано литералами в пяти слоях:

| Слой                            | Файл                                                                                                          | Что зашито                                                                               |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1. Канонический словарь         | `packages/core/src/types/chain.ts:10`                                                                         | `z.enum(['ethereum','solana','dash'])`                                                   |
| 2. Таблица маршрутов            | `packages/core/src/providers.config.ts:16-71`                                                                 | `chains: [...]` в каждом из **18 маршрутов** (17 различных capability)                   |
| 3. Приватные маппинги адаптеров | `adapters/defillama/index.ts:17-25`, `adapters/dexscreener/index.ts:10,30`, `adapters/nansen/endpoints.ts:19` | свой `SupportedChain` + свой vendor-key (`CHAIN_TVL_KEY`, `NATIVE_QUERY`, `NansenChain`) |
| 4. Схемы MCP-инструментов       | 7 файлов в `packages/mcp-server/src/tools/`                                                                   | 7× повторённый литерал `z.enum(['ethereum','solana'])`                                   |
| 5. Валидация адресов            | `packages/core/src/chain/address.ts:91-120`                                                                   | `switch (chain)` по **имени сети**, а не по семейству                                    |

Добавление одной сети сегодня = ручной проход по всем пяти слоям; любой пропуск даёт
рассинхрон, при котором схема инструмента разрешает сеть, а адаптер её роняет.

### 1.2. Цель

Сделать сеть **данными, а не кодом**: одна строка в реестре описывает сеть целиком, и ни один
слой выше не содержит списка сетей литералом. Это ровно тот принцип, который проект уже объявил
для активов и метрик (DB-SCHEMA-CONCEPT §1, anti-goals: «масштабирование через `asset`/`metric`

- реестр, НЕ таблица-на-сеть») — здесь он применяется к сетям.

### 1.3. Решения, зафиксированные владельцем 2026-07-26 — не пересматриваются в этой задаче

1. **`chain` в схемах MCP-инструментов — открытая строка + отдельный discovery-инструмент
   `onchain_list_chains`.** Не закрытый `z.enum`.
   **Обоснование (измерено):** `z.enum` из 461 сети — 4998 символов ≈ **1249 токенов на один
   инструмент**; при 7 инструментах это **≈8.7k токенов схемы, которые платятся в каждом
   запросе к модели**. Открытая строка стоит ~5 токенов; корректность переносится в рантайм-резолв
   по реестру с внятной ошибкой и подсказкой «did you mean».
   **Принятая цена решения:** модель не видит список сетей в схеме и иногда потратит один
   лишний вызов `onchain_list_chains`. Это осознанный размен ~8.7k токенов на запрос против
   редкого лишнего вызова.
2. **Capability, которые физически не могут быть универсальными, обслуживаются матрицей покрытия
   и мягкой деградацией.** Не молчаливым сужением и не ложным обещанием универсальности.
   **Обоснование:** Nansen — платный и покрывает ограниченный набор сетей; `wallet.balances.native`
   требует доверенного RPC-хоста на сеть. Реестр хранит покрытие на **паре** (capability, chain);
   неподдержанная пара даёт явную ошибку со списком доступных сетей для этой capability **и**
   списком доступных capability для этой сети.

### 1.4. Связь с существующей системой

Задача **аддитивна к M1/M2 по поведению, но рефакторинг-heavy по коду**: она не добавляет
провайдеров и не меняет каноническую доменную модель (D5), но переписывает то, как каждый
существующий адаптер и инструмент узнаёт о сети. Все 8 существующих MCP-инструментов
сохраняют свой контракт для `ethereum`/`solana` (R-59) — это регрессионный гейт, а не пожелание.

## 2. Use Cases

### UC-1: Агент запрашивает TVL сети, о которой движок раньше не знал

**Актёры:** LLM-агент (Claude Code) → MCP-сервер → DeFiLlama.
**Предусловия:** движок запущен, реестр сетей вендорен в сборке, ключи не требуются.

**Основной сценарий:**

1. Агент вызывает `onchain_chain_tvl({ chain: "berachain" })`.
2. Сервер резолвит `"berachain"` по реестру → `{ caip2: "eip155:80094", family: "evm",
defillama: "Berachain", coingecko: "berachain", dexscreener: "berachain" }`.
3. Registry проверяет покрытие пары (`chain.tvl`, `eip155:80094`) → покрыта адаптером `defillama`.
4. Адаптер берёт вендорский ключ **из реестра** (не из приватной мапы), делает keyless-запрос.
5. Ответ нормализуется в канонический вид, кешируется, возвращается с `_meta.cache`.

**Альтернативы:**

- **A1 — опечатка в имени сети.** `"beara"` не резолвится → ошибка
  `unknown chain 'beara'. Did you mean: berachain? Call onchain_list_chains to browse.`
  Подсказка строится по расстоянию Левенштейна над slug'ами и алиасами реестра. **Ни одного
  сетевого вызова не сделано** — резолв чисто локальный.
- **A2 — сеть есть в реестре, но не покрыта этой capability.** Ошибка перечисляет, какие
  capability доступны на этой сети.
- **A3 — вендор ответил 5xx/таймаут.** Существующее поведение R-11/R-24 (fallback по маршруту,
  затем `CapabilityUnavailableError`) — эта задача его не меняет.

**Постусловия:** ответ получен; реестр не мутировал; сетевых вызовов ровно столько, сколько
потребовал промах кеша.

**Критерии приёмки:**

- ✅ Запрос по сети, которой не было в `z.enum` до этой задачи, возвращает данные без правок кода.
- ✅ Неизвестная сеть даёт ошибку с непустым списком кандидатов и **нулём** сетевых вызовов.
- ✅ Резолв `"berachain"` даёт `eip155:80094` — сверено с живой пробой `eth_chainId → 0x138de`.

### UC-2: Агент выясняет, какие сети вообще доступны и для чего

**Актёры:** LLM-агент → MCP-сервер (локально, без сети).
**Предусловия:** реестр загружен.

**Основной сценарий:**

1. Агент вызывает `onchain_list_chains({ capability: "chain.tvl", minTvlUsd: 10000000 })`.
2. Сервер фильтрует реестр по матрице покрытия и порогу.
3. Возвращает компактный список: canonical slug, отображаемое имя, family, набор доступных
   capability; результат **урезан по умолчанию** (`limit`, дефолт умеренный) с полем `total`.

**Альтернативы:**

- **A1 — поиск по подстроке.** `{ query: "bera" }` → совпадения по slug, имени и алиасам.
- **A2 — фильтр по семейству.** `{ family: "evm" }`.
- **A3 — фильтров нет.** Возвращается урезанный список + `total: 461` + подсказка сузить запрос
  (защита от выброса 461 строки в контекст модели).

**Постусловия:** агент знает точные допустимые значения `chain` — компенсация за открытую строку
вместо енума (решение владельца §1.3.1).

**Критерии приёмки:**

- ✅ Инструмент не делает ни одного сетевого вызова.
- ✅ Без фильтров ответ урезан и несёт `total`; полный список без явного `limit` не выдаётся.
- ✅ Фильтр `capability` возвращает **ровно** те сети, на которых эта capability реально покрыта.

### UC-3: Запрошена capability, недоступная на этой сети (мягкая деградация)

**Актёры:** LLM-агент → MCP-сервер.
**Предусловия:** сеть в реестре есть; пара (capability, chain) не покрыта.

**Основной сценарий:**

1. Агент вызывает `onchain_smart_money_flows({ chain: "berachain", tokenAddress: "0x…" })`.
2. Матрица покрытия сообщает: `smart-money.flows` обслуживается только `nansen`, чей chain-scope
   не включает `eip155:80094`.
3. Инструмент возвращает `isError: true` с текстом, содержащим (a) какая пара не поддержана,
   (b) на каких сетях эта capability доступна, (c) какие capability доступны на этой сети.
4. **Платный вызов не совершён, кредиты не списаны, бюджет не тронут.**

**Альтернативы:**

- **A1 — сеть покрыта, но провайдер недоступен** (нет ключа): существующий путь R-24
  `isAvailable()` → `CapabilityUnavailableError`. Это **другая** ошибка, чем «не покрыто», и
  тексты не должны сливаться.
- **A2 — покрытие частичное внутри capability** (провайдер поддерживает сеть, но не операцию):
  трактуется как непокрытая пара; в реестре фиксируется на уровне (capability, chain).

**Постусловия:** ноль платных вызовов; агент получил достаточно информации, чтобы выбрать
альтернативу без второго слепого вызова.

**Критерии приёмки:**

- ✅ Тест доказывает: непокрытая пара для платной capability не доводит до HTTP-вызова Nansen и не
  увеличивает `usage`.
- ✅ Текст ошибки содержит оба списка (сети для capability, capability для сети).
- ✅ «Не покрыто» и «провайдер недоступен» различимы по типу ошибки, не только по тексту.

### UC-4: Оператор обновляет реестр под новую сеть вендора

**Актёры:** оператор/разработчик → скрипт синхронизации → git.
**Предусловия:** есть сеть, появившаяся у вендоров после последней сборки.

**Основной сценарий:**

1. Оператор запускает dev-скрипт синхронизации (не рантайм движка).
2. Скрипт тянет три каталога, джойнит по явным ключам (`gecko_id`↔`native_coin_id`,
   `chain_identifier`↔`chainId`), нормализует и пишет **детерминированный** снапшот реестра.
3. Скрипт печатает human-readable дифф: добавлено / удалено / изменено, отдельно — строки,
   склеенные по fallback-ключу (имя), требующие ручного ревью.
4. Оператор ревьюит дифф и коммитит снапшот.

**Альтернативы:**

- **A1 — вендор недоступен.** Скрипт падает громко, **не** записывает частичный снапшот.
- **A2 — конфликт join'а** (один `gecko_id` на две сети): строка помечается, в снапшот не
  попадает молча — попадает в отчёт для ручного решения.
- **A3 — сеть исчезла у вендора.** Не удаляется автоматически: помечается `deprecated`, чтобы
  ключи кеша и уже сохранённые ссылки не ломались.

**Постусловия:** снапшот детерминирован (повторный прогон без изменений у вендора даёт побайтово
тот же файл); история изменений реестра видна в git.

**Критерии приёмки:**

- ✅ Двукратный прогон подряд даёт идентичный файл (нет timestamp'ов/произвольного порядка внутри).
- ✅ Скрипт **никогда** не вызывается из рантайма движка — доказано оффлайн-гейтом (UC-5).
- ✅ Дифф-отчёт отдельно перечисляет строки, склеенные фаззи-ключом.

### UC-5: Тесты и оффлайн-прогон не делают сетевых вызовов

**Актёры:** CI → тест-сьют.
**Предусловия:** реестр вендорен в репозитории как статический артефакт.

**Основной сценарий:**

1. CI гоняет полный сьют без сетевого доступа.
2. Реестр читается из вендоренного снапшота, входящего в сборку.
3. Существующий гейт «оффлайн-прогон = 0 сетевых вызовов» (унаследован из M1/M2) остаётся зелёным.

**Альтернативы:**

- **A1 — реестр не найден/повреждён.** Загрузка падает громко на старте с внятным сообщением, а не
  деградирует в пустой реестр (пустой реестр превратил бы **любой** запрос в «unknown chain»).
- **A2 — реестр валиден, но не проходит собственную схему** (дубли canonical id, битый CAIP-2):
  падение на старте, не в момент первого запроса.

**Постусловия:** детерминизм CI сохранён; сетевой доступ не является требованием для тестов.

**Критерии приёмки:**

- ✅ Полный сьют зелёный при отсутствии сети.
- ✅ Валидация реестра (уникальность canonical id, формат CAIP-2, непустой набор алиасов) — тест.

### UC-6: Существующие вызовы по `ethereum`/`solana` не ломаются

**Актёры:** уже написанные плейбуки/скиллы → MCP-сервер.
**Предусловия:** миграция на реестр выполнена.

**Основной сценарий:**

1. Существующий вызов `onchain_get_token({ chain: "ethereum", address: "0x…" })` приходит без
   изменений.
2. `"ethereum"` резолвится в canonical id как **алиас** — прежнее строковое значение остаётся
   валидным навсегда.
3. Ответ идентичен доэтому по форме и содержанию.

**Альтернативы:**

- **A1 — ключ кеша.** Канонизация не должна расколоть кеш-ключ так, чтобы прежние записи стали
  недостижимы «наполовину» (часть по `ethereum`, часть по `eip155:1`). Ключ строится **только**
  от canonical id; при выкатке прежние записи считаются холодными (переcчитываются) — это
  допустимо, кеш восстановим по определению (ARCHITECTURE §9.2), но должно быть **осознанным**, а
  не случайным следствием.

**Постусловия:** M1/M2-регрессий нет.

**Критерии приёмки:**

- ✅ Все существующие тесты M1/M2 проходят без правок ожиданий (кроме явно перечисленных в плане).
- ✅ `"ethereum"` и `"eip155:1"` резолвятся в один и тот же canonical id.
- ✅ Инвалидация кеша при переходе на новый вид ключа — явно описанное, задокументированное
  следствие, а не сюрприз.

---

### UC-7: Адрес валидируется по семейству сети, а не по её имени

**Актёры:** MCP-сервер (input-валидация) → `chain/address.ts`.
**Предусловия:** сеть резолвится, у неё известно `family`.

**Основной сценарий:**

1. Приходит `{ chain: "berachain", address: "0xabc…" }`.
2. Резолв даёт `family: "evm"` → адрес валидируется как EVM и нормализуется в EIP-55.
3. Канонический адрес участвует в ключе кеша (существующее поведение M1 сохраняется).

**Альтернативы:**

- **A1 — `family: "svm"`** → base58, 32 байта, регистр не трогаем (существующее поведение).
- **A2 — семейство известно, но валидатора нет** (например `move`, `cosmos`): адрес принимается
  без структурной проверки, помечается как непроверенный; ключ кеша строится от исходной строки
  без нормализации. Ошибка вендора «адрес не найден» — нормальный результат, а не наш баг.
- **A3 — `family: "unknown"`** → как A2.

**Постусловия:** одна ветка кода обслуживает все 270+ EVM-сетей вместо одной ветки на сеть.

**Критерии приёмки:**

- ✅ EIP-55 применяется ко всем EVM-сетям, не только к `ethereum`.
- ✅ Отсутствие валидатора для семейства **не** приводит к отказу в обслуживании — только к отказу
  от нормализации.
- ✅ Существующие тесты EIP-55/base58 не изменены.

## 3. В рамках задачи (In Scope)

1. Реестр сетей как вендоренный статический артефакт + типизированный загрузчик/резолвер.
2. Dev-скрипт синхронизации реестра из трёх каталогов + дифф-отчёт + verify-гейт.
3. Миграция всех пяти слоёв (§1.1) на реестр; удаление приватных вендорских мап из адаптеров.
4. Матрица покрытия (capability × chain) + типизированная ошибка непокрытой пары.
5. Новый инструмент `onchain_list_chains`.
6. Новая capability `chain.tvl` + инструмент `onchain_chain_tvl` (исходный вопрос владельца).
7. Валидация/нормализация адресов по семейству.
8. Живая проба chain-покрытия Nansen для заполнения колонки реестра.
9. Обратная совместимость `ethereum`/`solana` + регрессионный гейт M1/M2.

## 4. Вне рамок (Out of Scope) — явно

1. **Новые провайдеры.** Ни Bitquery, ни Covalent/GoldRush, ни Moralis. Универсальность берётся из
   уже подключённых источников.
2. **Расширение chain-скоупа Nansen сверх того, что вендор реально отдаёт.** Проба фиксирует факт,
   а не создаёт покрытие.
3. **Оживление `dune`** (по-прежнему interface/config-stub) и **живой gRPC для `dash-platform`**.
4. **M3 (signals/alerts)** — сдвигается, не сливается с этой задачей.
5. **Исторические ряды по chain-TVL.** `chain.tvl` в этой задаче — текущее значение; ряды — не
   здесь.
6. **Автоматическое обновление реестра в рантайме** (cron/at-startup fetch). Реестр обновляется
   dev-скриптом и коммитом — иначе рушится оффлайн-гейт и детерминизм CI.
7. **Постгрес/снапшоттер.** Автономный контур n8n+Postgres не затрагивается (решение владельца
   2026-07-25, ADR).

## 7. Нефункциональные требования

- **Стоимость схемы инструментов.** Суммарный размер схем инструментов (сейчас **8**, после этой
  задачи **10**: `+onchain_list_chains`, `+onchain_chain_tvl`) не должен расти пропорционально
  числу сетей. Базовая точка отсчёта — измеренные 8.7k токенов для закрытого енума на 7
  chain-принимающих инструментах; целевое — единицы токенов на параметр `chain`.
- **Детерминизм.** Реестр и его генератор детерминированы; CI не зависит от сети.
- **Безопасность.** SSRF-allowlist остаётся статическим (R-56c) — расширение множества сетей **не
  должно** превращаться в расширение множества хостов, которым мы доверяем по данным из сети.
- **Бюджет.** Матрица покрытия обязана отказывать в непокрытой платной паре **до** резервирования
  кредитов (R-51d) — иначе расширение множества сетей становится вектором расхода денег.
- **Зависимости.** Цель — ноль новых npm-зависимостей (реестр — данные + zod, оба уже есть).

## 8. Ограничения и допущения

1. **Допущение:** три выбранных каталога (DeFiLlama, CoinGecko, chainid.network) остаются
   keyless и стабильными по форме. Риск дрейфа снимается verify-гейтом генератора (R-49), а не
   доверием.
2. **Ограничение:** «все сети» достижимо только для тех capability, чьи источники универсальны.
   Топ-10 сетей дают 91.8% всего TVL, топ-50 — 99.1%; длинный хвост из ~400 сетей будет
   технически доступен, но содержательно почти пуст. Это ожидаемое свойство данных, не дефект.
3. **Ограничение:** 191 из 461 платформы CoinGecko не имеют EIP-155 chainId — для них canonical id
   строится по не-`eip155` namespace CAIP-2, и качество join'а ниже (235 явных совпадений).
4. **Допущение:** инвалидация кеша при переходе ключа на canonical id приемлема (кеш восстановим,
   ARCHITECTURE §9.2). Требует явного подтверждения владельца — см. OQ-3.

## 10. Известные проблемы, учтённые при постановке

Прочитан [KNOWN_ISSUES.md](KNOWN_ISSUES.md). Релевантны:

- **SEC-1** (`open`) — дневной потолок кредитов не ограничивает всплеск, velocity-guard'а нет.
  Расширение множества сетей увеличивает поверхность вызовов → R-51d (отказ до резервирования)
  становится важнее, чем был. Саму SEC-1 эта задача **не** закрывает.
- **Q-3** (`open`) — 0-кредитный tier `entity.labels` структурно неотказуем кредитным гейтом.
  Пересекается с R-51: матрица покрытия — второй, некредитный слой отказа.
- **RF-2** (`open`) — evidence-записи M2 разъехались с закоммиченным деревом. Для этой задачи:
  evidence-файл (§0) датирован и привязан к пробе, генератор реестра обязан быть
  воспроизводимым (R-49c), чтобы расхождение было обнаружимо, а не обнаруживалось постфактум.
