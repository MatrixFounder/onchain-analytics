# Задача 015.10: жизненный цикл резерва — завершение вне `withTrace`, условное кредитование, возврат баланса сверкой, поздний исход

## Связь со сценариями

- UC-1 — списание на границе тула независимо от исхода кеша (A2, A4, A5)
- UC-2 — ретрай с тем же `client_request_id` не списывает дважды (A1)
- UC-5 — фаза 0 работает на оси SQLite без Postgres

<!-- contract:goal -->

## Цель задачи

Замкнуть переход резерва в терминальное состояние так, чтобы каждая строка `client_usage` его
получала на всех трёх профилях, а баланс двигался один раз на строку.

**Why одна задача, а не четыре.** MAJOR-A, MAJOR-B, MAJOR-C раунда 2 и MAJOR-9 раунда 1 описывают
один путь — жизнь резерва после переноса дебета на `reserve()`. Все четыре правят одну
транзакционную границу. Раунд 2 назвал это прямо: планирование порознь означает четыре правки
одного места.

**Why граница принадлежит этой задаче.** Задача 015-09 создаёт резерв, задача 015-11 проверяет правило на
каждом исходе. Переход между ними принадлежит одному владельцу.

## Описание изменений

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/tools/registry.ts`** (MAJOR-B раунда 2):

- Перенести вызов `settle`/`refund` из замыкания `withTrace` в тело обёртки
- Завершение исполняется после вычисления `outcome` и после возврата `withTrace`
- Обе ветви обязаны его исполнить: ни одна не возвращает результат раньше
- Отказ `settle` или `refund` не отменяет ответ; он пишется на `stderr` с идентификатором строки

**Why перенос обязателен.** `withTrace` возвращает управление первой строкой:
`packages/mcp-server/src/tools/registry.ts:623` — `if (ctx.requestTrace === undefined) return result;`.
`ctx.requestTrace` кладётся в контекст только при наличии движка:
`packages/mcp-server/src/index.ts:235` — подстрока `identity === null ? {} : { requestTrace:`. А
`identity === null` — совпадает с `transport !== 'http'` (`packages/mcp-server/src/index.ts:119-127`),
то есть профиль `local`.

**Why следствие невозможно оставить.** На профиле `local` ни одна строка `client_usage` не покидает
состояния `reserved`, и закрыть её некому: воркфлоу сверки ходит только в Postgres. Это отменяет
R-2.4 и R-3 на той оси, где леджер объявлен пишущимся.

**Why обязательная операция не стоит под охраной необязательной.** `system-architecture.md`
§3.5.2 обосновывает обязательность `ctx.billing` тем, что `ctx.requestTrace` может отсутствовать,
не останавливая трафик. Вызов из `withTrace` подчинял бы первую второй.

Две точки возврата обёртки, через которые проходят обе ветви:
`packages/mcp-server/src/tools/registry.ts:685` — `if (outcome.ok) return withTrace(` и
`packages/mcp-server/src/tools/registry.ts:709` — `return withTrace(`.

**Why отказ завершения пишется, а не глотается.** Прецедент `OD-014-30-6` уже действует рядом:
`packages/mcp-server/src/tools/registry.ts:677` — `request trace: FAILED to record served request`.
Строка `client_usage` — бухгалтерская запись, и её незакрытие называется вслух.

**Файл `packages/mcp-server/src/engine/billing-store.ts`** (MAJOR-C раунда 2, MAJOR-9 раунда 1):

- `refund(rowId, reason)` кредитует баланс только при непустом `RETURNING` условного `UPDATE`
- Нулевой результат условного `UPDATE` делает `refund` no-op целиком, включая баланс
- `settle(rowId)` баланса не трогает: величина списана на резерве
- Докстринг `refund` называет условие кредитования тем же словом, что и шаг 2 резерва

**Why условие обязано быть записано.** Симметричная оговорка для резерва сформулирована буквально:
`docs/architectures/system-architecture.md:4021` — `Only when step 1 inserted a NEW row`. Для
`refund` её нет: `docs/architectures/system-architecture.md:3988` — подстрока
`PLUS crediting`. Асимметрия оставляет прочтение «кредитуем безусловно».

**Why два `refund` по одной строке — штатный путь.** UC-2 ведёт оба ретрая через полный обработчик,
и при отказе оба доходят до завершения. Второй условный `UPDATE` совпадает с нулём строк.
Безусловное кредитование вернуло бы `price_raw` дважды на один дебет.

### Правило позднего исхода (MAJOR-9 раунда 1)

`<исход пришёл после того, как сверка закрыла строку по expired>` → `<строка остаётся refunded;
ответ отдаётся клиенту; расхождение наблюдаемо>`.

Правило выводится из уже принятой формы, а не выбирается заново: `settle` — условный `UPDATE`
с охраной `WHERE state = 'reserved'` (`docs/architectures/system-architecture.md:4278` — подстрока
`Idempotent completion — first completer wins`). По закрытой строке он совпадает с нулём строк.

Наблюдаемый след — два признака, ни один из которых не требует нового словаря событий:

| Признак                                                                                              | Где читается                                      |
| :--------------------------------------------------------------------------------------------------- | :------------------------------------------------ |
| строка `stderr` с идентификатором строки и её состоянием                                             | журнал процесса                                   |
| строка `request_trace` с `outcome='answer'` против строки `client_usage` с `refund_reason='expired'` | соединение по `(principal_id, client_request_id)` |

**Why не новое событие диагностики.** Словарь `diagnostics.event` закрыт восемью значениями
(`data-model.md` §4.5.8). Девятое значение — правка словаря, а не наблюдаемость этой задачи.

**Why строка не перезаряжается вторым резервом.** Ключ дедупликации `(principal_id,
client_request_id)` уникален (`docs/architectures/data-model.md:1740` — `UNIQUE (principal_id,
client_request_id)`). Второй резерв по тому же ключу невозможен по построению хранилища.

**Отвергнутая альтернатива — повторное списание по тому же ключу.** Оно потребовало бы времени в
ключе идемпотентности, что прямо запрещает R-5.1.

### Сверка возвращает кредиты одним оператором

Сегодняшний проект сверки описывает переход тремя колонками
(`docs/architectures/data-model.md:2141` — `Each matched row transitions`), а исполнителем назначен
SQL-узел n8n. `credits_balance_raw` в §4.6.5 не встречается ни разу.

**Why один оператор, а не два узла.** n8n не даёт транзакции между узлами. Пара «узел перехода,
затем узел возврата» оставляет окно, в котором строка закрыта, а кредиты не возвращены.

Форма оператора:

```sql
WITH t AS (
  UPDATE onchain.client_usage
     SET state = 'refunded', refund_reason = 'expired', terminal_at = $1
   WHERE state = 'reserved' AND reserved_at < $2
  RETURNING access_profile_id, price_raw
)
UPDATE onchain.access_profiles p
   SET credits_balance_raw = (p.credits_balance_raw::numeric + s.sum_raw)::text
  FROM (SELECT access_profile_id, SUM(price_raw::numeric) AS sum_raw
          FROM t WHERE access_profile_id IS NOT NULL GROUP BY 1) s
 WHERE p.id = s.access_profile_id;
```

**Why `numeric`, а не `float`.** `numeric` — точный тип Postgres произвольной разрядности. Канон
CLAUDE.md запрещает `Number` на кредитах, и текстовое сравнение читает `'9' > '10'` как истину.

**Why пропуск при NULL в `access_profile_id`.** Локальный принципал профиля доступа не имеет
(R-7.5), и возвращать ему нечего.

**Why возврат вообще нужен под `unlimited`.** Не нужен: баланс на этом режиме не движется. Оператор
пишется ради оси, которую R-7.3 объявляет авторитетной, и ради режима `metered`, который включается
без правки воркфлоу.

### Закрыватель зависшей строки на оси SQLite (MINOR-9 раунда 1)

Воркфлоу сверки ходит только в Postgres. На оси SQLite зависшую строку `reserved` закрывает сам
процесс: при открытии хранилища `BillingStore` переводит строки старше порога в `refunded` с
причиной `expired`.

**Why закрыватель назван, а не подразумевается.** R-3 объявлен тотальной функцией. Ось, на которой
строка не покидает `reserved` никогда, эту тотальность отменяет.

**Why порог берётся константой, а не литералом.** `REPLAY_AND_RECONCILE_CEILING_MS` равен 120 000 мс
и читается и окном реплея (R-5.6), и порогом сверки (R-14.2). Два литерала были бы двумя
источниками одного факта.

## Примечания

Этап 3 (точка перехвата и терминальность резерва), проход `impl`. Зависит от 015-09.

Задача 015-18 создаёт воркфлоу `onchain-billing-reconcile` и пишет строку `retention_runs`. Здесь
объявляется форма оператора, который тот воркфлоу исполняет. Установка воркфлоу требует отдельного
согласия владельца (`deployment.md` §10.6.1).

AC-39 закрывается двумя задачами: состояние строки — здесь, прогон и строка лога — в 015-18.

Предусловие оси Postgres: `STATE_TABLES` (`packages/core/src/pg/state-client.ts:87` —
`export const STATE_TABLES = [`) содержит `client_usage`. Расширение принадлежит задаче 015-03.
Задача 015-10 его не делает; при отсутствии имени `qualify` отвергнет обращение
`UnknownEngineTableError`.

Ветвь `metered` в фазе 0 не исполняется: единственный сеяный профиль несёт
`credits_mode='unlimited'` (R-6.2). Тесты 4–7 работают на профиле, заведённом самим тестом.

Задача — носитель риска превышения оценки вдвое: правило касается четырёх мест — обёртка, две оси
хранилища и внешний исполнитель сверки.
