# Задача 014.15: перехват в обёртке `defineTool` `[LOGIC]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Разместить резолв принципала в обёртке `defineTool` — до `resolve()` и до кеша — и удержать
принципала вне ключа кеша, вне stderr и вне `_meta`.

**Why до кеша, а не после.** Владелец объявил бизнес-модель: платят оба клиента, даже если второй
получил ответ из кеша (`docs/TASK.md:530`). Перехват после кеша оставляет обслуженные из кеша
запросы неучтёнными.

Архитектура называет точку прямо: `system-architecture.md` §3.4.3, «The interception point is

Замер по репозиторию на 2026-08-13:

| Величина                                                           | Значение                                            |
| :----------------------------------------------------------------- | :-------------------------------------------------- |
| Файлов в `packages/mcp-server/src/tools/`                          | 26                                                  |
| Из них вызывают `resolveCapability`                                | 18                                                  |
| Файлов-обработчиков тулов                                          | 20                                                  |
| Обработчиков, не вызывающих `resolveCapability`                    | 2 — `ping.ts`, `list-chains.ts`                     |
| Мест в `packages/mcp-server/src`, вызывающих `server.registerTool` | 1 — `packages/mcp-server/src/tools/registry.ts:437` |

`packages/mcp-server/src/tools/registry.ts` импортирует из `resolve-capability.js` только типы
`CacheMeta`, `MergedCacheMeta` и `TimingMeta` (`packages/mcp-server/src/tools/registry.ts:6`),
функцию не вызывает.

**Why путь пишется целиком.** Коротким именем `registry.ts` в репозитории называются три разных
файла: `packages/core/src/adapters/registry.ts`, `packages/core/src/chain/registry.ts` и этот.

**Why обёртка `defineTool`.** Это единственное место в `src`, которое трогает
`server.registerTool`, поэтому хук пишется один раз и не может быть забыт ни двадцать первым, ни
двадцать вторым тулом задачи 014-32b.

**Why не `resolve-capability.ts`.** Два обработчика в этот файл не заходят: `onchain_ping` и
`onchain_list_chains` отвечают синхронно и способность не резолвят. Хук в этом файле их не
наблюдает.

**Why не граница адаптера.** Чтение кеша выполняется внутри `CapabilityRegistry.resolve()` — шаг 3
порядка гейтов §3.2, выше `adapter.isAvailable()` и выше гейта бюджета. Хук ниже кеша наблюдает
только промахи.

**Why попадание в кеш пропустить нельзя.** Попадание в кеш — тарифицируемый запрос: платят оба
клиента, второй обслужен из кеша. Хук ниже кеша недосчитал бы те запросы, на которых построена
модель маржи.

**Why различие «кеш или вендор» доступно здесь.** R-27.2 требует записать, откуда пришёл ответ. Это
различие делает то, что работает до кеша и читает результат после.

### Почему принципал вне ключа кеша

Кеш разделяется между принципалами. Принципал в ключе кеша даёт каждому свою копию, и второй клиент
стоит нам вендорского вызова, которого можно было не делать.

### Где принципал не появляется

- В `args_hash` — состав ключа проверяется гейтом (R-5.1, AC-8)
- В stderr — R-5.3
- В `_meta` — R-5.4

**Why не в stderr.** Идентификатор принципала на stderr связывает строку лога с плательщиком без
разграничения доступа к логу. Строка события несёт `diagnostics.id`, а принципал читается из
таблицы.

### Непроверенный путь не доходит ни до кеша, ни до резолва

Проверка выполняется в middleware, до вызова `transport.handleRequest`. Обработчик тула не
запускается, `resolve()` не вызывается, счётчики `CacheStore` и `fetchImpl`, которые читает AC-3,
остаются нулевыми. Отказ выражен статусом транспорта, а не результатом тула (R-26.2).

### Принципал резолвится на каждый запрос

Результат проверки не кешируется — ни положительный, ни отрицательный.

**Why не на время сессии.** AC-26 требует отказать отозванному токену на следующем запросе.
Удержанный результат оставил бы отозванный токен рабочим до закрытия сессии по бездействию — до
`900_000` мс по §3.4.2. Принятая цена: одно индексное чтение `api_tokens` на запрос.

## Тест-кейсы

### Сквозные тесты

1. **TC-E2E-01:** вызов без принципала не доходит до `resolve()` и до кеша
   - Входные данные: запрос без заголовка `Authorization`; счётчики на `CacheStore` и `fetchImpl`
   - Ожидаемый результат: оба счётчика — ноль (AC-19)
2. **TC-E2E-02:** `onchain_ping` по HTTP проходит через обёртку
   - Входные данные: один вызов `onchain_ping` с валидным токеном
   - Ожидаемый результат: обработчик получил `ctx.principal` с `transport = 'http'`
3. **TC-E2E-03:** отозванный токен отвергается на следующем запросе
   - Входные данные: два запроса одним токеном, отзыв между ними
   - Ожидаемый результат: первый обслужен, второй отвергнут (AC-26)

### Модульные тесты

1. **TC-UNIT-01:** `args_hash` не изменяется при смене принципала
   - Входные данные: два принципала, равные аргументы
   - Ожидаемый результат: хеши совпадают (AC-8)
2. **TC-UNIT-02:** принципал не встречается в stderr
   - Входные данные: перехват `process.stderr.write` на полном вызове тула
   - Ожидаемый результат: `principalId` в записанных строках отсутствует
3. **TC-UNIT-03:** принципал не встречается в `_meta` ни при роли `admin`, ни при роли `user`
4. **TC-UNIT-04:** гейт состава ключа красный на внесённом принципале
   - Входные данные: `deriveArgsHash` с принципалом в аргументах
   - Ожидаемый результат: гейт падает с указанием поля
5. **TC-UNIT-05:** `server.registerTool` вызывается из одного места
   - Входные данные: обход исходников `packages/mcp-server/src`
   - Ожидаемый результат: одно вхождение, в `registry.ts`
6. **TC-UNIT-06:** каждый зарегистрированный тул получает принципала
   - Входные данные: обход `toolSpecs`, число тулов не зашито
   - Ожидаемый результат: `ctx.principal` присутствует в каждом вызове

### Регрессионные тесты

- Попадания в кеш между двумя принципалами сохраняются: второй читает запись первого
- Снимок `tools/list` не изменился
