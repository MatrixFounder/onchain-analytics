# Задача 014.02: интерфейсы репозиториев движка и стабы `[STUB]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети
- UC-3 — оператор запускает локально

<!-- contract:goal -->

## Цель задачи

Объявить пять интерфейсов репозиториев в пакете `mcp-server` и стабы под ними. Стабы возвращают
фиксированные значения; тесты проверяют форму и проходят на стабах.

**Why миграции сюда не входят.** Объявление таблиц вынесено в задачи 014-35 (Postgres), 014-36
(SQLite) и 014-37 (засев первого администратора). Текущая задача объявляет форму доступа к таблицам
и не создаёт ни одной из них.

**Why пакет `mcp-server`, а не `core`.** `security.md` §7.5.1: проверки живут в пакете `mcp-server`,
рядом с транспортом, которому они нужны. `packages/core` не получает знания о токенах, ролях и
заголовках. SQL, называющий таблицы личности, пишется из того же пакета.

## Описание изменений

### Новые файлы

- `packages/mcp-server/src/auth/access-profile-store.ts` — интерфейс чтения `access_profiles` и стаб
- `packages/mcp-server/src/auth/user-store.ts` — интерфейс и стаб
- `packages/mcp-server/src/auth/token-store.ts` — интерфейс и стаб
- `packages/mcp-server/src/auth/index.ts` — реэкспорт
- `packages/mcp-server/src/engine/request-trace-store.ts` — интерфейс и стаб
- `packages/mcp-server/src/engine/diagnostics-store.ts` — интерфейс и стаб
- `packages/mcp-server/src/engine/index.ts` — реэкспорт
- `packages/mcp-server/test/engine-store-contracts.test.ts` — тесты формы

**Why каталог `auth/`.** Архитектура называет в нём два файла дословно:
`packages/mcp-server/src/auth/principal.ts` (`system-architecture.md` §3.4.3) и
`packages/mcp-server/src/auth/access-profile.ts` (`security.md` §7.5.3a). Хранилища личности лежат
рядом с ними.

**Why два стора вне `auth/`.** `request_trace` и `diagnostics` — записи о работе, а не таблицы
личности (`data-model.md` §4.5). Оба тоже пишутся из `mcp-server`: `deployment.md` §10.2.1 называет
`onchain.request_trace` и `onchain.diagnostics` среди SQL вне `packages/core/src`.

### Кто дополняет объявленные интерфейсы

| Файл | Кто объявляет методы | Кто заменяет стаб |
| :--- | :--- | :--- |
| `auth/access-profile-store.ts` | 014-02 | табличный поставщик после T-014 |
| `auth/user-store.ts` | 014-06 | 014-07 |
| `auth/token-store.ts` | 014-06 | 014-07 |
| `engine/request-trace-store.ts` | 014-02 | 014-30 |
| `engine/diagnostics-store.ts` | 014-02 | 014-27 |

Общий механизм доступа к Postgres — квалифицированный схемой SQL через клиент записи — даёт задача
014-03 файлом `packages/mcp-server/src/engine/pg-engine-store.ts`. Каждая замена стаба идёт поверх
него. Методов репозиториев задача 014-03 не реализует.

**Why механизм назван рядом с таблицей.** Столбец «кто заменяет стаб» перечисляет четырёх владельцев.
Без имени общего механизма каждый из них завёл бы свой путь к базе, и квалификация схемы проверялась
бы в четырёх местах.

**Why табличный поставщик профиля назван отдельно.** T-014 поставляет значения профиля из умолчаний
в коде (R-13.3), а `access-profile-store` — цель второго поставщика. Гейт R-13.3a задачи 014-04
разрешает чтение семи полей профиля читателю, его поставщику, их тестам и двум названным местам
применения.

**Why журнал доступа не получает шестого стора.** `access_audit` достигается методом `appendAudit`
хранилища токенов (014-06). Пять репозиториев остаются пятью.

### Что не меняется

- `packages/core/src/index.ts` — реэкспорт не добавляется
- `createServer` сохраняет форму `createServer(deps: CreateServerDeps): McpServer`

**Why форма фабрики названа здесь.** `security.md` §7.5.1 держит её решением владельца
(`docs/TASK.md:84`). Задача 014-02 не добавляет в `CreateServerDeps` ни одного поля.

### Форма значений, обязательная к соблюдению

Интерфейсы объявляются под колонки `data-model.md` §4.5 и канон DB-SCHEMA §1:

- время — epoch-ms UTC целым числом, без функций времени БД в логике
- идентификаторы генерирует приложение: ULID строкой
- JSON переносится строкой и разбирается в коде
- точные значения — строками: `credits_balance_raw`, `value_raw`
- `access_audit` и `request_trace` — только на добавление
- `request_trace` несёт ключ дедупликации `(principal_id, client_request_id, received_at)`
- `diagnostics` пишет `detail_json` полной операторской отрисовкой (R-31.1)

**Why точные значения строками.** Кредиты — точные целые. Число JS теряет точность за 2^53, и
`data-model.md` §4.5.3 объявляет `credits_balance_raw` как `TEXT` по этой причине.

**Why ключ дедупликации назван на уровне интерфейса.** `data-model.md` §4.5.7 объявляет
`UNIQUE (principal_id, client_request_id, received_at)`. Стаб, не знающий ключа, принял бы повтор
запроса за вторую запись.

## Тест-кейсы

### Модульные тесты
1. **TC-UNIT-01:** каждый стаб реализует объявленный интерфейс
   - Входные данные: вызов каждого метода стаба
   - Ожидаемый результат: компиляция проходит, метод возвращает объявленную форму
2. **TC-UNIT-02:** баланс профиля доходит до вызывающего строкой
   - Входные данные: стаб, отдающий значение больше 2^53
   - Ожидаемый результат: тип поля — строка, значение совпадает посимвольно
3. **TC-UNIT-03:** поля времени объявлены числом epoch-ms
   - Входные данные: строка ISO в поле `receivedAt` под `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает присваивание
4. **TC-UNIT-04:** запись следа несёт ключ дедупликации
   - Входные данные: две записи с одинаковыми `principalId`, `clientRequestId` и `receivedAt`
   - Ожидаемый результат: стаб называет пару как повтор по объявленному ключу
5. **TC-UNIT-05:** событие диагностики объявлено из закрытого словаря
   - Входные данные: значение `auth.denied` в поле `event` под `@ts-expect-error`
   - Ожидаемый результат: компиляция отвергает присваивание

### Регрессионные тесты
- `pnpm test`, `pnpm typecheck`, `pnpm build`
- Поиск `token`, `role`, `Authorization` по `packages/core/src` не даёт новых совпадений

## Примечания

Стаб остаётся стабом до задач 014-07, 014-27 и 014-30; стаб `access-profile-store` — до табличного
поставщика после T-014. Тег `[STUB]` в заголовке — признак, по которому ревью отличает незавершённую
пару.

Задача больше не корень для миграций. Задачи 014-35, 014-36 и 014-37 от неё не зависят и идут
параллельно. Задача 014-03 даёт общий механизм доступа, зависит и от 014-02, и от миграций и стабов
не заменяет.
