# Задача 012-6 — дескриптор политики + реестр классов; шаг 2 валидации после шага 1

**Эпик:** E-1 (политика достаточности ответа, D2) · **Требования:** R-133, R-134, R-135 ·
**Критерии приёмки:** AC-1, AC-2, AC-3 · **Фаза:** 6 из 10 · **Зависимости:** 012-4

## Use Case Connection

- **UC-2** — маршрут ссылается на незарегистрированный `kind` политики: сборка/старт процесса падает
  с сообщением, называющим маршрут и `kind`, **до** любого реального вызова тула. Провал, который
  надо исключить: ошибка проявляется только на первом запросе к этому конкретному маршруту в проде,
  спустя недели после деплоя.

<!-- contract:goal -->

## Цель задачи

Заменить литеральную функцию `CapabilityRoute.isSatisfying` (`types.ts:121`) сериализуемым
дескриптором `{ kind, ...params }`, разрешаемым против реестра классов в коде ядра, и перенести
проверку `kind` на **конструирование реестра**.

**Поведение не меняется ни на одном из 21 маршрута** — но утверждение об эквивалентности
**ограничено фикстурным набором TASK-008**, а не безусловно, и вот почему.

**Одно поле расходится намеренно (найдено ревью плана 2, проверено).** Живой литерал проверяет
`typeof label.name === 'string'` (`providers.config.ts:100`) — то есть `name: ''` его
**удовлетворяет**. Семантика класса `someElementHasAny` («непустое значение по одному из полей»,
TC-UNIT-02) считает `''` **пустым**, и не удовлетворяет. Вход представим: `EntityLabelSchema.name`
— это `z.string().max(256).optional()` **без** `.min(1)`.

**Решение: ужесточение намеренное, и объявляется таковым.** Запись с пустым `name` — это та
бессодержательная запись, о которой и написан H-1: непустой массив, в котором смотреть не на что.
Принять её за достаточный ответ значило бы заслонить Nansen на весь TTL — тот самый дефект.
Следствия для формулировок: «бит-в-бит тот же вердикт» в Цели, R-133 и AC-2 читается **на фикстурном
наборе TASK-008**, а общая эквивалентность **не утверждается**; новый вердикт для `name: ''`
закрепляется отдельным кейсом (TC-UNIT-03a).

## Описание изменений

### Новые файлы

#### `packages/core/src/adapters/policy.ts`

```ts
export type PolicyDescriptor =
  | { kind: 'any' } // умолчание; отсутствие поля означает его
  | { kind: 'someElementHasAny'; fields: string[] };
```

| `kind`              | Предикат                                                                         | Кого заменяет                                                       |
| ------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `any`               | всегда `true`                                                                    | 20 из 21 маршрута, не несущих политики сегодня                      |
| `someElementHasAny` | массив, и **хотя бы один** элемент имеет непустое значение по одному из `fields` | литеральный предикат `entity.labels` (`providers.config.ts:94-104`) |

- Словарь классов — **словарь имён, а не движок политик**. Докстринг `types.ts` уже прямо запрещает
  выращивать здесь движок (веса, частичные слияния, многоисточниковый сбор — работа роутера), и
  ADR-002 §«Что отклонено» п.7 отвергает ближайший промах (конфигурируемый маппинг полей) на том же
  основании.
- **Третий класс не заводится.** У него нет потребителя: первый появится вместе с D5/T-013
  («собранного достаточно» — другая семантика).
- **Класс НЕ называется и не алиасится `nonEmpty`** — ни в имени экспорта, ни в комментарии, ни в
  тесте. Это не вкусовщина: буквальный `nonEmpty` воспроизводит **H-1** дословно. Blockscout часто
  отвечает **непустым массивом пустых по содержанию записей**. Предикат вида `array.length > 0`
  счёл бы такой ответ достаточным и заслонил бы Nansen на весь TTL.

#### `packages/core/test/blockscout-fallback.test.ts` — **новый объём, найденный ревью плана**

Файл ставит `isSatisfying` на **маршрутных литералах** в двух местах.

**Точная формулировка вместо «compile break»:** оба литерала присваиваются локальным
константам без аннотации типа. Поэтому строгая проверка лишних свойств (TS2353) на них **не
срабатывает** — упало бы только присваивание свежего литерала прямо в позицию
`CapabilityRoute[]`. То есть компилятор здесь **не** сторож: поле молча стало бы мёртвым, а
а у сторожей M-1/M-2 не осталось бы входа, на котором они падают. Обнаружение держится на трёх ACs
(grep-гейт `nonEmpty`, мутация «убрать try/catch», проверка падения), а не на сборке. Правка обязательна ровно поэтому —
не потому, что иначе «не соберётся».

- **`:315`** — реальный предикат маршрута B в тесте парности «адаптер ↔ политика **своего**
  маршрута» (M-2). Конвертируется в `policy: { kind: 'someElementHasAny', fields: ['labels'] }`.
  Поле — именно `labels`, а не полный набор `['name','tags','labels']`. Комментарий теста
  объясняет, что предикат обязан **проваливать** пустой ответ blockscout, который является массивом
  из **одной** записи без меток. На нём `length > 0` истинен. Без этого различения
  мутацию «применить политику маршрута B к адаптеру маршрута A» обнаружить нельзя. Вердикт на тех же
  фикстурах обязан остаться прежним.
- **`:269`** — намеренно **бросающий** предикат, сторож fail-open M-1. Этот кейс **переезжает в
  отдельный файл** (следующий раздел) и из `blockscout-fallback.test.ts` **удаляется**. После
  переезда этот файл политику **не мокает вовсе** — в нём остаётся ровно одна правка, конвертация
  `:315`.

#### Новый файл `packages/core/test/policy-fail-open.test.ts` — потому что `vi.mock` файл-глобален

**Что нашло ревью плана 2 (проверено).** `blockscout-fallback.test.ts:5` импортирует **настоящие**
`routes` и конструирует реестр над `[...routes]` на `:107` и `:236`. Мок модуля поднимается на весь
**файл**, поэтому `vi.mock('../src/adapters/policy.js')` внутри него сделал бы предикат бросающим
для **всех** тестов файла, а fail-open превратил бы каждый бросок в «ответ достаточен». Последствия
измеримы: упали бы `:135`, `:168`, `:186`, `:212` — четыре кейса, которым нужен **настоящий**
вердикт `false`, включая TC-INT-04 (регрессия H-1). И хуже: новый TC-INT-07 (парность M-2) стал бы
проходить **вакуумно** — fail-open удовлетворяет его, ни разу не спросив политику. Один
компиляционный слом превратился бы в четыре рантайм-падения плюс тавтологию.

**Решение: сторож fail-open живёт в собственном файле**, где мокать модуль политики безопасно,
потому что больше в нём ничего нет. Файл — `packages/core/test/policy-fail-open.test.ts`, владелец —
эта задача (§0.4 плана).

**Что переезжает вместе с кейсом — пять помощников, и судьба каждого названа** (иначе §0.4
получает необъявленное расширение: `blockscout-fallback.test.ts` перестал бы быть файлом с одной
правкой).

| Помощник                | Где сейчас                                                    | Судьба                                                   |
| ----------------------- | ------------------------------------------------------------- | -------------------------------------------------------- |
| `isolatedThrottle`      | **уже общий модуль** `./helpers/isolated-throttle.js` (`:11`) | импортируется новым файлом — ничего не делаем            |

| `nansenSpy()`           | локальная фабрика `:41`                                       | **дублируется**                                          |
| `MemoryCacheStore`      | локальный класс `:77`                                         | **дублируется**                                          |

**Дублирование, а не извлечение — сознательно.** Извлечение в общий модуль тронуло бы
`blockscout-fallback.test.ts` сверх одной конвертации `:315` и расширило бы запись §0.4; ставка —
~40 строк тестового кода против размывания заявленного радиуса задачи. Если общий модуль когда-то
понадобится третьему файлу, извлечение сделает **та** задача, объявив радиус.

**Что именно бросает — сказано однозначно, потому что это две разные вещи.** Мок подменяет
**словарь классов**; его запись `someElementHasAny` — это функция, которая **возвращается успешно**
при резолюции на конструировании и **бросает в момент ВЫЗОВА предиката**. Если бы бросала сама
фабрика/резолюция, упало бы **конструирование реестра**, и наблюдать fail-open было бы уже не на
чём — сторож проверял бы совсем другое свойство.

#### Чем заменяется бросающий предикат — решение задачи, а не «искусственно»

**Проблема.** После 012-6 маршрут несёт только `{kind}`, разрешаемый против **фиксированного**
словаря в `policy.ts`. Ни `any`, ни `someElementHasAny` бросить не могут; у словаря нет точки
внедрения зависимости (пять параметров конструктора —
`routes, adapters, cache, chains, manifests`); `satisfies()` (`registry.ts:238-254`) — замыкание
внутри `resolve()`, снаружи недостижимое. **Самый дешёвый способ получить зелёный прогон —
удалить сторож M-1**, то есть ровно тот исход, ради запрета которого написан §0.3 плана.

**Решение: `vi.mock('../src/adapters/policy.js')`** с фабрикой, чей `someElementHasAny` бросает.
Мок поднимается выше импортов, поэтому действует и на резолюцию предиката **на конструировании**.

**Отклонённая альтернатива — шестой инжектируемый параметр конструктора (карта классов политики).**
`data-model.md` §M-6 прямо решает, что инжектируется **только** карта манифестов, а словарь классов
остаётся модульным. Заводить шестой параметр — переигрывать одобренное архитектурное решение мимо
архитектора. `vi.mock` не добавляет ни байта к продовой поверхности.

**Но обоснование M-6 этой находкой опровергнуто.** Оно гласит: «нет сценария, где тесту нужен
ДРУГОЙ словарь политик, — только маршрут, ссылающийся на `kind`, которого в реальном нет». Вот этот
сценарий: сторожу fail-open нужен предикат, который **бросает**, а такого `kind` в реальном словаре
нет и быть не должно. Контрпример записывается в `open-questions.md` (012-10), а не обходится молча.

## Тест-кейсы

### Юнит

- **TC-UNIT-01** — `any` на любом входе (пустой массив, `null`, объект, строка) → `true`.
- **TC-UNIT-02** — `someElementHasAny({fields:['name','tags','labels']})`, таблица кейсов:
  - не массив → `false`;
  - пустой массив → `false`;
  - массив записей, у которых все три поля пусты (`''`, `[]`, `null`, `undefined`) →
    **`false`** (это и есть H-1);
  - массив, где хотя бы у одной записи непусто `name` → `true`;
  - то же для `tags`;
  - то же для `labels`.
- **TC-UNIT-03** (главный, R-133b/AC-2) — эквивалентность **на фикстурном наборе TASK-008**: на
  каждом ответе Blockscout из этого набора старый литеральный предикат и новый дескриптор дают
  **одинаковый** вердикт. Реализация: старый предикат вносится в тест копией и прогоняется рядом.
  Расхождение хотя бы на одном кейсе — падение. Заголовок и докстринг теста обязаны сказать
  «на этом наборе», а не «всегда»: безусловная эквивалентность **ложна**, см. следующий кейс.
- **TC-UNIT-03a** (Med-3 — намеренное ужесточение) — запись `{ name: '' }` (и только она,
  без `tags`/`labels`): **старый** предикат → `true` (`typeof '' === 'string'`), **новый** →
  `false`. Кейс закрепляет **новый** вердикт как правильный и называет причину: пустое `name` — это
  и есть бессодержательная запись, о которой написан H-1. Тест существует затем, чтобы расхождение
  было **зафиксированным решением**, а не сюрпризом, который потом «починят» ослаблением класса.
- **TC-UNIT-04** — отсутствие `policy` эквивалентно `{ kind: 'any' }`.

### Гейты

- **TC-GATE-01** (AC-3; переформулирован — прежняя редакция противоречила самой задаче).
  Запрет пристёгнут к **идентификаторам**: имя экспорта, ключ словаря классов, алиас, имя
  переменной/типа, заголовок теста. Он **не** пристёгнут к прозе. Сегодняшнее единственное
  вхождение в `packages/*/src` — `adapters/types.ts:106`, **внутри докстринга**. Этот докстринг
  задача переписывает, и он **обязан продолжать объяснять**, почему класс так не называется
  (R-134c требует ровно этого объяснения). Буквальный запрет токена сделал бы две инструкции
  задачи взаимоисключающими, а «починка» состояла бы в удалении объяснения — то есть в потере
  причины, по которой имя запрещено.
  **Что выигрывает:** объяснение остаётся, идентификатор запрещён. Проверить падение: временно ввести
  `export const nonEmpty = …` (и отдельно — алиас `const nonEmpty = someElementHasAny`), увидеть
  красный на обоих, откатить.

### Интеграционные

- **TC-INT-01** (R-135b/AC-1) — реестр над тестовой таблицей маршрутов с `policy: { kind: 'bogus' }`
  бросает `UnregisteredPolicyClassError` **на конструировании**, до первого `resolve()`. Тест
  подаёт **свою** карту манифестов, покрывающую его синтетическую capability, чтобы шаг 1 прошёл
  молча и упал именно шаг 2.
- **TC-INT-02** — порядок шагов фиксирован: маршрут, у которого **и** нет манифеста, **и** плохой
  `kind`, даёт `MissingCapabilityManifestError`, а не `UnregisteredPolicyClassError`. Это то, что
  позволяет каждому негативному тесту ломать ровно одну вещь.
- **TC-INT-03** (R-135d) — реальные 21 маршрут проходят валидацию; поведение не изменилось.
- **TC-INT-04** (H-1, регрессия) — `entity.labels` на записанной фикстуре Blockscout-с-пустыми-тегами
  по-прежнему **проваливается к Nansen**, а не завершает обход. Тот же кейс, что закрывал H-1 в
  TASK-008, теперь идёт через дескриптор.
- **TC-INT-05** — политика применяется к **кеш-хиту** так же, как к свежему результату.
- **TC-INT-06** (переписан; живёт в **`policy-fail-open.test.ts`**, не в
  `blockscout-fallback.test.ts`) — fail-open сохранён. Бросающий предикат получается
  **`vi.mock('../src/adapters/policy.js')`**, где запись `someElementHasAny` **резолвится успешно**,
  а **бросает при вызове** (если бы бросала резолюция, упало бы конструирование, и наблюдать было бы
  нечего). Механизм назван, слово «искусственно» убрано — оно и было той дырой, через которую тест
  «чинился» бы удалением сторожа. Утверждается ровно то, что утверждает сегодняшний
  `blockscout-fallback.test.ts:265-297`: на **обоих** путях (свежий и кеш-хит) отвечает
  `blockscout`, платный провайдер **не вызван ни разу**, в stderr одна строка. Мутация «убрать
  try/catch из `satisfies()`» обязана уронить именно этот тест.
  Файл конструирует **свою** маленькую таблицу маршрутов, а не `[...routes]`: импорт настоящих
  `routes` вернул бы в него ровно ту связанность, ради разрыва которой он и заведён.
- **TC-INT-07** — парность M-2 после конвертации `:315`: политика маршрута B не судит адаптер
  маршрута A. Пустой ответ blockscout (массив из одной записи без меток) принимается маршрутом A
  как есть; тот же ответ не удовлетворил бы политику маршрута B — что и делает мутацию обнаружимой.

- [ ] `isSatisfying` заменён на `policy?: PolicyDescriptor`; литеральных функций в маршрутах не
      осталось
- [ ] Ровно два класса; третий не заведён; ни одного вхождения `nonEmpty` в коде и тестах
- [ ] `entity.labels` даёт тот же вердикт **на фикстурном наборе TASK-008** (TC-UNIT-03), и это
      ограничение сказано вслух; расхождение на `name: ''` зафиксировано как **намеренное
      ужесточение** отдельным кейсом (TC-UNIT-03a), а не оставлено необъявленным
- [ ] Незарегистрированный `kind` роняет **конструирование**; сообщение называет и capability, и `kind`
- [ ] Порядок валидации «манифест → `kind`» зафиксирован тестом, а не только докстрингом
- [ ] `satisfies()` не изменил поведения (fail-open, stderr, применение к кеш-хитам)
- [ ] Оба маршрутных литерала в `blockscout-fallback.test.ts` обработаны: `:315` конвертирован
      на месте, `:269` **вынесен** в `policy-fail-open.test.ts`; задача заканчивается **зелёным**
      прогоном, а не компиляционной ошибкой
- [ ] `blockscout-fallback.test.ts` **не мокает** модуль политики — иначе четыре кейса (`:135`,
      `:168`, `:186`, `:212`, включая регрессию H-1) падают, а TC-INT-07 проходит вакуумно
- [ ] Сторож fail-open M-1 **сохранён и работает**: бросающий предикат производится названным
      механизмом (`vi.mock`), причём бросок происходит **при вызове предиката**, а не при его
      резолюции
- [ ] Мутация «убрать try/catch из `satisfies()`» роняет TC-INT-06
- [ ] Контрпример к `data-model.md` §M-6 записан для 012-10, а не обойдён молча
- [ ] Докстринг `types.ts` больше не помечает механизм PROVISIONAL
- [ ] Полный набор гейтов §0.5 плана зелёный

## Заметки

- Порядок 012-4 → 012-6 выбран так, чтобы конструктор писался **сразу в финальном порядке шагов**.
  Иначе шаг 1 пришлось бы вставлять перед уже написанным шагом 2, а негативные тесты —
  переписывать под новую карту манифестов.
- ADR-002 §«Revisit when» упоминает `nonEmpty` как историческое имя — это **документ**, а не код и
  не тест; grep-гейт AC-3 умышленно ограничен `packages/*/src` и `packages/*/test`, чтобы не
  требовать переписывания истории решения.
