# Задача 013-4 — Обход слияния: дедуп, ранговый выбор, поадаптерный кеш, политика за участника

**Требования:** [R-161], [R-165], [R-166], [R-167], [R-182] · **Эпик:** E-1 ·
**Критерии приёмки:** AC-23, AC-28, AC-29, AC-30, AC-44, AC-47 · **Фаза:** 4 из 10 ·
**Зависимости:** 013-2, 013-3

## Use Case Connection

- **UC-11** — оба источника отвечают с пересечением по `identities_total`. Слитый ряд несёт метку
  один раз за час. Провал, который надо исключить: дубликат точки от обоих источников либо потеря
  метрик, которые есть только у второго участника.
- **UC-18** — ревьюер видит две разные метки в слитом ответе `privacy_pool`. Обе точки
  присутствуют раздельно. Провал, который надо исключить: слияние выбирает одну метку и отбрасывает
  вторую.

<!-- contract:goal -->

## Цель задачи

Построить цикл слияния внутри `resolve()` так, чтобы точки участников объединялись по ключу
`(metric, asset, ts)` с победой старшего по рангу, кеш оставался поадаптерным, а порядок опроса
совпадал с существующим правилом траты.

## Описание изменений

### `packages/core/src/adapters/registry.ts` — ветвление

После построения `plan` проверяется, несёт ли хотя бы один совпавший маршрут `merge: true`. Да —
исполняется цикл слияния; нет — существующий цикл, байт в байт. Предшествующий порядок не меняется:
GATE 2 (`:669-682`) → единый `effectiveDeadlineAtMs` (`:497-531`) → `plan` (`:551-563`).

### Что цикл слияния переиспользует БЕЗ правок

Пре-чек дедлайна (`:716-724`), проверка регистрации адаптера (`:726-737`), пропуск по `chainSupport`
(`:743-745`), `isAvailable()` (`:747-752`), чтение кеша вместе с отрицательной записью (`:756-788`,
`:790-793`), триада `fetch`/`normalize`/`cache.set` (`:795-857`, `:859-882`).

Отличие ровно одно: ранние `return withDiagnostics(...)` на `:789` и `:858` заменяются шагом
«накопить и продолжить». Цикл слияния не возвращает результат в середине обхода.

### Дедуп и разрешение конфликта

- Точки вкладчиков вставляются в `Map` с ключом `` `${metric}\0${asset}\0${ts}` `` **только при
  отсутствии ключа**. Участники обходятся в порядке ранга, то есть в порядке `plan`.
- Победитель конфликта — первый по рангу; проигравшая точка отбрасывается целиком.
- `value_raw` на этом пути не читается вовсе. Ни `Number(...)`, ни `BigInt`, ни строковое сравнение
  значений не нужны: решает ранг.
- Слияние никогда не вычисляет среднее, сумму или другую производную величину.

### `sources` и `source`

- `sources` — вкладчики: участники, чьи точки присутствуют в `result`. Опционально, отсутствует,
  когда пусто.
- `source` — старший по рангу вкладчик. Когда вкладчиков нет вовсе, `source` — старший по рангу
  ответивший, чтобы поле не стало пустой строкой (AC-47).
- `perSourceCache` несёт по записи на каждого ОТВЕТИВШЕГО участника, включая того, чей ответ не
  дал точек (решение `013-3`: факт кеша — факт об ответе, не о вкладе).
- Агрегатное `cache` равно `'hit'` только когда каждая запись `perSourceCache` — `'hit'`.

### Политика за участника (`OQ-T013-4`)

Тот же `satisfies(policy, value, adapterId)` применяется к кешированному и к свежему ответу
участника. Удовлетворивший становится вкладчиком; неудовлетворивший записывается в `tried`, не
входит в `sources`, не считается отказом и не попадает в `missingSources`.

**Запасной ответ `unsatisfying` на слитом пути не применяется.** Если политику не удовлетворил
никто, возвращается ветка (a) с пустым `sources` — пустой слитый успех. Возврат сырого ответа одного
участника расслитил бы ровно тот ответ, который запрошен как слитый.

### Кеш

`cache.set()` вызывается ровно по разу на каждого участника, ответившего с сети. Попадание из кеша
`cache.set()` не вызывает. Слитый массив собирается в памяти и никогда не пишется как запись кеша.

### Докстринг механизма

Цитирует D5 про порядок адаптеров как правило траты (R-166(c)) и называет выбранное место оценки
политики — за участника (R-182(a), AC-44).

### Фазы

- **Фаза 1.** Ветвление и каркас цикла: участники обходятся, результаты накапливаются, ответ всегда
  собирается как слитый успех. Тесты дедупа, кеша и порядка пишутся сразу и красные.
- **Фаза 2.** Дедуп, ранг, `sources`/`source`/`perSourceCache`, политика за участника.

## Тест-кейсы

### Новый файл `packages/core/test/registry.merge.test.ts`

- **TC-INT-01** — два участника пишут `identities_total` за один и тот же час → в слитом ряду одна
  точка, от старшего по рангу. Fails when вставка в `Map` перезаписывает существующий ключ.
- **TC-INT-02** — точки с несовпадающим `metric` присутствуют обе, каждая под своей меткой. Fails
  when ключ дедупа строится без `metric`.
- **TC-INT-03** — ключ не включает `source`, `height`, `valueNum`: две точки, различающиеся только
  ими, схлопываются в одну. Fails when ключ расширен лишним полем.
- **TC-INT-04** — конфликт на `value_raw` > 2^53: выбранное значение совпадает побитово с исходной
  строкой старшего по рангу. Фикстура синтетическая — сегодня такой конфликт недостижим на боевых
  данных, тест защищает механизм.
- **TC-INT-05** — оба участника промахнулись мимо кеша: `cache.set()` вызван дважды, по разу на
  адаптер, без агрегатного ключа.
- **TC-INT-06** — один промах, одно попадание: `cache.set()` вызван один раз.
- **TC-INT-07** — оба попадания: `cache.set()` не вызван ни разу.
- **TC-INT-08** — маршрут с одним бесплатным и одним платным адаптером: платный опрошен не раньше
  бесплатного. Тест конструирует `CapabilityRegistry` напрямую и не зовёт
  `assertMergeParticipantsAreFree`. Fails when реализация сортирует участников по состоянию бакета
  лимитера вместо тарифа.
- **TC-INT-09** — `sources` содержит только вкладчиков: участник, ответивший пустым массивом, в нём
  отсутствует, а `source` называет того, чьи точки в ответе.
- **TC-INT-10** — вкладчиков нет (все ответили пусто): `sources` отсутствует, `source` не пустая
  строка.
- **TC-INT-10a** — композиция UC-19: первый ответил пусто ИЗ КЕША, второй внёс точки с сети.
  `perSourceCache` несёт обе записи, `sources` — только вторую, агрегат `cache` — `'miss'`.
- **TC-INT-11** — политика маршрута не удовлетворена одним участником: он в `tried`, не в `sources`,
  не в `missingSources`; результат — слитый успех из второго.
- **TC-INT-12** — политика не удовлетворена никем: пустой слитый успех, запасной ответ
  `unsatisfying` не возвращается.
- **TC-INT-13** — эквивалентность для двух боевых маршрутов: результат одинаков независимо от того,
  оценивается ли политика за участника или за целое, потому что оба маршрута несут умолчание
  `{kind:'any'}` (R-182(c)).

### Регрессионные

## Критерии приёмки

- [ ] Ключ дедупа — ровно тройка `(metric, asset, ts)`; дедуп сработал на реально пересекающейся
      паре `identities_total`
- [ ] Конфликт решается выбором точки целиком по рангу; `value_raw` не читается через `Number`
- [ ] `cache.set()` — по разу на сетевого участника, ноль раз на попадание; агрегатного ключа нет
      ни в одном из трёх составов
- [ ] Порядок опроса не переставлен: платный участник не раньше бесплатного; мутация порядка роняет
      названный тест
- [ ] Место оценки политики названо в докстринге и подтверждено тестом эквивалентности
- [ ] `sources` — вкладчики, `source` — старший по рангу вкладчик, при пустых вкладчиках — старший
      ответивший
- [ ] Полный набор гейтов §0.2 плана зелёный; снимок `tools-list.snapshot.json` без диффа

- Включение слияния на боевых маршрутах — `013-6`.

## Заметки

- Строгий цикл обязателен (PLAN §0.9): тест дедупа на непересекающихся фикстурах проходит и без
  механизма. Пересечение по `identities_total` — единственная пара, где обе стороны пишут одну
  метрику, поэтому TC-INT-01 строится именно на ней.
