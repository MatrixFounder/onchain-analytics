# Task 007-3: `safeFetch` — потоковый кап размера тела (закрытие R-47(1))

## Use Case Connection

- UC-1, альтернативный сценарий **A5**: тело больше капа → соединение закрывается, тело в память не поднимается

## RTM

**R-65**

## Task Goal

Сделать `maxResponseBytes` действующим ограничением, а не декларацией: считать байты **на потоке**,
когда `Content-Length` отсутствует.

## Почему это в области задачи

`api.llama.fi` отдаёт ответы **без `Content-Length`** (замер 2026-07-27: HTTP/2, `cf-cache-status`,
заголовка нет вовсе), а `assertResponseSizeWithinCap` (`safe-fetch.ts:147-154`) при отсутствующем
заголовке делает ранний `return`. То есть на том самом хосте, куда задача добавляет трафик, кап
**не работает вообще**, а глобальный документ вендора — 18 МБ. Без этой правки тест из DoD
(«усечение большого документа») проверял бы пустоту.

Это пункт **(1)** из R-47 в [docs/BACKLOG.md](../BACKLOG.md). Пункт **(2)** (`rpc-solana` lamports)
в область **не входит** — независимый дефект в другом файле.

## Changes Description

### Изменения в существующих файлах

#### `packages/core/src/net/safe-fetch.ts`

- Оставить существующую проверку `Content-Length` **без изменений** — она дешевле и отвергает
  ответ до чтения тела.
- Добавить `function capResponseStream(response: Response, url: string, maxBytes: number): Response`:
  - применяется **только** когда `Content-Length` отсутствует и `response.body !== null`;
  - оборачивает `response.body` в `ReadableStream`, который суммирует `chunk.byteLength`;
    при превышении `maxBytes` — `reader.cancel()` и `controller.error(new SafeFetchResponseTooLargeError(url, seen, maxBytes))`;
  - возвращает `new Response(cappedStream, { status, statusText, headers })` — заголовки и статус
    сохраняются побайтово, чтобы вызывающий код (`response.ok`, `response.status`) не изменил поведения.
- Вызывать её сразу после `assertResponseSizeWithinCap`, **до** возврата ответа и до проверки редиректа.
- Обновить докстринги `DEFAULT_MAX_RESPONSE_BYTES` и `safeFetch`: «документированное ограничение»
  превращается в описание реального поведения. Старый текст («не капается mid-stream … future
  hardening») удалить — он станет ложным.

### Точка внимания (иначе ошибка всплывёт в другом месте)

Ошибка возникает **при чтении тела** (`.json()`/`.text()`), а не при возврате `safeFetch`. Значит
она вылетит внутри `adapter.fetch()` и будет поймана `CapabilityRegistry.resolve()` как «этот адаптер
не смог ответить» → `tried` → `CapabilityUnavailableError`. Это **правильно**: переполнение
транспортного капа — не детерминированный отказ `normalize()`, и негативно кэшироваться оно не должно.

## Test Cases

### Unit-тесты (`packages/core/test/safe-fetch.test.ts` — расширить)

1. **TC-UNIT-01** (**AC-2**) — ответ **без** `Content-Length`, тело потоком из чанков суммарно выше
   капа → `SafeFetchResponseTooLargeError` при `.text()`. Собирается через
   `new Response(new ReadableStream({...}))` в фейковом `fetchImpl` — без сети.
2. **TC-UNIT-02** — ответ **без** `Content-Length` и **в пределах** капа читается полностью и
   побайтово равен исходному телу (кап не должен резать легальные ответы).
3. **TC-UNIT-03** — ответ **с** `Content-Length` выше капа по-прежнему отвергается **до** чтения тела
   (существующее поведение не изменилось).
4. **TC-UNIT-04** — при переполнении вызывается `cancel()` апстрим-ридера: закрывать соединение —
   смысл упражнения, иначе мы просто перестаём читать 18 МБ, продолжая их получать.
5. **TC-UNIT-05** — `status`, `statusText` и заголовки обёрнутого ответа равны исходным.

### Регрессия

- **Полный `pnpm test` обоих пакетов.** Это правка в `net/`, общем для десяти адаптеров: любой
  контрактный тест адаптера, читающий тело, — регрессионный для этой задачи.

## Notes

Изменение строго защитное: поведение меняется **только** для ответов свыше 10 МБ, которые сегодня
принимаются молча. Ни один существующий путь не может от этого сломаться — потому что ни один
существующий путь таких ответов не отдаёт (максимум, замеренный в проекте, — 1.7 МБ).
