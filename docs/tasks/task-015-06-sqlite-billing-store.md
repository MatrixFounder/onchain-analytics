# Задача 015.06: реализация `BillingStore` на оси SQLite — атомарный резерв и условное завершение

## Связь со сценариями

- UC-1 — клиент списывается на границе тула независимо от исхода кеша
- UC-2 — ретрай с тем же `client_request_id` не списывает дважды
- UC-5 — фаза 0 работает на оси SQLite без Postgres

<!-- contract:goal -->

## Цель задачи

Реализовать `BillingStore` на оси SQLite так, чтобы резерв был атомарным, повтор одного
`client_request_id` не создавал второй строки, а завершение шло условным `UPDATE`.

**Why ось SQLite пишет строку, не будучи авторитетной.** R-7.2 объявляет строки оси SQLite
неавторитетными, а R-2.4 требует записи на всех трёх профилях. Путь записи упражняется без базы, и учётный
запрос эти строки не читает.

**Why реализация отделена от интерфейса.** Ось хранилища выбирает реализацию. Задача 015-04
объявляет интерфейс и стаб; здесь стаб заменяется операторами SQLite.

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/engine/billing-store.ts`:**

- Реализовать `reserve`, `settle`, `refund` поверх клиента оси SQLite
- Реализовать `sumSettled` броском именованной ошибки (MINOR-5 раунда 2)
- Интерфейс и класс ошибки объявлены задачей 015-04; здесь объявляются только операторы хранилища

**Why writer живёт в `mcp-server`, а не в `core`.** `client_usage` несёт `principal_id` и
`access_profile_id`, поэтому её store проектируется и пишется в этом пакете
(`docs/architectures/data-model.md:1712` — подстрока `Package boundary, stated once here`).
`packages/core` нового экспорта под эту задачу не получает.

### Один текст оператора на две оси

Оператор пишется схемно-квалифицированным и в диалекте Postgres. Обратные подстановки для SQLite
делает клиент: `packages/core/src/sqlite/state-client.ts:30` — `export function toSqliteDialect(sql:
string): string {`.

Гейт неквалифицированной ссылки действует и на этой оси:
`packages/core/src/sqlite/state-client.ts:37` — `const UNQUALIFIED_TABLE_RE = new RegExp(`. Оператор
без `onchain.` отвергается здесь так же, как на оси Postgres.

**Why один текст, а не два.** Две редакции одного оператора расходятся на первой правке. Клиент
объявляет обратный перевод собственной задачей (`packages/core/src/sqlite/state-client.ts:16` —
подстрока `Why the callers do not change`).

### Резерв — атомарная транзакция в режиме `IMMEDIATE`

`reserve()` исполняется внутри `db.transaction(fn).immediate()`
(`docs/architectures/system-architecture.md:3999` — подстрока `db.transaction(fn).immediate()`).

Прецедент режима — вендорский гейт: `packages/core/src/cache/budget-store.ts:420` —
`return attempt.immediate();`, с обоснованием на `packages/core/src/cache/budget-store.ts:289` —
подстрока `IMMEDIATE`, not the driver's default `DEFERRED`.

**Расхождение с сегодняшним клиентом состояния названо, а не обойдено.** Клиент оси SQLite
открывает транзакцию строкой `packages/core/src/sqlite/state-client.ts:158` —
`database.exec('BEGIN');`, то есть в режиме `DEFERRED`. Режим `IMMEDIATE` требуется архитектурой
именно для этого писателя, и разница наблюдаема: `DEFERRED` даёт параллельному писателю гонку
«чтение, затем повышение блокировки» с немедленным `SQLITE_BUSY_SNAPSHOT` мимо таймаута ожидания.

Допустимы два носителя режима, и выбор принадлежит реализации:

| Носитель                                   | Что меняется                               |
| :----------------------------------------- | :----------------------------------------- |
| режим объявлен в самом клиенте состояния   | `BEGIN IMMEDIATE` для всех писателей файла |
| писатель леджера открывает свою транзакцию | второй путь к тому же файлу базы           |

**Why выбор записан развилкой, а не решён здесь.** Первый носитель меняет поведение чужих
писателей, второй заводит второй путь к одному файлу. Оба следствия принадлежат прогону, а не
плану. Тест TC-UNIT-05 меряет исполненный режим, поэтому носитель проверяем в любом варианте.

### Идемпотентная вставка

```sql
INSERT INTO onchain.client_usage
  (id, principal_id, access_profile_id, client_request_id, tool, capability,
   price_raw, state, reserved_at, created_at, updated_at)
VALUES ($1, $2, $3, $4, $5, $6, $7, 'reserved', $8, $8, $8)
ON CONFLICT (principal_id, client_request_id) DO NOTHING
RETURNING id, state;
```

Пустой `RETURNING` означает, что существующая строка уже отвечает на этот `client_request_id` в
любом из трёх состояний. Вызывающий читает её обратно и второй не пишет
(`docs/architectures/data-model.md:1766` — подстрока `INSERT … ON CONFLICT (principal_id,
client_request_id) DO NOTHING`).

**Why гонка разрешается ограничением хранилища, а не кодом обработчика.** R-5.5 называет носителем
разрешения уникальный индекс. Код обработчика на двух процессах над одним файлом дал бы два
прохода по устаревшему чтению.

**Why фаза 0 идёт одним оператором.** Сеяный профиль несёт `credits_mode='unlimited'` (R-6.2), и
ветвь дебета баланса на этой оси не исполняется. Ветвь `metered` принадлежит задаче 015-07.

### Завершение — условный `UPDATE`

```sql
UPDATE onchain.client_usage
   SET state = $2, terminal_at = $3, updated_at = $3, refund_reason = $4
 WHERE id = $1 AND state = 'reserved'
RETURNING id;
```

`settle` подставляет `'settled'` и пустую причину; `refund` подставляет `'refunded'` и имя класса.

**Ноль совпадений — не ошибка.** Строка уже вышла из `reserved`, и первый завершивший победил
(`docs/architectures/system-architecture.md:4278` — подстрока `Idempotent completion — first
completer wins`). Метод возвращает управление без броска.

**Why охрана `WHERE state = 'reserved'` обязательна на обоих методах.** Без неё второй вызов
переписал бы терминальную строку. На оси Postgres тот же оператор кредитовал бы баланс второй раз —
находка MAJOR-C раунда 2, владелец которой задача 015-10.

### `client_request_id` приходит параметром

`reserve()` собственного идентификатора не минтует. Серверное значение — уже минтуемый `traceId`:
`packages/mcp-server/src/tools/registry.ts:480` — `const traceId = ulid(now());`.

То же правило уже действует для следа запроса:
`packages/mcp-server/src/tools/request-trace-row.ts:182` — `clientRequestId: input.clientRequestId
?? input.id,`.

**Why не новый ULID.** Новое значение развело бы `client_usage.client_request_id` и
`request_trace.client_request_id` на одном серверном запросе, и соединение двух леджеров, на
которое опирается постусловие UC-2, перестало бы сходиться (MINOR-3 раунда 1).

### `sumSettled` на этой оси бросает

Метод объявлен обязательным и читает только строки Postgres (R-7.3). На оси SQLite он бросает
именованную ошибку, объявленную задачей 015-04.

**Why бросок, а не `'0'`.** Молчаливый ноль дал бы читателю AC-4 уверенный ответ по неавторитетным
строкам — то самое законное отрицание, которым оплачен `L-10` (MINOR-5 раунда 2).

## Тест-кейсы

### Модульные тесты

1. **TC-UNIT-01:** резерв пишет одну строку в объявленной форме
   - Входные данные: `reserve()` с ценой `'1'` над пустой базой
   - Ожидаемый результат: одна строка, `state='reserved'`, `price_raw='1'`, `terminal_at` пуст
2. **TC-UNIT-02 (AC-10):** повторная отправка одного `client_request_id` второй строки не создаёт
   - Входные данные: два `reserve()` с одной парой `(principal_id, client_request_id)`
   - Ожидаемый результат: в таблице одна строка; второй вызов возвращает существующую резервацию с
     признаком `existing`; падает при снятии `ON CONFLICT DO NOTHING`
3. **TC-UNIT-03 (AC-11):** два параллельных резерва одного идентификатора дают ровно один резерв
   - Входные данные: два вызова `reserve()` без ожидания между ними
   - Ожидаемый результат: одна строка; второй вызов читает её обратно; падает при снятии
     ограничения уникальности `(principal_id, client_request_id)`
4. **TC-UNIT-04 (AC-14):** прогон без `ONCHAIN_STATE_PG_URL` пишет строку в `DATA_DIR`
   - Входные данные: окружение без `ONCHAIN_STATE_PG_URL`, `DATA_DIR` во временном каталоге
   - Ожидаемый результат: строка `client_usage` читается из файла базы этого каталога
     (`packages/core/src/sqlite/state-client.ts:69` — `const file = deps.path ??
cacheDbPath(resolveDataDir(deps.env ?? process.env));`)
5. **TC-UNIT-05:** транзакция резерва открыта в режиме `IMMEDIATE`
   - Входные данные: конструктор базы, поданный через `DatabaseCtor`
     (`packages/core/src/sqlite/state-client.ts:51` — `readonly DatabaseCtor?: SqliteCtor;`), с
     записью исполненных операторов
   - Ожидаемый результат: среди исполненных операторов есть `BEGIN IMMEDIATE`; падает при возврате
     к `BEGIN`
6. **TC-UNIT-06:** `settle` переводит строку в `settled` и заполняет `terminal_at`
   - Входные данные: строка `reserved`, затем `settle`
   - Ожидаемый результат: `state='settled'`, `terminal_at` заполнен, `refund_reason` пуст
7. **TC-UNIT-07:** повторный `settle` по закрытой строке ошибки не даёт
   - Входные данные: `settle` дважды по одной строке
   - Ожидаемый результат: второй вызов возвращает управление без броска; `terminal_at` первого
     вызова не переписан
8. **TC-UNIT-08:** `refund` переводит строку в `refunded` и записывает причину
   - Входные данные: строка `reserved`, затем `refund` с именем класса
   - Ожидаемый результат: `state='refunded'`, `refund_reason` равен переданному имени
9. **TC-UNIT-09:** `settle` по строке `refunded` не меняет ни одной колонки
   - Входные данные: строка `refunded`, затем `settle`
   - Ожидаемый результат: ноль совпадений; `state` и `refund_reason` прежние; падает при снятии
     охраны `WHERE state = 'reserved'`
10. **TC-UNIT-10:** оператор схемно-квалифицирован
    - Входные данные: текст оператора резерва
    - Ожидаемый результат: гейт неквалифицированной ссылки его принимает; версия без `onchain.`
      отвергается броском
11. **TC-UNIT-11:** store не минтует `client_request_id`
    - Входные данные: `reserve()` со значением, переданным вызывающим
    - Ожидаемый результат: записанное значение равно переданному; в модуле нет вызова генератора
      идентификатора для этой колонки
12. **TC-UNIT-12:** `sumSettled` на оси SQLite бросает именованную ошибку
    - Входные данные: вызов `sumSettled` над клиентом оси SQLite
    - Ожидаемый результат: бросок объявленного класса; значение `'0'` не возвращается

## Критерии приёмки

- [ ] AC-10 — повторная отправка одного `client_request_id` не создаёт вторую строку и не списывает
      повторно
- [ ] AC-11 — два параллельных запроса с одним `client_request_id` порождают ровно один резерв
- [ ] AC-14 — прогон без `ONCHAIN_STATE_PG_URL` пишет строку `client_usage` в `DATA_DIR`
- [ ] `reserve()` исполняется внутри `db.transaction(fn).immediate()` и использует
      `INSERT ... ON CONFLICT DO NOTHING`
- [ ] `settle` и `refund` — условный `UPDATE ... WHERE state = 'reserved'`; нулевое совпадение
      ошибки не даёт
- [ ] Серверный `client_request_id` берётся из уже минтуемого `traceId`, а не из нового ULID
- [ ] `sumSettled` на этой оси бросает именованную ошибку и не возвращает `'0'`

## Примечания

Этап: **Этап 2. Леджер на двух осях хранилища**. Проход: **impl**. Зависимости: 015-02 (форма
таблицы на этой оси), 015-03 (тринадцатое имя в `STATE_TABLES`), 015-04 (интерфейс, признак
существующей строки, класс ошибки чтения), 015-05 (прайс-лист и `DEFAULT_PRICE_RAW`).

Тринадцатое имя в перечне `STATE_TABLES` (`packages/core/src/pg/state-client.ts:87` — `export const
STATE_TABLES = [`) добавляет задача 015-03, и она же правит сверку перечня с текстом миграции.

**Why зависимость от 015-03 объявлена, хотя ось здесь SQLite.** Гейт неквалифицированной ссылки
строится из того же перечня (`packages/core/src/sqlite/state-client.ts:37` — `const
UNQUALIFIED_TABLE_RE = new RegExp(`). Без имени TC-UNIT-10 зелён и на мутации.

Ветвь `credits_mode='metered'`, арифметика баланса и `sumSettled` на оси Postgres принадлежат задаче
015-07. Окно реплея надстраивает задача 015-08. Транзакционную границу вызова `settle`/`refund` в
обёртке тула владеет задача 015-10; здесь объявляются только операторы хранилища.

Требования: R-1.2, R-1.4, R-5.2, R-5.3, R-5.4, R-5.5, R-7.2.
