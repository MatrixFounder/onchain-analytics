# Задача 015.24: verify-гейт переноса — четыре проверки данных и проверка формы `usage`

## Связь со сценариями

- UC-6 — таблицы движка переезжают в выделенный контейнер Postgres на dev-VM (шаг 5)

<!-- contract:goal -->

## Цель задачи

Снять четыре проверки `DB-SCHEMA-CONCEPT` §5.3 и проверку формы `onchain.usage` на обоих
контейнерах и предъявить отчёт, который называет направление расхождения по каждой таблице.

**Why отчёт стоит между переносом и удалением.** Шаг 10 UC-6 необратим. Расхождение, найденное
после него, восстанавливается только из артефакта отката (`deployment.md:952-955`).

**Why направление, а не «не совпадает».** Больше строк на новом контейнере — это материализованная
угроза дублирования `access_audit`; меньше — недокопировано (`deployment.md:946-950`). Причины
разные, и разбираются они по-разному (MAJOR-2 и MAJOR-1 раунда 3 спецификации).

## Описание изменений

### Новые файлы

- `sql/verify/wi62_verify.sql` — скрипт четырёх проверок данных и проверки формы, исполняемый на каждом контейнере

### Изменения в существующих файлах

**Файл `docs/onchain-analytics/PROD-RUNBOOK.md`:**

- Раздел «Engine network profile — verify-гейт переезда» после раздела про две роли (`:195`)
- Две команды запуска через stdin в `docker exec -i`, по образцу уже записанного вызова миграции
  (`PROD-RUNBOOK.md:232-235`)
- Правило блокировки: расхождение останавливает шаг удаления

### Два режима одного файла

| Режим                 | Переменные psql                                    | Что делает                          |
| :-------------------- | :------------------------------------------------- | :---------------------------------- |
| снимок старой стороны | `-v SIDE=old -v SAMPLE=<N>`                        | печатает отчёт и одну строку base64 |
| сверка новой стороны  | `-v SIDE=new -v SAMPLE=<N> -v OLD_REPORT=<base64>` | печатает отчёт, сравнение и сирот   |

**Why одна база не читает другую напрямую.** Контейнеры не связаны ролью, читающей чужую базу.
Отчёт переносится значением через оператора, а не соединением.

**Why снимок переносится base64 одним параметром.** Он декодируется на стороне сверки через
`convert_from(decode($1,'base64'),'utf8')::jsonb` и `jsonb_to_recordset` — тот же приём, которым
уже связываются данные в воркфлоу (CLAUDE.n8n.md). Значение не несёт ни запятой, ни `$`.

**Why числа снимаются в момент переезда.** На момент планирования `ssh vm` отвечает таймаутом
устойчиво, и число строк в таблицах старого контейнера не измерено (`docs/TASK.md` §0). Скрипт
берёт обе стороны в момент прогона, а не сверяется с ранее записанной оценкой.

### Проверка 1 — число строк по каждой таблице

Одиннадцать таблиц несут строки к переносу.

| Таблица            | Проверка 1                                       | Проверка 2 — столбец времени        |
| :----------------- | :----------------------------------------------- | :---------------------------------- |
| `users`            | применима                                        | `created_at`                        |
| `access_profiles`  | применима                                        | `created_at`                        |
| `api_tokens`       | применима                                        | `created_at`                        |
| `access_audit`     | применима                                        | `ts`                                |
| `request_trace`    | применима                                        | `received_at`                       |
| `diagnostics`      | применима                                        | `ts`                                |
| `retention_runs`   | применима                                        | `started_at`                        |
| `providers`        | применима                                        | неприменима — столбца времени нет   |
| `cache_entries`    | применима                                        | `created_at`                        |
| `usage`            | применима                                        | `day`                               |
| `usage_window`     | применима                                        | `window_start`                      |
| `client_usage`     | неприменима — источника на старом контейнере нет | неприменима — источника нет         |
| `provider_buckets` | неприменима — строки не переносятся (R-8.11)     | неприменима — строки не переносятся |

Колонки взяты из `sql/migrations/002_t014_network_profile.sql`.

**Why `client_usage` помечена неприменимой, а не нулём.** Таблица создаётся пустой на новом
контейнере и до его первого обслуживания остаётся пустой; копировать её неоткуда
(`deployment.md:861-866`). Ноль утверждал бы, что сравнение сделано.

**Why `providers` выпадает из второй проверки.** У таблицы три колонки — `id`, `kind`, `notes` — и
столбца времени среди них нет. Неприменимость названа, а не свёрнута в пропуск (R-8.13, «отмечая
неприменимые»).

**Why `provider_buckets` названа в таблице, хотя не переносится.** Отсутствие строки читалось бы
как забытая таблица. Уступка записана отдельно (`deployment.md:956-968`).

### Проверка 2 — границы времени

`min` и `max` по столбцу таблицы, обе границы сравниваются на равенство.

**Why обе границы, а не только `max`.** Совпадающий `max` при разошедшемся `min` означает
недокопированный хвост истории — потерю, которую верхняя граница не видит.

### Проверка 3 — спот-чек точных колонок

N строк каждой таблицы, выбираемых `ORDER BY md5(<ключ>::text) LIMIT :SAMPLE`, сравниваются
побайтно по точным колонкам.

| Таблица           | Точные колонки спот-чека                     | Ключ выборки                          |
| :---------------- | :------------------------------------------- | :------------------------------------ |
| `users`           | `email`, `role`, `status`                    | `id`                                  |
| `access_profiles` | `credits_balance_raw`, `tool_allowlist_json` | `id`                                  |
| `api_tokens`      | `token_hash`, `prefix`, `status`             | `id`                                  |
| `access_audit`    | `target_id`, `before_json`, `after_json`     | `id`                                  |
| `request_trace`   | `args_hash`, `tried_json`, `refusal_class`   | `id`                                  |
| `diagnostics`     | `detail_json`, `event`                       | `id`                                  |
| `retention_runs`  | `detail_json`, `job`                         | `id`                                  |
| `providers`       | `kind`, `notes`                              | `id`                                  |
| `cache_entries`   | `value_json`, `args_hash`                    | `id`                                  |
| `usage`           | `credits_used`                               | `provider \|\| ':' \|\| day`          |
| `usage_window`    | `credits_used`, `calls_made`                 | `provider \|\| ':' \|\| window_start` |

**Why выборка упорядочена по `md5` ключа, а не по `random()`.** Обе стороны обязаны выбрать ОДНИ И
ТЕ ЖЕ строки, иначе сравнивать нечего. `md5` даёт один и тот же порядок на обеих базах и не зависит
от физического порядка строк.

**Why `token_hash` и `credits_balance_raw` названы поимённо.** Дайджест токена — обычный `TEXT`,
зависящий от перца в `.env` сервера (R-8.11); баланс кредитов — точное значение строкой по канону
§1 п.7. Расхождение в любом из двух ломает аутентификацию либо бухгалтерию молча.

**Why значения печатаются, а не сворачиваются в одну контрольную сумму.** Несовпавшая сумма не
называет строку. Отчёт печатает значения, поэтому расхождение указывает на строку и колонку.

### Проверка 4 — ноль сирот

Явный `SELECT`, потому что ни одна из ссылок не несёт внешнего ключа.

```sql
-- PLANNED — sql/verify/wi62_verify.sql, проверка 4, на НОВОМ контейнере
SELECT 'request_trace' AS source, count(*) AS orphans
  FROM onchain.request_trace rt
 WHERE rt.principal_id <> 'local'
   AND NOT EXISTS (SELECT 1 FROM onchain.api_tokens t WHERE t.id = rt.principal_id)
UNION ALL
SELECT 'access_audit', count(*)
  FROM onchain.access_audit a
 WHERE a.target_type = 'api_token'
   AND NOT EXISTS (SELECT 1 FROM onchain.api_tokens t WHERE t.id = a.target_id)
UNION ALL
SELECT 'client_usage.principal', count(*)
  FROM onchain.client_usage c
 WHERE c.principal_id <> 'local'
   AND NOT EXISTS (SELECT 1 FROM onchain.api_tokens t WHERE t.id = c.principal_id)
UNION ALL
SELECT 'client_usage.profile', count(*)
  FROM onchain.client_usage c
 WHERE c.access_profile_id IS NOT NULL
   AND NOT EXISTS (SELECT 1 FROM onchain.access_profiles p WHERE p.id = c.access_profile_id);
```

Ноль по каждой строке — постусловие. Ненулевое значение называет, какая из ссылок потеряла цель.

**Why внешнего ключа нет ни у одной из четырёх ссылок.** Локальный принципал `'local'` строки
токена не имеет, и внешний ключ отказывал бы записи на транспорте, которому токен не нужен
(`data-model.md:1773-1778`).

**Why леджер входит в проверку.** MINOR-12 раунда 1: дисциплина «ноль сирот» не была распространена
на саму `client_usage`, хотя её две колонки — того же класса, что колонки `request_trace`.

**Why проверка сирот идёт и по пустой таблице.** Пустая таблица даёт ноль, и это верный ответ.
Прецедент — verify-гейт миграции 002, где та же проверка оставлена на пустых таблицах
(`sql/migrations/002_t014_network_profile.sql:300-304`).

### Проверка 5 — перечень колонок `usage` на новом контейнере

```sql
-- PLANNED — sql/verify/wi62_verify.sql, проверка 5, на НОВОМ контейнере
SELECT count(*) AS has_calls_made
  FROM information_schema.columns
 WHERE table_schema = 'onchain' AND table_name = 'usage' AND column_name = 'calls_made';
```

Единица — постусловие. Ноль останавливает шаг удаления и возвращает работу к задаче 015-21.

**Why колонка проверяется отдельно от чисел строк.** Проверки 1–3 сравнивают ДАННЫЕ и слепы к форме
таблицы: спот-чек `usage` покрывает только `credits_used`. Форма, разошедшаяся между двумя
контейнерами, даёт `column "calls_made" does not exist` у первого же вызова гейта задачи 015-14.

**Why проверка стоит здесь, а не в 015-21.** Она сравнивает две базы, и это единственный шаг этапа,
который обе видит.

### Отчёт сравнения

Строка на таблицу: имя, число на старой стороне, число на новой, направление.

| Направление      | Условие              | Что означает                        |
| :--------------- | :------------------- | :---------------------------------- |
| `equal`          | `new = old`          | перенос полон                       |
| `more_on_new`    | `new > old`          | дублирование, угроза `access_audit` |
| `less_on_new`    | `new < old`          | недокопировано                      |
| `not_applicable` | сторона не считается | причина названа в отчёте            |

**Why направление вычисляется в SQL, а не глазами по двум распечаткам.** Сравнение двух выводов
глазами не оставляет артефакта, а AC-36 требует записанный отчёт до и после переноса.

### Блокировка шага удаления

Любое значение, кроме `equal` и `not_applicable`, в проверке 1; любое несовпадение границ в
проверке 2; любое расхождение в проверке 3; любое ненулевое число в проверке 4; ноль в проверке 5 —
шаг 10 UC-6 не исполняется.

**Why блокировка записана в runbook, а не только в отчёте.** Отчёт называет факт; исполнителю
нужна инструкция, что делать с ним (UC-6 A2).

### Переиспользование

Скрипт остаётся в репозитории и запускается при следующем переезде хоста.

**Why не одноразовый скрипт на VM.** `DB-SCHEMA-CONCEPT` §5.3 прямо требует: «Скрипт verify
остаётся в repo — он же используется при переездах хоста (§6)». Имена контейнеров приходят
параметрами команды, а не зашиты в файл.

   - Падает при мутации: файл 005 применён без четвёртого отличия задачи 015-21

### Проверки на искусственном расхождении

Исполняются на копии, не на живых данных.

**Отклонение, исполненное осознанно (2026-08-31): дефекты вносились в ЖИВОЙ новый контейнер внутри
транзакций, которые откатывались.** Каждый прогон — `BEGIN; <дефект>; <весь файл гейта>; ROLLBACK;`
одним конвейером в `psql`.

| Почему так                 | Что это даёт                                                                                                               |
| :------------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| проверяется НАСТОЯЩИЙ файл | копия базы потребовала бы применить `005` к третьей базе; проверялась бы схема-двойник, а не та, на которой пойдёт переезд |
| откат гарантирован         | незавершённая транзакция откатывается и при обрыве соединения, не только по `ROLLBACK`                                     |
| дешевле, чем копия         | окно молчания канала оповещений открыто, и создание третьей базы его удлиняет                                              |

**Чем подтверждено, что откат состоялся.** После пяти прогонов сняты заново числа строк, границы
времени и `md5` содержимого — совпали с послепереносным снимком побайтно; строк с идентификаторами
`01NEG%` ноль; `md5(token_hash)` вернулся к исходному.

**Почему это не нарушение духа требования.** Требование защищает живые данные от порчи. Транзакция
с откатом даёт то же свойство сильнее, чем копия: копия защищает данные тем, что их не трогает, а
откат — тем, что трогает и возвращает, и возврат измерен.

1. **TC-NEG-01:** удвоенная строка `access_audit` на новой стороне даёт `more_on_new`
2. **TC-NEG-02:** недокопированная таблица даёт `less_on_new`
3. **TC-NEG-03:** изменённый байт в `token_hash` находится спот-чеком
4. **TC-NEG-04:** строка `client_usage` с `principal_id`, которого нет в `api_tokens`, даёт
   ненулевое число сирот
5. **TC-NEG-05:** строка `alert.delivered`, записанная внутри окна переезда, отличима от
   дублирования `access_audit`
   - Входные данные: `diagnostics` новой стороны с лишней строкой `event='alert.delivered'` и `ts`
     внутри окна; `access_audit` новой стороны с удвоенной строкой
   - Ожидаемый результат: спот-чек называет `event` и `ts` первой строки, и обе причины `more_on_new`
     различимы по таблице и по признаку
   - Падает при мутации: отчёт печатает только число, без `event` и границ времени

**Why отрицательный кейс на этот случай существует.** Задача 015-23 деактивирует оба воркфлоу на
время окна, и это первое средство. Кейс — второе: если писатель всё же записал строку, гейт обязан
назвать её, а не выдать безымянное расхождение собственного производства.

- Скрипт не выполняет ни одного `INSERT`, `UPDATE`, `DELETE` и `DROP`

## Примечания

Задача зависит от 015-23: перенос строк одиннадцати таблиц завершён, все три писателя ещё
остановлены.

Гейт стоит между «строки скопированы» и «профиль обслуживает трафик» (`deployment.md:855-860`).
Задача 015-25 запускает профиль после него, задача 015-27 удаляет таблицы в старом контейнере
после обеих.

Скрипт читает; деструктивных операций он не содержит, поэтому по skill `vm-deploy` подтверждения
владельца не требует. Подтверждение требуется задаче 015-27.

Отчёт попадает в лог инсталляции задачей 015-28 как «результат verify» формы «дата, хосты,
verify-результат».

Для повторного прогона копии `access_audit` действует именованное исключение: таблица очищается
в одной транзакции и копируется целиком (`deployment.md:902-916`). Verify-гейт исполняется после
такого повтора заново.
