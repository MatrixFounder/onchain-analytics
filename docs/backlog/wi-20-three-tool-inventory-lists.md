# WI-20 — добавление MCP-тула требует правки трёх независимых инвентарей, и последний падает только на `smoke:dist`

Чтобы добавить один тул, надо отредактировать **три** списка, которые друг на друга не ссылаются, и
каждый падает в своём гейте:

| список                                          | что ловит                                             | когда срабатывает                     |
| ----------------------------------------------- | ----------------------------------------------------- | ------------------------------------- |
| `test/e2e.stdio.test.ts` — имена + счётчик       | `pnpm test`                                           | рано                                  |
| `eval/capabilities.mjs` → `CAPABILITY_TOOLS`     | `test/eval-capability-coverage.test.ts` (фикс RF-5)   | рано                                  |
| `scripts/smoke-dist.mjs` → `expectedNames`       | `pnpm smoke:dist`                                     | **после того, как test И build прошли** |

В TASK-009 сработали все три, по очереди.

**Они работают как задумано, и их надо оставить.** Каждый охраняет своё свойство — список по stdio,
согласие двух осей eval, собранный `dist/` — и каждый уже поймал реальный пропуск (RF-4, RF-5).

Цена в том, что задача узнаёт о них по одному, а про последний — только после полной сборки.
Варианты, ни один не очевиден:

1. **Оставить как есть.** Три дешёвых падения с внятными сообщениями — не дефект, а избыточность
   здесь и есть смысл. Зафиксировать сам факт «списков три» там, где задача его прочитает: сделано в
   `packages/mcp-server/.AGENTS.md` и `docs/TASK.md` §4.1 для TASK-009.
2. **Вывести два из третьего** (например, `smoke-dist` читает список e2e). Убирает независимость,
   которая и делает их полезными, — скорее потеря, чем выигрыш.
3. **Сообщение ПЕРВОГО падения называет два остальных.** Дешевле всего, независимость сохраняется:
   задача платит один поиск вместо трёх циклов сборки.

**Рекомендация — вариант 3.** Ни один контракт сегодня не нарушен, поэтому это полировка, а не дефект.

**Связано:** [RF-4](../issues/rf-4-smoke-dist-ci-gate-still-asserts-8-tools-so-it-has-been-red-on-main-since-task-006.md)
(`smoke-dist` утверждал устаревший счётчик и был красным на main),
[RF-5](../issues/rf-5-live-eval-capability-axis-is-hand-written-so-dex-volume-history-ships-untested.md)
(ось capability в eval писалась руками, `dex.volume.history` уехал непокрытым). Оба `fixed`; эта
запись — про форму, которую они после себя оставили, а не про любой из двух симптомов.

## Закрыто 2026-07-29 — вариант 3, и списков оказалось ЧЕТЫРЕ, а не три

Реализовано в прогоне `/update-docs` по TASK-009. Каждый сторож теперь называет остальные:

- `test/e2e.stdio.test.ts` — константа `ADD_A_TOOL` передаётся вторым аргументом в обе проверки
  (`toHaveLength` и `toStrictEqual`), поэтому текст виден в самом падении, а не в комментарии рядом;
- `test/eval-capability-coverage.test.ts` — то же сообщение на `unaccounted`;
- `scripts/smoke-dist.mjs` — прежний текст «добавьте имя в `expectedNames`» дополнен тремя
  остальными адресами.

**Уточнение, найденное при закрытии: список не третий, а четвёртый.** Тот же прогон добавил
`test/docs-counts.test.ts` (см. [WI-21](wi-21-architecture-index-drifts-from-its-sections.md)),
который требует, чтобы каждый зарегистрированный тул был **назван** в
`docs/architectures/interfaces.md` §5. Это не удорожание: ровно этот пропуск и произошёл в TASK-008,
и раньше его не ловило ничто. Все сообщения перечисляют четыре пункта.

Слияние по-прежнему отвергнуто: сторожа независимы намеренно — они проверяют разные свойства
(список по stdio, согласие двух осей eval, собранный `dist/`, названность в контракте), и вывод
одного из другого убрал бы именно ту избыточность, ради которой они существуют.
