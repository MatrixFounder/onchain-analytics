# Задача 014.04: `AccessProfileReader` — асинхронное чтение, умолчания в коде `[STUB]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети
- UC-3 — оператор запускает локально

<!-- contract:goal -->

## Цель задачи

Ввести один интерфейс чтения значений профиля доступа и одного поставщика значений. Источник
значений в T-014 — умолчания в коде; форма чтения асинхронна с первого дня (R-13.2, R-13.3).

**Why асинхронная форма при синхронном источнике.** Второй поставщик — таблица за соединением.
Синхронную сигнатуру пришлось бы переписать, чтобы его допустить (`security.md` §7.5.3a).

**Why пакет `mcp-server`, а не `core`.** `security.md` §7.5.1: проверки живут рядом с транспортом,
которому они нужны, а `packages/core` не получает знания о токенах, ролях и заголовках. Путь файла
объявлен в §7.5.3a.

## Описание изменений

### Новые файлы

- `packages/mcp-server/src/auth/access-profile.ts` — тип профиля и интерфейс читателя
- `packages/mcp-server/src/auth/default-access-profile.ts` — поставщик умолчаний фазы 0
- `packages/mcp-server/test/access-profile-reader.test.ts` — тесты на двух поставщиков
- `packages/mcp-server/test/settings-access.gate.test.ts` — гейт R-13.3a

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/server.ts`, строка 74 — `for (const spec of toolSpecs) {`:**
- При режиме `'list'` пропускать спецификацию, имени которой список профиля не несёт
- При режиме `'all'` пересечение не вычислять и инвентарь не менять
- Заголовок и описание оставить чтением из определения тула
  (`packages/mcp-server/src/tools/registry.ts:281`, `server.registerTool(`)

Координату называет `system-architecture.md` §3.4.9 — тот же файл и та же строка. Доставку
прочитанного профиля в фабрику объявляет задача 014-10 (см. «Примечания»).

**Why правка стоит в цикле, а не в обработчике `tools/list`.** Экземпляр `McpServer` посессионный, и
посессионный инвентарь собирается там, где сессия его строит (§3.4.9). При едином экземпляре
`tools/list` был бы фактом процесса, и сужению потребовался бы второй механизм.

### Объявление типа

Семь полей повторяют состав `security.md` §7.5.3a. Порядок объявления отличается: там
`routeDisclosureMode` стоит шестым, здесь — последним. Поле отображается на колонку
`access_profiles.route_disclosure_mode` (`data-model.md` §4.5.3, решение владельца 2026-08-13).

```ts
// PLANNED — packages/mcp-server/src/auth/access-profile.ts
export interface AccessProfile {
  readonly creditsMode: 'unlimited' | 'metered';
  readonly creditsBalanceRaw: string | null; // exact value as a string
  readonly rateLimitMode: 'unlimited' | 'metered';
  readonly rateLimitPerMin: number | null;
  readonly toolAllowlistMode: 'all' | 'list';
  readonly toolAllowlist: readonly string[] | null;
  readonly routeDisclosureMode: 'full' | 'none'; // R-20.4 — раскрытие маршрута в успешном ответе
}

export interface AccessProfileReader {
  read(accessProfileId: string): Promise<AccessProfile>;
}
```

**Why седьмое поле заводит эта задача.** `data-model.md` §4.5.3 называет `route_disclosure_mode`
четвёртой настройкой профиля, а `interfaces.md` §5.4.4.1 помещает её на профиль доступа рядом с
тремя другими. Другого владельца типа профиля план не заводит.

**Why имя `routeDisclosureMode`.** Шесть действующих полей — camelCase имени колонки.
`interfaces.md` §5.4.4.1 оставляет имя за перечнем полей R-13.7 и другого не задаёт.

### Семь полей: каждое значение со своим режимом

Форма повторяет колонки `access_profiles` из `data-model.md` §4.5.3 поле в поле.

| Поле | Значение | Колонка |
| :--- | :--- | :--- |
| `creditsMode` | `'unlimited'` \| `'metered'` | `credits_mode` |
| `creditsBalanceRaw` | `string` \| `null` — точное значение строкой | `credits_balance_raw` |
| `rateLimitMode` | `'unlimited'` \| `'metered'` | `rate_limit_mode` |
| `rateLimitPerMin` | `number` \| `null` | `rate_limit_per_min` |
| `toolAllowlistMode` | `'all'` \| `'list'` | `tool_allowlist_mode` |
| `toolAllowlist` | `readonly string[]` \| `null` | `tool_allowlist_json` |
| `routeDisclosureMode` | `'full'` \| `'none'` — умолчание `'full'` | `route_disclosure_mode` |

**Why режим рядом с каждым значением.** `null` со смыслом «безлимит» неотличим от профиля, который
никогда не заводили. Это класс дефекта L-10: 43 сети из 458 отвечали уверенным «не развёрнут», и оба
гейта оставались зелёными (`data-model.md` §4.5.3).

**Why пустой список — не отсутствие сужения.** Пустой `toolAllowlist` под режимом `'list'` означает,
что не разрешён ни один тул. Прочитанный как «сужения нет», он даёт случай «пусто читается как
безопасно». Режим `'all'` — другое состояние, и три пары `CHECK` держат их раздельно на уровне
движка (`data-model.md` §4.5.3).

**Why баланс объявлен строкой.** Кредиты — точные целые, и §1.7 канона называет их причиной, по
которой точные значения хранятся строками. Число JS теряет точность за 2^53.

**Why у седьмого поля нет парной величины.** Три другие настройки соединяют режим с величиной. У
раскрытия маршрута величины нет, поэтому режим — всё значение. Колонка объявлена `NOT NULL`, и
непровизионированного состояния у неё нет (`data-model.md` §4.5.3).

### Отказ поставщика

Поставщик может отказать, и отказ fail-closed. Неудачное чтение на создании сессии отказывает в
сессии; неудачное чтение на пути запроса отказывает в запросе. Умолчательный профиль не
подставляется (`security.md` §7.5.3a).

**Why fail-closed.** Подставленное умолчание расширило бы инвентарь или потолок в момент, когда
источник настроек недоступен.

### Гейт R-13.3a

Файл `packages/mcp-server/test/settings-access.gate.test.ts` — статическая проверка над
`packages/core/src` и `packages/mcp-server/src`. Она идёт внутри `pnpm test`, который
`deployment.md` §10.2 уже держит в конвейере. Вход — прогон
`grep -RnE --include='*.ts' "process\.env" packages/core/src packages/mcp-server/src`.

Два правила, дословно из `security.md` §7.5.3a:

1. Вхождение `process.env` вне `env.ts` и вне двух форм инъекции валит проверку. Постусловие:
   потребитель, читающий значение окружения напрямую, не может влиться.
2. Одно из семи имён полей `AccessProfile`, прочитанное вне читателя, его поставщика, их тестов и
   двух названных мест применения, валит проверку. Постусловие: второй читатель одной настройки не
   может появиться рядом с первым.

Два места применения, названные поимённо: цикл регистрации тулов в `createServer` читает
`toolAllowlist` (`system-architecture.md` §3.4.9), `toCallToolResult` читает `routeDisclosureMode`
(задача 014-16, `security.md` §7.5.3).

Формы, которые проверка пропускает (замер 2026-08-13: 20 вхождений, 10 в комментариях, 10 в коде):

| Форма | Мест в коде | Пример |
| :--- | :--- | :--- |
| `deps.env ?? process.env` | 8 | `packages/core/src/adapters/coingecko/index.ts:96` |
| параметр по умолчанию | 1 | `packages/core/src/cache/data-dir.ts:13` |
| разбор схемы | 1 | `packages/mcp-server/src/env.ts:167` |

**Why статическая проверка, а не ревью.** §7.3 называет ревью кода слабейшим из трёх контролей, а
прямое чтение настройки — правка в одну строку.

**Why гейт назван отдельным предметом.** Задача 014-05 держит другой гейт — классификацию настроек
по классу (AC-44, `deployment.md` §10.2.1 пункт 2). Два гейта друг друга не заменяют.

**Why поставщик и его тесты названы в правиле 2.** Табличный поставщик задачи 014-02
(`auth/access-profile-store.ts`) читает те же семь полей. Без исключения правило запретило бы
второго поставщика, ради которого читатель асинхронен.

**Why места применения названы в правиле 2.** Прочитанный профиль применяется вне читателя: список
тулов — в цикле регистрации, режим раскрытия — в рендере результата. Без этих двух имён правило
запрещает применение значения, ради которого его читают.

### Сужение инвентаря тулов

Место применения списка — цикл регистрации тулов в `createServer`, один раз на сессию:
`packages/mcp-server/src/server.ts:74` (`system-architecture.md` §3.4.9). Применяется пересечение
`profile.toolAllowlist ∩ toolSpecs`.

- Имя в профиле, которого не несёт ни одна спецификация, не выбирает ничего
- Режим `'all'` пересечение не вычисляет; фаза 0 не сужает ничего (R-14.4)
- Заголовки и описания читаются из определения тула, не из профиля (R-14.3)

**Why пересечение.** Пересечение не может добавить, и это делает профиль сужающим (R-14.1).

### Умолчания фазы 0

Все три лимитных значения объявлены безлимитными (R-13.7, R-14.4), поэтому измеренного числа задача
не вводит (`security.md` §7.5.3a). Раскрытие маршрута объявлено `'full'` — умолчание колонки и
затравочной строки `phase0-unlimited` (`data-model.md` §4.5.3).

**Why безлимит объявляется, а не выводится из пропуска.** `ADR-003` D5: отсутствующее поле нельзя
выставить в безлимит. T-014 заводит поля, квоты применяет T-015.

**Why умолчание раскрытия — `'full'`, а не `'none'`.** Токен фазы 0 получает все тулы и безлимитную
квоту по `ADR-003` D5. Поле существует с начала в разрешающем значении; сужение доступно на токен
(`interfaces.md` §5.4.4.1).

### Модульные тесты
1. **TC-UNIT-01:** два поставщика, один читатель
   - Входные данные: поставщик умолчаний и второй поставщик, отвечающий с задержкой

2. **TC-UNIT-02:** отказ поставщика умолчанием не подменяется
   - Входные данные: поставщик, чей `read` отвергает промис
   - Ожидаемый результат: создание сессии отказано; ни одно поле профиля не прочитано из умолчаний
3. **TC-UNIT-03:** отказ поставщика на пути запроса отказывает в запросе
   - Входные данные: `read`, отвергающий промис на уже созданной сессии
   - Ожидаемый результат: запрос отвергнут названным классом; профиль не подставлен
4. **TC-UNIT-04:** `EnvSchema.parse({})` проходит (AC-24, первая половина)
5. **TC-UNIT-05:** режим `'list'` с пустым списком не разрешает ни одного тула
   - Входные данные: `toolAllowlistMode: 'list'`, `toolAllowlist: []`
   - Ожидаемый результат: `tools/list` пуст, и результат отличается от прогона в режиме `'all'`
6. **TC-UNIT-06:** имя тула вне реестра инвентарь не расширяет
   - Входные данные: режим `'list'` с одним именем, которого нет ни в одной спецификации
   - Ожидаемый результат: `tools/list` пуст, инвентарь процесса не изменён
7. **TC-UNIT-07:** гейт красный на внесённом прямом чтении `process.env`
   - Входные данные: временная правка потребителя на чтение переменной напрямую
   - Ожидаемый результат: проверка красная и называет файл и строку
8. **TC-UNIT-08:** гейт красный на втором читателе поля профиля
   - Входные данные: чтение `creditsMode` вне читателя, его поставщика и их тестов
   - Ожидаемый результат: проверка красная и называет файл и строку
9. **TC-UNIT-09:** сужение применяет цикл `server.ts:74`, а не обработчик запроса
   - Входные данные: счётчик вызовов `spec.register` и профиль в режиме `'list'` с двумя именами
     из инвентаря
   - Ожидаемый результат: `register` вызван дважды за создание сессии; последующие вызовы
     `tools/list` счётчик не двигают
10. **TC-UNIT-10:** поставщик умолчаний отдаёт `routeDisclosureMode: 'full'`
    - Входные данные: `read` поставщика умолчаний
    - Ожидаемый результат: значение `'full'`; профиль со значением `'none'` собирается вторым
      поставщиком без правки читателя — это вход TC-E2E-02 задачи 014-16
11. **TC-UNIT-11:** гейт зелёный на двух названных местах применения
    - Входные данные: чтение `toolAllowlist` в цикле регистрации и `routeDisclosureMode` в
      `toCallToolResult`
    - Ожидаемый результат: проверка зелёная; чтение того же поля в третьем файле — красная

## Примечания

Владелец седьмого поля — эта задача: тип, поставщик умолчаний и умолчание `'full'`. Задача 014-16 —
потребитель: она читает `routeDisclosureMode` через объявленный здесь читатель и применяет значение
к трём полям успешного ответа.

`security.md` §7.5.3a объявляет интерфейс семью полями и в правиле 2 гейта называет семь имён с двумя
названными местами применения. Расхождение с `data-model.md` §4.5.3 закрыто в пользу колонки: она
заведена решением владельца 2026-08-13.

Как прочитанный профиль доходит до цикла регистрации, архитектура не объявляет: §3.4.3 называет одно
новое необязательное поле `principals?: PrincipalResolver` в `CreateServerDeps`. Пункт закрывается
задачей 014-10 вместе с менеджером сессий.
