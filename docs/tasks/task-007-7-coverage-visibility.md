# Task 007-7: Видимость покрытия и кэша (E2E)

## Use Case Connection

- UC-2: агент выясняет, на каких сетях вопрос имеет смысл
- UC-1, альтернативные A1 (повторный вызов) и A2 (сеть вне покрытия)

## RTM

**R-72**

## Task Goal

Доказать, что новая capability видна ровно там, где она есть, — и невидима там, где её нет. Оба
последних пункта DoD задачника A-1 закрываются здесь.

## Почему это отдельная задача

Предыдущие задачи доказывали поведение **адаптера**. Здесь доказывается поведение **системы**: что
матрица покрытия, гейт и кэш говорят об одном и том же. TASK-006 показала, чем кончается расхождение
этих трёх ответов (H-1: матрица обещала, транспорт не мог), и лекарством было «один предикат
обслуживает всех трёх читателей». Тесты ниже — проверка, что лекарство подействовало.

## Changes Description

Кода не добавляется. Задача целиком состоит из тестов; если хоть один требует правки продукта,
правка идёт в задачу-владельца соответствующей RTM-строки, а не сюда.

### Тесты

#### `packages/mcp-server/test/tools/list-chains.test.ts` — расширить

1. **TC-01** (**AC-4**) — `onchain_list_chains({capability: 'dex.volume.history'})`:
   `total` равен числу сетей реестра, чьё `vendors.defillama` присутствует в `DEFILLAMA_DEX_CHAINS`.
   Ожидание **вычисляется в тесте из тех же двух источников**, не зашивается литералом.
2. **TC-02** — то же значение **строго меньше** `total` для `chain.tvl` по тому же реестру.
   Это и есть машинная формулировка «мы не переобещали»: если кто-то вернёт наивный предикат, два
   числа сравняются и тест упадёт с понятной причиной.
3. **TC-03** — в строке покрытой сети (`ethereum`) `capabilities[]` содержит `dex.volume.history`;
   в строке непокрытой (`zcash`) — **не** содержит, но содержит `chain.tvl`.
4. **TC-04** — тул по-прежнему не делает **ни одного** сетевого вызова (инжектированный
   `fetchImpl`-счётчик = 0).

#### `packages/mcp-server/test/e2e.inprocess.test.ts` — расширить

5. **TC-E2E-01** (**AC-3**) — два одинаковых вызова `onchain_dex_volume` подряд через реальный
   `CapabilityRegistry` с реальным двухуровневым кэшем и фейковым `fetchImpl`:
   первый — `_meta.cache.status === 'miss'`, второй — `'hit'` с определённым `ageMs`;
   `fetchImpl` вызван **один** раз.
6. **TC-E2E-02** — вызов по непокрытой сети даёт `isError: true`, текст называет capability и сеть и
   перечисляет доступные сети; `fetchImpl` вызван **0** раз.
7. **TC-E2E-03** — сообщение об отказе не длиннее разумного и не вываливает все 274 слага
   (существующий кап в десять записей + честное `+N more`).

## Acceptance Criteria

- [ ] `total` для новой capability вычислен из двух источников, а не зашит
- [ ] `total(dex.volume.history) < total(chain.tvl)` — переобещание ловится машинно
- [ ] `miss` затем `hit`, один сетевой вызов на два обращения
- [ ] Непокрытая сеть: `isError`, ноль сетевых вызовов, перечень доступного
- [ ] `pnpm test` зелёный целиком

## Notes

TC-02 — самый ценный тест задачи, и стоит сказать почему. Он проверяет не число, а **отношение**:
покрытие DEX-объёмов обязано быть строго у́же покрытия TVL. Это утверждение переживёт и синхронизацию
реестра, и дрейф вендора, тогда как любое литеральное ожидание (274, 458) сломается на первом же
обновлении и будет «починено» правкой числа — то есть перестанет что-либо проверять.
