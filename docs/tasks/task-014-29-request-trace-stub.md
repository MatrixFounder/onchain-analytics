# Задача 014.29: форма записи следа запроса `[STUB]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Зафиксировать форму записи следа запроса и её леджер до того, как след начнут писать четыре пути.

**Why форма раньше записи.** След пишется на попадании в кеш, на ожидании чужого вендорского вызова,
на живом вызове и на отказе. Четыре пути, писавшие в разной форме, дали бы T-015 четыре источника
вместо одного.

### Состав записи

Двадцать четыре колонки, из них одиннадцать объявлены `NOT NULL`.

| Колонка               | Тип     | Пусто | Смысл                                                        |
| :-------------------- | :------ | :---- | :----------------------------------------------------------- |
| `id`                  | TEXT    | нет   | ULID; объявлен `TEXT PRIMARY KEY NOT NULL` (§4.5.2a)         |
| `received_at`         | INTEGER | нет   | время допуска, epoch-ms UTC (R-27.5)                         |
| `completed_at`        | INTEGER | нет   | время завершения, epoch-ms UTC                               |
| `principal_id`        | TEXT    | нет   | `api_tokens.id`, либо `local` в локальном профиле            |
| `user_id`             | TEXT    | да    | `users.id`; пусто в локальном профиле                        |
| `access_profile_id`   | TEXT    | да    | профиль доступа токена                                       |
| `client_request_id`   | TEXT    | нет   | значение клиента, иначе ULID, выпущенный сервером            |
| `session_id`          | TEXT    | да    | метка сессии транспорта                                      |
| `transport`           | TEXT    | нет   | `stdio` или `http`                                           |
| `tool`                | TEXT    | нет   | имя тула                                                     |
| `capability`          | TEXT    | да    | пусто, когда способность не резолвилась                      |
| `args_hash`           | TEXT    | да    | то же значение, что несёт `cache_entries`                    |
| `outcome`             | TEXT    | нет   | `answer`, `refusal` или `partial_deadline`                   |
| `refusal_class`       | TEXT    | да    | имя класса ошибки, только при `outcome='refusal'`            |
| `served_from`         | TEXT    | нет   | `cache`, `coalesced`, `vendor` или `none`                    |
| `cache_age_ms`        | INTEGER | да    | возраст записи кеша                                          |
| `vendor_provider`     | TEXT    | да    | `REFERENCES providers(id)`                                   |
| `vendor_credits`      | INTEGER | да    | вклад запроса в `usage`; пусто при `served_from='coalesced'` |
| `vendor_calls`        | INTEGER | да    | вклад в `usage_window.calls_made`; пусто при `coalesced`     |
| `vendor_day`          | INTEGER | да    | координата `usage(provider, day)`                            |
| `vendor_window_start` | INTEGER | да    | координата `usage_window(provider, window_start)`            |
| `escalated_to_paid`   | INTEGER | нет   | `0` или `1`, умолчание `0` (R-28.2)                          |
| `tried_json`          | TEXT    | да    | пройденный порядок адаптеров, JSON как TEXT                  |
| `created_at`          | INTEGER | нет   | epoch-ms UTC                                                 |

**Why `id` несёт слово `NOT NULL` рядом с `PRIMARY KEY`.** SQLite допускает `NULL` в колонке
`TEXT PRIMARY KEY`, Postgres — нет (`data-model.md` §4.5.2a). Один и тот же DDL без этого слова даёт
на двух осях разное ограничение и разный счёт обязательных колонок.

**Why `principal_id` не допускает пустого значения.** Запись существует ради тарификации, а запись
без плательщика тарификации не служит. Протокольный отказ строки следа не оставляет: у запроса,
отвергнутого на шаге 1 или 2, принципала нет. Он наблюдаем в канале диагностики (§4.5.8).

**Why `principal_id` — метка, а не внешний ключ.** У принципала локального профиля строки токена
нет, поэтому внешний ключ отверг бы запись на том транспорте, которому токен не нужен.

**Why `tool` не допускает пустого значения при пустом `capability`.** Строка пишется на каждый
допущенный вызов тула, включая те, где способность не резолвится. Имя тула известно всегда, имя
способности — не всегда.

**Why `args_hash` — то же значение, что в кеше.** Хеш выдаёт `deriveArgsHash(capability, args)`
(`packages/core/src/net/args-hash.ts:44`). Два следа разных принципалов над равными аргументами
несут равные хеши, что и наблюдает AC-8. T-014 не добавляет принципала во вход (R-5.1).

### Связь с вендорским расходом — координата, а не ссылка на строку

Пять вендорских колонок вместо одной ссылки: `vendor_provider`, `vendor_credits`, `vendor_calls`,
`vendor_day`, `vendor_window_start`.

| Что адресуется                                 | Колонки                                   |
| :--------------------------------------------- | :---------------------------------------- |
| корзина `usage(provider, day)`                 | `vendor_provider` + `vendor_day`          |
| корзина `usage_window(provider, window_start)` | `vendor_provider` + `vendor_window_start` |
| вклад этого запроса                            | `vendor_credits`, `vendor_calls`          |

**Why координата, а не ссылка на строку.** `usage` ключуется `(provider, day)`, `usage_window` —
`(provider, window_start)`. Обе величины — счётчики по окнам, и построчной записи, на которую можно
указать, не существует.

### `served_from` имеет четыре значения

| Значение    | Когда записывается                                   |
| :---------- | :--------------------------------------------------- |
| `cache`     | ответ прочитан из кеша                               |
| `coalesced` | запрос ждал чужого незавершённого вендорского вызова |
| `vendor`    | запрос был ведущим и сам ходил к вендору             |
| `none`      | ни кеш, ни вендор запрос не обслуживали              |

Четвёртое значение — `coalesced`, решение владельца 2026-08-13, закрывающее `OQ-T014-SA-1`.

**Why ведомый не записан ни как `vendor`, ни как `cache`.** Платят оба клиента (OQ-6), и один
вендорский вызов обслужил два списания. Свёртка ведомого в соседа теряет счёт, который T-015 обязан
проследить: сколько списаний породил один вендорский вызов.

**Why у ведомого нет собственного расхода.** `vendor_credits` и `vendor_calls` на такой строке
пусты; всю величину держит строка ведущего.

**Why пусто, а не `0`.** Ноль утверждает, что расход здесь измерен и оказался нулевым. Это неверно:
расход стоит на строке ведущего. Пустое значение говорит, что величина сюда не относится.

**Why суммирование сходится с `usage`.** `SUM` пропускает пустые значения в обоих движках, поэтому
строка ведомого не добавляет ничего ни к одной сумме (R-27.3). Период из одних ведомых даёт пустой
результат, который читатель показывает как отсутствие относимого расхода.

**Why координаты корзин записаны и на строке ведомого.** Они называют корзины `usage` и
`usage_window`, в которые попал вызов ведущего. Это связь списания ведомого с расходом, который его
обслужил.

### Ключ дедупликации

`UNIQUE (principal_id, client_request_id, received_at)`

**Why каждый компонент `NOT NULL`.** В обоих движках `NULL` не равен `NULL` в уникальном индексе,
поэтому один допускающий пустое значение компонент отключил бы дедупликацию целиком. Сервер
выпускает `client_request_id`, когда клиент его не прислал.

**Why `received_at` входит в ключ.** Повтор клиента — новый серверный запрос: он допускается заново,
читает кеш заново и может заново вызвать вендора. Своя строка ему нужна. Идемпотентность списания по
`client_request_id` — уровнем выше, в T-015.

### Ограничения и индексы

Ограничения:

- `CHECK (outcome IN ('answer','refusal','partial_deadline'))`
- `CHECK (served_from IN ('cache','coalesced','vendor','none'))`
- `CHECK ((outcome = 'refusal') = (refusal_class IS NOT NULL))`
- `CHECK (escalated_to_paid IN (0,1))`

Индексы:

- `idx_request_trace_principal (principal_id, received_at)` — периодный запрос T-015 по принципалу
- `idx_request_trace_received (received_at)` — удержание
- `idx_request_trace_spend (vendor_provider, vendor_day)` — сверка с `usage`

**Why `outcome` несёт три класса `ADR-003` D4 и ничего больше.** Ответ, отказ и частичный ответ по
дедлайну. Третий класс тарифицируется по полной цене в T-015, поэтому его нельзя свернуть ни в
одного из соседей.

### Леджер: одна запись, при завершении

Запись живёт только на добавление и переживает перезапуск (R-27.7). Резервирования с последующим
дописыванием нет.

**Why не две фазы.** Двухфазная строка не была бы только-добавляемой. Это обратный выбор по
сравнению с `usage`, который является аддитивным счётчиком и потому резервирует и сверяет.

**Why следствие названо, а не скрыто.** Процесс, умерший в середине запроса, строки следа не
оставляет. Такой запрос виден по строкам диагностики, записанным до падения: их `trace_id` не
находит строки следа (`data-model.md` §4.5.8).

**Why этого следа может не быть вовсе.** Словарь диагностики закрыт восемью событиями, и события про
прерванный запрос среди них нет. Запрос, не породивший ни одного из восьми, после падения процесса
не наблюдаем ничем.

### Удержание

`tried_json` — слой RAW: обнуляется через 90 дней. Строка — слой NORMALIZED: хранится не менее года.
Оба прохода — задания, пишущие в `retention_runs` (§4.5.9).

### Почему запись ведётся и без списания

T-014 списания не делает. След нужен T-015, и без записи, начатой сейчас, T-015 посчитает только с
даты своего запуска (R-27.4).
