# Revisit typescript pin ^6.0.3 when tsup supports TS7 dts

> **DONE 2026-07-28. Ответ: пин держит реальная зависимость — но не tsup.**
> `typescript-eslint@8.65.0` объявляет peer `typescript: ">=4.8.4 <6.1.0"`. TS 7 вне диапазона, и
> его не поддерживает **ни одна** опубликованная версия, включая пререлизы `8.65.1-alpha.1…8`.
> Владелец подтвердил, что пин не был его требованием и должен существовать только если этого
> требует зависимость. Требует — значит остаётся, но приведён к правильной форме и с правильным
> триггером пересмотра.

## Что было записано изначально (M0, 2026-07-22)

tsup 8.5.1 ломается на dts под `typescript@7` (TypeError в нативном API) и выдаёт TS5101
(`baseUrl` deprecated) под TS6 — M0 уезжает на TS `^6.0.3` с двухшаговой сборкой
(`tsup` с `dts:false`, затем `tsc --emitDeclarationOnly`). Формулировка триггера — «когда tsup
научится TS7 dts» — **неверна**, и именно она держала запись открытой шесть дней в статусе
ожидания релиза, которого ждать бессмысленно.

## Измерено 2026-07-28

**Кто на самом деле держит пин.**

| Пакет                                               | peer на typescript                 |
| :-------------------------------------------------- | :--------------------------------- |
| `typescript-eslint@8.65.0` (и все `8.65.1-alpha.*`) | **`>=4.8.4 <6.1.0`** ← ограничение |
| `ts-api-utils@2.5.0` (latest)                       | `>=4.8.4`                          |
| `tsup@8.5.1`                                        | `>=4.5.0`                          |

Ни `tsup`, ни `ts-api-utils` не мешают. Мешает линтер: `@typescript-eslint/typescript-estree`
загружает модуль `typescript` даже в syntax-only режиме (наш `eslint.config.js` берёт
`tseslint.configs.recommended` без `project`/`projectService`, то есть без type-aware правил — но
парсер всё равно требует компилятор).

**Про сборку в один шаг — по-прежнему заблокировано, и виновник назван точно.** Изолированный
прогон tsup 8.5.1 + typescript 7.0.2 с `dts: true`:

```
TypeError: Cannot read properties of undefined (reading 'useCaseSensitiveFileNames')
    at .../rollup-plugin-dts@6.1.1_rollup@4.53.2_typescript@5.7.3/...
```

То есть падает `rollup-plugin-dts@6.1.1`, который тянет собственный `typescript@5.7.3`. tsup с M0
не выпускался (8.5.1 = npm `latest`). Всё это уже корректно описано в
`packages/mcp-server/.AGENTS.md` («tsup bundles its own dts pipeline — rollup-plugin-dts's logic»)
— **поправка к предыдущей редакции этой записи**, где было сказано, будто `.AGENTS.md` винит tsup.
Не винит; документ точнее, чем утверждала запись.

**Сам репозиторий к TS7 готов** — обе сборки чисто проходят `--noEmit` под 7.0.2 (read-only, чужим
компилятором, репозиторий не тронут):

```
tsc 7.0.2 --noEmit -p packages/core/tsconfig.json        -> exit 0
tsc 7.0.2 --noEmit -p packages/mcp-server/tsconfig.json  -> exit 0
```

Так что блокирует **только** линтер. Как только `typescript-eslint` расширит peer — переход
становится вопросом одной строки в двух `package.json`.

## Что было сделано

**`^6.0.3` → `~6.0.3` в `packages/core` и `packages/mcp-server`.** Старый диапазон был **шире
ограничения**: `^6.0.3` = `>=6.0.3 <7.0.0`, а peer заканчивается на `<6.1.0`. Сегодня безвредно —
стабильных 6.x опубликовано ровно две, `6.0.2` и `6.0.3`, никакой 6.1 не существует. Но в день
выхода TS 6.1 обычный `pnpm install` молча увёл бы нас за границу поддерживаемого окна:

| версия    | `^6.0.3`      | `~6.0.3` | внутри peer `<6.1.0` |
| :-------- | :------------ | :------- | :------------------- |
| 6.0.3     | ✅            | ✅       | ✅                   |
| 6.0.9     | ✅            | ✅       | ✅                   |
| **6.1.0** | **✅ ← дыра** | ❌       | ❌                   |
| 7.0.2     | ❌            | ❌       | ❌                   |

И это не было бы поймано: **pnpm на нарушение peer-диапазона отвечает одной строкой `[WARN]` и
кодом выхода 0** (проверено — подставил `^7.0.2`, `pnpm install --lockfile-only` завершился
успешно). CI на эту строку не гейтится. `~6.0.3` закрывает дыру там, где она возникает, оставляя
патчи `6.0.x` проходить свободно; резолв не изменился, в локфайле поменялись два спецификатора.

Глобальный `strict-peer-dependencies=true` не включался: `pnpm peers check` сейчас чист, но это
политика на весь репозиторий, ломающая установку при любом будущем расхождении, а дыра была ровно
одна и закрыта точечно.

## Триггер пересмотра — не tsup

Следить за **peer-диапазоном `typescript-eslint`**. Проверка в одну команду:

```sh
npm view typescript-eslint peerDependencies.typescript
```

Не `<6.1.0` → можно поднимать TypeScript (репозиторий, как показано выше, уже готов). Отдельно, и
только для схлопывания сборки в один шаг — `rollup-plugin-dts` с поддержкой TS7:

```sh
mkdir -p /tmp/dtsprobe && cd /tmp/dtsprobe && npm i -D tsup typescript >/dev/null \
  && printf 'export const x = (n: number): string => `${n}`\n' > index.ts \
  && npx tsup index.ts --dts --format esm
```
