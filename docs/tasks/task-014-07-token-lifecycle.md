# Задача 014.07: выпуск, хеш с префиксом, отзыв, журнал `[LOGIC]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети
- UC-3 — оператор запускает локально

<!-- contract:goal -->

## Цель задачи

Реализовать жизненный цикл токена в пакете `mcp-server`: выпуск через CSPRNG, хранение дайджеста с
перцем, видимый префикс, отзыв и журнал только на добавление.

**Why пакет `mcp-server`, а не `core`.** `security.md` §7.5.1: проверки живут в пакете `mcp-server`,
рядом с транспортом, которому они нужны. `packages/core` не получает знания о токенах, ролях и
заголовках. SQL, называющий таблицы личности, пишется из того же пакета.

## Описание изменений

### Изменения в существующих файлах

Оба файла — стабы задачи 014-06. Каждый заменяется реализацией поверх репозитория 014-03: SQL идёт
через общий механизм доступа, квалифицированный схемой `onchain`.

**Why через общий механизм, а не своим соединением.** Клиент записи один на процесс, и права на
таблицы держит роль состояния (`deployment.md` §10.5.1). Второе соединение из хранилища токенов
завело бы вторую роль и второй набор прав.

**Файл `packages/mcp-server/src/auth/token-store.ts`:**
- Реализовать `issue`: значение чеканит `randomBytes` из `node:crypto`, энтропия не ниже 128 бит
- Реализовать `lookup`: одно индексное равенство по дайджесту, решение о живости — в коде
- Реализовать `revoke`: `status = 'revoked'` и `revoked_at`, строка не удаляется
- Реализовать `appendAudit`: вставка без правки и без удаления

**Файл `packages/mcp-server/src/auth/user-store.ts`:**
- Реализовать `createUser`, `findUser`, `listUsers` поверх таблицы `users`

### Форма токена, воспроизводится дословно

`security.md` §7.5.2: «`oi_` + an 8-character random label + `_` + a 43-character base64url secret
over 32 random bytes. The stored `prefix` is the leading 11 characters».

| Часть | Значение |
| :--- | :--- |
| постоянное начало | `oi_` |
| случайная метка | 8 символов |
| разделитель | `_` |
| секрет | 43 символа base64url над 32 случайными байтами |
| хранимый `prefix` | первые 11 символов значения |

**Why у токена есть префикс.** R-15.2 требует, чтобы токен опознавался без раскрытия. Префикс
называет его в строке журнала, в списке администратора и в записи диагностики (`security.md` §7.5.2).

**Why префикс никогда не ключ поиска.** Поиск идёт только по дайджесту. Второй путь поиска по
короткому несекретному значению был бы более слабым удостоверением в той же таблице.

**Why 32 случайных байта.** R-15.1 требует не менее 128 бит энтропии. Тридцать два байта дают 256
бит, и в base64url это 43 символа.

### Дайджест

`api_tokens.token_hash` несёт `sha256(pepper || presented)` в нижнем регистре hex, 64 символа
(`data-model.md` §4.5.4, `CHECK (length(token_hash) = 64)`). Перец — секрет `ONCHAIN_TOKEN_HASH_SALT`
из `.env` (`deployment.md` §10.3).

**Why перец лежит вне базы.** Соль в той же базе делает дамп самодостаточным. Украденная таблица без
перца — не список кандидатов для словарного перебора (`data-model.md` §4.5.4).

**Why перец один на процесс, а не соль на строку.** Чтение — одно индексное равенство по
`token_hash`. Соль на строку заставила бы перебирать каждую строку-кандидата (`security.md` §7.5.2).

**Следствие, названное заранее.** Смена перца обесценивает все выпущенные токены разом. Пути
пересчёта нет: предъявленные секреты не хранятся (`security.md` §7.5.2).

**Why сравнения секрета в коде нет.** Движок хешит предъявленное значение и просит у индекса
совпадение, поэтому строкового равенства над удостоверением, время которого можно замерить, не
возникает (`security.md` §7.5.2).

### Столкновение по префиксу

`api_tokens.prefix` объявлен `UNIQUE`. Выпуск повторяет чеканку на нарушении ограничения и не
записывает неоднозначную строку (`data-model.md` §4.5.4).

**Why префикс уникален здесь, а в образце нет.** R-15.2 требует, чтобы префикс опознавал токен
однозначно. Повторяющийся префикс делает опознание неоднозначным.

### Четыре состояния отказа

Решение принимается в коде над строкой, которую вернул запрос, а не в его `WHERE`. Четыре состояния
отказывают, и каждое — отдельный `refusal_class` (`security.md` §7.5.2):

| Состояние | Наблюдается на строке | Клиент видит |
| :--- | :--- | :--- |
| неизвестный токен | строки нет | `401` |
| отозван | `api_tokens.status = 'revoked'` | `401` |
| истёк | `api_tokens.expires_at <= now` | `401` |
| пользователь приостановлен | `users.status = 'suspended'` | `401` |

**Why один статус на четыре состояния.** Класс нужен оператору и пишется в строку диагностики
`auth.rejected` (`data-model.md` §4.5.8). Вызывающий без валидного токена из различия не узнаёт
ничего.

**Why класс не пишется в `request_trace.refusal_class`.** У запроса, отвергнутого на шаге 2,
принципала нет, а `request_trace.principal_id` объявлен `NOT NULL`, поэтому строки этой таблицы для
него не существует (`security.md` §7.5.2, `data-model.md` §4.5.7).

Отрисовку ответа `401` держат задачи 014-12 и 014-26. Текущая задача поставляет класс отказа.

### Отзыв и сессия

Каждый запрос проверяется заново, включая запрос в установленной сессии. Кеша проверенных токенов
нет, поэтому отзыв действует со следующего запроса (R-15.6, AC-26).

Отозванный токен теряет и сессию: отвергнутый запрос снимает запись `sessionId` → `McpServer` и
закрывает транспорт. Снятие пишется событием `session.evicted` с причиной в `detail_json`.

**Why запись снимается, а не отвергается только запрос.** Сессия Streamable HTTP держит открытый
поток. Оставленная запись позволила бы позднему POST переприцепиться к сессии, чьего владельца
больше нет (`security.md` §7.5.2).

**Why уже открытый поток не обрывается.** Такой поток не шлёт запроса, поэтому снятие для него
ничем не запускается. `interfaces.md` §5.4.7 закрывает вопрос решением владельца от 2026-08-12:
поток заканчивается на следующем запросе клиента или на вытеснении по простою.

### Журнал

Действия с пользователями, токенами и профилями пишутся в `access_audit` только на добавление.
Словарь действий закрыт: `user.create`, `user.suspend`, `token.issue`, `token.revoke`,
`profile.update` (`data-model.md` §4.5.5).

`before_json` и `after_json` не несут ни значения токена, ни его дайджеста: событие о токене
записывает `id` и `prefix`.

**Why журнал читается шире, чем путь аутентификации.** Читателей у журнала больше, а дайджест —
проверяющее значение (`data-model.md` §4.5.5).

Правило `DO INSTEAD NOTHING` на `DELETE` и триггер `BEFORE UPDATE` для Postgres ставит задача
014-35; два триггера `BEFORE` с `RAISE(ABORT)` для SQLite — задача 014-36. Текущая задача пишет код
поверх этих объявлений и проверяет их поведение.

## Тест-кейсы

### Сквозные тесты
1. **TC-E2E-01:** отозванный токен получает отказ на следующем запросе
   - Входные данные: активная сессия, отзыв токена, следующий запрос тем же токеном
   - Ожидаемый результат: `401`; запись сессии снята, событие `session.evicted` записано (AC-26)

### Модульные тесты
1. **TC-UNIT-01:** значение токена не встречается в хранилище открытым
   - Входные данные: выпуск токена, затем поиск его значения по всем колонкам трёх таблиц
   - Ожидаемый результат: совпадений нет (AC-26)
2. **TC-UNIT-02:** форма выпущенного значения совпадает с §7.5.2
   - Входные данные: одно значение из `issue`
   - Ожидаемый результат: начало `oi_`, метка 8 символов, разделитель `_`, секрет 43 символа
     base64url; `prefix` равен первым 11 символам (AC-41)
3. **TC-UNIT-03:** дайджест равен `sha256(перец || значение)` в нижнем регистре hex
   - Входные данные: известные перец и значение токена
   - Ожидаемый результат: сохранённое значение совпадает посимвольно с вычисленным вне кода, длина
     64
4. **TC-UNIT-04:** смена перца обесценивает выпущенный токен
   - Входные данные: `lookup` того же значения при другом перце
   - Ожидаемый результат: строка не найдена
5. **TC-UNIT-05:** два выпуска подряд дают разные значения и разные префиксы
6. **TC-UNIT-06:** столкновение по `UNIQUE (prefix)` приводит к повторной чеканке
   - Входные данные: генератор, первым вызовом повторяющий уже занятый префикс
   - Ожидаемый результат: записана строка с другим префиксом, неоднозначной строки нет
7. **TC-UNIT-07:** четыре состояния отказа различимы по возвращённой строке
   - Входные данные: неизвестный дайджест, отозванный токен, истёкший токен, приостановленный
     пользователь
   - Ожидаемый результат: четыре разных класса отказа при одном статусе `401`
8. **TC-UNIT-08:** журнал не изменяется задним числом
   - Входные данные: `UPDATE` и `DELETE` по строке журнала на объявлении SQLite задачи 014-36
   - Ожидаемый результат: `UPDATE` поднимает ошибку, `DELETE` не удаляет строки (AC-41)
9. **TC-UNIT-09:** запись журнала о токене несёт `id` и `prefix`
   - Входные данные: выпуск и отзыв одного токена
   - Ожидаемый результат: в `before_json` и `after_json` нет ни значения токена, ни дайджеста
10. **TC-UNIT-10:** отзыв не удаляет строку
    - Входные данные: `revoke` по активному токену
    - Ожидаемый результат: строка на месте, `status = 'revoked'`, `revoked_at` заполнено

### Регрессионные тесты
- `pnpm test`, `pnpm typecheck`
- Значение токена не встречается в выводе ни на одном уровне логирования
- Поиск `token`, `role`, `Authorization` по `packages/core/src` не даёт новых совпадений

администратора над пользователями и токенами — задача 014-08, засев первого администратора —
задача 014-37.
