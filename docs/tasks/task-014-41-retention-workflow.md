# Задача 014.41: воркфлоу `onchain-retention`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Спроектировать один воркфлоу n8n по имени `onchain-retention`, выполняющий три задания очистки, и
получить на каждый прогон каждого задания строку в `onchain.retention_runs`.

**Why исполнитель — n8n, а не серверный процесс.** Постоянное ограничение 1 держит автономный цикл
на n8n бессрочно (ARCHITECTURE §1.2 пункт 1). Сетевой профиль мог бы нести планировщик; владелец
решил его не добавлять (решение 2026-08-13, закрывает `OQ-T014-DEP-2`).

## Описание изменений

### Новые файлы

- `n8n-workflows/proposed/onchain-retention.json` — определение воркфлоу, собранное и
  провалидированное в репозитории
- `n8n-workflows/README.md` — раздел про каталог `proposed/` и порядок продвижения в `exported/`

Серверный процесс планировщика не получает: файлов в `packages/` эта задача не добавляет.

**Why `proposed/`, а не сразу `exported/`.** `exported/` — зеркало того, что РАБОТАЕТ, и `import.sh`
импортирует оттуда всё подряд. Предложение, положенное туда, установилось бы следующим прод-импортом
— с креденшелом, которого на том инстансе нет. Разделение оставляет `import.sh` нетронутым.
Продвижение после снятия блокировок: `cp proposed/… exported/` → `import.sh` → проверка на инстансе
→ `export.sh`, который перезапишет файл формой инстанса и сделает его настоящим экспортом.

### Три задания

| Задание                  | Цель                    | Действие                                | Окно по умолчанию                                |
| :----------------------- | :---------------------- | :-------------------------------------- | :----------------------------------------------- |
| `diagnostics.purge`      | `onchain.diagnostics`   | удаляет строки старше окна              | 90 дней; пол 90 дней, максимум — окно NORMALIZED |
| `request_trace.raw_null` | `onchain.request_trace` | ставит `tried_json` в NULL за окном RAW | 90 дней; пол 90 дней, максимум — окно NORMALIZED |
| `request_trace.purge`    | `onchain.request_trace` | удаляет строки за окном NORMALIZED      | 365 дней; пол 365 дней, максимум 730 дней        |

Имена заданий воспроизводят §10.6 дословно и попадают в колонку `job` таблицы `retention_runs`
(`data-model.md` §4.5.9).

### Строка на каждый прогон

Каждое задание в том же проходе пишет строку в `onchain.retention_runs`: `id`, `job`,
`target_table`, `period_from`, `period_to`, `rows_affected`, `started_at`, `finished_at`, `outcome`,
`detail_json`. Уникальный ключ дедупликации — `(job, period_from, period_to, started_at)`.

Прогон, удаливший ноль строк, всё равно пишет свою строку с `rows_affected = 0` и `outcome = 'ok'`.

**Why нулевой прогон тоже пишет строку.** «Нечего удалять» и «задание не запускалось» — разные
факты, и различает их только записанная строка (DB-SCHEMA §4, §4.5.9).

**Why каждое задание пишет строку внутри своего прохода.** Строка, записанная отдельным поздним
проходом, не может назвать период, который удаление покрыло.

Каждый проход пишет также одну строку `retention.cleanup` в `onchain.diagnostics`; этот воркфлоу —
её единственный писатель (§4.5.8, §10.6.1).

### Окно вне диапазона

Окно вне диапазона §10.3.1 отвергается: задание не удаляет ничего и пишет строку `retention_runs` с
`outcome = 'failed'`, называя отвергнутую настройку в `detail_json`. Отказ доходит до Telegram через
`errorWorkflow`.

**Why отказ, а не подрезка.** Подрезанное окно удаляет строки, которые оператор просил сохранить, и
таблица записала бы подрезанный период как запрошенный.

### Форма воркфлоу

| Элемент         | Значение                                                                       |
| :-------------- | :----------------------------------------------------------------------------- |
| Триггер         | Schedule, ежедневно                                                            |
| Параметр-нода   | Set-нода с тремя окнами §10.3.1, паттерн Normalize Input                       |
| Креденшел       | Postgres-креденшел state-роли `onchain_engine_state` (§10.5), не «Supabase DB» |
| Писатели        | по одной Postgres-ноде на задание, за каждой — вставка в `retention_runs`      |
| `errorWorkflow` | `onchain-error-alert`                                                          |
| Экспорт         | `./n8n-workflows/export.sh` → `n8n-workflows/exported/onchain-retention.json`  |
| Стикер          | обязательная Overview-заметка (CLAUDE.n8n.md)                                  |

**Why окна живут в параметр-ноде.** Один узел владеет контрактом конфигурации, и смена окна не
правит ноду с запросом (CLAUDE.n8n.md, §10.6.1).

**Why окна не ключи окружения.** Задания исполняются в n8n, а n8n не читает `.env` серверного
процесса; `$env` на этом инстансе заблокирован (§10.3.1, CLAUDE.n8n.md).

**Why отдельный креденшел.** Действующий «Supabase DB» аутентифицируется как роль снапшоттера, у
которой нет прав на двенадцать таблиц движка, поэтому установка добавляет второй Postgres-креденшел
(§10.5).

Значения времени — epoch-ms UTC, `id` — ULID, порождаемый в Code-ноде (DB-SCHEMA §1.2, §1.3).
Вставка в `retention_runs` связывает данные параметром запроса и не интерполирует их в SQL
(CLAUDE.n8n.md).

### Установка требует явного согласия владельца

Архитектура предлагает воркфлоу; она его не создаёт и не активирует. Инстанс общий, и создавать на
нём допускается только `onchain-*` воркфлоу этого проекта (CLAUDE.n8n.md, §10.6.1). Установка —
шаг 7 порядка §10.4.2, выполняемый после согласия владельца.

**Why согласие отдельным шагом.** Активация пишущего воркфлоу на общем инстансе — операция над
чужой средой, и её нельзя вывести из принятой задачи.

## Тест-кейсы

### Что проверено до установки

- **TC-WF-01 выполнен.** `validate_workflow` на собранном графе: `valid: true`, ошибок 0,
  предупреждений 0, связей 14, выражений 7. Тела Code-нод при валидации заменены заглушкой и
  проверены отдельно синтаксическим разбором в той обёртке, в которую их помещает n8n, — все шесть
  разбираются. `validate_workflow` тела Code-нод и не анализирует.
- **Логика окон прогнана на шести сценариях** (умолчания; 1000 д при максимуме 730; 30 д при поле 90;
  400 д RAW выше NORMALIZED 365; те же 400 д при NORMALIZED 730 — допустимо; нечисловое значение).
  Во всех случаях отвергнутое задание получает `cutoff: null`, `outcome: 'failed'` и названную
  настройку **в том виде, в каком она задана**, а `period_to > period_from` держится — это CHECK
  таблицы.
- **Каскад отказа NORMALIZED окна.** Максимумы обоих RAW-окон определены через NORMALIZED, поэтому
  недопустимое NORMALIZED окно отвергает все три задания: измерять RAW не против чего.

Предупреждение валидатора «большинство нод без обработки ошибок» отклонено сознательно.
`onError: continueRegularOutput` пустил бы отказ дальше как данные, а этому воркфлоу нужен громкий
отказ через `errorWorkflow` — выбор, который CLAUDE.n8n.md предписывает именно для этого случая.

### Что осталось, и почему это не невыполненная работа

Три предусловия установки не выполнены, и ни одно из них автор не может выдать себе сам:

1. ~~**Роль `onchain_engine_state` на Postgres не создана**~~ — **снято 2026-08-22.** Владелец создал
   `onchain_engine_state` и `onchain_engine_read`; обе `login=true`, ни одна не суперпользователь.
   Шаги записаны в `PROD-RUNBOOK.md` разделом «the two database roles», с разделением на половину без
   секрета и половину с ним.
2. ~~**Миграции 002 и 003 на VM не применены**~~ — **002 применена 2026-08-22**, четыре её встроенных
   гейта зелёные: 0 объектов в `public`, посеянная цель внешнего ключа на месте, ноль сирот на восьми
   таблицах с `REFERENCES`, state-роль не достаёт ни одной таблицы снапшоттера. Схема `onchain` держит
   15 таблиц — три снапшоттера и двенадцать движка. Замер шага 2a: `onchain_engine_read` видит ровно
   три, `onchain_engine_state` — ровно двенадцать, пересечения нет.
   **003 применена владельцем 2026-08-22.** Замер: `users=1`, `api_tokens=1`, `access_audit=2`; админ
   активен, токен активен, префикс правильной формы (`oi_` плюс восемь символов). Постусловия
   рунбука: обе строки журнала начальной загрузки без действующего лица (до первого админа некому
   было действовать), в `api_tokens` нет колонки с открытым токеном — только `token_hash` и `prefix`,
   дайджест 64 знака в нижнем регистре, срок и отзыв пусты.
   **Первая попытка упала и ничего не записала:** в команду ушли многоточия из шаблона инструкции,
   `api_tokens_prefix_check` их отверг, транзакция откатилась целиком. Причина была в инструкции, а не
   в операторе; рунбук исправлен коммитом `128a6b7` — примера этой команды на странице больше нет
   намеренно, потому что команду с заглушками вставляют целиком.
   **Побочно заведён [SEC-2](../issues/sec-2-a-stock-supabase-role-holds-pg-read-all-data-so-the-engine-tables-are-readable-by-it.md):**
   `supabase_read_only_user` состоит в `pg_read_all_data` и читает все пятнадцать таблиц. Это
   измерение шага 2a, и предписанное им исправление — операция над стоковой ролью Supabase.
   **С применением 003 запись перестала быть теоретической:** в `users` лежит адрес админа, в
   `access_audit` — две строки журнала, и обе читаются этой ролью. Дайджест с перцем рабочего токена
   не даёт, поэтому это раскрытие личности и истории, а не компрометация доступа. Решение владельца
   по-прежнему открыто.
3. **Креденшела state-роли в n8n нет.** Замер 2026-08-21: на инстансе ровно один Postgres-креденшел,
   «Supabase DB». Пароль роли — секрет, он живёт только в n8n Credentials, и завести его может лишь
   владелец. Параметры подключения измерены: оба контейнера в сети `n8n-project_default`, n8n резолвит
   `supabase-db` → 172.18.0.26, порт 5432, база `postgres`. Имя креденшела обязано быть ровно
   `Onchain engine state` — воркфлоу ссылается по имени.

Каждый из трёх — операция над чужой средой, и §10.6.1 требует явного согласия отдельным шагом.

## Примечания

`retention_runs` не очищается: таблица растёт на несколько строк в день, а задание, которое чистило
бы её, писало бы в неё же (§4.5.9).

Воркфлоу обслуживает ось хранилища Postgres: на оси SQLite задания ретенции не устанавливаются
(задача 014-38, `deployment.md` §10.1.1). Профиль `local` остаётся без изменений.

Максимум 730 дней применён, а не измерен: объёма запросов HTTP пока нет. §4.5.8 обязуется измерить
число строк первого месяца, и этот замер выводит число заново.

Задача зависит от 014-35 и 014-27. Миграция 014-35 создаёт `onchain.retention_runs` и
`onchain.diagnostics` и выдаёт state-роли права на них; 014-27 закрепляет словарь событий, в
котором объявлено `retention.cleanup`. Задача 014-02 объявляет интерфейсы доступа и не создаёт ни
одной таблицы, поэтому в зависимостях её здесь нет.

Установка воркфлоу — единственный шаг T-014, исполняемый на общем инстансе n8n. Он остаётся
незакрытым, пока владелец не дал согласия, и это состояние отличается от невыполненной работы.
