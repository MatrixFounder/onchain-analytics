# Задача 014.37: seed-миграция первого админа `[LOGIC]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Создать отдельный нумерованный файл под `sql/migrations/`, который заводит первого администратора и
строку его токена из дайджеста, приходящего параметром `psql`. Постусловие: ровно одна строка
`status = 'active'` в `onchain.api_tokens`.

**Why задача заведена отдельно.** §4.4 пункт 5 называет засев админа пятым обязательством T-014 и
требует для него второго нумерованного файла. План не назвал ни файла, ни исполнителя.

**Why миграция, а не путь первого старта.** Путь, создающий админа при старте, достижим до того, как
появился хотя бы один админ. Это единственная неаутентифицированная запись, которой у сетевого
профиля быть не должно (`security.md` §7.5.2, решение владельца, закрывающее `OQ-T014-DM-3`).

## Описание изменений

### Новые файлы

- `sql/migrations/003_seed_engine_admin.sql` — засев одной строки `users`, одной строки `api_tokens`
  и строк журнала

Номер файла следует за миграцией задачи 014-35. PROD-RUNBOOK называет файл шаблоном
`sql/migrations/0NN_seed_engine_admin.sql`.

### Параметры применения

| Параметр | Значение | Кто вычисляет |
| :--- | :--- | :--- |
| `ADMIN_EMAIL` | адрес администратора, в нижнем регистре | владелец |
| `ADMIN_TOKEN_SHA256` | `sha256(pepper \|\| token)`, 64 hex-символа в нижнем регистре | владелец |
| `ADMIN_TOKEN_PREFIX` | первые 11 символов токена (`security.md` §7.5.2) | владелец |
| `ADMIN_USER_ID` | ULID строки `users` | владелец |
| `ADMIN_TOKEN_ID` | ULID строки `api_tokens` | владелец |

Файл начинается блоком предпроверки: на каждый обязательный параметр — `\if :{?VAR}`, иначе `\echo`
с именем параметра и `\quit 1`. Применение идёт с `ON_ERROR_STOP=1`.

**Why дайджест приходит параметром, а не литералом.** Токен в файле миграции — токен в истории git.
Владелец чеканит токен, вычисляет дайджест вне миграции и передаёт только hex. Открытый токен не
достигает ни диска инсталляции, ни репозитория (`security.md` §7.5.2, PROD-RUNBOOK шаги 1–3).

**Why значение токена генерирует владелец.** Сервер сравнивает дайджесты и никогда не нуждается в
секрете обратно. Токен чеканится CSPRNG (`randomBytes` из `node:crypto`) и несёт не менее 128 бит
энтропии (R-15.1, `security.md` §7.5.2).

**Why идентификаторы строк тоже приходят параметрами.** Канон §1.3 запрещает опираться на нумерацию
движка, а SQL не имеет генератора ULID. Литерал в файле сделал бы засев второго админа конфликтом
первичного ключа, а PROD-RUNBOOK называет такой засев штатным путём при утрате токена.

**Why pepper не является параметром.** `ONCHAIN_TOKEN_HASH_SALT` — постоянный секрет класса R-29.1,
он живёт в `.env` сервера и входит в дайджест до применения. Смена pepper обесценивает все выпущенные
токены, и пути перехеширования нет (`security.md` §7.5.2).

### Что записывает файл

1. Строка `onchain.users`: `id = :ADMIN_USER_ID`, `email = :ADMIN_EMAIL`, `role = 'admin'`,
   `status = 'active'`, вставка `ON CONFLICT (email) DO NOTHING`
2. Строка `onchain.api_tokens`: `id = :ADMIN_TOKEN_ID`, `user_id = :ADMIN_USER_ID`,
   `token_hash = :ADMIN_TOKEN_SHA256`, `prefix = :ADMIN_TOKEN_PREFIX`, `status = 'active'`,
   `access_profile_id` — литеральная ULID строки `phase0-unlimited`, вставка
   `ON CONFLICT (token_hash) DO NOTHING`
3. Строки `onchain.access_audit` с `actor_user_id = NULL`: `action = 'user.create'` и
   `action = 'token.issue'`

**Why строки журнала пишутся с пустым актором.** Колонка `actor_user_id` объявлена допускающей NULL
для загрузочной записи: администратора, который выполнил бы операцию, ещё не существует
(§4.5.3, §4.5.5).

**Why строк журнала две.** Каждая операция выпуска и отзыва пишет свою строку (R-15.7), а засев
выполняет две операции: заводит пользователя и выпускает токен.

**Why вставки идемпотентны.** Файл применяется по stdin вручную, и повторный запуск случается при
исправлении соседнего шага. `DO NOTHING` на обоих естественных ключах оставляет число активных строк
неизменным.

**Why существующий пользователь с этим адресом не повышается до админа.** `DO UPDATE SET role`
отдал бы права администратора тому, кто занял адрес раньше засева. Файл в этом случае отказывает и
называет адрес; повышение остаётся операцией администратора (R-15.4).

### Ограничения, которые проверяет движок

- `CHECK (length(token_hash) = 64)` — дайджест хранится 64 hex-символами (§4.5.4)
- `CHECK (length(prefix) >= 8)` — префикс опознаёт токен, не раскрывая его (R-15.2)
- `UNIQUE (prefix)` — опознание однозначно (§4.5.4)
- `CHECK ((status = 'revoked') = (revoked_at IS NOT NULL))` — засеваемая строка активна и без даты
  отзыва

### Применение и проверка

Команда применения (PROD-RUNBOOK, шаг 3):

```bash
ssh vm 'docker exec -i supabase-db psql -qU supabase_admin -d postgres -v ON_ERROR_STOP=1 \
  -v ADMIN_TOKEN_SHA256="'"'"'<64-hex>'"'"'" -v ADMIN_EMAIL="'"'"'you@example.com'"'"'"' \
  < sql/migrations/003_seed_engine_admin.sql
```

Проверка после применения (PROD-RUNBOOK, шаг 4):

```sql
SELECT prefix, role, status FROM onchain.api_tokens t JOIN onchain.users u ON u.id = t.user_id;
```

**Why проверка читает префикс, а не дайджест.** Префикс опознаёт строку и не является ключом поиска;
дайджест — проверяющее значение, и в отчёт оператора он не выводится (§4.5.4, `security.md` §7.5.2).

## Тест-кейсы

### Сквозные тесты

Требуют живого Postgres, помечаются интеграционными и исключаются из прогона CI по R-21.

1. **TC-E2E-01:** засев на свежемигрированной базе

   - Ожидаемый результат: одна строка `users` с `role = 'admin'`, одна строка `api_tokens` со
     `status = 'active'`, две строки `access_audit` с `actor_user_id IS NULL`
2. **TC-E2E-02:** повторное применение с теми же параметрами
   - Ожидаемый результат: число строк `api_tokens` со `status = 'active'` осталось равным одному
3. **TC-E2E-03:** пропущен обязательный параметр
   - Входные данные: применение без `ADMIN_TOKEN_SHA256`
   - Ожидаемый результат: `psql` завершается с ненулевым кодом, называет параметр, строк не пишет
4. **TC-E2E-04:** дайджест неверной длины
   - Входные данные: `ADMIN_TOKEN_SHA256` из 63 символов
   - Ожидаемый результат: отказ по `CHECK (length(token_hash) = 64)`
5. **TC-E2E-05:** короткий префикс
   - Входные данные: `ADMIN_TOKEN_PREFIX` из 7 символов
   - Ожидаемый результат: отказ по `CHECK (length(prefix) >= 8)`
6. **TC-E2E-06:** адрес занят не-администратором
   - Входные данные: строка `users` с тем же адресом и `role = 'user'`
   - Ожидаемый результат: применение отказывает, роль строки не изменилась
7. **TC-E2E-07:** старт сетевого профиля до и после засева
   - Ожидаемый результат: до засева процесс выходит с ненулевым кодом и не связывает сокет; после
     засева связывает `ONCHAIN_HTTP_BIND` (`deployment.md` §10.3.2)

## Примечания

PROD-RUNBOOK (шаг 3) передаёт два параметра — `ADMIN_TOKEN_SHA256` и `ADMIN_EMAIL`, тогда как
`data-model.md` §4.5.3 и `security.md` §7.5.2 требуют ещё и видимый префикс. Задача следует
архитектуре и передаёт префикс параметром. Расхождение вынесено оркестратору.

PROD-RUNBOOK (шаг 1) чеканит токен командой `openssl rand -base64 32`, а `security.md` §7.5.2
объявляет форму `oi_` + 8-символьная метка + `_` + 43-символьный секрет base64url. Команда рунбука
этой формы не даёт, и первые 11 символов её вывода префиксом §7.5.2 не являются. Расхождение
вынесено оркестратору.

`deployment.md` §10.4.2 шаг 4 ссылается на засев админа как на «§4.4 step 4», тогда как в
`data-model.md` §4.4 это пункт 5, а пункт 4 — verify-гейт. Задача следует нумерации `data-model.md`.
Расхождение вынесено оркестратору.

При утрате токена восстановления нет: дайджест односторонний. Второй админ засевается повторением
шагов 1–3 с другим адресом, а утраченная строка отзывается, а не правится (PROD-RUNBOOK).
