# Задача 013-2 — Активация на маршруте, ранг конфликта и запрет платного участника

**Требования:** [R-162], [R-163], [R-183] · **Эпик:** E-1 · **Критерии приёмки:** AC-24, AC-25,
AC-26, AC-45 · **Фаза:** 2 из 10 · **Зависимости:** 013-1

## Use Case Connection

- **UC-20** — разработчик активирует слияние на маршруте способности, чей манифест права не
  объявлял. Конструктор `CapabilityRegistry` отказывает, называя способность и отсутствие права.
  Провал, который надо исключить: активация молча включает слияние для способности, для которой оно
  никогда не было объявлено допустимым.

<!-- contract:goal -->

## Цель задачи

Ввести второй гейт активации на дескрипторе маршрута и обе конструкторные проверки вокруг него так,
чтобы несогласованная конфигурация роняла старт процесса, а не первый запрос.

## Описание изменений

### `packages/core/src/adapters/types.ts`

- `CapabilityRoute` (`:214`) получает `merge?: boolean` — активация. Право (`mergeable`) остаётся
  фактом манифеста, введённым в `013-1`. Две оси независимы: маршрут против способности.
- Новая экспортируемая функция `assertMergeParticipantsAreFree(routes, registrations)` — рядом с
  `assertValidAdapterRegistrations` (`:179`), потому что оба её параметра объявлены в этом файле и
  новых импортов это не требует.
- Правило проверки: для каждой способности, у которой хотя бы один маршрут несёт `merge: true`,
  каждый id из **объединения `adapterIds` всех её маршрутов** обязан резолвиться в регистрацию с
  `tier: 'free'`. Иначе throw с именем способности и первого не-бесплатного участника.
- Проверка читает `tier`. Строку `.trust` она не содержит, поэтому `TC-GATE-02` остаётся зелёным
  без правок.

**Why.** Ранг конфликта — порядок `adapterIds`, а порядок траты ставит платного участника последним.
Последний по порядку — младший по рангу, поэтому платный участник проигрывал бы каждый конфликт
дедупа молча. Проверка превращает это в отказ старта до появления настоящего ранга T-016.

**Почему объединение маршрутов, а не `adapterIds` одного маршрута.** `resolve()` строит `plan` как
дедуплицированное объединение `adapterIds` всех совпавших маршрутов. Платный адаптер, достижимый
только через соседний не-сливаемый маршрут той же способности, вошёл бы в слитый обход непроверенным.
Сегодня такой конфигурации нет; проверка по объединению закрывает её по построению.

### `packages/core/src/adapters/registry.ts`

- Конструктор получает шаг 3 валидации, после шага 1 и независимо от шага 2: если
  `route.merge === true`, строка манифеста, найденная шагом 1, обязана нести право. Иначе — новый
  класс ошибки, называющий способность и отсутствие права, по образцу `UnregisteredPolicyClassError`.
- Маршрут, неверный и по `policy.kind`, и по `merge`, сообщает находку шага 2 первой. Это
  детерминированный разрыв ничьей, а не утверждение о важности одного дефекта над другим.
- Ранг конфликта не заводит новой структуры: это порядок `plan`, который конструктор уже строит.
  Докстринг механизма называет переиспользование временным и адресует замену к T-016.

### `packages/core/src/index.ts` и `packages/mcp-server/src/index.ts`

- `assertMergeParticipantsAreFree` экспортируется из ядра тем же приёмом, что
  `assertValidAdapterRegistrations` (`index.ts:94`).
- `mcp-server/src/index.ts` зовёт её сразу после `assertValidAdapterRegistrations(adapterRegistrations)`
  (`:38`) и до конструирования `CapabilityRegistry`.
- **Сам вызов проверяется тестом.** Прецедент — `packages/mcp-server/test/registration-validation.integration.test.ts`:
  он мокает ядро одной испорченной регистрацией и утверждает, что `await import('../src/index.js')`
  отклоняется. Зеркальный кейс подаёт платного участника на сливаемом маршруте.

**Why.** Без такого теста удаление строки вызова оставляет TC-UNIT-01 и TC-UNIT-02 зелёными: они
зовут функцию напрямую. Проверка тогда объявлена, но не применяется — то самое различение, которым
обоснованы WI-34…WI-37.

### Фазы

- **Фаза 1.** Тип `merge`, сигнатуры шага 3 и `assertMergeParticipantsAreFree` с пустыми телами.
  Тесты пишутся сразу и красные.
- **Фаза 2.** Логика обеих проверок, вызов при старте, grep-гейт.

## Тест-кейсы

### Новый файл `packages/core/test/merge-activation.test.ts`

- **TC-INT-01** — маршрут `{capability:'x', adapterIds:['a'], merge:true}` со своей маленькой картой
  манифестов, где `x` несёт `shape:'point'` → конструктор бросает; сообщение содержит `x` и слово о
  недостающем праве. Fails when шаг 3 читает не ту строку манифеста.
- **TC-INT-02** — тот же маршрут, но манифест `x` несёт `shape:'series', mergeable:true` →
  конструирование проходит. Положительный контроль.
- **TC-INT-03** — маршрут без `merge` и способность без права → конструирование проходит: шаг 3 не
  срабатывает на неактивированном маршруте.
- **TC-INT-04** — маршрут, неверный сразу по `policy.kind` и по `merge`, сообщает находку шага 2.
- **TC-UNIT-01** — `assertMergeParticipantsAreFree` на массиве, где участник сливаемой способности
  имеет `tier: 'paid'` → бросает, называя способность и адаптер. Fails when проверка читает
  `adapterIds` одного маршрута вместо объединения (кейс с платным адаптером в соседнем маршруте).
- **TC-UNIT-02** — на реальных `routes`/`adapterRegistrations` после `013-6` проверка молчит.
  Здесь исполняется на тестовой паре, эквивалентной боевой.
- **TC-UNIT-03** — ранг: `plan` для сливаемой способности равен `adapterIds` маршрута в том же
  порядке; отдельной таблицы ранга в коде нет.

### Гейты

- **TC-GATE-01** — grep по `packages/core/src` и `packages/mcp-server/src`: строка `source_priority`
  не встречается. Положительный контроль — гейт находит искусственно внесённое вхождение и после
  отката снова зелёный; прогон записывается.
- **TC-GATE-02** (существующий, `tier-single-source.test.ts:432`) — зелёный без единой правки:
  новый код `.trust` не читает.

### Интеграционный кейс на вызов при старте

- **TC-INT-05** — ядро мокается набором, где участник сливаемой способности несёт `tier: 'paid'`;
  `await import('../src/index.js')` отклоняется, сообщение называет способность и адаптер. Fails
  when строка вызова удалена из `src/index.ts`.

### Регрессионные

- `registration-validation.integration.test.ts` — старт процесса с боевыми регистрациями проходит.
- Полный прогон §0.2 плана.

## Критерии приёмки

- [ ] `CapabilityRoute.merge` объявлен; продовая конфигурация в этой задаче не тронута
- [ ] Шаг 3 валидации стоит после шага 1, независим от шага 2, и сообщение называет способность
- [ ] `assertMergeParticipantsAreFree` живёт вне конструктора, вызывается при старте и обходит
      объединение маршрутов способности
- [ ] Вызов при старте покрыт тестом, который падает при удалении строки вызова (TC-INT-05)
- [ ] Ранг конфликта — порядок `plan`; новой таблицы ранга в дереве нет
- [ ] `TC-GATE-02` зелёный без правок; grep-гейт `source_priority` исполнен с положительным контролем
- [ ] Полный набор гейтов §0.2 плана зелёный; снимок `tools-list.snapshot.json` без диффа

## Вне области этой задачи

- Любой код обхода, дедупа и накопления — `013-4`.
- Простановка `merge: true` на боевых маршрутах — `013-6`.
- Проверка согласия соседних маршрутов одной способности по `merge` — объявлена Архитектурой вне
  области задачи целиком.

## Заметки

- **Проверку нельзя переносить в конструктор.** Тест `R-166` (`013-4`) строит сливаемый маршрут с
  платным адаптером именно затем, чтобы наблюдать порядок опроса. В конструкторе проверка сделала бы
  этот тест непостроимым. Разделение — условие исполнимости обоих требований (PLAN §0.7).
