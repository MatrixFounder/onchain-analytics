**Эпик:** E-2 (манифест capability + судьба `chains`) · **Требования:** R-139 ·
**Критерий приёмки:** AC-7 · **Фаза:** 1 из 10 · **Зависимости:** нет

## Use Case Connection

- Прямого UC нет: это предусловие, снимающее мёртвый механизм с двух файлов, которые правят ещё
  четыре задачи. Косвенно обслуживает **UC-2** (валидация маршрута на конструировании — 012-6)
  тем, что к моменту её появления `CapabilityRoute` уже в финальной форме.

<!-- contract:goal -->

## Цель задачи

Разрешить **OQ-C** по факту аудита. Поле `CapabilityRoute.chains` объявлено (`types.ts:81`),
**читается** роутером (`registry.ts:191-195`) и **не задано ни одним** из 21 маршрута. Удалить поле
вместе с фильтром. До удаления доказать: разделение сетей выполняет предикат
`adapter.chainSupport()`, а не удаляемый литерал.

Тест `packages/core/test/registry.test.ts:87-111` («selects the route whose chains list matches the
requested chain…») строит фейки `makeAdapter` (`:16-36`) **без `chainSupport`**.

**Риск R1** — фильтр удалён, фейки не тронуты → оба маршрута отдают адаптеры, `rpc-evm` отвечает
первым, ожидание `expect(solResult.source).toBe('rpc-solana')` (`:108`) не выполняется.

**Риск R2** — ожидания теста приведены к новому поведению вместо правки фейков → проверка семантики
выбора маршрута по сети исчезает, прогон при этом зелёный.

Оба риска снимает порядок из раздела «Порядок шагов»: фейки получают `chainSupport` **до** удаления
фильтра.

## Описание изменений

### Правки в существующих файлах

#### `packages/core/src/adapters/types.ts`

**Интерфейс `CapabilityRoute`:**

- Удалить поле `chains?: Chain[]` (`:81`).
- Поправить докстринг интерфейса: формулировка «which adapters … serve `capability` on `chains`
  (or any chain, if `chains` is omitted)» после удаления ложна. Новый текст: покрытие сетей —
  свойство пары `(адаптер, capability)` и выводится из `chainSupport()`; маршрут сети не описывает.
- Импорт `Chain` не удалять вслепую — проверить, остались ли другие потребители в файле.

#### `packages/core/src/adapters/registry.ts`

**Метод `resolve()`:**

- `:191-195` — фильтр `this.routes.filter((candidate) => candidate.capability === capability &&
(!candidate.chains || …))` схлопывается до сравнения по `capability`.
- Комментарий над фильтром (TASK-006, «A route that still carries `chains` keeps being narrowed by
  it — the two mechanisms agree») теряет предмет: механизм остаётся один. Переписать, сохранив
  историческую причину («до TASK-006 сети разделял литерал маршрута; с TASK-006 их разделяет
  `chainSupport()`; T-012 удалила литерал по OQ-C»).

#### `packages/core/src/providers.config.ts` — правка ТОЛЬКО докстринга

`:12-14` сегодня утверждает: поле «remains part of `CapabilityRoute` and is still honoured if set —
nothing forces a caller with its own route table to migrate». После этой задачи поля нет, и фильтра,
который его «honoured», тоже.

**Автоматической проверки на этот докстринг нет:** ни `docs-counts`, ни `readme-tool-table` его не
читают. Без правки в том же коммите файл продолжит описывать удалённый механизм как действующий.

Докстринг заменяется на историческую формулировку: поле существовало, аудит T-012 не нашёл ни одного
маршрута, которому нужно сузить сети сверх `chainSupport()`, поле удалено (OQ-C). **Кода в этом
файле задача не трогает.**

**`CapabilityDescriptor.chains` — ДРУГОЕ поле, оно остаётся.** В тех же файлах строкой ниже стоит
`capabilities: () => [{ id: '…', chains: [...] }]` (например `get-token.test.ts:33`,
`entity-label.test.ts:34`, `new-pairs.test.ts:31,109,141`, `protocol-tvl.test.ts:27,119`,
`token-risk.test.ts:33`, `wallet-balances.test.ts:35`, `smart-money-flows.test.ts:41`). Это описание
способностей **адаптера**, дизайн его сохраняет. Считать правки по строкам таблицы выше, а не
grep-ом по слову `chains`.

#### `packages/core/test/registry.test.ts` — переписывание, а не перекомпиляция

- `makeAdapter` (`:16-36`) получает необязательный `chainSupport?: (chain, capability) => boolean` в
  `MockAdapterOpts` и прокидывает его в возвращаемый адаптер тем же условно-спред-паттерном, каким
  сейчас прокидывается `isAvailable`.
- Тест `:87-111` («selects the route whose chains list matches…») получает новый заголовок,
  описывающий действующий механизм, и фейки с `chainSupport`, соответствующим разделению
  `rpc-evm` ↔ `rpc-solana`.

### Порядок шагов (фальсифицирующий, вместо красной фазы)

1. **Аудит.** Пройти все 21 маршрута `providers.config.ts` и ответить письменно: есть ли маршрут,
   которому нужно сузить сети **сверх** того, что уже выражает `chainSupport()`? Ожидаемый ответ —
   нет ни одного. Найденный контрпример **останавливает удаление**, поле остаётся, и задача обязана
   назвать потребителя поимённо (R-139c) — «на всякий случай» запрещено.
2. **Дать фейкам `chainSupport`** и прогнать `registry.test.ts` — зелёный (работают оба механизма).
3. **Убрать `chains:` из литералов ЭТОГО теста, оставив фильтр в коде**, и прогнать снова —
   зелёный. Зелёный прогон в этой конфигурации и есть доказательство: сети разделяет предикат
   `chainSupport()`. Без шага 3 удаление опирается на тест, который после правки ожиданий уже не
   проверяет выбор маршрута по сети.
4. **Удалить поле и фильтр.**
5. **Снять остальные 12 литералов** в 8 файлах.
6. Полный прогон.

## Тест-кейсы

### Регрессионные

- **TC-REG-01** — `packages/core/test/registry.test.ts` целиком: 5 литералов сняты, тест выбора
  маршрута переписан, остальные кейсы не тронуты.
- **TC-REG-02** — `pnpm --filter @onchain-intel/mcp-server test`: 8 файлов с литералами зелёные,
  поведение тулов не изменилось.
- **TC-REG-03** — полный прогон: **1195** зелёных, ни одного нового и ни одного упавшего.

### Юнит

- **TC-UNIT-01** — «маршрут выбирается по `chainSupport`, а не по литералу»:
  `wallet.balances.native` × `ethereum` → `rpc-evm`; × `solana` → `rpc-solana`; фейки объявляют
  `chainSupport`; в маршрутах **нет** поля `chains`. Проверяется и то, что второй адаптер **не**
  вызывался (`expect(evm.fetch).toHaveBeenCalledTimes(1)` после второго `resolve`).
- **TC-UNIT-02** (типовой) — поле удалено из типа: `CapabilityRoute` с ключом `chains` не
  компилируется. Реализация — `@ts-expect-error` на литерале в тесте; если директива окажется
  лишней, тест не соберётся, то есть удаление не сможет тихо откатиться.
- **TC-UNIT-03** — фальсификация шага 3 записана в отчёте: прогон с фильтром и **без** литералов
  зелёный.

## Заметки

- ADR-002 D2 сам предусматривает запасной выход: если аудит найдёт маршрут, которому нужно сузить
  сети сверх `chainSupport`, поле **возвращается с названным потребителем**. Такой исход предусмотрен
  заранее: OQ-C был оставлен открытым «до факта T-012».
- Задача идёт первой не по важности, а по топологии: она правит `types.ts` и `registry.ts`, которые
  дальше правят 012-2, 012-4, 012-6 и 012-8.
