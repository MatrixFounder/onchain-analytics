# Постановка: как доставать сложные запросы из Dune Analytics (и чем их заменить бесплатно)

> Формат под динамический пайплайн `dune-query-discovery`:
> **repo-audit → discover → profile → adversarial-verify → critic → follow-up → synthesize**.
> Язык отчёта: **ru** (термины/эндпоинты — как в первоисточнике). Дата верификации подставляется
> в `args.date`; `Date.now()` в workflow-скриптах недоступен.
>
> **Этот файл написан ДО прогона** и фиксирует контракт полноты: закрытый набор вердиктов,
> точный список вопросов, жёсткие фильтры, схему профиля и анти-цели. Отчёт проверяется на
> покрытие ровно этого набора (CLAUDE.md §1).

## 0. Зачем этот прогон

Движок `onchain-intel` (`/Users/sergey/dev-projects/onchain-analytics`) закрыл M0–M2 и TASK-006:
10 адаптеров, 10 MCP-тулов, реестр 458 сетей, двухуровневый кэш, credit budget-guard. Бесплатный
контур отвечает на **точечные** вопросы (цена токена, TVL протокола/сети, новые пары, нативный
баланс). На **агрегирующие** вопросы по цепочке («сколько биткоина уже добыто», «дневной объём DEX
по сетям», «распределение холдеров токена», «сколько активных адресов за квартал») он отвечает
явным отказом — по дизайну (`CapabilityRegistry` → explicit unavailability вместо тихого `undefined`).

Единственный адаптер, задуманный под этот класс, — `dune` — остаётся интерфейсным стабом:
`isAvailable()` безусловно `{ok:false, reason:'dune query authoring deferred to M2'}`
(`packages/core/src/adapters/dune/index.ts:39`), маршрут `token.holders → dune` зарегистрирован
(`packages/core/src/providers.config.ts`), `chainSupport()` возвращает `false` для всех сетей.

Гипотеза владельца, которую прогон обязан проверить или убить: **бóльшая часть «хитрых» ответов уже
написана внутри Dune тысячами публичных запросов и дашбордов — агента надо не учить писать SQL, а
научить ЭТИ запросы находить, исполнять в рамках free-лимита и проверять на корректность.**

## 1. Решение, которое принимаем по итогам

**Вердикт прогона** — ровно один из закрытого набора:
- **GO** — строить Dune-слой как основной путь для агрегирующих вопросов;
- **NARROW-AND-GO** — строить, но в суженном виде (назвать, в каком именно и что отрезано);
- **NO-GO** — не строить; назвать, чем закрывается класс вопросов вместо Dune.

**Вердикт по каждому кандидату** (кандидат = конкретный *способ доступа* к сложному ответу) —
ровно один из закрытого набора:
- **adopt** — встроить в `onchain-intel` (указать: какая capability, какой тул, какой файл);
- **steal-pattern** — не тащить как зависимость, но скопировать приём (какой именно);
- **reference** — знать и не встраивать (указать, при каком условии пересмотрим);
- **reject** — не годится (машиночитаемая причина + доказательство).

| `dune-sdk` | Клиенты/обёртки/коннекторы | `dune-client` (py), `@duneanalytics/client-sdk` (ts), Trino/dbt/Snowflake коннекторы, community MCP-серверы |

**Кандидат = способ доступа, а не компания.** «Dune» — это не один кандидат, а минимум пять
(execute-чужого-запроса / results-only / authoring / discovery / spellbook), у каждого своя цена,
своё плановое гейтирование и свой вердикт.

## 4. Сиды и оси sweep (расширять синонимами; расширение фиксируется в `methodology.md`)

Discovery ведём **ортогональными параллельными свипами** (CLAUDE.md §4), а не одним запросом:

- **S1 — первоисточник Dune:** `docs.dune.com` (api-reference, execution, results, CRUD, MCP,
  credits, rate limits, plans), `dune.com/pricing`, статус-страница.
- **S2 — OSS-экосистема:** GitHub через `gh` — `duneanalytics/spellbook`, `duneanalytics/dune-client`,
  `@duneanalytics/client-sdk`, community MCP (`kukapay/dune-analytics-mcp`, `ekailabs/dune-mcp-server`,
  `demomagic/dune-mcp-server`, deacix), awesome-подборки, реестры query-id.
- **S3 — как люди реально ищут готовые запросы:** поиск по dune.com, browse-разделы, теги, топ-дашборды,
  «Dune wizards», подборки в блогах/X/Reddit, дашборды команд протоколов.
- **S4 — бесплатные альтернативы под тот же класс вопросов:** Flipside, BigQuery public datasets,
  Coin Metrics community, mempool.space, Blockchair, blockchain.com charts, growthepie, Artemis,
  Token Terminal, Bitquery, Subsquid/Goldsky/The Graph.
- **S5 — корректность:** как проверяют правильность чужого запроса — Spellbook-происхождение таблиц,
  свежесть последнего исполнения, доверие к автору/команде, дефолты параметров, известные случаи
  «дашборд врал», гайды Dune по data quality.
- **S6 — экономика и лимиты:** кредитная модель (что стоит кредит, сколько за datapoint/engine),
  free-лимит, rate limits, что именно гейтится планом, поведение при 402/429.

**Сиды — стартовая точка, не потолок:** обязательна попытка выйти за них (§4 стандартов);
`N_discovered` логируется.

## 5. Жёсткие фильтры включения / исключения

**Включать, только если:**
- механизм пригоден для **headless-агента** (REST/CLI/MCP/SDK — не «зайти в браузер и посмотреть»);
- есть **первоисточник** (официальная документация/страница цен/статус) — либо поле уходит в `unverified`;
- на входе — **бесплатно или free-tier-жизнеспособно** (базовая стоимость $0/мес; платное допускается
  только как `reference`).

**Исключать (`verdict=reject`, но с логом причины):**
- скрапинг web-UI Dune как основной механизм (ToS-риск + хрупкость) — задокументировать и отклонить;
- продукты, у которых подтверждён sunset/архив (в частности **Dune Sim, 01.08.2026**) — понижение
  вердикта до `reference`/`reject` с датой и источником (§3 lifecycle-check);
- решения, требующие платного плана «с первого дня» без бесплатного пути (Allium, Glassnode Pro,
  Dune Analyst/Plus как ОБЯЗАТЕЛЬНОЕ условие) — `reference` максимум, не `adopt`;
- «MCP-обёртки» без реального кода/поддержки (toy-репо) — `reject` с доказательством.

**Доменный гейт для омонимов:** `dune` также = язык сборки OCaml (`dune build`), Frank Herbert /
Dune (фильм), Dune HD (медиаплееры). Токен-гейт: результат учитывается, только если присутствует
целевой токен (`dune analytics`, `dune.com`, `duneanalytics`, `DuneSQL`, `spellbook`, `query id`,
`X-Dune-API-Key`) И отсутствует чужой (`ocaml`, `dune-project`, `opam`, `movie`, `Villeneuve`,
`media player`, `Herbert`). Отброшенное по гейту — перечислить поимённо.

## 6. Вопросы, на которые отчёт ОБЯЗАН ответить

Формат каждого ответа в отчёте: **Ответ → Доказательство (URL первоисточника / `file:line` / grep) →
Confidence: high|medium|low → Что делаем мы**.

- **Q1.** Как агент программно **находит** существующий запрос/дашборд под вопрос на естественном
  языке? Полный список поисковых поверхностей, для каждой — официальная/нет, бесплатная/нет.
- **Q2.** Можно ли **исполнить чужой публичный** запрос по API? На каком плане, за сколько кредитов,
  в чём разница `POST /execute` vs `GET /results` (latest cached) и что из этого free-tier-жизнеспособно?
- **Q3.** Можно ли **создать/форкнуть** запрос через API на бесплатном плане? Если нет — какой обход
  (курируемый каталог чужих query id, ручное создание слотов в UI, materialized views)?
- **Q4.** Точная **экономика free-tier**: кредитов в месяц, стоимость исполнения (в чём считается),
  rate limits, поведение при исчерпании (402/429). Сколько «агентских вопросов в месяц» это даёт —
  с формулой, а не «много/мало».
- **Q5.** Как **проверить корректность** найденного чужого запроса? Чек-лист из проверяемых шагов
  (SQL читается? какие таблицы? Spellbook-происхождение? когда последний раз исполнялся? кто автор?
  дефолты параметров? сходится ли с независимым источником?).
- **Q6.** **Мотивирующий пример, доведённый до конца:** «сколько биткоина уже добыто» — есть ли в Dune
  bitcoin-данные, какой путь самый дешёвый и правильный, и что скажет независимая сверка. Плюс один
  сложный in-chain пример (на выбор: дневной объём DEX по сетям / распределение холдеров).
- **Q7.** **Интеграционный дизайн для `onchain-intel`:** какие capability и тулы завести, как выглядит
  адаптер, где кэш и TTL, как считать кредиты в существующем budget-guard, что с SSRF-allowlist,
  и что делать с риском **модель-сгенерированного SQL** (prompt-injection → произвольный запрос).
  Точки врезки — с `file:line`.
- **Q8.** Какие **бесплатные не-Dune источники** закрывают тот же класс вопросов и когда роутер
  обязан предпочесть их, чтобы не жечь кредиты? Явное правило маршрутизации.
- **Q9.** **Lifecycle-риски:** статус Dune MCP (beta/GA), плановые изменения гейтинга, sunset Sim
  01.08.2026, что именно у нас ломается при каждом сценарии и какой fallback.
- **Q10.** **Каталог vs живой поиск:** курируемый версионируемый реестр проверенных query id (с
  ожидаемой схемой результата и проверкой-зондом) против поиска под каждый вопрос — сравнить по
  цене, задержке, хрупкости и проверяемости; дать рекомендацию.
- **Q11.** *(поправка владельца, внесена ДО запуска — см. §14)* **Официальный Dune MCP как основной
  коннектор:** поштучный инвентарь тулов (имя → вход → что возвращает → плановый гейт), способы
  авторизации (OAuth2+PKCE vs `x-dune-api-key`), подключение к Claude Code
  (`claude mcp add --scope user --transport http dune https://api.dune.com/mcp/v1`), что он даёт
  агенту сверх REST и чего в нём НЕТ. Главная развилка, которую надо разрешить явно:
  **проксировать официальный MCP · писать свой REST-адаптер · гибрид** — с ценой каждого варианта.
  Требование владельца: коннектор должен быть **максимально продвинутым**, т.е. раскрывать полную
  поверхность (поиск → чтение SQL → исполнение с параметрами → materialized views → дашборды),
  а не минимальный «один тул».

## 8. Формула ранжирования (аддитивная, с диапазонами) и жёсткие оверрайды

```
fit = access(0–3) + free_fit(0–3) + coverage(0–2) + verifiability(0–2) + integration(0–2)   // 0..12
```

| Под-скор | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| `access` | только web-UI / скрапинг | community-обёртка без офиц. поддержки | документировано, но гейтится планом | официальный документированный API/MCP, доступен на free |
| `free_fit` | платно-только | free-tier маргинален (< 30 вопросов/мес) | free-tier достаточен (≥ 100 вопросов/мес) | полностью бесплатно/keyless |
| `coverage` | одна метрика | узкий, но глубокий класс | произвольные агрегаты по многим сетям | — |
| `verifiability` | чёрный ящик | метод описан, но не воспроизводим | метод/SQL полностью читается и сверяется независимо | — |
| `integration` | нужна новая подсистема | умеренная новая машинерия | ложится на существующие адаптер/кэш/бюджет без новых зависимостей | — |

**Оверрайды применяются КОДОМ (не промптом), и бьют сырой скор:**
1. `is_scrape == true` ⇒ `verdict = reject`.
2. `lifecycle` ∈ {`sunset:*`, `archived`, `deprecated`} ⇒ вердикт не выше `reference` (+ строка в
   разделе «Мёртвое/гаснущее» с датой и источником).
3. `plan_gate == 'paid-only'` (`free_fit == 0`) ⇒ вердикт не выше `reference`.
4. Пустой `kill_shot` ⇒ строка помечается `UNVERIFIED` и не участвует в финальных рекомендациях.
5. Нет `primary_url` ⇒ `confidence ≤ medium` и вердикт не выше `reference`.

**Порог глубокого профилирования:** профилируем top-K после доменного гейта, `K = args.maxCandidates`
(дефолт 16). Всё, что ниже линии, логируется через `log()` поимённо (§6 — «ничего не режем молча»).

## 9. Adversarial-протокол

- **Разделение ролей:** профиль пишет один агент, убивает — ДРУГОЙ (skeptic), с прямой задачей
  опровергнуть основное утверждение строки.
- **Контракт данных:** `refutation_attempted:true`, непустой `kill_shot`, `refuted:bool`.
  Пустой `kill_shot` ⇒ строка UNVERIFIED и в финал не идёт.
- **Два доказательства на каждый не-reject кандидат:** (1) позитивное — где первоисточник прямо
  заявляет возможность; (2) дисквалификатор — доказательство отсутствия анти-паттерна.
- **Compound-claim roll-up:** составное утверждение (например «официальный MCP умеет искать чужие
  запросы И исполнять их бесплатно») получает CONFIRMED только если подтверждены ВСЕ материальные
  под-утверждения; иначе — не выше `major-fixes` с явным указанием, какая часть верна.
- **Loop-until-dry:** discovery крутится, пока не будет **K = 2** подряд пустых раундов
  (максимум 3 раунда — потолок стоимости), дедуп по ключу `lower(vendor + '|' + name)` против
  множества `seen` (всё встреченное, включая отклонённое), а не против `confirmed`.
- **Completeness-critic** перед синтезом; число follow-up ≤ `args.maxFollowups` (дефолт 3),
  фактическое число и каждый follow-up логируются в `methodology.md`.

## 11. Анти-цели (сознательно вне области)

1. **Не пишем код адаптера в этом прогоне.** `dynamic-test` — стенд исследований; реализация уходит
   в `onchain-analytics` отдельной задачей. Выход прогона — дизайн + каталог, не TypeScript.
2. **Не строим «SQL-песочницу для модели»** как продукт: произвольный SQL от модели — это риск,
   который надо назвать и ограничить, а не витрина возможностей.
3. **Не заменяем Nansen** и не пересматриваем платный ярус.
4. **Не меряем латентность** и не делаем нагрузочное тестирование.
5. **Не занимаемся торговыми сигналами/альфой** — только доступ к данным и их корректность.
6. **Не выбираем enterprise-склад данных** (Allium/Snowflake share) для закупки.

> Отсутствие темы в отчёте — это **решение об области**, а не пропуск. Всё, что отрезано, названо здесь.

## 12. Воспроизводимость

- Команда повтора — одна: `Workflow dune-query-discovery { date:"YYYY-MM-DD", maxCandidates:16,
  maxFollowups:3, lang:"ru", repoPath:"/Users/sergey/dev-projects/onchain-analytics" }`.
- Дата берётся **только** из `args.date`; производные величины считаются от неё явной формулой.
- `args` нормализуются (`try/JSON.parse` + дефолты) — они могут прийти строкой.
- Два режима: **FULL** (агентский discovery, дефолт) и **INJECT** (`args.preVerified` — детерминированная
  фактбаза, discovery пропускается).
- Инварианты для сравнения прогонов: сиды, `date`, формула fit, набор Q1–Q10, ключ дедупа.
  Сравнивать только по пересечению. Каденция перепроверки — **раз в квартал** либо немедленно при
  изменении тарифов/планов Dune.
- **Ограничение этого прогона:** `DUNE_API_KEY` в окружении отсутствует (проверено:
  `.env` содержит только `NANSEN_API_KEY`), поэтому живые вызовы Dune API невозможны. Все числа —
  из первоисточников-документов, не из live-ответа API. Это фиксируется как bias и как next-step
  (получить free-ключ → прогнать зонд-скрипт → перевести `unverified` в `verified`).
