# Задача 014.33: живой гейт на сетевом транспорте

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети
- UC-2 — две сессии делят вендорскую квоту

<!-- contract:goal -->

## Цель задачи

Расширить живой гейт HTTP-набором: отказ по неверному токену, отказ периметра, сквозной успешный
вызов и общее ограничение между двумя сессиями.

**Why гейт, а не сьюта.** Живой гейт — единственный детектор класса «сломали они». Сьюта ловит
«сломали мы» и по построению работает на фикстурах: R-21 запрещает сеть в CI. `token.holders`
отдавал 50 строк на приёмке TASK-008 и отдаёт HTTP 403 сегодня, и все 1651 тест оставались
зелёными (L-6).

### Третий вид кейса

| Поле        | Требование                                                                        |
| :---------- | :-------------------------------------------------------------------------------- |
| `kind`      | строка `transport`                                                                |
| `transport` | непустая строка, сегодня `http`                                                   |
| `exercise`  | функция: исполняет запросы над поднятым профилем и возвращает наблюдение          |
| `check`     | функция: принимает наблюдение, возвращает список претензий, пустой список — успех |
| `catches`   | непустая строка: какой дрейф ловит кейс                                           |

Инвариант сохраняется: `check` и `catches` обязательны для всех трёх видов, поэтому кейс, который
ничего не утверждает, не грузится. Отсутствие любого поля таблицы даёт `throw` на импорте.

Метка строки отчёта выводится из имени файла: `http-auth-rejected.mjs` даёт
`transport:http-auth-rejected`. Ключ строки — `—/transport:http-auth-rejected`, поэтому строка
называется в `eval/acknowledged.json` без второго источника имени.

**Why третий вид, а не подгонка под форму bootstrap.** `indexByTool` в `eval/checks.mjs` индексирует
кейсы по имени тула и отвергает два кейса на один тул с разными `check`. Кейс `http-success`,
назвавший `onchain_ping`, столкнулся бы с `bootstrap-ping.mjs` на импорте.

**Why форма bootstrap не подходит и по второй причине.** Её `check` принимает `structuredContent`.
У отвергнутого по токену или по периметру запроса его нет, поэтому два кейса отказа не смогли бы
предъявить наблюдённые статус и заголовок.

**Why форма capability не подходит.** `toolFor` разрешает способность по сгенерированному
`tool-inventory.json` и бросает на неизвестной. `auth-rejected` способностью реестра не является, а
кейс этой формы вызывался бы по разу на каждую выбранную цепь.

**Why `indexByTool` пропускает транспортные кейсы.** Без пропуска он вызвал бы `toolFor(undefined)` и
бросил на импорте. Ключ, не являющийся зарегистрированным тулом, уронил бы проверку «нет проверки для
несуществующего тула» в `test/eval-checks-coverage.test.ts`.

**Why функция проверки экспортируется.** Офлайн-тест обязан доказать отказ на неполном кейсе. Файл с
неполным кейсом, положенный в каталог, уронил бы импорт у всех потребителей, поэтому проверяется
функция, а не каталог.

### Фаза HTTP-набора в раннере

1. Раннер разрешает профиль набора из `ONCHAIN_EVAL_HTTP_PROFILE`, умолчание — `network-sqlite`.
2. Раннер выпускает тестовый токен в хранилище выбранной пары запуском `src/admin/cli.ts` через
   `node --import tsx`. Постусловие: в `api_tokens` есть одна активная строка.
3. Раннер стартует процесс с этим профилем и ждёт привязки слушателя.
4. Транспортные кейсы исполняются последовательно, по строке отчёта на кейс.
5. В блоке `finally` токен отзывается, процесс останавливается, временный `DATA_DIR` удаляется.

Контекст, который раннер передаёт в `exercise`:

| Поле          | Значение                                                                 |
| :------------ | :----------------------------------------------------------------------- |
| `baseUrl`     | адрес слушателя поднятого профиля                                        |
| `token`       | значение выпущенного тестового токена                                    |
| `request`     | один HTTP-запрос к `baseUrl`, без заголовка `Authorization` по умолчанию |
| `openSession` | сессия MCP поверх Streamable HTTP: `initialize` плюс вызов тула          |

**Why токен выпускается до старта процесса.** Предстартовая проверка сетевого профиля отказывает при
нуле активных строк в `api_tokens` (задача 014-38, шаг 3 порядка старта). Процесс, стартованный до
выпуска, не поднялся бы.

**Why выпуск идёт через запуск CLI, а не импортом.** Каталог `eval/` — простой ESM без шага сборки, и
это условие записано в `eval/capabilities.mjs`. Раннер уже запускает TypeScript отдельным процессом
с `--import tsx`.

**Why умолчание — `network-sqlite`.** Пара `network` требует поднятого Postgres, а гейт запускается на
машине разработки перед сдачей этапа. Пара `network-sqlite` объявлена для отладки транспорта
(`deployment.md` §10.1.1).

**Why умолчание не покрывает всё.** Токен, периметр, таблицы личности и приёмник диагностики следуют
оси транспорта, а состояние лимитера — оси хранилища (`deployment.md` §10.1.1). Кейс общего
ограничения измеряет ту пару, под которой прогнан, поэтому `onchain.provider_buckets` покрывается
только при `ONCHAIN_EVAL_HTTP_PROFILE=network`.

**Why имя пары попадает в артефакт и в строку леджера.** Строка леджера — единственное свидетельство
прогона. Без имени пары прогон на `network-sqlite` неотличим от прогона на `network`.

**Why непроведённая фаза даёт `error`, а не пропуск.** Вердикт `no-probe` не входит в счёт отказов,
поэтому пропуск прочитался бы как успех. Гейт, который не смог отработать, не пройден.

**Why ключ раннера не принадлежит задаче 014-40.** `ONCHAIN_EVAL_HTTP_PROFILE` читает скрипт прогона,
как `ONCHAIN_EVAL_CHAINS`. Ключом `EnvSchema` он не становится и под классификацию AC-44 не попадает.

### Что остаётся на stdio

Матрица способностей. Она от транспорта не зависит и дешевле поднимается по stdio.

**Why разделение такое.** Всё, что добавляет HTTP — аутентификация, периметр, сессия, принципал,
лимитер под конкуренцией — юнит-тестами на фикстурах не проверяется. Матрица способностей по HTTP
проверялась бы дороже без выигрыша.

### Кейс общего ограничения

Две сессии по HTTP делят вендорскую квоту. Кейс проверяет, что суммарная частота не превышает
объявленной, и сводит ветви 014-20 и 014-23 в одной проверке.

### Стоимость

Гейт остаётся на бесплатных провайдерах и кредитов Nansen не расходует.

### Как добавляется покрытие

Один файл под `eval/cases/` несёт запрос, ожидание и утверждение вместе. Общего списка, который
можно забыть обновить, нет (RF-5).

## Примечания

Заблокированный гейт означает, что этап не сдан: сначала завести дефект, затем внести его в
`eval/acknowledged.json` с идентификатором, чтобы он перестал блокировать чужую работу, оставаясь
названным на каждом прогоне.

Шаг 8 процедуры развёртывания (`deployment.md` §10.4) называет команду гейта без значения
`ONCHAIN_EVAL_HTTP_PROFILE`. На поднятом сетевом профиле команда без этого значения прогонит
HTTP-набор под парой `network-sqlite`. Правка принадлежит фазе архитектуры.

Выпуск и отзыв токена опираются на операции задачи 014-08, разрешение профиля — на задачу 014-38.
До их завершения фаза HTTP-набора записывает четыре строки с вердиктом `error`.
