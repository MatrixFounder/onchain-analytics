# Задача 013-10 — Живой вызов из Claude Code и запись протокола

**Требования:** [R-173] · **Эпик:** E-3 · **Критерии приёмки:** AC-35 · **Фаза:** 10 из 10 ·
**Зависимости:** 013-9

## Use Case Connection

- **UC-17** — оператор выполняет реальный вызов нового тула из Claude Code и записывает конкретные
  значения ответа. Провал, который надо исключить: критерий приёмки закрывается ссылкой на
  юнит-тесты, а реальный вызов не выполнен.

<!-- contract:goal -->

## Цель задачи

Выполнить вызов тула из Claude Code против боевых хостов и записать конкретные значения ответа в
отчёт задачи.

**Это ручной шаг, запланированный как шаг.** Он не выводится из зелёного прогона и не может быть
им заменён: весь остальной сьют работает на фикстурах и виртуальных часах, и именно поэтому он не
закрывает разрыв, который `packages/mcp-server/.AGENTS.md:612-615` называет открытым.

<!-- contract:changes -->

## Описание изменений

Кода задача не меняет. Меняется отчёт задачи и, при необходимости, запись в `docs/reviews/`.

### Шаг 1 — подготовка

- `pnpm build` на дереве, прошедшем `013-9`.
- MCP-сервер перезапускается в Claude Code, чтобы список инструментов перечитался. Тестовый клиент
  не годится: критерий требует боевого хоста.

### Шаг 2 — два вызова

- `onchain_dash_platform_history` с `chain: 'dash'`, `series: 'platform_metrics'`.
- Тот же тул с `series: 'shielded_pool'`.
- Живой участник — `platform-explorer.pshenmic.dev`. `pg-history` участвует, если `ONCHAIN_PG_URL`
  задан в среде проверки.

### Шаг 3 — запись

В отчёт задачи записываются: имена `metric` каждой группы, число точек в каждой группе, значение
`source`, состав `sources`, содержимое `missingSources`, статус `_meta.cache` с `perSource[]`.
Формулировка «вызов прошёл успешно» критерий не закрывает.

### Шаг 4 — допустимые исходы

- `ONCHAIN_PG_URL` не задан → ответ от одного `platform-explorer` засчитывается: он демонстрирует
  ветку R-164(b), деградацию к одному источнику. Это выполнение критерия, а не дефект.
- ExplorerAPI недоступен в момент проверки → записывается причина пустого ответа. Это тоже
  засчитывается: важен факт живого вызова, а не число участников, ответивших в конкретную минуту.
- Обе способности недоступны одновременно → вызов повторяется позже; пустая запись критерий не
  закрывает.

## Тест-кейсы

### Ручной прогон

- **TC-MAN-01** — `series: 'platform_metrics'`: ответ получен, группы перечислены с числом точек.
- **TC-MAN-02** — `series: 'shielded_pool'`: ответ получен, обе метки видны раздельно либо
  задокументировано, почему присутствует одна.
- **TC-MAN-03** — `missingSources` прочитан и записан: пустой при обоих живых участниках, непустой
  при недоступном `pg-history`.

### Регрессионные

- Полный набор гейтов §0.2 плана остаётся зелёным на том же дереве: ручной вызов ничего в дереве не
  меняет.
- Живой вызов — единственный сетевой вызов задачи на боевые хосты; таблица `usage` не растёт, оба
  участника бесплатны.

## Критерии приёмки

- [ ] Вызов выполнен из Claude Code, не из тестового клиента
- [ ] Оба селектора вызваны
- [ ] В отчёте записаны конкретные значения: `metric`, число точек, `source`, `sources`,
      `missingSources`
- [ ] Деградация к одному источнику, если она случилась, записана как выполнение критерия с
      названной причиной
- [ ] `usage` не выросла; иных сетевых вызовов задача не делает

## Вне области этой задачи

- Любая правка кода: находка живого вызова заводится как дефект и чинится отдельной задачей, а не
  правится по ходу приёмки.
- Запись фикстур с живого ответа: `record-fixture.mjs` — отдельный ручной сценарий, в приёмку не
  входит.

## Исполнено 2026-08-09 — оба вызова живые, критерий закрыт

**AC-35 закрыт.** Оба селектора вызваны из Claude Code против боевого
`platform-explorer.pshenmic.dev`. Конкретные значения — в `packages/mcp-server/.AGENTS.md`,
запись `## T-013 task 013-10`; здесь свод.

| Селектор           | Группы                        | Точек | Значения                             |
| ------------------ | ----------------------------- | ----- | ------------------------------------ |
| `platform_metrics` | `identities_total`            | 12    | `valueRaw: "2085"` строкой на каждой |
| `shielded_pool`    | `shielded_pool_shield_amount` | 12    | одна ненулевая: `"9700000000"`       |

`source` = `platform-explorer`, `sources` = один участник, `missingSources` =
`[{adapterId: 'pg-history', reason: 'pg-history: database unavailable'}]` на обоих вызовах.
`usage` — 0 строк / 0 кредитов до и после.

**Шаг «допустимые исходы» применён по пункту 1**, но с уточнённой причиной: `ONCHAIN_PG_URL` был
задан, и деградация вызвана не его отсутствием. `pg-history` был СПРОШЕН и упал — состояние
«спрошен, не ответил» (R-164), то есть композиция UC-21, а не UC-12. Ветка (b) сработала: недостающий
участник назван с причиной, ответ второго опубликован.

**Побочный результат, ради которого шаг и существует.** 12 точек с шагом 300 000 мс — это
подтверждение правки 013-6 на БОЕВЫХ данных: при правиле, каким оно было построено, тот же ответ
вендора схлопнулся бы в ОДНУ точку за час. Фикстуры это показали, живой вызов подтвердил.

**Находка заведена, а не исправлена** (граница задачи): [WI-47](../backlog/wi-47-pg-history-search-path-lost-through-the-pooler.md)
— Supavisor подменяет `search_path`, а SELECT `pg-history` обращается к `snapshots` без схемы,
поэтому через пулер не резолвится ни один запрос. База при этом здорова и несёт 341 строку на
каждую из восьми метрик.

## Повторный вызов 2026-08-09, после закрытия WI-47 — слияние двух источников на живых данных

Первый прогон приёмки шёл с одним участником (WI-47). После её закрытия оба селектора вызваны
заново; `missingSources` **отсутствует на обоих** — вклад внесли ОБА участника.

**`series: 'platform_metrics'` — четыре группы:**

| Метрика                  | Кто пишет                   | Шаг точек |
| ------------------------ | --------------------------- | --------- |
| `identities_total`       | оба (конфликт решён рангом) | 5 минут   |
| `documents_total`        | только `pg-history`         | ~1 час    |
| `data_contracts_total`   | только `pg-history`         | ~1 час    |
| `platform_total_credits` | только `pg-history`         | ~1 час    |

Три метрики, которых у вендора нет вовсе, — это причина 3 D6 (заполнение пропусков), исполненная и
наблюдаемая. UC-11 закрыт живыми данными.

**`series: 'shielded_pool'` — две группы раздельно:** `shielded_pool_shield_amount` (от
`platform-explorer`) и `shielded_pool_balance_credits` (из леджера, `source='derived'` — метрика
L-2). Ни дедуп, ни разрешение конфликта между ними не сработали: ключ не совпадает по построению.
UC-18 закрыт живыми данными.

**Неравномерная плотность ряда видна и она предсказана.** `identities_total` идёт с шагом вендора в
5 минут, три леджерных метрики — с часовым шагом снапшоттера. Ровно та цена решения R-161(f),
которая записана в ADR-002 §Changelog от 2026-08-09; на живом ответе она выглядит так, как описано,
и дефектом не является.

**Канон `value_raw` подтверждён на живом значении.** `platform_total_credits` пришёл как
`valueRaw: "2994827525986485"` (точно) при `valueNum: 2994827525986480` — расхождение в 5.
Замерено, где именно теряется: в самой БД `to_char(value_num)` даёт полное `…485`, то есть
сохранённый double точен, а пять единиц теряются в ТЕКСТОВОМ представлении float8 на проводе,
которое парсит драйвер. Это не дефект: DB-SCHEMA §1.7 объявляет `value_num` лоссовой проекцией для
графиков, а каноном — `value_raw` строкой. Живой вызов показал ровно то поведение, ради которого
канон и выбран.

`usage` — 0 строк / 0 кредитов и после этих двух вызовов.

## Заметки

- Задача исполняется последней намеренно: до регистрации тула (`013-8`) вызывать нечего, а до
  регрессионного выхода (`013-9`) вызов проверял бы дерево, про которое ещё не сказано, что оно
  зелёное.
