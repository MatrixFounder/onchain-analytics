# L-29 — суточный гейт вызовов не готовился на Postgres, и каждый вызов blockscout отклонялся

**Что.** Оператор резервации `checkAndReserve` — тот самый, ради которого существует весь суточный
гейт вызовов T-015, — не проходил `PREPARE` на PostgreSQL **ни разу**. На профиле `network` это
означало отказ КАЖДОГО вызова blockscout и пустую таблицу `onchain.usage`.

**Измерено 2026-09-01** на `onchain-engine-db` (PostgreSQL 16.13), первым приёмочным прогоном живого
гейта задачи 015-30:

```
ERROR:  inconsistent types deduced for parameter $3
LINE 3: SELECT $1, $2, $3, 1, $4 WHERE ($5 IS NULL OR $3 <= $5) AND ...
                       ^
DETAIL:  text versus bigint
```

**Почему.** PostgreSQL выводит тип параметра из ВСЕХ контекстов, где тот встречается, и требует их
согласия. `$3 <= $5` сравнивает два ПАРАМЕТРА: ни один не типизирует другой, и оба скатываются к
`text`. Двумя строками ниже `onchain.usage.credits_used + $3` выводит `bigint` из колонки.
Противоречие фатально на этапе подготовки — до того, как связано хоть одно значение.

**Как это выглядело снаружи.** Тул отвечал
`capability unavailable: chain.transactions on arbitrum`, а причина оставалась в `diagnostics`:
`tried: blockscout (pg/state-client: database reachable, request rejected (SQLSTATE 42P08, ERROR))`.
Гейт не пропускал ничего — то есть отказывал ВСЕГДА, а это снаружи неотличимо от вендора, который
перестал отвечать. Отказ «на всякий случай» здесь не безопасная сторона: он тихо снимает с гейта
обязанность считать, и `usage.calls_made` остаётся нулём при любом трафике.

**Почему сьюта была зелёной.** SQLite типизирован динамически: параметры получают тип в момент
связывания, вывода типов у него нет вовсе. Тот же текст оператора исполнялся там безупречно. Это
касается и `packages/core/test/pg-store-parity.test.ts` — теста, который называет себя проверкой
паритета осей: его «постгресовая» сторона есть `better-sqlite3` с обратной трансляцией диалекта.
Все 38 его проверок были зелёными на неготовящемся операторе, и все 1738 проверок пакета `core`
тоже.

Соседний оператор `recordDelta` в том же файле правки НЕ потребовал: `GREATEST(0, $3)` типизирует
`$3` целочисленным литералом, и второй контекст с ним согласуется. Различает эти два случая не
аккуратность автора, а наличие хотя бы одной типизированной стороны.

**Правка.** Приведение типа на ДВУХ параметрах-потолках: `CAST($5 AS BIGINT)`, `CAST($6 AS BIGINT)`
в суточном операторе и `CAST($4 …)`, `CAST($5 …)` в оконном. Одной типизированной стороны хватает:
`$3` берёт `bigint` из арифметики с колонкой, и все контексты сходятся.

- **Стоимость НЕ приводится намеренно.** `CAST(0.5 AS BIGINT)` в PostgreSQL ОКРУГЛЯЕТ, а в SQLite
  УСЕКАЕТ. Приведение на стоимости внесло бы расхождение осей ровно в то значение, по которому они
  обязаны совпадать.
- **Форма `CAST(x AS BIGINT)`, а не `x::bigint`.** `toSqliteDialect` транслирует подстановкой и
  ничего не вычёркивает, поэтому `::bigint` дошёл бы до SQLite дословно и не разобрался. Стандартная
  форма исполняется на обоих движках без правки — то самое правило, которое §4.2.4 уже формулирует
  для всех прочих различий.

**Чем поймано и чем ловится впредь.** Поймано первым живым прогоном гейта на оси Postgres
(`packages/mcp-server/eval/cases/blockscout-daily-gate.mjs`, задача 015-29) — на первом же запуске.
Класс дефекта недостижим для фикстурной сьюты по построению: он проявляется только там, где есть
статический вывод типов, то есть только на настоящем PostgreSQL, а R-21 запрещает сеть в CI.
Ограничение теперь названо в докстроке `pg-store-parity.test.ts` рядом с двумя, которые она называла
раньше: harness, чьи слепые зоны не перечислены, читается как полный.

Побочно закрыт второй дефект того же файла: два текстовых мутанта опирались на подстроку
`$5 IS NULL`, которой после правки не стало. Мутант, чей шаблон не совпал, — это утверждение об
ИСХОДНОМ операторе; здесь он упал громко, но мог бы и пройти. Помощник `mutate` теперь отказывается
от мутации, ничего не изменившей.
