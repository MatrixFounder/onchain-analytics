# WI-35 — У пути чтения Postgres ограничено подключение, но не запрос

> Origin: TASK-012, задача 012-4. Найдено при выводе `deadlineMs` для
> `privacy.shielded_pool.history` и `platform.metrics.history`: искали, что ограничивает время
> запроса, и не нашли ничего.

**Signal — прочитано в `packages/core/src/pg/read-client.ts:120-130`.** Пул конструируется ровно с
четырьмя опциями:

```ts
pool = new PoolCtor({
  connectionString,
  options: '-c search_path=onchain',
  connectionTimeoutMillis: DEFAULT_CONNECTION_TIMEOUT_MS, // 10_000 (:47)
  max: DEFAULT_MAX_POOL_SIZE, // 3 (:48)
});
```

Ни `statement_timeout`, ни `query_timeout`, ни `idle_in_transaction_session_timeout` — ни здесь, ни
в строке `options`, ни где-либо ещё в `packages/core/src` (проверено грепом по всему пакету).
`connectionTimeoutMillis` ограничивает **получение соединения**; после того как соединение получено,
`await pool.query(sql, params)` (`:141`) ждёт столько, сколько потребуется.

**Механизм.** `pg-history.fetch()` шлёт
`SELECT ts, asset, metric, value_raw, value_num, source, height FROM snapshots WHERE asset = $1 AND metric = ANY($2) ORDER BY ts DESC LIMIT $3`
с `LIMIT 100`. Ограничено число **строк**, а не время: блокировка, неудачный план, сервер,
переставший отвечать уже после установления соединения, — любое из этого держит `await` без
верхней границы.

**Why it matters.** Это **единственный I/O-путь в кодовой базе без границы времени**. Каждый
HTTP-путь несёт `AbortSignal.timeout` на КАЖДЫЙ хоп внутри цикла редиректов
(`net/safe-fetch.ts:32`, `DEFAULT_TIMEOUT_MS = 15_000`; `blockscout`/`blockchain-info`
переопределяют на 5_000). Сервер MCP однопоточный (stdio), поэтому зависший запрос останавливает
сервер целиком, а не одну способность.

Это и записано в выводе числа 012-4. Огибающая E-PG сформулирована как **«≥10_000 мс с
неограниченным хвостом»**. `deadlineMs: 30_000` обеих `*.history` способностей описан там как
«единственная внутрипроцессная граница, которая у этого хвоста вообще есть». Пока это описание
верно, число несёт нагрузку, которую номинально нести не должно.

**Дедлайн T-012 эту запись не закрывает.** 012-8 отменяет **ожидание** вызывающего.
`statement_timeout` ограничивает работу СЕРВЕРА: отменённый по дедлайну вызов оставляет запрос
выполняться и держать одно из трёх соединений пула. Две границы решают разные задачи, и вторая не
заменяется первой.

**Why not a defect.** Сломанного контракта нет: ни один документ не обещает, что запрос ограничен по
времени. На рабочей инсталляции зависание запроса ни разу не наблюдалось; `pg-history` — второй по
приоритету источник в двух маршрутах и включается только при выставленном `ONCHAIN_PG_URL`. Это
отсутствующая граница, найденная чтением, — сигнал, а не воспроизводимое неверное поведение.
Work-item.

**Options.**

| # | Option | Cost | Trade-off |
|---|--------|------|-----------|
| 1 | `statement_timeout` — через строку `options` или отдельной опцией пула | S | Границу ставит СЕРВЕР: запрос снимается, соединение освобождается (см. ниже) |
| 2 | `query_timeout` (клиентская опция `pg`) | S | Клиент отпускается, запрос на сервере продолжает выполняться и держать соединение |
| 3 | Обе | S | Два числа вместо одного, каждое со своей записью вывода (R-149) |
| 4 | Положиться на дедлайн 012-8 | — | Не закрывает: дедлайн отменяет ожидание, а не работу сервера |

**Варианты 1 и 3 — подробно.** Строка `options` принимает
`'-c search_path=onchain -c statement_timeout=…'`; точка внедрения уже используется в конструкторе
пула. Вариант 3 даёт обе границы сразу: клиент не ждёт дольше своей границы, сервер не работает
дольше своей.

**Recommendation.** **Вариант 1**, и число выводится, а не выбирается: `LIMIT 100` по индексу на
`snapshots` — это единицы миллисекунд, поэтому граница в единицы секунд не режет ничего рабочего.
Записать его обязана та же двухчисловая форма, что и все дедлайны 012-4: измеренное время запроса
и применённая граница, с указанием, что чем является. Решать вместе с **012-8**, чтобы граница
сервера и дедлайн вызывающего попали в дерево согласованной парой, а не порознь.

**Минимально приемлемое:** у запроса появляется верхняя граница времени, и формулировка
«неограниченный хвост» уходит из записи вывода `E-PG` вместе с приездом числа.

**Acceptance.**

1. Запрос, выполняющийся дольше границы, завершается ошибкой, текст которой не содержит DSN
   (санитизация на этом пути уже обязательна, `read-client.ts:143-150`); проверено тестом с
   мокнутым `PoolCtor`, чей `query()` не резолвится.
2. Запись вывода `E-PG` в `packages/core/src/capability-manifest.ts` обновлена в том же коммите, а
   `deadlineMs` обеих `*.history` способностей пересмотрены против новой огибающей.
