# Задача 014.13: предел сессий, вытеснение по простою, конкурентные запросы `[LOGIC]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети
- UC-2 — две сессии делят вендорскую квоту

## Цель задачи

Задать предел числа одновременных сессий, таймаут простоя и семантику конкурентных запросов внутри
одной сессии.

## Описание изменений

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/transport/http.ts`:**

- Ввести потолок числа живых сессий по ключу `ONCHAIN_SESSION_MAX`
- Ввести таймаут простоя по ключу `ONCHAIN_SESSION_IDLE_MS` и вытеснение по нему
- Отвечать на превышение объявленным классом отказа

### Значения потолка и таймаута простоя

| Настройка       | Ключ окружения            | Применено    | Замер        |
| :-------------- | :------------------------ | :----------- | :----------- |
| таймаут простоя | `ONCHAIN_SESSION_IDLE_MS` | `900_000` мс | `330_000` мс |
| потолок сессий  | `ONCHAIN_SESSION_MAX`     | `64`         | замера нет   |

Имена обоих ключей объявлены таблицей окружения `deployment.md` §10.3 (`:199`, `:200`). Применённые
значения и замер взяты из `system-architecture.md` §3.4.2.

Замер таймаута простоя — худший конверт запроса из `system-architecture.md` §3.4.2: отменяемая часть
около 60 000 мс плюс платная часть около 270 000 мс на способности `entity.labels`. Применённое
значение `900_000` мс — пол, который нужно перекрыть, а не цель.

**Why применено больше замера.** Таймаут ниже замеренного числа вытесняет сессию, чей собственный
запрос ещё выполняется. Платную часть отменять запрещает `ADR-002` D4 п.2.

**Why потолок помечен без замера.** Посессионная стоимость экземпляра `McpServer` с транспортом не
измерена (§3.4.2). Число `64` ограничивает память утверждением, и первый месяц работы его замеряет.

### Утверждение на старте

Таймаут простоя сверяется с манифестом при запуске: `idleTimeoutMs > max(manifest.deadlineMs)`. Замер
2026-08-12 дал `max(deadlineMs) = 60_000` на всех 26 строках `packages/core/src/capability-manifest.ts`.

**Why проверяется эта граница, а не конверт.** Платная часть — производная величина, а не объявленное
поле манифеста. Утверждение слабее конверта, зато проверяемо машиной.

### Отказ на потолке — 503, не 429

**Why.** 429 утверждает, что этот вызывающий звал слишком часто. Измеренная причина — общая ёмкость
процесса по всем принципалам. `Retry-After` — то, что делает отказ действенным, и AC-30 требует
объявленного класса, а не таймаута.

### Конкурентные запросы одной сессии

Оба запроса завершаются. Порядок ответов не влияет на их содержимое. Общий контекст сессии гонки не
порождает.

**Why это проверяется.** Экземпляр `McpServer` посессионный, и два запроса одной сессии делят его
состояние. Гонка здесь проявляется как перепутанные ответы, а не как исключение.

### Наблюдаемость

Достижение потолка и вытеснение по простою пишут события `session.limit_reached` и
`session.evicted` в канал задачи 014-27.

## Тест-кейсы

### Сквозные тесты

1. **TC-E2E-01:** на N+1-й сессии сервер отвечает объявленным классом отказа, не таймаутом
   - Ожидаемый результат: HTTP 503 с `Retry-After`, JSON-RPC `-32000` (AC-30)
2. **TC-E2E-02:** брошенная сессия вытесняется по таймауту простоя (AC-30)
3. **TC-E2E-03:** обе строки канала диагностики читаются после условий TC-E2E-01 и TC-E2E-02
   - Входные данные: выборка по `event` из `onchain.diagnostics` после отказа на потолке и после
     вытеснения брошенной сессии
   - Ожидаемый результат: найдены строка `session.limit_reached` и строка `session.evicted`,
     каждая несёт `session_id` своей сессии

### Модульные тесты

1. **TC-UNIT-01:** оба конкурентных запроса одной сессии завершаются (AC-31)
2. **TC-UNIT-02:** обратный порядок ответов не меняет их содержимого (AC-31)
3. **TC-UNIT-03:** вытеснение освобождает экземпляр `McpServer`
4. **TC-UNIT-04:** умолчание таймаута простоя — `900_000` мс
   - Входные данные: разбор окружения без ключа `ONCHAIN_SESSION_IDLE_MS`
   - Ожидаемый результат: применённое значение таймаута простоя равно `900_000`
5. **TC-UNIT-05:** утверждение старта сверяет таймаут простоя с манифестом
   - Входные данные: два запуска при `max(manifest.deadlineMs) = 60_000` — таймаут `900_000` мс и
     таймаут `60_000` мс
   - Ожидаемый результат: первый запуск поднимается, второй отказан на старте с обоими числами в
     тексте отказа
6. **TC-UNIT-06:** утверждение старта читает манифест, а не константу
   - Входные данные: манифест-двойник со строкой `deadlineMs: 1_800_000`
   - Ожидаемый результат: запуск при таймауте `900_000` мс отказан

### Регрессионные тесты

- Тест не ждёт реального времени: часы подставляются
