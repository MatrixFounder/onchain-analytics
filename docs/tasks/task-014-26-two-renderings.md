# Задача 014.26: два рендеринга отказа и идентификатор события `[LOGIC]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети
- UC-3 — оператор запускает локально

<!-- contract:goal -->

## Цель задачи

Рендерить отказ дважды: полностью в лог сервера и сокращённо клиенту. Клиентский рендеринг несёт
идентификатор события, по которому админ находит полный текст.

**Why идентификатор, а не полный текст по роли.** Решение владельца 2026-08-13. Ролевой гейт
проходит зелёным, собрав только клиентский случай, а операторский рендеринг на проводе превращает
утечку админского токена в утечку нашей юнит-экономики.

<!-- contract:changes -->

## Описание изменений

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/tools/registry.ts`:**

- Разделить рендеринг отказа на операторский и клиентский
- Клиентский несёт `diagnostics.id` строки, записанной до отправки ответа

**Файл `packages/mcp-server/src/transport/http.ts`:**

- Протокольные отказы собственного слушателя несут идентификатор в `error.data.event`

### Что уходит из клиентского рендеринга

- Имена переменных окружения
- Остаток и потолок оператора
- Имена адаптеров и порядок обхода

**Why порядок обхода тоже.** Действующая строка
`capability unavailable: entity.labels on ethereum — tried: blockscout (…), nansen (…)` выдаёт
порядок обхода, то есть косвенно — кто из поставщиков бесплатный.

### Где едет идентификатор

| Отказ              | Где                | Событие                 |
| :----------------- | :----------------- | :---------------------- |
| аутентификация 401 | `error.data.event` | `auth.rejected`         |
| периметр 403       | `error.data.event` | `perimeter.rejected`    |
| предел сессий 503  | `error.data.event` | `session.limit_reached` |
| исполнение тула    | текст `content[0]` | `tool.refused`          |

Идентификатор едет в тексте, а не в `_meta`: видимость `_meta` — функция роли, и поле там
отсутствовало бы у роли, которой оно нужнее всего.

### Два класса без идентификатора

Недействительный `sessionId` и неподдержанный метод HTTP не скрывают ничего, поэтому восстанавливать
там нечего. Отсутствие идентификатора у них — соблюдение правила, а не пробел в нём.

### Порядок записи

Строка `diagnostics` пишется до отправки ответа. Идентификатор, не разрешающийся ни во что, хуже
отсутствия идентификатора.

## Тест-кейсы

### Сквозные тесты

1. **TC-E2E-01:** ни один ответ по сетевому транспорту не несёт операторских деталей
   - Входные данные: все классы отказа, оба принципала; два словаря читаются из репозитория —
     идентификаторы адаптеров из `adapterRegistrations` и ключи `EnvSchema`, числа не зашиты
   - Ожидаемый результат: гейт зелёный независимо от роли (AC-47)
2. **TC-E2E-02:** отказ, показанный по сети, несёт идентификатор, и он резолвится в `diagnostics`
   - Входные данные: протокольный класс и класс исполнения тула
   - Ожидаемый результат: обе выборки находят строку (AC-50)

### Модульные тесты

1. **TC-UNIT-01:** полный текст присутствует в логе сервера
2. **TC-UNIT-02:** строка `diagnostics` записана до отправки ответа
3. **TC-UNIT-03:** классы 404 и 405 идентификатора не несут
4. **TC-UNIT-04:** три перечисленных выше вида деталей в клиентском рендеринге отсутствуют

### Регрессионные тесты

- Локальный профиль: оператор продолжает получать детализацию, читая её из `diagnostics`
