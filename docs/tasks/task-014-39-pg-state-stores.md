# Задача 014.39: реализации хранилища на оси Postgres `[LOGIC]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети
- UC-2 — две сессии делят вендорскую квоту

<!-- contract:goal -->

## Цель задачи

Дать оси Postgres клиент записи и реализации `PgCacheStore`, `PgBudgetStore` и `PgLimiterStore`, не
изменив ни одной интерфейсной сигнатуры.

**Why сигнатуры не меняются.** Обе действующие интерфейсные сигнатуры уже асинхронны. `CacheStore.get`
возвращает `Promise<CacheGetResult | undefined>` (`packages/core/src/adapters/cache-store.ts:26`,
`get(provider: string, capability: string, argsHash: string)`), и каждый метод `BudgetStore`
возвращает промис (`packages/core/src/cache/budget-store.ts:63`, `checkAndReserve(`). Ось Postgres
добавляет реализации.

**Why промис был объявлен заранее.** `packages/core/src/cache/budget-store.ts:17` называет причиной
`future Postgres-backed implementation`. `CapabilityRegistry` уже ожидает оба вызова через `await`.

## Описание изменений

разные права на таблицы (`deployment.md` §10.5.1).

**Why потребитель назван, а файл не правится.** Задача 014-03 зависит от текущей. Правка её файла

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/index.ts`:**

Миграция в эту задачу не входит. Двенадцать таблиц, их индексы и гранты двум ролям создаёт задача

### Замены диалекта, общие для четырёх таблиц

`data-model.md` §4.2.4 объявляет три замены, обязательные для каждого statement этой задачи:
`MAX(x, y)` заменяется на `GREATEST(x, y)`, `INTEGER` — на `BIGINT`, каждое имя объекта
квалифицируется схемой (R-30.1). Ключи, столбцы и арифметика идентичны (`data-model.md:536-538`,
`MAX(x, y)` `becomes` `GREATEST(x, y)`).

**Why замена `MAX` названа отдельно.** В Postgres `MAX` — агрегатная функция, и формы с двумя
аргументами у неё нет. Перенесённое дословно ограничение снизу `MAX(0, credits_used + @delta)`
(`packages/core/src/cache/budget-store.ts:204`) отказывает на каждом вызове, а не на краевом входе.

### `checkAndReserve` на оси Postgres

В SQLite гарантия держится на синхронном теле транзакции: `packages/core/src/cache/budget-store.ts:420`
(`return attempt.immediate();`) оборачивает чтение, сравнение и запись, которые не ждут промисов. В
Postgres каждый statement — сетевой обход, поэтому сравнение переезжает внутрь statement.

**Why этот образец.** Кросс-процессная атомарность уже отлажена в парном виде: `BEGIN IMMEDIATE` в
SQLite и условный upsert с пустым `RETURNING` в Postgres. Второй механизм на тот же класс задачи —
второй набор гонок.

1. Суточное резервирование — один условный upsert, отказывающий возвратом нуля строк.

```sql
INSERT INTO onchain.usage (provider, day, credits_used, updated_at)
SELECT $1, $2, $3, $4 WHERE ($5 IS NULL OR $3 <= $5)
ON CONFLICT (provider, day) DO UPDATE SET
  credits_used = onchain.usage.credits_used + $3,
  updated_at   = $4
WHERE ($5 IS NULL OR onchain.usage.credits_used + $3 <= $5)
RETURNING credits_used;
```

`$3` — это `cost`, `$5` — это `ceiling`. Постусловие: ноль возвращённых строк означает, что не
записано ничего.

2. Счётчики скорости — второй statement той же формы против `usage_window`, с добавленным
   `calls_made + 1 <= $maxCalls`. Постусловие: вызов нулевой стоимости остаётся ограниченным (Q-3).
3. Оба statement выполняются на одном взятом соединении внутри одного `BEGIN` / `COMMIT`. Нулевой
   результат любого из них откатывает оба. Постусловие: два счётчика не расходятся (SEC-1).
4. Уборка строк `usage_window` старше часа выполняется тем же соединением внутри того же `BEGIN`.
   Постусловие: уборка наследует блокировку резервирования и откатывается вместе с ним.

**Why уборка внутри транзакции, а не отдельным заданием.** §4.2.4 требует того же размещения, что и
на оси SQLite (`packages/core/src/cache/budget-store.ts:410`, `this.pruneWindowStmt.run({`).
Дословно: `The opportunistic prune of old window rows stays inside that transaction` … `so it
inherits the same lock instead of racing it` (`data-model.md:589-590`). Отдельное задание
конкурировало бы за ту же блокировку строки.

**Why текст приведён дословно.** Это канонический текст `system-architecture.md` §3.4.8, на который
`data-model.md` §4.2.4 ссылается вместо своей копии. Пересказ способен опустить ветку `$5 IS NULL`:
потолок `off` тогда сравнивается как `… <= NULL`, сравнение даёт `NULL`, statement возвращает ноль
строк, и каждое резервирование отказано.

**Why `WHERE` повторён на ветке вставки.** `ON CONFLICT DO UPDATE ... WHERE` управляет только
конфликтной веткой. Без охраняемого источника `SELECT` первый за сутки вызов зарезервировал бы
стоимость больше всего потолка.

**Why арифметика читает таблицу, а не значение, прочитанное этим процессом раньше.** Обе ветки
называют `onchain.usage.credits_used` — версию строки, которую statement сам и заблокировал.
Конкурентная транзакция ждёт на этой блокировке и переоценивает условие против зафиксированного
значения.

**Why `SERIALIZABLE` не требуется.** Условный upsert берёт нужную блокировку строки, поэтому
`READ COMMITTED` — умолчание `pg` — уже сериализует два резервирования на одном ключе.

**Why неограниченный потолок связывается как `NULL`.** `+Infinity` — объявленный признак отсутствия
самоограничения (`packages/core/src/cache/budget-store.ts:326`, `may legitimately be`) и не имеет
числового представления в Postgres. Параметр связывается на каждом вызове и не опускается.
Нефинитная стоимость или `NaN` потолок отказывают до отправки statement — правило, которое
реализация на SQLite уже применяет (`packages/core/src/cache/budget-store.ts:334`).

**Why отсутствие связывания не должно читаться как «без потолка».** Опускаемый параметр сделал бы
«без потолка» значением ошибки, а не значением решения (L-10).

**Отказ несёт число `used`, которого нет в нулевом результате.** При отказе хранилище делает одно
дополнительное чтение `credits_used` — только ради текста сообщения
(`packages/core/src/cache/budget-store.ts:346`, `budget exceeded for provider=`).

**Why это чтение не расширяет гейт.** Решение уже принято statement, и не записано ничего. Чтение
заполняет три числа, которые операторский текст называет сегодня.

### Остальные четыре метода `BudgetStore` на оси Postgres

Интерфейс объявляет пять методов, и выше описан один. `PgBudgetStore` реализует все пять.

| Метод | Строка интерфейса | Реализация на оси Postgres |
| :--- | :--- | :--- |
| `recordDelta(provider, dayBucketMs, signedDelta, windowStartMs?): Promise<void>` | `budget-store.ts:80` | два безусловных upsert со знаковой дельтой, один `BEGIN` |
| `getUsage(provider, dayBucketMs): Promise<number>` | `budget-store.ts:87` | `SELECT credits_used FROM onchain.usage`, ноль при отсутствии строки |
| `getWindowUsage(provider, windowStartMs): Promise<number>` | `budget-store.ts:90` | `SELECT credits_used FROM onchain.usage_window`, ноль при отсутствии строки |
| `getWindowCalls(provider, windowStartMs): Promise<number>` | `budget-store.ts:92` | `SELECT calls_made FROM onchain.usage_window`, ноль при отсутствии строки |

1. Ни один statement `recordDelta` не связывает потолок. Постусловие: возврат кредитов записывается
   всегда, включая отрицательную дельту.
2. `recordDelta` пишет в `usage_window` дельту кредитов и ноль вызовов. Постусловие: `calls_made`
   не уменьшается ни одним путём записи.
3. Оба upsert `recordDelta` идут на одном соединении внутри одного `BEGIN`. Постусловие: суточный и
   оконный счётчики не расходятся после возврата (SEC-1).
4. Обе ветки обоих upsert ограничивают счётчик снизу через `GREATEST(0, …)`. Постусловие: возврат
   больше израсходованного не делает счётчик отрицательным.

**Why реконсиляция — второй statement без потолочной границы.** §4.2.4:
`Reconciliation is a second statement and carries no ceiling bound` (`data-model.md:582`). Возврат,
отказанный клаузой `WHERE`, оставил бы записанными кредиты, которых никто не потратил
(`data-model.md:583`, `strand credits nobody spent`).

**Why `calls_made` монотонен и на этой оси.** §4.2.4: `calls_made` `stays monotonic` …
`reconciliation adjusts credits and never the call count` (`data-model.md:591-592`). Вызов к вендору
уже состоялся, и возврат счётчика открыл бы проход мимо лимита последовательностью дешёвых и
возвращённых вызовов.

**Why три читающих метода названы поимённо.** Они не участвуют в гейте, но обработчики инструментов
читают `getUsage` для `_meta.budget` (`system-architecture.md:2484-2486`, `interfaces.md` §5.1.2), а
`getWindowUsage` и `getWindowCalls` — единственный способ прочитать оконные счётчики снаружи
транзакции. Класс, реализующий один `checkAndReserve`, интерфейсу не удовлетворяет.

### `PgCacheStore` и `PgBudgetStore` при построении

1. `PgCacheStore.get` — один `SELECT` с фильтром по `expires_at`; устаревшая строка удаляется тем же
   путём, каким её удаляет реализация на SQLite. Постусловие: истёкшая запись не отдаётся.
2. `PgCacheStore.set` — upsert §3.2 по `(provider, capability, args_hash)` с `excluded.*` в ветке
   обновления. Постусловие: пересчитанное значение заменяет устаревшее.
3. Уборка истёкших строк остаётся счётчиковой и индексной, как на SQLite. Постусловие: внутри
   процесса сервера не работает таймер.
4. `PgBudgetStore` при построении делает upsert двенадцати строк `providers` и не выполняет DDL.
   Постусловие: цель внешнего ключа существует до первой записи в `usage`, и процесс сервера не
   создаёт объектов в общей базе.

**Why процессу сервера запрещён DDL, хотя на оси SQLite выполняется `CACHE_DDL`.** Общий сервер
Postgres не принадлежит этому процессу; единственный писатель схемы — нумерованный файл миграции
(`data-model.md` §4.4, пункт 2).

### `TwoLevelStore`: что переезжает

Переезжает только персистентная половина. `TwoLevelStore` принимает её через конструктор
(`packages/core/src/cache/two-level-store.ts:41-44`, `private readonly persistent: CacheStore,`),
поэтому ось Postgres строит тот же класс над другим вторым аргументом.

**Why горячий слой остаётся в процессе на обеих осях.** `LruHotLayer` — это память, и общий горячий
слой требовал бы сетевого обхода на каждый поиск, то есть расхода, ради устранения которого слой
введён.

Над одной таблицей Postgres стоят несколько горячих слоёв. Гарантия разделения при этом
переформулирована, а не сохранена, и три следствия объявлены:

1. Значение, записанное процессом A, невидимо горячему слою процесса B до истечения его собственной
   записи. Постусловие: B способен отдать значение старше того, что держит A.
2. Устаревание ограничено TTL способности, который уже ограничивает попадание в горячий слой одного
   процесса (`packages/core/src/cache/two-level-store.ts:95`). Постусловие: ответ не старше того,
   что допускает таблица TTL §3.2.
3. `_meta.cache.ageMs` остаётся возрастом значения, а не возрастом записи, потому что поднятая
   запись датируется задним числом (`packages/core/src/cache/two-level-store.ts:70`). Постусловие:
   клиент видит возраст ответа.

**Why общий горячий слой не является решением.** Контракт свежести уже допускает устаревание на
полный TTL, поэтому второй горячий слой не добавляет ничего, чего контракт не разрешал.

### Поведение при отказе хранилища

| Хранилище | Поведение | Где решено |
| :--- | :--- | :--- |
| `LimiterStore` | внутрипроцессная корзина по объявленному потолку | §3.4.4, R-7.7, задача 014-19 |
| `BudgetStore` | отказ закрытый: платный вызов не выполняется | §3.2, «Fail-closed, never fail-open» |
| Чтение `CacheStore` | трактуется как промах | `packages/core/src/adapters/registry.ts:1165` |
| Запись `CacheStore` | по возможности; результат всё равно возвращается | `packages/core/src/adapters/registry.ts:1242` |

Когда отказавшее хранилище — хранилище диагностики, событие уходит только в stderr.

**Why так.** Строка `diagnostics`, записанная в базу, которая только что отказала в записи, была бы
потеряна, и процесс не сообщил бы ничего.

## Тест-кейсы

### Сквозные тесты
1. **TC-E2E-01:** два процесса против одного Postgres не пробивают потолок
   - Входные данные: потолок 100 кредитов, два процесса `network` резервируют по 60 параллельно
   - Ожидаемый результат: одно резервирование проходит, второе отказано, `credits_used` = 60 (AC-4)
2. **TC-E2E-02:** состояние переживает перезапуск процесса на оси Postgres
   - Входные данные: зарезервировать 60, завершить процесс, прочитать из второго процесса
   - Ожидаемый результат: второй процесс видит `credits_used` = 60 (AC-5)
3. **TC-E2E-03:** поведение совпадает с осью SQLite на одинаковых входах
   - Входные данные: одна последовательность троек `(cost, ceiling, velocity)` на обе оси, включая
     потолок `off`, нулевую стоимость, превышение оконного лимита и возврат отрицательной дельтой
   - Ожидаемый результат: совпадающие последовательности `ok`, совпадающие причины отказа и
     совпадающие показания `getUsage`, `getWindowUsage` и `getWindowCalls` после каждого шага
4. **TC-E2E-04:** потолок `off` не отказывает
   - Входные данные: `ceiling` = `+Infinity`, `cost` = 1
   - Ожидаемый результат: резервирование проходит; тест красный при опущенной ветке `$5 IS NULL`
5. **TC-E2E-05:** истёкшая строка кеша не отдаётся и удаляется
   - Входные данные: запись с `expires_at` в прошлом
   - Ожидаемый результат: `get` возвращает `undefined`, строки в таблице нет
6. **TC-E2E-06:** подменённый `search_path` не меняет результат запроса
   - Входные данные: соединение с `search_path`, не содержащим `onchain`
   - Ожидаемый результат: те же строки, что и при умолчании (AC-46)

### Модульные тесты
1. **TC-UNIT-01:** `PgBudgetStore` не выполняет DDL при построении
   - Входные данные: соединение ролью без права `CREATE` в схеме `onchain`
   - Ожидаемый результат: построение проходит, двенадцать строк `providers` на месте
2. **TC-UNIT-02:** недецидируемое сравнение отказывает до отправки statement
   - Входные данные: `cost` = `+Infinity`, затем `ceiling` = `NaN`
   - Ожидаемый результат: оба вызова дают `ok: false`, клиент не получил ни одного запроса
3. **TC-UNIT-03:** отказ по потолку не меняет ни одной строки
   - Входные данные: `credits_used` = 90, потолок 100, стоимость 20
   - Ожидаемый результат: `ok: false`, `usage` и `usage_window` побайтно прежние
4. **TC-UNIT-04:** нулевой результат второго statement откатывает первый
   - Входные данные: суточный потолок свободен, оконный исчерпан
   - Ожидаемый результат: `ok: false`, `usage` и `usage_window` не изменены
5. **TC-UNIT-05:** сообщение отказа несёт три числа
   - Входные данные: отказ по суточному потолку
   - Ожидаемый результат: текст называет стоимость, израсходованное и потолок

## Примечания

Сквозные тесты требуют живого Postgres. Они помечаются интеграционными и исключаются из прогона CI
по канону R-21: сеть в CI запрещена. Это та же пометка, что у сквозного теста задачи 014-03.

Разделение с соседними задачами. Оператор атомарного взятия слота — задача 014-18; здесь
`PgLimiterStore` получает клиент записи и место в оси, файл — `packages/core/src/pg/limiter-store.ts`.
Общий механизм доступа репозиториев личности, следа и диагностики даёт задача 014-03, их методы —
задачи 014-07, 014-27 и 014-30. Деградация лимитера при отказе хранилища — задача 014-19. Миграция
Postgres — задача 014-35.

AC-4 и AC-5 закрываются на двух осях: задача 014-18 измеряет два процесса `local` против одного
`DATA_DIR`, эта — два процесса `network` против одного Postgres (`data-model.md` §4.5.11).

Архитектура называет классы `PgCacheStore`, `PgBudgetStore` и `PgLimiterStore`, но не называет файлов
для них. Пути выше выбраны по действующему размещению `packages/core/src/pg/read-client.ts`.
