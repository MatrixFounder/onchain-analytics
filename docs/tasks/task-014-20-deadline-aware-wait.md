# Задача 014.20: дедлайн прерывает ожидание в корзине `[LOGIC]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети
- UC-2 — две сессии делят вендорскую квоту

<!-- contract:goal -->

## Цель задачи

Прервать ожидание в общем лимитере по дедлайну вызова, а не по `MAX_WAIT_MS`, и назвать в отказе
остаток и потолок.

**Why это становится важным на сети.** До T-014 ожидающий был один. С двумя сессиями ожидание
между принципалами становится наблюдаемым: вызов с коротким дедлайном не должен ждать столько же,
сколько вызов с длинным.

<!-- contract:changes -->

## Описание изменений

### Изменения в существующих файлах

**Файл `packages/core/src/net/rate-limit.ts`:**
- Ожидание завершается по `deadlineAtMs`, если он ближе, чем `MAX_WAIT_MS`
- Отказ называет остаток и потолок

### Что не меняется

- `MAX_WAIT_MS` = 30 000 мс остаётся верхней границей
- `MIN_POST_WAIT_REMAINDER_MS` = 5 000 мс остаётся: после ожидания вызову должно остаться время на
  сам вызов
- Очередь между ожидающими не вводится

### Два рендеринга текста отказа

| Рендеринг | Остаток и потолок лимитера | Требование |
| :--- | :--- | :--- |
| операторский (лог сервера, `diagnostics`) | называются | R-9.4 |
| клиентский (ответ по сетевому транспорту) | отсутствуют | AC-47 |

**Why это перестало быть прозой.** R-9.4 требует, чтобы отказ называл остаток и потолок, а AC-47
запрещает остаток и потолок оператора на проводе при любой роли. Оба правила выполняются только
разделением рендерингов, которое вводит задача 014-26, поэтому проверка стала тест-кейсом.

## Тест-кейсы

### Модульные тесты
1. **TC-UNIT-01:** на насыщенной корзине ожидание завершается по дедлайну, а не по `MAX_WAIT_MS`
   - Входные данные: два принципала с разными дедлайнами
   - Ожидаемый результат: короткий дедлайн отказывает раньше (AC-21)
2. **TC-UNIT-02:** дедлайн дальше `MAX_WAIT_MS` не удлиняет ожидание
3. **TC-UNIT-03:** остаток `MIN_POST_WAIT_REMAINDER_MS` соблюдён
4. **TC-UNIT-04:** операторский рендеринг отказа называет остаток и потолок
   - Входные данные: насыщенная корзина, отказ по дедлайну
   - Ожидаемый результат: обе величины присутствуют в тексте для лога (R-9.4)
5. **TC-UNIT-05:** клиентский рендеринг того же отказа остатка и потолка не несёт
   - Входные данные: тот же отказ, сетевой транспорт, обе роли принципала
   - Ожидаемый результат: ни одна из двух величин не присутствует в ответе (AC-47)

### Регрессионные тесты
- Вызовы без дедлайна ведут себя как прежде

## Критерии приёмки
- [ ] AC-21: ожидание прерывается дедлайном на насыщенной корзине
- [ ] `MAX_WAIT_MS` остаётся верхней границей
- [ ] `MIN_POST_WAIT_REMAINDER_MS` соблюдён
- [ ] R-9.4: операторский рендеринг отказа называет остаток и потолок
- [ ] AC-47: клиентский рендеринг отказа остатка и потолка не несёт ни при какой роли

## Примечания

PR-3 плана: эта задача и 014-23 обе трактуют сужение дедлайна. Расхождение между ними обнаруживается
живым гейтом 014-33.

Зависит от 014-26: разделение операторского и клиентского рендеринга вводится там, и TC-UNIT-05
выполним только после него.
