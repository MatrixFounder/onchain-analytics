# ADR-003 — Сетевой транспорт, периметр и коммерческая модель

- **Статус:** Accepted (решения владельца 2026-07-31). D1 подписан **безусловно** с 2026-08-01 — проба принципала выполнена, см. §«Проба принципала»
- **Дата:** 2026-07-31
- **Контекст-документы:** [DPAL-OPTIONS-2026-07-31.md](DPAL-OPTIONS-2026-07-31.md) §0.2, [ADR-001](ADR-001-tech-stack.md) D3/D6/D10, [ADR-002](ADR-002-configurable-routing.md), [open-questions.md](../architectures/open-questions.md), [DB-SCHEMA-CONCEPT](DB-SCHEMA-CONCEPT.md) §1
- **Решает:** каким интерфейсом зовут способности движка по сети, кто такой вызывающий и что ему можно, и как устроен учёт — вендорского расхода и клиентского списания.
- **Закрывает:** **OQ-M3-1** (интерфейс, которым n8n зовёт способности движка).

> ADR фиксирует **набор связанных решений (D1…D6)**. Три темы — транспорт, периметр и тарификация —
> **нельзя разделить**: принципал появляется в D1, проверяется в D2 и списывает кредиты в D4. Любые
> два решения без третьего дают либо сетевой адрес без владельца запроса, либо владельца без учёта.
> Реализация — этапы T-014 и T-015 ([ROADMAP](ROADMAP.md) §Now); **этот документ кода не меняет**.

## D1 — Транспорт: **Streamable HTTP**, stdio остаётся ✅

**Решение.** Движок получает транспорт **Streamable HTTP** из официального SDK. Это закрывает
OQ-M3-1 и переносит вперёд то, что ADR-001 D3 планировал на M6.

**Три варианта записи и почему выбран первый** (варианты воспроизведены дословно из
`open-questions.md`, чтобы закрытый вопрос не переоткрывался с нуля):

| Вариант                                              | Цена                                                                     | Вердикт                                                                                              |
| ----------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **1. Streamable HTTP** (перенести с M6)               | публичная поверхность + вопросы auth/CORS/порта                          | ✅ **выбран** — единственный, совместимый с решением продавать доступ                                   |
| 2. One-shot CLI (`Execute Command`, процесс на вызов) | старт процесса на каждый вызов; n8n обязан жить на той же машине          | ❌ наименее инвазивен для M3, но исключает клиента вообще: у «глобального MCP» нет способа зайти в CLI |
| 3. n8n пишет задание в Postgres, движок его забирает  | возвращает always-on процесс движка, что противоречит **ADR-001 D8** (дополнение 2026-07-25) | ❌                                                                              |

**Довод, которого в записи не было.** Вариант 2 оценивался при допущении «потребитель — только наш
n8n». Ответ про продажу доступа делает это допущение ложным: клиент, покупающий ключ, физически не
может вызвать one-shot CLI на нашей машине. Выбор перестал быть компромиссом по инвазивности.

**stdio не удаляется.** Локальная разработка под Claude Code не должна требовать поднятого сервера,
и контрактные тесты по stdio (`e2e.stdio.test.ts`) — самый дешёвый способ проверять инвентарь тулов.
Транспорт выбирается один раз, в `index.ts`; `createServer` остаётся неизменным — так и записано в
его собственном докстринге (`server.ts:52-55`) и в комментарии на `mcp-server/src/index.ts:132-133`. **Шов уже
существует**, и это заметно удешевляет T-014 против оценки разбора.

**Что ответ открывает.** Порт и адрес привязки (по умолчанию — только loopback, наружу через
обратный прокси); TLS (терминируется прокси, движок не носит сертификатов); CORS (браузерных
потребителей нет, значит по умолчанию запрещено, а не «*»); время жизни сессии и её привязка к
принципалу. Эти четыре пункта — предмет T-014, а не отдельного ADR: они конкретизируют D2, а не
конкурируют с ним.

## D2 — Принципал: клиентский токен доступа, и что он **не** даёт ✅

**Решение.** У запроса появляется владелец. `ctx.principal` возникает на границе тула и доходит до
леджера. Токен предъявляется в заголовке `Authorization`, проверяется **до** маршрутизации, и любой
запрос без валидного токена отклоняется до того, как коснётся реестра.

**Разграничение терминов — без него разговор рассыпается:**

| Термин                              | Что это                                                | Статус                                                        |
| ------------------------------------ | ------------------------------------------------------- | -------------------------------------------------------------- |
| **Клиентский ключ**                  | ключ доступа **к нашему MCP**, выпускается в кабинете   | ✅ это и есть продукт                                          |
| **Клиентские кредиты**               | наша внутренняя валюта, списывается по нашему прайсу    | ✅ закладывается сейчас; сегодня — один токен, безлимит         |
| **Вендорский ключ (наш)**            | `NANSEN_API_KEY` и прочие — `.env`, 0600, ADR-001 D10   | ✅ без изменений                                               |
| **Вендорский ключ клиента (BYO)**    | клиент приносит свой ключ Nansen                        | ❌ **не проектируется** — модель ровно обратная                |

🔴 **Чего токен не даёт — это и есть граница безопасности.**

> **Клиентский токен может потратить только свой баланс, но не может изменить, к какому хосту мы
> пойдём и какого провайдера позовём.**

Токен выбирает **что спросить** (тул + аргументы) и **сколько у него осталось**. Он не выбирает
маршрут, не переставляет адаптеров, не дописывает хост в allowlist и не меняет credential. Это
прямое следствие инварианта ADR-002 D1 и причина, по которой конфигурация маршрутизации остаётся на
ярусе 1, даже когда всё остальное станет многоарендным.

🔴 **Принципал определяет и то, что клиент видит в `_meta`.** Найдено при сверке
[ADR-002](ADR-002-configurable-routing.md) D8 и относится сюда: `_meta.budget` — это поле ответа
тула (`tools/budget-meta.ts:9`), несущее `{provider: 'nansen', creditsUsedToday}`. Пока
единственный вызывающий — владелец, это операторская телеметрия; после D1/D2 то же поле сообщает
**платящему клиенту наш суточный расход у вендора**. Поэтому в T-014:

- `_meta.budget` отдаётся **только операторскому принципалу**, клиентскому — нет;
- `tier` адаптера (ADR-002 D8) в `_meta` не добавляется вовсе;
- `_meta.cache` (`status` + `ageMs`) остаётся видимым **всем** — это часть коммерческого контракта
  (D4), а не телеметрия.

Разграничение видимости `_meta` по принципалу — часть периметра, а не «полировка»: без него первый
же платящий клиент получает нашу юнит-экономику вместе с ответом.

## D3 — Периметр: общий лимитер и ревизия SSRF под недоверенный вход ✅

**Решение.** Два свойства, верных для одной локальной сессии, перестают быть верными для сетевого
сервера, и оба пересматриваются в T-014.

🔴 **1. Внутрипроцессный лимитер перестаёт быть достаточным.** Сегодня состояние бакетов — это
`new Map` внутри процесса (`net/rate-limit.ts:118`), ключ — `providerId`. Для одной локальной сессии
это ровно правильно: один процесс, один потребитель, вендорский лимит соблюдается арифметически. У
сетевого сервера ломается сразу три допущения:

- **Много клиентов через один вендорский ключ.** Лимит вендора общий, а желающих — сколько угодно;
  честность распределения перестаёт быть автоматической.
- **Состояние теряется при рестарте.** Деплой обнуляет бакеты, и первая минута после него
  проходит без ограничения — ровно тогда, когда клиенты переподключаются пачкой.
- **Второй процесс не виден первому.** Любое горизонтальное масштабирование множит наш реальный
  расход на число инстансов, ничего об этом не сообщая.

Форма замены: состояние бакета переезжает в то же хранилище, где уже живёт `usage_window` — тот же
паттерн `(provider, window_start)`, та же атомарность. Отдельно от этого лимит **на принципала**
(D5, шов 6) — это другая ось: вендорский лимитер защищает нас от вендора, клиентский — нас от
клиента.

**2. SSRF-гейт пересматривается под недоверенный вход.** Сегодня `assertAllowedHost`
(`safe-fetch.ts:19-23`) — точное строковое совпадение hostname со списком **этого** адаптера, и оно
перепроверяется на каждом хопе редиректа (`safe-fetch.ts:361`). Пер-адаптерная изоляция и
перепроверка после `Location` — сильные свойства, и они сохраняются. Что меняется, когда аргументы
приходят от постороннего:

- Гейт не резолвит DNS и не смотрит на IP: он доверяет тому, что имя из нашего списка ведёт туда,
  куда вело при внесении. Против **нашей же** конфигурации это верно; против внешнего
  DNS-перепривязывания — нет.
- Нормализации регистра и порта нет — сравнение строковое. Пока хосты пишем мы, вариантов не
  возникает; поверхность, принимающая чужой ввод, обязана нормализовать до сравнения.
- Превышение лимита редиректов бросает **нетипизированную** ошибку (`safe-fetch.ts:390`), в отличие
  от таймаута и переразмерного тела, у которых есть свои классы. Для клиентской поверхности ошибка
  без типа — это ошибка, которую нельзя ни посчитать, ни отличить от чужой.

Ни один из трёх пунктов не является дефектом **сегодня**: все три верны ровно в той модели, для
которой писались. Они становятся дефектами в тот момент, когда появляется D2, — и потому чинятся
там же, а не «когда-нибудь».

## D4 — 🔴 Два леджера: вендорская трата и клиентское списание ✅

**Решение.** Счётчиков два, и сливать их нельзя.

|                       | **Вендорский расход**                                     | **Клиентское списание**                        |
| --------------------- | ----------------------------------------------------------- | ------------------------------------------------ |
| Что считает           | сколько мы задолжали Nansen / Blockscout                    | сколько мы списали с клиента                     |
| Единица               | вендорские кредиты + вызовы                                 | **наши** кредиты по нашему прайсу                |
| Где считается         | **внутри `adapter.fetch()`** — решение OQ-2, не трогаем      | **на границе тула, ДО обращения к кешу**         |
| При попадании в кеш   | **ноль**                                                    | **полная цена**                                  |
| Кто назначает         | вендор                                                      | мы, прайс-листом                                 |
| Хранилище             | `usage` / `usage_window` — **существуют** (`cache/ddl.ts`)   | `client_usage` — новое                           |

**Почему «до кеша» — требование, а не деталь.** Ответ владельца: «второй пользователь должен будет
нам заплатить столько же, даже если использует кэш — в этом бизнес-модель». Значит списание **не
может** жить там, где живёт вендорский гейт: тот вызывается только на промахе (единственный
вызывающий `checkAndReserve` — адаптер `nansen`). Тарификация обязана стоять на границе тула, до
`resolve()`, иначе попадание в кеш окажется для клиента бесплатным — то есть скидкой, которую никто
не назначал.

🔴 **«До кеша» означает резерв, а не финальное списание — иначе клиент платит за отказ.** Момент
списания стоит раньше, чем становится известен исход вызова, поэтому строка `client_usage` имеет
три состояния — `reserved` → `settled` | `refunded` — тот же паттерн `reserve → settle`, что уже
работает на вендорском бюджете. Правило исхода:

| Исход вызова                                                              | Что происходит с резервом                                    |
| --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Ответ получен (из кеша или от вендора)                                     | `settled` — **полная цена**, попадание в кеш не даёт скидки     |
| Отказ: `CapabilityUnavailableError`, невалидный по контракту результат      | `refunded` — клиент не платит за то, чего не получил            |
| Частичный ответ по дедлайну ([ADR-002](ADR-002-configurable-routing.md) D4 п.5) | `settled` **полностью**: ответ выдан, недостающие источники в нём перечислены |
| Ретрай с тем же `request_id`                                               | ни резерва, ни списания — идемпотентность (шов 4, D5)           |

Третья строка — единственная неочевидная, и решается она в пользу полного списания сознательно: по
D4 клиент платит **за ответ**, а частичный ответ с явным перечислением недостающих источников —
это ответ, а не сбой. Пропорциональная тарификация здесь потребовала бы цены за источник, которой в
прайсе нет и которая противоречила бы самой модели «клиент не заботится о том, как мы достаём
данные».

**Следствие: ключ кеша не сегментируется по клиенту.** `deriveArgsHash` хеширует ровно
`{capability, args}` (`net/args-hash.ts:45`), уникальность записи — `(provider, capability, args_hash)`
(`cache/ddl.ts:63`). Это **не меняется**. Клиент платит не за вызов вендора, а за ответ, поэтому
арендной сегментации кеша не требуется — и это одновременно дешевле (никакого умножения объёма кеша
на число клиентов) и правильнее (кеш перестаёт быть механизмом экономии для клиента и становится
нашей маржой). Побочно снимается конфликт интересов вокруг TTL: агрессивный кеш выгоден нам и при
этом не обкрадывает клиента.

**Обязательная плата за это — раскрытие возраста данных.** Если клиент платит полную цену за ответ
из кеша, он обязан видеть, что ответ из кеша и какого он возраста. Механизм **уже есть**:
`_meta.cache` со статусом и `ageMs` (`CapabilityResolution`, `adapters/registry.ts:78`; отдаётся
тулами, например `tools/chain-tvl.ts:87`). Меняется его **статус**: из отладочного поля оно
становится частью коммерческого контракта и не может быть убрано «за ненадобностью». Иначе это
продажа несвежих данных без раскрытия.

## D5 — Фаза 0: швы стоят, кабинета нет ✅

> **Решение владельца 2026-07-31:** «Сейчас я создаю ключ для себя и пользуюсь им безлимитно, пока
> тестирую и разрабатываю».

**Решение.** Реализуется **фаза 0**: один самовыпущенный токен, безлимитная квота, все тулы
разрешены, `client_usage` **пишется, но ничего не запрещает**. Это единственный способ убедиться,
что швы рабочие, не строя кабинет.

**Шесть швов — дешёвые сейчас и дорогие потом:**

1. **Принципал протянут через весь путь запроса.** `ctx.principal` на границе тула → леджер.
   Сегодня значение всегда одно (`self`), квота безлимитна. Цена сейчас: одно поле в контексте.
   Цена потом: правка 13 тулов и сигнатуры роутера.
2. **Тарификация — отдельный `BillingStore`, а не колонка в `BudgetStore`.** Тот же проверенный
   паттерн `reserve → settle` (атомарность через `BEGIN IMMEDIATE`), но **другой леджер и другая
   единица**. Слить их в одну таблицу — значит навсегда потерять различие «наш расход» / «выручка»,
   а на попадании в кеш они расходятся **всегда**.
3. **Прайс-лист — версионируемые данные, отдельно от вендорских цен.** Цена **фиксируется в момент
   списания** и хранится в строке леджера: иначе изменение прайса задним числом переписывает
   историю начислений.
4. **Идемпотентность списания.** Клиентский `request_id`: ретрай по таймауту не должен списывать
   дважды. У сетевого клиента ретраи — норма, а не исключение. *(Сегодня идемпотентности списания
   нет вовсе — проверено поиском.)*
5. **`shareable: boolean`** — необязательное поле манифеста capability, объявленное в
   [ADR-002](ADR-002-configurable-routing.md) D3 со значением по умолчанию `true`. Сегодня все
   способности — публичные ончейн-факты, общий кеш безопасен. Флаг нужен как страховка: первая же
   capability, чей ответ зависит от личности вызывающего (watchlist, приватный алерт), не должна
   попасть в общий кеш по невнимательности. Правило: `shareable: false` → кеш в пределах принципала
   либо не кешируется вовсе.

   > **Аннотация T-014 (2026-08-20, задача 014-31).** Из двух ветвей проект взял **вторую**: при
   > `shareable: false` способность не читается из кеша и не пишется в него. Первая закрыта
   > требованием R-5.1 — принципал не входит в ключ кеша, поэтому кеша «в пределах принципала» в этом
   > движке нет и ключа под него не существует. Правило применяет `CapabilityRegistry.resolve()`;
   > оно же снимает склейку одинаковых вызовов в singleflight, потому что ключ склейки принципала не
   > несёт по той же R-5.1. Подробности и цена решения — `docs/architectures/interfaces.md` §5.4.6.
   > Само решение ADR не переписано: аннотация в стиле ARCHITECTURE §1.2 к ADR-001 D6.
6. **Квоты и лимиты — поля на токене с самого начала:** `creditsBalance`, `rateLimit`,
   `toolAllowlist`. Сегодня безлимит и все тулы. **Отсутствующее поле нельзя выставить в
   «безлимит»** — его придётся вводить, а вместе с ним и весь путь проверки.

**Чем проверяется, что шов рабочий, а не декоративный.** Приёмка фазы 0 — не «поле существует», а:
после серии вызовов, часть которых попала в кеш, `client_usage` содержит строку **на каждый вызов**,
включая попадания; повторная отправка того же `request_id` **не** создаёт второй строки; сумма
списаний по леджеру не равна вендорскому расходу за тот же период (если равна — значит списание
стоит после кеша, то есть в неправильном месте).

**Чего сознательно не делаем сейчас:** кабинет и портал, приём платежей, инвойсинг, тарифные планы,
экспорт метрик потребления, SLA и дежурство. Всё это — **по появлению первого платящего клиента, не
по календарю**. Заложенные швы делают их аддитивными, а не переделкой.

## D6 — Замер расхода Blockscout: счётчик **вызовов**, не кредитов ✅

> **Решение владельца 2026-07-31** (вопрос 7): «Да, надо померить и посчитать, чтобы ориентироваться
> на эти цифры. Можно будет сделать заодно с другими задачами».

**Факт.** Blockscout помечен у нас как бесплатный: `costOf` возвращает 0, строки в `usage` нет,
бюджет-гейт на него не смотрит. У вендора при этом есть реальный лимит: **100 000 кредитов в
сутки**, а один наш вызов `get_address_info` внутри вендора расходится на три запроса и стоит
**≈160 кредитов**. Это **≈625 вызовов в сутки** — после чего вендор перестаёт отвечать.

**Почему знаменатель — вызовы, а не кредиты.** Считать кредиты нельзя: для нас цена вызова равна
нулю, и **любой** кредитный потолок пропустит бесконечно много вызовов (`used + 0 > ceiling` ложно
при любом потолке). Считать вызовы можно — это единственная величина, видимая с нашей стороны. На
Nansen мы уже на это наступили (записи SEC-1 и Q-3): кредитного счётчика оказалось недостаточно,
пришлось добавить счётчик вызовов.

🔴 **Уточнение к разбору, найденное при сверке: механизм уже существует.** Разбор предлагал «завести
строку в `usage` со счётчиком вызовов». Этого делать не нужно — таблица `usage_window`
(`packages/core/src/cache/ddl.ts:107-116`) уже несёт колонку `calls_made` с ключом
`(provider, window_start)`, и её собственный комментарий формулирует ровно этот довод: «`calls_made`
is the SECOND denominator (Q-3). A credit-denominated gate […] can never refuse a call that costs
ZERO credits». Работа T-015 — не новая таблица, а **обобщение существующего сторожа с одного
провайдера на любой**, у которого есть невидимый нам лимит.

**Как исчерпание проявится, если ничего не делать.** По-разному в двух местах, и оба раза неочевидно:

- на `entity.labels` цепочка просто уйдёт на **платный** Nansen (`providers.config.ts:93`) — то есть
  исчерпание бесплатного провайдера начнёт незаметно тратить деньги;
- на `token.holders` — жёсткий отказ (`providers.config.ts:76`, единственный адаптер).

**Текущий лимитер помечен как оборонительный, а не измеренный.** Значение `refillPerSec` у
blockscout выбрано «на глаз», и в комментарии рядом прямо написано, что цитировать его как
измеренный потолок вендора нельзя. T-015 заменяет догадку измерением.

**Побочная выгода, ради которой это и прицеплено к тарификации.** Как только появится клиентский
прайс, «≈625 вызовов в сутки» перестаёт быть абстракцией и становится **входом в юнит-экономику**:
сколько бесплатных ответов в сутки мы физически можем продать, прежде чем начнём платить Nansen за
то, что клиенту продано как бесплатный ярус.

## Чего не будет — вычеркнуто, а не отложено

**BYO вендорские ключи от клиентов.** Клиент не приносит свой `NANSEN_API_KEY`. Модель ровно
обратная: продаём доступ по **своим** ключам за клиентские кредиты. Вместе с этим из плана уходят —
не откладываются, а вычёркиваются:

- KMS и хранилище чужих секретов;
- ротация чужих секретов и уведомления об их истечении;
- шифрование клиентских credential'ов и связанный с ним ключевой материал;
- **сегментация кеша по арендатору** — прямое следствие D4.

Это не экономия и не упрощение: это другой продукт. Проксирование чужих ключей делает нас
хранителем чужих секретов и не приносит выручки; продажа доступа по своим — приносит и не делает.

## Проба принципала — выполнена 2026-08-01, SDK 1.29.0

Скрипт: `packages/mcp-server/scripts/probe-principal.mjs` (`pnpm --filter @onchain-intel/mcp-server
probe:principal`). Ни одного сетевого вызова, ни одного кредита: `InMemoryTransport.send()`
принимает `authInfo` — тот же шов, который над HTTP наполняет `requireBearerAuth`. Скрипт
**перезапускается на каждом подъёме версии SDK**: он и есть evidence, на которую ссылается D1.

| # | Вопрос | Ответ |
| --- | --- | --- |
| Q1 | `authInfo` доходит до колбэка `registerTool` | ✅ хендлер увидел `clientId`, `scopes[]` и `extra` целиком |
| Q1b | без авторизации хендлер видит `undefined`, а не чужой принципал | ✅ `null`, утечки нет |
| Q2 | один общий `McpServer` принимает второе подключение | ❌ **отказ: «Already connected to a transport»** |
| Q3 | посессионный `McpServer` даёт пер-принципальный `tools/list` | ✅ полный скоуп — 2 тула, узкий — 1 |
| Q4 | `scopes` несут произвольные строки, годятся под `toolAllowlist` | ✅ отказ без скоупа, ответ со скоупом |

🔴 **Q2 — главный результат, и он сильнее, чем вопрос, который задавался.** Спрашивалось,
протекает ли `enable()/disable()` между принципалами; выяснилось, что до этого не доходит:
`McpServer` **вообще не принимает второе одновременное подключение**. Значит посессионный сервер —
не вариант дизайна, а **условие работы сетевого сервера**. Сегодняшняя раскладка
(`mcp-server/src/index.ts:129-131`: один `McpServer`, один реестр, один `BudgetStore` на процесс)
для одного локального stdio-клиента верна и для сети непригодна в принципе, а не по качеству.

**Что из этого следует для T-014 — граница «общее / посессионное».**

| Компонент | Где живёт | Почему |
| --- | --- | --- |
| `McpServer` | **на сессию** | иначе второе подключение отвергается (Q2) |
| `CapabilityRegistry` + 12 адаптеров + кеш | **общий** | кеш глобальный и не сегментируется по клиенту (D4); отдельный кеш на сессию отменил бы всю модель маржи |
| `BudgetStore` (вендорские кредиты) | **общий** | это наш потолок у вендора, он один на инсталляцию |
| `BillingStore` (клиентские кредиты) | **общий**, с ключом по принципалу | леджер один, различает строки, а не экземпляры |

**Цена оказалась ниже оценки.** `createServer` уже принимает зависимости параметрами и уже
документирован как транспорт-агностичный (`mcp-server/src/server.ts:52-55`), поэтому переход
выглядит как «собрать общие зависимости один раз, а `McpServer` конструировать на каждую сессию над
теми же зависимостями» — без правки самой фабрики. Оценка «полдня на пробу» тоже оказалась
завышенной: искать было нечего, всё типизировано.

**Связь с ADR-002 D7.** Q3 показывает, что пер-принципальный `tools/list` получается **составом
регистрации на сессию**, а не фильтром на лету. Значит вход для этой фильтрации — единый `ToolSpec`
(ADR-002 D7, этап T-011): без него «зарегистрировать подмножество тулов» означает ветвление в
тринадцати местах.

**Что проба НЕ проверяла и что остаётся на T-014:** поведение под реальным HTTP-транспортом
(`sessionIdGenerator`, `onsessioninitialized`/`onsessionclosed`), время жизни и вытеснение сессий,
и поведение при конкурентных запросах внутри одной сессии. Это вопросы эксплуатации, а не
существования механизма, и они решаются кодом, а не пробой.

**Приятный побочный результат для D3.** Опции транспорта включают `allowedHosts`, `allowedOrigins`
и `enableDnsRebindingProtection` — защита периметра, которую я записывал как «надо будет
пересмотреть», частично встроена в SDK. Плюс `OAuthTokenVerifier` — интерфейс из **одного** метода
`verifyAccessToken(token) → AuthInfo`, поэтому наши собственные непрозрачные токены не требуют
OAuth-сервера.

**OQ-F — где живёт хранилище леджера. ✅ ЗАКРЫТ решением владельца 2026-08-25.**

**Вопрос в исходной форме больше не стоит.** Он был поставлен как выбор «SQLite рядом с кешем ИЛИ
Postgres рядом с данными снапшоттера». T-014 задачей 014-38 построил **ось хранилища**: профиль
`local` разрешается в SQLite в `DATA_DIR`, `network` — в Postgres, схему `onchain`, `network-sqlite` —
в SQLite для отладки транспорта. `BillingStore` следует этой оси, как `CacheStore`, `BudgetStore` и
`LimiterStore`. Иначе профиль `local` начинает требовать Postgres, а он обязан подниматься на пустом
окружении: `EnvSchema.parse({})` не имеет права упасть (R-13.5).

**Само правило не новое — это применение уже принятого.** Владелец закрыл `OQ-8` 2026-08-12
формулировкой «данные времени выполнения — только Postgres; локальный профиль сохраняет SQLite»
([TASK-014](../tasks/task-014-t014-http-transport-auth-perimeter-profiles-shared-limiter.md) §5.1). `client_usage` — данные времени выполнения. Отсюда: **авторитетны
только строки Postgres**; на оси SQLite шов прогоняется без базы, и денег там нет по построению —
токен самовыпущенный (`003_seed_engine_admin.sql`) и указывает на профиль `phase0-unlimited`,
который `002_t014_network_profile.sql` сеет с `credits_mode = 'unlimited'`.

**Довод, которого при постановке вопроса ещё не было: три четверти картины уже лежат в Postgres.**
Миграция `002_t014_network_profile.sql` завела `users`, `api_tokens`, `access_profiles` и
`access_audit` — сам ключ и его владелец. `access_profiles` несёт `credits_balance_raw`,
`rate_limit_per_min` и `tool_allowlist_json`, то есть **шов 6 из D5 построен**, и баланс, который
покажет будущий кабинет, уже там. `request_trace` пишет построчно `principal_id`,
`client_request_id`, `capability`, `served_from`, `cache_age_ms`, `outcome` и наш вендорский расход.
`client_usage` на оси SQLite оставил бы один вопрос — «сколько потратил этот ключ и на что» —
склеенным через два движка.

**`client_usage` — отдельная таблица, а не состояние на `request_trace`.** Поля пересекаются, ключи
служат разному: `request_trace` уникален по `(principal_id, client_request_id, received_at)`, и
**время входит в ключ**, поэтому ретрай создаёт вторую строку. Это дедуп на точную повторную
доставку, а не идемпотентность. Леджеру нужен ключ **без времени**, иначе ретрай спишет дважды — это
шов 4 из D5, и существующий ключ его не закрывает.

**Что решение тянет за собой.** Движок сегодня пишет в тот же контейнер Supabase, где лежат данные
снапшоттера в dev-VM. Пока туда идут кеш, бюджет и лимитер — это гигиена. С леджером списаний
формулировка становится другой: финансовая запись живёт в dev-базе на VM внутри ноутбука. Траекторию
уже назвал `OQ-T014-B` — «сейчас VM, затем VPS с общей базой; строго своя схема с явной
квалификацией» (R-30), — поэтому
[WI-62](../backlog/wi-62-engine-tables-move-to-a-dedicated-postgres-container-on-the-separated-host.md)
входит в область T-015, а не остаётся отдельной уборкой.

**OQ-G — как долго живёт идемпотентность по `client_request_id`. ✅ ЗАКРЫТ решением владельца
2026-08-26.**

**Вопрос возник из самого OQ-F.** Ключ идемпотентности обязан быть **без времени**, иначе ретрай его
не встретит. Но ключ без времени не истекает **никогда**, а `D4` при этом велит списывать за ответ.
Сложение двух правил даёт то, чего никто не назначал: клиент, повторяющий один
`client_request_id`, обслуживается бесплатно неограниченно долго и тратит **наши** вендорские
кредиты. Ни `D4`, ни `D5` этого не разрешали — оно возникло на их пересечении. Ограничение частоты на
токене (`rate_limit_per_min`, шов 6) здесь не защищает: оно ограничивает темп, а не бесплатность.

**Решение: у идемпотентности есть срок, и он выводится из TTL способности, а не назначается.**

> `окно_реплея = min(ttlSeconds способности, 120 000 мс)`

**Почему TTL — правильная граница, а не компромисс.** Внутри TTL повтор не делает данные хуже:
свежий запрос в тот же момент получил бы **те же байты** из кеша, потому что запись ещё жива. За
пределами TTL — делает, причём **невидимо**: реплей не перечитывает кеш и отдаёт ответ старше того
контракта свежести, который движок сам объявил. Верхняя граница `120 000` мс не выдумана: это
удвоенный наибольший объявленный `deadlineMs` — та же величина, которую T-015 уже вывела для порога
фоновой сверки зависших резервов, и по той же причине. Дольше этого вызывающий физически не может
всё ещё ждать первый ответ.

Практический разброс на сегодняшнем манифесте: `gas.price` и `pairs.active` — **30 с**;
`token.price` и `wallet.balances.native` — **60 с**; остальные двадцать три способности — **120 с**
(их TTL от 300 до 3600 с, поэтому связывает верхняя граница).

**За окном `client_request_id` — одноразовый токен с истёкшим сроком.** Повтор после истечения не
ретрай, а новый запрос под старым ярлыком; он получает **именованный класс отказа**, сообщающий, что
нужен свежий идентификатор. Это же поведение у идемпотентных ключей в платёжных API.

**Два срока на одной строке, и их нельзя путать.** Строка `client_usage` живёт **три года** — это
бухгалтерия (`OQ-4`, решение владельца 2026-08-25). Её **воспроизводимость** истекает через 30–120
секунд. Одна запись, два срока; не различить их в тексте — значит получить реализацию одного.

**Обязанность, которая идёт вместе с решением.** `_meta.cache.ageMs` при реплее сообщает **истинный
возраст данных**, а не возраст на момент первого ответа. `D4` сделал раскрытие возраста частью
коммерческого контракта именно потому, что клиент платит полную цену за ответ из кеша; реплей,
занижающий возраст, — это продажа несвежего под видом свежего.

**Что решением НЕ решено и передаётся в проектирование.** Чем именно обслуживается повтор внутри
окна: (i) повторным исполнением, которое внутри TTL и так попадёт в кеш, либо (ii) записанным
исходом, адресуемым `args_hash` строки леджера. Разница наблюдаема ровно в одном случае — **промах
кеша внутри окна** (вытеснение LRU): при (i) движок сходит к вендору и не спишет, то есть заплатит
за клиента; при (ii) — не сходит. Вариант (ii) вернее замыслу «не тратить свои кредиты»; вариант (i)
не требует хранить ответы. Выбор — за фазой архитектуры, **с записью довода**, а не молча.

## Revisit when (триггеры пересмотра)

- **D1 → добавить второй сетевой транспорт**, если появится потребитель, которому Streamable HTTP не
  подходит. Абстракция для этого уже стоит (`server.ts:52-55`).
- **D2 → перейти на OAuth / внешний провайдер идентичности**, когда появится больше нескольких
  клиентов или потребуется делегирование. Собственные токены — правильный старт, но не потолок.
- **D3 → вынести лимитер во внешнее хранилище** (Redis), когда инстансов станет больше одного. До
  тех пор общего хранилища достаточно.
- **D4 → пересмотреть модель «полная цена за кеш»**, если клиенты начнут воспринимать это как
  несправедливость. Механизм раскрытия (`_meta.cache.ageMs`) для этого разговора уже есть; менять
  придётся прайс, а не архитектуру.
- **D6 → вернуться к оборонительному лимитеру**, если измерение покажет, что реальный потолок
  Blockscout **ниже** ≈625 вызовов в сутки.
- **Весь ADR → пересмотр**, если решение продавать доступ будет отменено: без принципала D2, D4 и D5
  теряют основание, а D1 сводится обратно к выбору между HTTP и one-shot CLI.

  T-015 (раунд 1, MAJOR-11) при чтении реализации, а не при чтении решений. Срок **выведен, а не
