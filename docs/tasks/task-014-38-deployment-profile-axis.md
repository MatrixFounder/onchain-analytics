# Задача 014.38: профиль развёртывания и ось хранилища `[LOGIC]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети
- UC-3 — оператор запускает локально

<!-- contract:goal -->

## Цель задачи

Разрешать `ONCHAIN_PROFILE` в пару «транспорт + хранилище» один раз при старте процесса и строить по
этой паре транспорт и хранилища. Профиль `network` без `ONCHAIN_STATE_PG_URL` завершает старт отказом.

**Why пункт существует.** Транспорт и хранилище — две независимые оси (`deployment.md` §10.1.1,
`system-architecture.md` §3.4.8). План описывает выбор транспорта (задача 014-09) и не описывает
выбор хранилища, поэтому вторая ось остаётся без исполнителя.

## Описание изменений

### Новые файлы

- `packages/mcp-server/src/profile.ts` — разрешение `ONCHAIN_PROFILE` в пару «транспорт +
  хранилище» и предстартовые проверки сетевого профиля
- `packages/mcp-server/test/deployment-profile.test.ts` — тесты трёх пар и отказа старта

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/index.ts`:**

- `main()` читает профиль один раз, присоединяет соответствующий транспорт и строит соответствующее
  хранилище
- Сигнатуру `createServer` не менять (R-1.2)

**Why сигнатура не меняется.** `deployment.md` §10.1.1: тогда профиль не доходит ни до одного тула и
ни до одного адаптера.

### Две оси

| Ось       | Значения                                       |
| :-------- | :--------------------------------------------- |
| Транспорт | stdio, Streamable HTTP                         |
| Хранилище | SQLite в `DATA_DIR`, Postgres, схема `onchain` |

**Why оси независимы.** Транспорт решает, кто дотягивается до процесса; хранилище решает, где лежит
его состояние. Ни один ответ не ограничивает другой (`deployment.md` §10.1.1).

### Три объявленные пары

| Профиль          | Транспорт       | Хранилище                 | Назначение                          |
| :--------------- | :-------------- | :------------------------ | :---------------------------------- |
| `local`          | stdio           | SQLite в `DATA_DIR`       | поставляемый локальный режим (UC-3) |
| `network`        | Streamable HTTP | Postgres, схема `onchain` | поставляемый серверный режим        |
| `network-sqlite` | Streamable HTTP | SQLite в `DATA_DIR`       | отладка транспорта без Postgres     |

Четвёртой комбинации — stdio поверх Postgres — архитектура не проектирует.

**Why третье имя профиля, а не второй ключ.** Два ключа делают настраиваемой четвёртую комбинацию.
Комбинация, которую документ не назвал, — это конфигурация, не покрытая ни гейтом, ни случаем живого
гейта (`system-architecture.md` §3.4.8, `deployment.md` §10.1.1).

**Why `network-sqlite` существует.** Владелец отлаживает HTTP на машине разработки до переключения
`.mcp.json`. Требование поднятого Postgres для этого — расход без назначения.

**Why умолчание — `local`.** `EnvSchema.parse({})` обязан продолжать проходить (R-13.5), поэтому
пустое окружение разрешается в профиль, не требующий ни одной настройки.

### Что следует за какой осью

Свойства оси транспорта (`deployment.md` §10.1.1):

| Свойство             | stdio                                   | Streamable HTTP                                                  |
| :------------------- | :-------------------------------------- | :--------------------------------------------------------------- |
| Токен                | не требуется, не проверяется (UC-3)     | bearer в `Authorization`, проверка до маршрутизации (R-3)        |
| Входящий периметр    | нет: слушателя не существует            | `allowedHosts`, `allowedOrigins`, защита от DNS-rebinding (R-12) |
| Таблицы личности     | объявлены, пусты, бездействуют (§4.5.1) | заполняются (R-15)                                               |
| `_meta.budget`       | присутствует                            | только у роли `admin` (R-6.1)                                    |
| Приёмник диагностики | stderr процесса                         | лог контейнера (R-32.1)                                          |

Свойства оси хранилища (`deployment.md` §10.1.1):

| Свойство                   | SQLite в `DATA_DIR`                           | Postgres, схема `onchain`                       |
| :------------------------- | :-------------------------------------------- | :---------------------------------------------- |
| Состояние лимитера         | `provider_buckets` в `DATA_DIR/cache.sqlite3` | `onchain.provider_buckets` (R-7.1)              |
| Кеш и `usage`              | SQLite в `DATA_DIR`                           | `onchain.cache_entries`, `onchain.usage` (OQ-8) |
| Долговременная диагностика | `DATA_DIR/cache.sqlite3`                      | `onchain.diagnostics` (R-32.2)                  |
| Задания ретенции           | не устанавливаются                            | воркфлоу n8n §10.6.1 (R-32.3)                   |

### Порядок старта

Порядок воспроизводит `deployment.md` §10.3.2.

1. `loadEnv()` разбирает окружение. Постусловие: каждый ключ необязателен, поэтому `{}` проходит.
2. Профиль разрешается из `ONCHAIN_PROFILE`. Постусловие: незаданное значение даёт `local`, и
   локальный путь продолжается без изменений.
3. Только в профиле `network` выполняются предстартовые проверки. Постусловие: непройденная
   проверка пишет своё имя в stderr и завершает процесс ненулевым кодом.
4. Транспорт присоединяется, и в профиле `network` слушатель привязывается. Постусловие: ни один
   сокет не привязан до успеха шага 3.

Предстартовые проверки сетевого профиля, по порядку: `ONCHAIN_STATE_PG_URL` задан; хранилище
состояния отвечает; в `api_tokens` есть хотя бы одна строка `active` без истёкшего срока (§4.5.4).

**Why отказ, а не понижение до SQLite.** Понижение без отказа положило бы токены сервера, следы и
леджер расхода в локальный файл, и каждый гейт отрапортовал бы успех (L-10). Постусловие:
отсутствующий или опечатанный DSN не выбирает ось SQLite.

**Why проверка предшествует привязке порта.** Слушатель, существующий до проверки токена, — это
неаутентифицированная поверхность на всё время проверки.

### Операционное ограничение

Два поставляемых профиля не запускаются одновременно против одних вендорских учётных данных
(решение владельца 2026-08-13). Владелец переключает `.mcp.json` со stdio на HTTP.

**Why ограничение записано, а не проверяется кодом.** Процесс не наблюдает другой процесс, держащий
тот же вендорский ключ, поэтому скомпилированной проверки у правила нет.

Следствие для AC-4: критерий охватывает два процесса одного профиля над одним хранилищем — два
процесса `network` над одним Postgres или два процесса `local` над одним `DATA_DIR`
(`data-model.md` §4.5.11).

### Разделение с задачей 014-40

Объявление `ONCHAIN_PROFILE` и `ONCHAIN_STATE_PG_URL` в `EnvSchema` и в `.env.example` принадлежит
задаче 014-40 вместе с остальными восемью ключами. Эта задача — их единственный потребитель.

**Why объявление вынесено.** Ключ, объявленный в двух задачах, получает два разных набора допустимых
значений, и расхождение проявляется на настройке установки, а не на тесте.

## Тест-кейсы

### Модульные тесты

1. **TC-UNIT-01:** `local` выбирает объявленную пару
   - Входные данные: окружение с `ONCHAIN_PROFILE=local`
   - Ожидаемый результат: транспорт stdio, персистентный слой кеша — `SqliteCacheStore`
2. **TC-UNIT-02:** `network` выбирает объявленную пару
   - Входные данные: `ONCHAIN_PROFILE=network` плюс заданный `ONCHAIN_STATE_PG_URL`
   - Ожидаемый результат: транспорт Streamable HTTP, персистентный слой кеша — `PgCacheStore`
3. **TC-UNIT-03:** `network-sqlite` стартует без Postgres
   - Входные данные: `ONCHAIN_PROFILE=network-sqlite`, `ONCHAIN_STATE_PG_URL` не задан
   - Ожидаемый результат: процесс стартует, транспорт HTTP, хранилище — SQLite в `DATA_DIR`
4. **TC-UNIT-04:** `network` без DSN не стартует
   - Входные данные: `ONCHAIN_PROFILE=network`, `ONCHAIN_STATE_PG_URL` не задан
   - Ожидаемый результат: ненулевой код выхода, имя ключа в stderr, порт не привязан
5. **TC-UNIT-05:** незаданный ключ даёт `local`
   - Входные данные: окружение без `ONCHAIN_PROFILE`
   - Ожидаемый результат: `EnvSchema.parse({})` проходит, разрешается пара `local` (AC-24)
6. **TC-UNIT-06:** неотвечающее хранилище состояния останавливает старт до привязки порта
   - Входные данные: `ONCHAIN_PROFILE=network`, DSN на закрытый порт loopback
   - Ожидаемый результат: ненулевой код выхода, имя непройденной проверки в stderr, порт не привязан
7. **TC-UNIT-07:** профиль не доходит до тула
   - Входные данные: объект зависимостей, переданный в `createServer` в профилях `local` и `network`
   - Ожидаемый результат: наборы ключей совпадают, ключа профиля нет ни в одном (R-1.2)

### Регрессионные тесты

- `e2e.stdio.test.ts` проходит без правок (AC-2)
- Локальный профиль стартует при отсутствующем `.env` (`deployment.md` §10.3, R-23)
- `pnpm test`, `pnpm typecheck`

## Примечания

Задача 014-09 добавляет второй транспорт и выбирает его по неназванной настройке. Эта задача даёт
настройке имя, добавляет вторую ось и оставляет правку `index.ts` из 014-09 в силе.

AC-24 закрывается совместно: проверка активного токена принадлежит задачам 014-04 и 014-07, здесь она
получает своё место в порядке старта. Классификация обоих ключей и гейт AC-44 — задачи 014-05 и
014-40.

TC-UNIT-06 адресует закрытый порт loopback и исходящей сети не требует, поэтому остаётся в прогоне CI
(R-21). Проверка «в `api_tokens` есть активная строка» требует хранилища и измеряется задачей 014-07.

Реализации хранилища на оси Postgres — задача 014-39. Эта задача выбирает ось, та её строит.
