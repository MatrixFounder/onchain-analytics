# Задача 015.16: ключ `BLOCKSCOUT_DAILY_CALL_CAP` — валидация, класс настройки, инъекция в `core`

## Связь со сценариями

- UC-7 — оператор проверяет срабатывание суточного гейта на сконфигурированном пороге, шаг 1

<!-- contract:goal -->

## Цель задачи

Завести ключ окружения, снижающий суточный потолок вызовов blockscout на время проверки, так чтобы
продуктивное значение оставалось объявленным потолком с пометкой происхождения.

**Why ключ, а не правка объявленного потолка.** UC-7 шаг 1 снижает порог до синтетического
значения и шаг 4 возвращает его обратно. Правка объявленного числа сделала бы возврат правкой кода,
а тестовое значение — частью истории продуктивного потолка.

**Why значение приходит инъекцией.** `packages/core` не читает `process.env` напрямую (R-13.3a).
Ключ парсится в `mcp-server` и передаётся параметром
(`docs/architectures/system-architecture-billing.md:513` — подстрока `The key is EnvSchema's, narrowing
class`).

### Форма значения

| Состояние ключа             | Что действует                                      |
| :-------------------------- | :------------------------------------------------- |
| не задан                    | объявленный потолок `providers.config.ts` (R-10.1) |
| пустая строка               | то же, что не задан                                |
| положительное целое         | действующий потолок сужается до этого значения     |
| `0`, отрицательное, дробное | отказ валидации                                    |
| `off`                       | отказ валидации — сентинела отключения нет         |

**Why сентинела отключения нет.** R-9.6 делает объявленный потолок обязательным для этого
провайдера, поэтому отключение гейта не является допустимой конфигурацией
(`docs/architectures/system-architecture-billing.md:509` — подстрока `No `off` sentinel is offered here`).

**Why значение только сужает.** Класс настройки — `narrowing`, а он означает, что любое допустимое
значение ограничивает поведение движка. То же правило уже применено к трём тормозам nansen:
`packages/mcp-server/src/settings-classification.ts:92` — подстрока `The three Nansen brakes are
narrowing`. Действующий потолок поэтому равен меньшему из двух: объявленного и заданного ключом.

**Why правило сужения записано, а не выведено из слова «переопределяет».** Значение выше
объявленного потолка расширило бы допустимое число вызовов, и класс `narrowing` перестал бы быть
верным. Меньшее из двух делает класс верным по построению и оставляет синтетическое значение
единиц вызовов работоспособным (R-12.1).

### Продуктивный порог и тестовый не смешиваются (AC-22)

| Величина           | Где живёт                       | Пометка                         |
| :----------------- | :------------------------------ | :------------------------------ |
| продуктивный порог | `providers.config.ts`           | «оценка `ADR-003` D6, не замер» |
| тестовое значение  | ключ окружения на время прогона | в код не пишется                |

Пометку происхождения объявляет задача 015-12 вместе с самим полем. Здесь она не переписывается.

### Гейты, которые эта задача обязана оставить зелёными

- `packages/mcp-server/test/settings-access.gate.test.ts:96` — `process.env` вне `env.ts` не
  читается
- `packages/mcp-server/test/env-example-in-sync.test.ts:99` — `.env.example` документирует каждый
  объявленный ключ
- `packages/mcp-server/test/settings-classification-gate.test.ts:89` — класс в коде равен классу в
  документе
- `packages/mcp-server/test/settings-classification-gate.test.ts:138` — T-014 не добавляет
  сужающего ключа

**Why гейт классификации проходит без правки документа.** Строка ключа в таблице §10.3 уже стоит:
`docs/architectures/deployment.md:208` — подстрока `BLOCKSCOUT_DAILY_CALL_CAP`. Сегодня она
шире схемы, и это допускается проверкой `documented.size >= schemaKeys.length`
(`packages/mcp-server/test/settings-classification-gate.test.ts:70`). После этой задачи документ и
схема сходятся.

**Why гейт «T-014 не добавляет сужающего ключа» остаётся зелёным.** Он отбирает ключи по префиксу
`ONCHAIN_` (`packages/mcp-server/test/settings-classification-gate.test.ts:141` — подстрока
`key.startsWith('ONCHAIN_')`). Имя нового ключа под отбор не попадает, поэтому утверждение о T-014
остаётся измеренным, а не обойдённым.

4. **TC-UNIT-04:** пустая строка равна отсутствию ключа
   - Входные данные: `BLOCKSCOUT_DAILY_CALL_CAP=''`
   - Ожидаемый результат: значение пусто; поведение совпадает с TC-UNIT-01
5. **TC-UNIT-05:** сообщение об отказе называет ключ и не называет значение
   - Входные данные: `BLOCKSCOUT_DAILY_CALL_CAP='0'` через `loadEnv`
   - Ожидаемый результат: текст ошибки содержит имя ключа и не содержит переданного значения (D10)
6. **TC-UNIT-06:** класс ключа — сужающий

## Примечания

Этап: **Этап 4. Суточный гейт вызовов**. Проход: **impl**. Зависимость: 015-13 (контракт гейта,
`createCallGate` и параметр переопределения).

Поле `dailyCallCeiling` и пометку его происхождения объявляет задача 015-12; включение гейта в
адаптер — задача 015-15. Здесь заводится только ключ и его путь до гейта.

Прогон по методике 015-01, использующий этот ключ, исполняет задача 015-30. Возврат порога к
продуктивному значению после прогона — шаг той задачи, а не этой.

`refillPerSec` blockscout и его пометка «не цитировать как измеренный потолок» этой задачей не
правятся (R-10.4, AC-42).

Требования: R-10.1, R-10.2, R-12.1.
