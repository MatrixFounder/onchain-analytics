## Цель

Заменить ветвление по **имени сети** на ветвление по **семейству**. Одна ветка `evm` начинает
обслуживать все 270+ EVM-сетей вместо одной. Содержание веток `evm`/`svm` не меняется ни на
строку — меняется только то, что их выбирает.

## Контракт

| `family`                             | Валидация                           | Канонизация         |
| ------------------------------------ | ----------------------------------- | ------------------- |
| `evm`                                | 40 hex-символов (с/без `0x`)        | EIP-55 checksum     |
| `svm`                                | base58 → ровно 32 байта             | как есть            |
| `move` / `cosmos` / `utxo` / `other` | **нет валидатора** — приём как есть | **нет канонизации** |

## Phase 1 — сигнатуры + стаб `[STUB CREATION]`

1. Изменить сигнатуры на приём `ChainInfo` (или `family`) вместо строкового `chain`.
   Решение о точной форме сигнатуры принимает Developer — критерий: вызывающая сторона не должна
   резолвить реестр дважды.
2. Ветки `move`/`cosmos`/`utxo`/`other` — стаб: `isValidAddress → true`,
   `normalizeAddress → raw` (это и есть целевое поведение, не временная заглушка).
3. Существующие тесты EIP-55/base58 должны пройти **без правок** — это гейт Phase 1.

## Phase 2 — логика `[LOGIC IMPLEMENTATION]`

1. Перенести существующие реализации `evm`/`svm` под новые ветки **дословно**.
2. Убрать ветку `dash`, бросавшую безусловно: теперь `dash` — `family: 'other'`, то есть приём
   без канонизации. Поведение вызывающих не ломается: `Wallet`/`Balance` для Dash по-прежнему не
   строятся (это решает матрица покрытия, не валидатор адреса).
3. Явно задокументировать в коде цену отказа от канонизации: ключ кеша строится от исходной
   строки → один адрес в разном регистре даст **две** записи кеша. Это потеря эффективности, не
   корректности; триггер пересмотра — появление платного провайдера на таком семействе.
