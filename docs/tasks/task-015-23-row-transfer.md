# Задача 015.23: остановка сетевого профиля и перенос строк одиннадцати таблиц `[VM]`

## Связь со сценариями

- UC-6 — таблицы движка переезжают в выделенный контейнер Postgres на dev-VM, шаги 3 и 4

<!-- contract:goal -->

## Цель задачи

Перенести строки таблиц движка в новый контейнер в окне, когда в старый контейнер не пишет никто.

**Why окно без писателя, а не сверка постфактум.** Идемпотентность по ключу UNIQUE дедуплицирует
двух писателей только внутри одной базы (`DB-SCHEMA-CONCEPT` §6). Здесь баз две: строка, записанная
в старую базу после начала копии, в новой не появится.

**Why задача помечена `[VM]`.** Каждый её шаг — операция на dev-VM по skill `vm-deploy`. Кода она не
меняет.

### Шаг 3 — остановлены ВСЕ писатели переносимых таблиц

Писателей переносимых таблиц трое, и останавливаются все три.

| Писатель                                    | Что пишет              | Как останавливается                           |
| :------------------------------------------ | :--------------------- | :-------------------------------------------- |
| сетевой профиль движка                      | все одиннадцать таблиц | процесс останавливается                       |
| `onchain-verify`, узел `Write delivery`     | `onchain.diagnostics`  | воркфлоу деактивируется                       |
| `onchain-error-alert`, узел записи доставки | `onchain.diagnostics`  | воркфлоу деактивируется — ДОПУЩЕНИЕ, см. ниже |

Постусловие — две величины, обе снимаются до первой команды копии:

1. `SELECT count(*) FROM pg_stat_activity WHERE usename = '<роль состояния>'` в старом контейнере
   даёт ноль
2. ни один из двух воркфлоу не активен на инстансе n8n

**Why постусловие меряется, а не предполагается.** Остановленный процесс и закрытое соединение —
разные события. Пул мог оставить соединение, которое ещё пишет.

**Why нулевой `count` сам по себе окна не даёт.** Соединения узла n8n транзиентны: ноль в момент
замера не запрещает записи минутой позже. Постусловие «в старый контейнер не пишет никто» держится
только вместе со вторым замером.

**Why два воркфлоу названы поимённо.** Оба пишут `alert.delivered` в `onchain.diagnostics` от роли
состояния (`n8n-workflows/exported/onchain-verify.json:161` — `"name": "Onchain engine state"`,
`n8n-workflows/exported/onchain-error-alert.json:160` — то же). `onchain.diagnostics` входит в
одиннадцать переносимых таблиц.

**Why их деактивация разрешена.** Оба — наши `onchain-*` воркфлоу (CLAUDE.n8n.md). Чужие воркфлоу
инстанса не трогаются.

### Рычаг остановки третьего писателя — НЕИЗМЕРЕННОЕ ДОПУЩЕНИЕ

Для `onchain-verify` деактивация — измеренный рычаг: воркфлоу запускается Schedule-триггером, и
неактивный триггер не срабатывает.

Для `onchain-error-alert` то же не измерено. Он вызывается не своим триггером, а ПО ССЫЛКЕ
`settings.errorWorkflow` из исполнений других воркфлоу. Единственный измеренный проектом факт об этом
пути — про режим исполнения, а не про признак активности (`CLAUDE.n8n.md` §«Executing a workflow from
an agent»; `docs/onchain-analytics/PROD-RUNBOOK.md:180-182`).

| Поле                    | Значение                                                        |
| :---------------------- | :-------------------------------------------------------------- |
| Допущение               | снятый признак активности гасит и вызов по ссылке               |
| Почему не измерено      | dev-VM остановлена; измерение требует живого инстанса n8n       |
| Способ проверки         | одноразовый воркфлоу-зонд, состав ниже                          |
| Когда проверять         | первым шагом задачи, после `ssh vm` и до первой команды копии   |
| Последствие, если ложно | запись в СТАРЫЙ контейнер после снимка → `less_on_new` у 015-24 |
| Класс отказа            | безопасный: гейт блокирует этап, строку называет TC-NEG-05      |
| Что делать, если ложно  | повторить копию `onchain.diagnostics` через `TRUNCATE`          |

**Состав зонда** — по рецепту `CLAUDE.n8n.md` §«Executing a workflow from an agent»: одноразовый
воркфлоу с Schedule-триггером на дату, которая не наступит; `settings.errorWorkflow` указывает на
`onchain-error-alert`; один узел, падающий на `http://127.0.0.1:9/`. Зонд активируется, запускается в
режиме `production`, после чего проверяется, появилась ли новая строка `alert.delivered`. Зонд
удаляется тем же шагом.

**Последствие ложного допущения — полностью.** Отказ любого воркфлоу инстанса внутри окна запишет
`alert.delivered` в старый контейнер после снятия снимка. Verify-гейт задачи 015-24 увидит это как
`less_on_new` по `onchain.diagnostics`. Восстановление — повтор копии этой таблицы через `TRUNCATE`
плюс полный повтор в одной транзакции, тот же порядок, что уже объявлен для `access_audit`.

**Why допущение записано, а не заменено гарантией.** Гарантии на неизмеренном рычаге не бывает, а
запись «вопрос решён» на её месте — единственная форма, которая не даст исполнителю проверить.
Прецедент — измерение WI-64, где ручной прогон казался доказательством пути оповещения и им не был.

**Why этап на этом не останавливается.** Отказ наблюдаем и обратим: verify-гейт стоит между копией и
любым удалением, а повторная копия одной таблицы дешевле, чем ожидание доступной VM.

### Уступка на время окна: канал оповещений молчит

Пока `onchain-error-alert` деактивирован, отказ любого воркфлоу инстанса не доходит до Telegram.

| Величина                          | Значение                                                                                                         |
| :-------------------------------- | :--------------------------------------------------------------------------------------------------------------- |
| Что открывает окно                | деактивация двух воркфлоу, эта задача                                                                            |
| Что закрывает окно                | реактивация обоих, задача 015-33                                                                                 |
| Ожидаемая длительность            | 12–22 часа — сумма оценок задач 015-24, 015-22, 015-25 и 015-33 (`docs/PLAN.md` § Оценка этапа)                  |
| Объявленная граница               | 24 часа от записанного начала окна                                                                               |
| Что делать при достижении границы | реактивировать `onchain-error-alert` досрочно, не дожидаясь задачи 015-33, и записать факт досрочной реактивации |

**Why не «минутами».** Минутами измеряется копирование строк шага 4. Молчание канала длится от этой
задачи до 015-33, а между ними по перечню этапа 6 стоят verify-гейт, перевод credential и запуск
профиля. Названная минутами величина — это чужая величина, поставленная на место своей.

**Why граница названа числом.** `onchain-error-alert` — терминальный читатель всех сигналов здоровья
инстанса, и цена его молчания уже оплачена проектом: L-21 — девять недоставленных оповещений за пять
дней, замеченных случайно. Срок, который не назван, нельзя превысить наблюдаемо, а PR-8 плана
объявляет обнаружением именно превышение.

**Why досрочная реактивация возможна только после задачи 015-22.** `onchain-error-alert` не читает
`onchain.diagnostics` — он в неё только пишет
(`n8n-workflows/exported/onchain-error-alert.json` — узел `Write delivery`), поэтому разделения
запроса задачи 015-33 ему не требуется. Но до перевода credential задачей 015-22 его запись идёт в
СТАРЫЙ контейнер, то есть ровно в отказ, описанный допущением выше. Досрочная реактивация после
015-22 пишет в новый контейнер — в целевое состояние, а не мимо него.

Начало и конец окна записываются в лог инсталляции (015-28), а реактивация обоих воркфлоу
принадлежит задаче 015-33.

**Why снапшоттер при этом не останавливается.** Он пишет `assets`/`metrics`/`snapshots` в старом
контейнере и в переезде не участвует (R-8.3). Его credential «Supabase DB» не правится.

**Why `onchain-retention` в перечне нет.** Воркфлоу не установлен (`deployment.md:79`), и писателем
он сегодня не является.

### Шаг 4 — порядок переноса

Двенадцать таблиц из тринадцати несут шаг переноса; `provider_buckets` исключена (R-8.11). Строки
несут одиннадцать из двенадцати: `client_usage` создаётся пустой и источника для копирования не
имеет (`deployment.md` §10.9.2).

| #   | Таблица            | Строки    | Ссылается на                       | Столбец времени |
| :-- | :----------------- | :-------- | :--------------------------------- | :-------------- |
| 1   | `providers`        | да        | —                                  | нет             |
| 2   | `users`            | да        | —                                  | `created_at`    |
| 3   | `access_profiles`  | да        | —                                  | `created_at`    |
| 4   | `api_tokens`       | да        | `users:125`, `access_profiles:126` | `created_at`    |
| 5   | `access_audit`     | да        | `users:147`                        | `ts`            |
| 6   | `cache_entries`    | да        | `providers:54`                     | `created_at`    |
| 7   | `usage`            | да        | `providers:64`                     | `updated_at`    |
| 8   | `usage_window`     | да        | `providers:73`                     | `updated_at`    |
| 9   | `request_trace`    | да        | `providers:192`                    | `received_at`   |
| 10  | `diagnostics`      | да        | —                                  | `ts`            |
| 11  | `retention_runs`   | да        | —                                  | `started_at`    |
| 12  | `client_usage`     | нет       | —                                  | `reserved_at`   |
| —   | `provider_buckets` | исключена | `providers:165`                    | `updated_at`    |

Номера строк — `sql/migrations/002_t014_network_profile.sql`.

**Why порядок такой.** Внешний ключ отвергает строку, чья цель ещё не перенесена. `users` и
`access_profiles` идут до `api_tokens`; `providers` — до `cache_entries`, `usage`, `usage_window` и
`request_trace`.

**Why у `providers` нет столбца времени.** Таблица объявлена тремя колонками
(`sql/migrations/002_t014_network_profile.sql:46`). Вторая проверка verify-гейта на ней неприменима,
и это её вход, а не находка.

**Why `provider_buckets` исключена.** Состояние лимитера эфемерно и доливается заново. Цена названа:
`tokens` может быть отрицательным, и потеря строки прощает накопленный долг (`deployment.md` §10.9.5).

**Why `client_usage` всё равно стоит в перечне.** У неё есть шаг переноса — и он пуст. Таблица без
шага выпала бы из счёта тринадцати.

### Механика — конвейер через stdin

```
ssh vm 'docker exec -i supabase-db pg_dump -U postgres -d postgres \
  --schema=onchain --table=onchain.<name> --data-only --format=plain' \
  | ssh vm 'docker exec -i <новый контейнер> psql -qU postgres -d postgres -v ON_ERROR_STOP=1'
```

**Why конвейер, а не файл внутри контейнера.** `-f /tmp/…` читает файловую систему контейнера и
исполняет устаревшую копию (skill `vm-deploy` §4).

**Why по одной таблице, а не одним дампом схемы.** Порядок задают внешние ключи, а `--schema=onchain`
захватил бы три таблицы снапшоттера, которые остаются на месте (R-8.3).

**Why `ON_ERROR_STOP=1`.** Без него отказ на одной таблице оставляет частичную копию и продолжает
следующие.

### `api_tokens` переносится вместе с остальными

**Why прежняя посылка отменена, а не поправлена молча.** Решение владельца 2026-08-25 (R-8.11)
отменило посылку документа о том, что перенести токены нельзя.

**Why перенос возможен.** `token_hash` — обычная колонка `TEXT`, копируется и спот-чекается
байт-в-байт, как любая точная колонка.

**Why перец не переносится.** `ONCHAIN_TOKEN_HASH_SALT` — не колонка, а секрет в `.env` сервера
(`sql/migrations/003_seed_engine_admin.sql:24-26`, «WHY THE PEPPER IS NOT A PARAMETER»). Переезд
контейнера его не трогает.

**Why это проверяемо.** Запрос уже выпущенным токеном после переключения писателя аутентифицируется
без переиздания (AC-44, задача 015-25).

### `access_audit` — копия одноразовая

**Why не `ON CONFLICT DO NOTHING`.** Таблица не несёт естественного ключа дедупликации по замыслу
(`sql/migrations/003_seed_engine_admin.sql:157-158`, «`access_audit` has no natural UNIQUE key by
design»). Ключу негде взяться, и повтор копии удваивает каждую строку.

Ветвь повтора — `TRUNCATE` и полная копия в одной транзакции:

```sql
BEGIN;
TRUNCATE onchain.access_audit;
-- повторить копию данных этой одной таблицы
COMMIT;
```

**Why ветвь требует явного подтверждения владельца.** `TRUNCATE` входит в перечень операций, которые
skill `vm-deploy` §5 запрещает без него.

**Ветвь повтора обязательна с самого начала, а не по условию (записано 2026-08-28).** На новом
контейнере в `onchain.access_audit` уже лежат ДВЕ строки — `user.create` и `token.issue` с
идентификаторами `01TESTPROBE…`. Их посеяла миграция `003_seed_engine_admin.sql`, запущенная при
ремонте записи `L-28` для проверки шестой охраны: подготовительная вставка не-админа не прошла
(не заполнила `status`), охрана поэтому не сработала, и файл отработал до конца. Строки `users` и
`api_tokens` того прогона удалены; строки `access_audit` удалить нельзя — таблицу защищает правило
`access_audit_no_delete` формы `DO INSTEAD NOTHING` плюс триггер `access_audit_no_update`, то есть
append-only канон работает как задумано.

Следствие для этой задачи: без `TRUNCATE` копия даст на новом контейнере на две строки больше
источника, и verify-гейт 015-24 назовёт это `more_on_new` — материализованной угрозой дублирования.
`TRUNCATE` входит в перечень операций, требующих явного подтверждения владельца (skill `vm-deploy`
§5), и подтверждение теперь нужно не по ветке отказа, а на первом же прогоне.

**Why ветвь применяется только на новом контейнере.** В старом контейнере строки — источник, и до
задачи 015-27 они остаются нетронутыми.

**Why исходные идентификаторы не регенерируются.** Идентичность строки несёт только её ULID.
Новый идентификатор разорвал бы ссылку `access_audit.target_id` на строку токена.

### MINOR-9 раунда 2 — отклонение от буквы R-8.14 записывается

| Редакция                              | Что говорит                                                       |
| :------------------------------------ | :---------------------------------------------------------------- |
| Текст R-8.14                          | verify-гейт стоит сразу после запуска профиля на новом контейнере |
| UC-6 шаг 5                            | verify снимается, пока профиль ещё остановлен                     |
| Архитектура (`deployment.md` §10.9.4) | следует UC-6                                                      |

**Why архитектура следует UC-6.** Первая и вторая проверки сравнивают две базы. Писатель, работающий
во время сверки, делает числа несравнимыми: расхождение читалось бы как недокопированное.

**Why отклонение записывается, а не исполняется молча.** Две редакции одного требования, из которых
исполняется одна, — это решение, а не деталь. Форма записи уже применена к R-8.10 в записи `WI-62`.

**Why ссылка ставится из §10.9.7.** Раздел удаления — единственное место, где порядок шагов
становится необратимым, и его читатель обязан видеть, какой редакции следовал verify.

### Что задача не делает

- не удаляет ни одной строки и ни одной таблицы в старом контейнере (задача 015-27)
- не снимает verify-гейт (задача 015-24)
- не переключает `ONCHAIN_STATE_PG_URL` и не запускает профиль (задача 015-25)
- не снимает артефакт отката (задача 015-26)
- не переносит `provider_buckets`
