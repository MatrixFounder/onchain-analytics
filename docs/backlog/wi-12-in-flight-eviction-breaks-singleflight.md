# Вытеснение незавершённых записей ломает singleflight на широких прогонах

> **✅ ВЫПОЛНЕНО 2026-07-28.** Запись кэша документов получила флаг `settled`, который ставится в
> `body.then(...)`/`catch(...)`. Обе фазы вытеснения — и sweep по TTL, и кап по размеру — теперь
> пропускают незавершённые записи.
>
> **Названная граница:** карта может превысить `MAX_DEX_DOCUMENTS` ровно на число **одновременных**
> загрузок, потому что кап уступает, а не выбрасывает идущую загрузку. Это ограничено конкурентностью
> вызывающего и token-bucket'ом провайдера, и каждая такая запись становится вытесняемой в момент
> завершения. Лучше временно превысить слот-кап, чем выбросить уже оплаченные байты.
>
> **Отказ по-прежнему не запоминается:** rejection одновременно помечает запись завершённой и удаляет
> её (с проверкой идентичности, чтобы поздний отказ не убил более новую запись под тем же ключом).
>
> **Тесты:** 2 новых в `defillama-dex-volume.test.ts` — шесть конкурентных загрузок против капа в 3
> слота не теряют ни одной (седьмой загрузки не происходит), и отдельно: когда всё завершено, кап
> по-прежнему вытесняет. Проверено, что **без правки первый краснеет**.

**Источник:** adversarial-цикл 3 TASK-007, `critic-performance` H-3.

`packages/core/src/adapters/defillama/index.ts` вытесняет записи **на вставке**, до того как исход
известен. Прогон шире `MAX_DEX_DOCUMENTS` (32) поэтому выбрасывает записи, чья загрузка ещё идёт.

Докстринг кэша обещает две вещи одновременно — «конкурентные вызывающие делят один запрос» и «карта
ограничена `MAX_DEX_DOCUMENTS`» — и при прогоне шире 32 сетей истинной может быть только одна.
Сейчас код выбирает не ту.

Масштаб не гипотетический: `onchain_list_chains` по умолчанию отдаёт **50** строк, то есть именно в
такой обход модель и уводят описания тулов. Прогон по 50 сетям теряет 18 документов, которые всё
равно были скачаны: **~4.5 МБ лишнего трафика** и 18 токенов лимитера (~3.6 с бюджета), как только
агент попросит второе окно по любой из них. При 100 сетях — 68 дублей, ~17 МБ.

Предыдущий цикл ревью посмотрел на это место и признал корректным («вытеснение записи с
незавершённым промисом безопасно») — и был прав **по корректности**. Это перформанс-дефект,
а не корректностный, поэтому он и уцелел.

## Как чинить

Помечать завершённость и никогда не вытеснять незавершённую запись:

```ts
const entry = { at: now(), body, settled: false };
body.then(
  () => {
    entry.settled = true;
  },
  () => {
    entry.settled = true;
  },
);
// вытеснение: искать первую settled, а не просто первую
```

После сокращения размера записи (WI-13) имеет смысл поднять и сам кап — 32 слота против 274
покрытых сетей дают 12% попаданий на полном обходе.

## Приёмка

- прогон шире капа не приводит к повторной загрузке уже полученного документа;
- тест на конкурентный прогон: N > cap сетей, затем второе окно по первой — без второго `fetch`.
