# Задача 015.18: воркфлоу `onchain-billing-reconcile` — один оператор, батч, период в строке прогона

## Связь со сценариями

- Сценария нет. R-14 закрывает путь, где процесс умер между резервом и исходом; ни один из UC-1…UC-8
  такого прогона не описывает. Критерий — AC-39.

<!-- contract:goal -->

## Цель задачи

Описать воркфлоу, который переводит зависшую строку `reserved` в `refunded` и возвращает кредиты
одним оператором SQL, и записать его прогон строкой `retention_runs`.

**Why отдельный воркфлоу, а не четвёртая работа в `onchain-retention`.** Один Schedule-триггер несёт
одну каденцию. Ретенция идёт раз в сутки, а порог зависания — 120 000 мс (`deployment.md` §10.8).

**Why задача не создаёт воркфлоу на инстансе.** Инстанс общий, установка требует явного согласия
владельца (`deployment.md:760`, «Installation requires the owner's explicit approval»).

Правка вносится на языке корпуса архитектуры — английском (ARCHITECTURE §7.3).

### Состав узлов

| Узел                                 | Тип             | Что делает                                              |
| :----------------------------------- | :-------------- | :------------------------------------------------------ |
| `Overview`                           | stickyNote      | обязательная карточка воркфлоу (CLAUDE.n8n.md)          |
| `Every 15 minutes`                   | scheduleTrigger | `minutesInterval: 15`                                   |
| `Set Parameters`                     | set             | `ThresholdMs`, `BatchSize`, `MaxBatches`                |
| `Plan run`                           | code            | ULID, `startedAt`, горизонт, период, проверка диапазона |
| `Refund expired`                     | postgres        | один оператор перехода и возврата, батч                 |
| `Tally`                              | code            | накопление числа закрытых строк и счётчика батчей       |
| `More to close?`                     | if              | ребро назад в `Refund expired`, пока выборка полна      |
| `Row client_usage.reconcile_expired` | code            | строка `retention_runs` в base64                        |
| `Write run`                          | postgres        | вставка строки прогона                                  |
| `Check backlog`                      | code            | читатель признака исчерпания батчей; бросает            |

**Why `Set Parameters` держит три числа.** Один узел владеет контрактом настройки. Смена каденции
или батча не правит узел запроса (CLAUDE.n8n.md, паттерн param-узла).

**Why `Check backlog` сцеплен ребром, а не поставлен рядом.** При `executionOrder: v1` порядок
параллельных ветвей задаёт геометрия. Гейт, наблюдающий завершённые побочные эффекты, требует ребра.

**Why у узлов выше стоит `alwaysOutputData: true`.** Пустой результат иначе пропускает гейт молча.

### Один оператор перехода и возврата

Форму объявляет задача 015-10 (`docs/architectures/data-model-billing-ledger.md` §4.6.5). Здесь она получает
границу батча и предикат по режиму профиля:

```sql
WITH p AS (SELECT convert_from(decode($1,'base64'),'utf8')::jsonb AS j),
     pick AS (
       SELECT id FROM onchain.client_usage
        WHERE state = 'reserved'
          AND reserved_at < (SELECT (j->>'horizon')::bigint FROM p)
        ORDER BY reserved_at
        LIMIT (SELECT (j->>'batchSize')::int FROM p)
        FOR UPDATE SKIP LOCKED
     ),
     closed AS (
       UPDATE onchain.client_usage c
          SET state = 'refunded', refund_reason = 'expired',
              terminal_at = (SELECT (j->>'nowMs')::bigint FROM p),
              updated_at  = (SELECT (j->>'nowMs')::bigint FROM p)
         FROM pick
        WHERE c.id = pick.id AND c.state = 'reserved'
       RETURNING c.access_profile_id, c.price_raw
     ),
     credited AS (
       UPDATE onchain.access_profiles pr
          SET credits_balance_raw = (pr.credits_balance_raw::numeric + s.sum_raw)::text
         FROM (SELECT access_profile_id, SUM(price_raw::numeric) AS sum_raw
                 FROM closed WHERE access_profile_id IS NOT NULL GROUP BY 1) s
        WHERE pr.id = s.access_profile_id
          AND pr.credits_balance_raw IS NOT NULL
       RETURNING 1
     )
SELECT (SELECT count(*) FROM closed)::bigint    AS rows_affected,
       (SELECT count(*) FROM credited)::bigint  AS profiles_credited;
```

**Why один оператор, а не два узла.** n8n не даёт транзакции между узлами. Пара «узел перехода,
затем узел возврата» оставляет окно, где строка закрыта, а кредиты не возвращены (MAJOR-A раунда 2).

**Why предикат `credits_balance_raw IS NOT NULL`.** Под `credits_mode='unlimited'` колонка пуста, и
ограничение `CHECK ((credits_mode = 'metered') = (credits_balance_raw IS NOT NULL))`
(`sql/migrations/002_t014_network_profile.sql:118`) требует, чтобы она такой осталась. Без предиката
оператор пишет `NULL` поверх `NULL` на каждом прогоне фазы 0.

**Why `AND c.state = 'reserved'` во втором операторе.** Строку, закрытую путём завершения в тот же
момент, `UPDATE` не находит: он совпадает с нулём строк, никогда с двумя
(`docs/architectures/data-model-billing-ledger.md` §4.6.5).

**Why `FOR UPDATE SKIP LOCKED`.** Прогон, не уложившийся в каденцию, пересекается со следующим. Две
пересекающиеся выборки берут разные строки.

**Why `numeric`, а не число JS.** Кредиты — точные целые; `Number` теряет разряды после 2^53
(CLAUDE.md, «BigInt, never Number»). Арифметика идёт в базе и не проходит через узел Code.

**Why параметр один и в base64.** `queryReplacement` — позиционный CSV: запятая в значении ломает
привязку, пустое значение сдвигает каждый следующий `$N`. Base64 не несёт ни запятой, ни `$`, и
привязывается драйвером, а не подставляется в текст (CLAUDE.n8n.md).

### Размер батча и поведение при переполнении — MINOR-10 раунда 2

| Параметр      | Значение | Происхождение           |
| :------------ | :------- | :---------------------- |
| `ThresholdMs` | 120 000  | R-14.2, порог зависания |
| `BatchSize`   | 500      | applied, не измерено    |
| `MaxBatches`  | 20       | applied, не измерено    |

Прогон дренажит выборку до пустой: `More to close?` возвращает поток в `Refund expired`, пока
`rows_affected` равно `BatchSize` и число батчей меньше `MaxBatches`.

**Why дренаж, а не один батч за прогон.** При остатке больше батча каждый следующий кусок ждал бы
следующей каденции, и объявленная граница видимости перестала бы быть границей.

**Why у дренажа есть потолок.** Цикл без границы держит соединение общего пула неограниченно долго.

**Why потолок наблюдаем, а не молчалив.** По достижении `MaxBatches` строка прогона несёт
`batchExhausted: true` в `detail_json`, а `Check backlog` бросает — сообщение уходит в Telegram через
`errorWorkflow`. Диагностика без читателя диагностикой не является (L-2).

**Why признак не переводит прогон в `outcome='failed'`.** Прогон закрыл строки, которые нашёл.
Словарь `outcome` закрыт двумя значениями (`data-model.md` §4.5.9).

### Период строки прогона — MINOR-8 раунда 1

`period_from = 0`, `period_to = startedAt − ThresholdMs`.

**Why период вычисляется из порога.** Верхняя граница — тот самый горизонт, который стоит в `WHERE`
оператора. Число, вписанное руками, разошлось бы с тем, что прогон реально закрыл.

**Why нижняя граница — ноль.** Работа закрывает всё старше горизонта, поэтому период открыт с эпохи.
Тот же выбор уже применён тремя работами ретенции (`Plan jobs`, `periodFrom: 0`).

**Why `period_to` не равен `startedAt`.** Строки моложе горизонта прогон не трогает, и период,
включающий их, назвал бы не тот отрезок.

### Строка `retention_runs`

| Колонка         | Значение                                                                |
| :-------------- | :---------------------------------------------------------------------- |
| `id`            | ULID, минтуется в `Plan run`                                            |
| `job`           | `client_usage.reconcile_expired`                                        |
| `target_table`  | `client_usage`                                                          |
| `period_from`   | `0`                                                                     |
| `period_to`     | `startedAt − ThresholdMs`                                               |
| `rows_affected` | сумма закрытых строк по всем батчам прогона                             |
| `started_at`    | `startedAt`                                                             |
| `finished_at`   | `Date.now()` в узле строки                                              |
| `outcome`       | `ok`, либо `failed` при отвергнутой настройке                           |
| `detail_json`   | порог, батч, число батчей, `batchExhausted`, `profilesCredited`, период |

Прогон без единой найденной строки пишет строку с `rows_affected = 0` и `outcome = 'ok'` (R-14.3).

**Why `target_table` записан без имени схемы.** `data-model-billing-ledger.md:448` называет значение
`'client_usage'`. Три работы `onchain-retention` пишут туда имя со схемой. Расхождение записано, а не
приведено к одному виду молча: правка чужих строк — отдельное решение.

**Why вставка идёт `ON CONFLICT (job, period_from, period_to, started_at) DO NOTHING`.** Тот же
естественный ключ уже объявлен таблицей (`sql/migrations/002_t014_network_profile.sql:238`).

**Why нового события `diagnostics` работа не пишет.** Словарь событий закрыт и компилируется
(`data-model.md` §4.5.8). Добавление значения — правка кода, и §4.6.5 её не требует.

### Отвергнутая настройка

`ThresholdMs` ниже 120 000 отвергается: оператор не исполняется, строка пишется с
`outcome = 'failed'`, `detail_json` называет отвергнутое значение, `Check backlog` бросает.

**Why порог имеет пол, а не потолок доверия.** Порог ниже 120 000 мс возвращает резерв запроса,
который ещё выполняется: платный вызов, принятый вендором, дорезается за собственным дедлайном
(R-14.2). Это возврат денег за работу, которая ещё идёт.

**Why отказ, а не подгонка к полу.** Подогнанное значение вернуло бы резервы за период, которого
оператор не выбирал, и строка прогона назвала бы подогнанный период запрошенным (прецедент L-3).

### Каденция и граница видимости

Каденция — 15 минут, `applied`, не измерена.

Граница: зависшая строка видна не дольше `ThresholdMs` плюс каденция — 120 000 + 900 000 =
1 020 000 мс.

**Why число в §10.8 правилось.** До правки этой задачи раздел называл границу «≤135 000 ms».
135 000 = 120 000 + 15 000, то есть арифметика была взята при каденции 15 секунд, а графа `Trigger`
(`deployment.md:737`) объявляет 15 минут. Одно из двух чисел было неверно, и правилось то, которое
сам раздел отвергает: секундная каденция противоречит его же доводу «without polling per second
against a shared connection pool». Ссылка на прежний текст здесь не ставится — его больше нет
(`deployment.md:743-745` несёт исправленную арифметику).

**Why каденция названа `applied`.** Трафика, по которому её можно было бы подобрать, ещё нет. Та же
форма уже применена к окну 90 дней (`data-model.md` §4.5.8).

### Credential

Узлы Postgres используют credential роли состояния — по имени, не по идентификатору. Сегодня это
`Onchain engine state`, тот же, что читают три работы `onchain-retention`.

**Why не «Supabase DB».** У роли снапшоттера нет привилегий на таблицах движка (`deployment.md`
§10.5). Отказ Postgres на чтение `onchain.snapshots` этим credential — проверка, а не соглашение.

**Why credential указан по имени.** Идентификаторы дрейфуют между инстансами; `import.sh` связывает
их по имени (CLAUDE.n8n.md, раздел Export / re-import).

**Why credential после переезда указывает на новый контейнер.** Леджер живёт только там (MAJOR-F
раунда 2, задача 015-03). Перецеливание принадлежит задаче 015-22.

### Установка

Задача описывает воркфлоу и экспортирует его файл. Создание на инстансе и активация не выполняются.

**Why согласие владельца обязательно.** Инстанс несёт больше двадцати чужих активных воркфлоу, и
проект создаёт на нём только свои `onchain-*` (CLAUDE.n8n.md).

**Why установка идёт через `./n8n-workflows/import.sh`.** Импорт через UI минтит новый идентификатор
и переприкрепляет чужие идентификаторы credential и `errorWorkflow`.

## Критерии приёмки

- [ ] AC-39 — прогон job пишет строку `retention_runs`, называя число возвращённых резервов и
      период; прогон без находок тоже пишет строку

- [ ] Каденция объявлена как применённое значение с названной границей видимости зависшей строки

## Примечания

Задача 015-10 владеет транзакционной границей резерва и правит `data-model.md` §4.6.5. Здесь
оператор получает границу батча и предикат по режиму профиля; форму кредитования задаёт 015-10.

AC-39 закрывается двумя задачами: состояние строки — 015-10, прогон и строка лога — здесь.

Зависимость от 015-21 стоит потому, что воркфлоу пишет в базу нового контейнера. До переезда леджера
там нет (MAJOR-F раунда 2).

`retention_runs` не чистится никогда: работа, которая чистила бы её, писала бы в неё
(`data-model.md` §4.5.9).

Экспорт файла воркфлоу после установки перезаписывается прогоном `./n8n-workflows/export.sh` — он
читает живой инстанс. Ручная правка экспортированного файла после установки не переживает следующий
экспорт.
