# Задача 014.16: видимость `_meta` по роли и `route_disclosure_mode` `[LOGIC]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Сделать видимость полей `_meta` функцией роли принципала и ввести настройку профиля доступа
`route_disclosure_mode`, управляющую раскрытием состава маршрута в успешном ответе.

**Why.** Роль `user` — платящая третья сторона, а `_meta.budget` сообщает наш расход у поставщика
(`ADR-003` D2). Правило должно действовать и на поля, добавленные позже (R-6.4).

<!-- contract:changes -->

## Описание изменений

### Изменения в существующих файлах

**Файл `packages/mcp-server/src/tools/registry.ts`:**
- Ввести одну функцию `metaFor(principal, parts)`, собирающую каждый объект `_meta`
- Применить проекцию по роли в `toCallToolResult` (строка 201,
  `function toCallToolResult<TOutput extends Record<string, unknown>>(`), над объектом `const meta = {`
  (строка 207)
- Прочитать поле `routeDisclosureMode` профиля доступа и убрать три перечисленных ниже поля при
  значении `'none'`; чтение выполняется в том же `toCallToolResult`

**Файл `packages/mcp-server/src/tools/budget-meta.ts`:**
- `budgetMeta()` продолжает считать часть `budget` и не решает, кому она видна

**Why проекция стоит в `toCallToolResult`, а не в `budgetMeta()`.** `security.md` §7.5.3: одна
функция рендерит результат каждого тула, поэтому новый тул наследует правило, а не повторяет его.
`system-architecture.md` §3.4.3 называет собирающую функцию — `metaFor(principal, parts)`. Она
собирает каждый объект `_meta`, поэтому R-6.4 держится построением, а не ревью.

### Класс видимости на каждом поле

Каждое поле `_meta` несёт один класс видимости: `client` или `operator`. Поле класса `client` уходит
любому принципалу; поле класса `operator` — только принципалу с ролью `admin` (`interfaces.md`
§5.4.4). Класс объявляется один раз, в компилируемой таблице рядом с объявлениями типов `_meta`
(§5.4.4 пункт 1, §5.1.2).

Классификация на сегодня, по `interfaces.md` §5.4.4:

| Поле `_meta` | Класс | Требование |
| :--- | :--- | :--- |
| `cache.status`, `cache.ageMs`, `cache.capability` | client | R-6.3 |
| `cache.provider` | client, сужается профилем | R-6.3; §5.4.4.1 |
| `cache.perSource[]` | client, сужается профилем | R-6.3; §5.4.4.1 |
| `timing.overrunMs` | client | R-16.4 |
| `budget.provider`, `budget.creditsUsedToday` | operator | R-6.1 |
| `tier` | не объявлен ни на одном транспорте | R-6.2, AC-7 |

### Поле, отсутствующее в таблице, трактуется как `operator`

`interfaces.md` §5.4.4 пункт 3: «A field absent from the table is treated as `operator`. A field
added later is therefore withheld from clients until someone classifies it» (R-6.4). `security.md`
§7.5.3 говорит то же о своей таблице: ключ, которого в ней нет, невидим для роли `user`, пока его
туда не внесут.

**Why умолчание, а не остановка сборки.** Довод `interfaces.md` §5.4.4: две стороны ошибки
несимметричны. Удержанное поле — недостающее удобство; выданное поле — операторский факт в контексте
клиента, а R-20 запрещает это постоянно.

### Три поля под управлением `route_disclosure_mode`

- `_meta.cache.provider`
- `_meta.cache.perSource[]`
- `structuredContent.missingSources`

При `'none'` их нет, при `'full'` есть. Настройка живёт на профиле доступа, который называет токен:
колонка `access_profiles.route_disclosure_mode TEXT NOT NULL DEFAULT 'full'` с ограничением
`CHECK (route_disclosure_mode IN ('full','none'))` (`data-model.md` §4.5.3, R-20.3). Затравочная
строка фазы 0 — `name = 'phase0-unlimited'`, `route_disclosure_mode = 'full'`.

**Why настройка, а не правило провода.** Оператору, разбирающему слияние, нужно видеть, какой
источник ответил. Платящей третьей стороне нельзя читать список наших поставщиков из успешного
ответа. Одно фиксированное правило обслуживает одного из них плохо.

Настройка только убирает поля и никогда не добавляет, поэтому по R-29.4 переносима в Postgres.

### Откуда берётся значение настройки

Поле `routeDisclosureMode` типа `AccessProfile` объявлено задачей 014-04 вместе с читателем
`AccessProfileReader` и поставщиком умолчаний. Эта задача — его потребитель: она читает значение
через читатель и не обращается к колонке напрямую (R-13.2, R-13.3a).

Значение читается на пути запроса, в обёртке `defineTool` задачи 014-15
(`packages/mcp-server/src/tools/registry.ts:289`), и передаётся в `toCallToolResult` рядом с
принципалом. Отказ чтения fail-closed по задаче 014-04: запрос отвергается, умолчание не
подставляется.

**Why чтение названо изменением этой задачи.** Гейт R-13.3a задачи 014-04 называет читателей поля
поимённо, и `toCallToolResult` — одно из двух названных мест. Читатель, не названный ни там, ни
здесь, валит гейт.

**Why значение применяется в `toCallToolResult`, а не в `metaFor`.** Настройка убирает и поле
`structuredContent.missingSources`, которого ни одна классификация `_meta` не несёт (`interfaces.md`
§5.4.4). Сигнатура `metaFor(principal, parts)` при этом остаётся объявленной
(`system-architecture.md` §3.4.3).

**Why чтение на пути запроса, а не на создании сессии.** Профиль называет токен, а токен резолвится
на каждый запрос (§3.4.3). Значение, удержанное на время сессии, отстало бы от смены профиля до
закрытия сессии по бездействию.

### Что настройка не трогает

`tier` не выводится ни на каком транспорте и ни при какой роли. `_meta.budget` управляется ролью, а
не настройкой: таблица классов остаётся его единственным правилом.

### Текст отказа

Имена переменных окружения и остаток кредитов оператора клиенту не выводятся. Действующие строки
уходят клиенту дословно и подлежат замене: `budget exceeded for provider=nansen: need 5, used 41,
ceiling 100`; `capability unavailable: entity.labels on ethereum — tried: blockscout (…), nansen (…)`.

## Тест-кейсы

### Сквозные тесты
1. **TC-E2E-01:** `_meta.budget` отсутствует у роли `user` и присутствует у роли `admin` (AC-6)
   - Входные данные: один и тот же вызов от двух принципалов
   - Ожидаемый результат: ключ `budget` есть только в ответе роли `admin`
2. **TC-E2E-02:** `route_disclosure_mode` управляет тремя полями успешного ответа
   - Входные данные: два поставщика `AccessProfileReader` задачи 014-04 — один отдаёт
     `routeDisclosureMode: 'none'`, второй `'full'`; один и тот же вызов на каждом
   - Ожидаемый результат: при `'none'` трёх полей нет, при `'full'` есть (AC-49)

### Модульные тесты
1. **TC-UNIT-01:** `tier` не встречается ни в одном ответе ни на одном транспорте
   - Входные данные: обход реестра тулов, счёт не зашит
   - Ожидаемый результат: ни одна форма ответа не объявляет поле `tier` (AC-7)
2. **TC-UNIT-02:** отказ клиенту не содержит имён переменных окружения и остатка кредитов (AC-14)
   - Входные данные: тексты отказов из перечня `security.md` §7.5
   - Ожидаемый результат: ни одна строка не содержит имени ключа `EnvSchema` и числа кредитов
3. **TC-UNIT-03:** поле `_meta`, отсутствующее в таблице классов, трактуется как `operator`
   - Входные данные: тестовое поле `_meta.probe`, не внесённое в таблицу
   - Ожидаемый результат: у роли `user` поля нет, у роли `admin` поле есть
4. **TC-UNIT-04:** `_meta.cache.status` и `_meta.cache.ageMs` видны обеим ролям
5. **TC-UNIT-05:** новый тул наследует правило без собственного кода
   - Входные данные: тул фикстуры, возвращающий часть `budget`
   - Ожидаемый результат: у роли `user` `_meta.budget` отсутствует
6. **TC-UNIT-06:** при `'none'` роль `admin` тоже не получает три поля
   - Входные данные: принципал с ролью `admin` и профиль со значением `'none'`
   - Ожидаемый результат: трёх полей нет; `_meta.budget` на месте — настройка и роль независимы
7. **TC-UNIT-07:** отказ чтения профиля отказывает в запросе
   - Входные данные: поставщик, чей `read` отвергает промис на пути запроса
   - Ожидаемый результат: запрос отвергнут; значение `'full'` не подставлено (задача 014-04)

### Регрессионные тесты
- Локальный профиль сохраняет прежний объём `_meta`: роль `admin`, умолчание `'full'`

## Примечания

Идентификатор события в клиентском рендеринге отказа вводится задачей 014-26. Эта задача убирает
операторские детали; та возвращает способ их найти.

Владельца поля `routeDisclosureMode` держит задача 014-04: тип, читатель, поставщик умолчаний.
`security.md` §7.5.3a объявляет интерфейс `AccessProfile` шестью полями и седьмого не называет;
правка секции — за оркестратором.

Прежняя редакция задачи требовала «поле без класса не собирается» и помещала проекцию в
`budget-meta.ts`. Оба пункта заменены объявлениями архитектуры: проекция — `toCallToolResult`
(`security.md` §7.5.3), умолчание для неклассифицированного поля — `operator` (`interfaces.md`
§5.4.4 пункт 3). Форма «не собирается» остаётся верной для гейта классификации настроек в задаче
014-05: `deployment.md` §10.2.1 пункт 2 требует, чтобы ключ вне таблицы ронял шаг.
