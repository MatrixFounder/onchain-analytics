# Задача 014.03: механизм доступа репозиториев и гейт явной квалификации схемы `[LOGIC]`

## Связь со сценариями
- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Дать пяти репозиториям задачи 014-02 общий механизм доступа к Postgres через клиент записи задачи
014-39 и ввести гейт, требующий явной квалификации схемы в каждом SQL-запросе и каждой миграции
обоих пакетов.

**Why.** Сервер переезжает с VM на VPS с общей базой. WI-47 измерила, что Supavisor подставляет свой
`search_path`: база была доступна, 3039 строк на месте, и `pg-history` не прочитал ни одной строки.
Настройка соединения не переживает пулер; явная квалификация переживает.

**Why методы репозиториев в задачу не входят.** Таблица задачи 014-02 закрепляет замену каждого стаба
за одной задачей: 014-07, 014-27, 014-30 и табличный поставщик после T-014. Реализация тех же методов
здесь дала бы каждому файлу второго владельца.

## Описание изменений

### Новые файлы

- `packages/mcp-server/src/engine/pg-engine-store.ts` — общий механизм доступа пяти репозиториев
  задачи 014-02: квалифицированный схемой SQL через клиент записи задачи 014-39
- `packages/mcp-server/test/schema-qualification.gate.test.ts` — гейт на явную квалификацию

**Why механизм доступа лежит в пакете `mcp-server`.** `security.md` §7.5.1: «The SQL that names the
identity tables therefore lives in `mcp-server` too». `deployment.md` §10.2.1 относит к тому же
пакету SQL по `onchain.request_trace` и `onchain.diagnostics`. Задача 014-02 объявила там все пять
интерфейсов.

**Why гейт лежит рядом с гейтом-прецедентом.** `security.md` §7.5.3a называет статическую проверку
над двумя каталогами и её файл: `packages/mcp-server/test/settings-access.gate.test.ts`. Второй гейт
с тем же входом читается вместе с первым.

### Изменения в существующих файлах

**Файл `packages/core/src/pg/read-client.ts`:**
- Пересмотреть запросы на явную квалификацию `onchain.`
- Не полагаться на `search_path` как на условие корректности: строка 383,
  `options: '-c search_path=onchain'`

### Кто заменяет стабы задачи 014-02

Замена стабов в эту задачу не входит. Владельцы объявлены таблицей задачи 014-02, и каждый из них
заменяет свой стаб реализацией поверх механизма доступа этой задачи.

| Файл | Кто заменяет стаб |
| :--- | :--- |
| `packages/mcp-server/src/auth/user-store.ts` | 014-07 |
| `packages/mcp-server/src/auth/token-store.ts` | 014-07 |
| `packages/mcp-server/src/engine/request-trace-store.ts` | 014-30 |
| `packages/mcp-server/src/engine/diagnostics-store.ts` | 014-27 |
| `packages/mcp-server/src/auth/access-profile-store.ts` | табличный поставщик после T-014 |

**Why методы токена названы за одной задачей.** `issue`, `lookup`, `revoke` и `appendAudit` — предмет
задачи 014-07 целиком. Вторая реализация тех же четырёх методов здесь разошлась бы с первой на первом
изменении формы токена.

**Why профиль доступа не реализуется здесь.** T-014 поставляет значения профиля из умолчаний в коде
(R-13.3). Реализация табличного поставщика в этой задаче открыла бы отложенный путь на этапе 1.

### Вход гейта — два пакета, а не один

Вход объявлен в `deployment.md` §10.2.1 пункт 1: `sql/migrations/*.sql` плюс строковые литералы SQL
под `packages/core/src` и под `packages/mcp-server/src`. Постусловие того же пункта: каждая ссылка
на таблицу несёт схему, каждый создаваемый объект — `onchain.<name>`, в `public` не создаётся ничего.

**Why вход называет оба пакета.** `security.md` §7.5.1: проверки токена живут в пакете `mcp-server`,
рядом с транспортом, который их требует, и SQL по `onchain.api_tokens`, `onchain.users`,
`onchain.request_trace`, `onchain.diagnostics` написан вне `packages/core/src`. Довод той же секции
дословно: «Every identity statement is a SQL literal in `mcp-server` ⇒ a gate whose input is
`packages/core/src` alone observes none of them».

**Why прецедент назван.** `deployment.md` §10.2.1: «The precedent is the gate of `security.md`
§7.5.3a. Its static check already takes both directories as input».

### Офлайн-гейт — единственный оставшийся детектор

`deployment.md` §10.5.3: «The offline gate of §10.2.1 is therefore the only detector left» (R-30.3,
AC-46). Вход того же абзаца: «every migration file plus every SQL literal under `packages/core/src`
and `packages/mcp-server/src`». Под двумя схемами неквалифицированное имя попадало в чужое
пространство имён и встречало роль без привилегий там. Под одной схемой роль состояния уже держит
привилегии внутри `onchain`, и второй детектор исчез.

Оставшийся исполняемый тест AC-46 — `TC-E2E-01` — требует живого Postgres и исключён из прогона CI
по R-21. В CI не остаётся ни одной проверки квалификации, кроме офлайн-гейта.

**Why это меняет требование ко входу.** Пропущенный квалификатор не даёт ни отказа по привилегиям,
ни падения теста в CI. Он даёт ответ без строк, как в WI-47.

### Устройство гейта

Гейт ищет неквалифицированные имена таблиц движка и завершается с ошибкой на каждом найденном,
называя файл и строку. Список таблиц гейт читает из миграции, а не из зашитого перечня.

**Why такой источник списка.** Зашитый перечень расходится с миграцией на первой добавленной
таблице, и расхождение читается как «гейт прошёл».

## Тест-кейсы

### Сквозные тесты
1. **TC-E2E-01:** запрос возвращает те же строки при подменённом `search_path`
   - Входные данные: соединение с `search_path = pg_catalog`
   - Ожидаемый результат: те же строки, что при умолчании (AC-46)
2. **TC-E2E-02:** механизм доступа пишет и читает через реальную таблицу
   - Входные данные: одна запись и одно чтение через механизм доступа, на клиенте записи
   - Ожидаемый результат: записанное значение читается обратно; методы репозиториев проверяют
     задачи 014-07, 014-27 и 014-30

### Модульные тесты
1. **TC-UNIT-01:** неквалифицированная ссылка в `packages/core/src` останавливает гейт
   - Входные данные: временная правка запроса на `FROM snapshots` в файле `packages/core/src`
   - Ожидаемый результат: гейт завершается с ошибкой и называет файл и строку
2. **TC-UNIT-02:** неквалифицированная ссылка в `packages/mcp-server/src` останавливает гейт
   - Входные данные: временная правка на `FROM api_tokens` в файле
     `packages/mcp-server/src/engine/pg-engine-store.ts`
   - Ожидаемый результат: гейт завершается с ошибкой и называет файл в `packages/mcp-server/src`
3. **TC-UNIT-03:** гейт со входом из одного пакета не наблюдает правку TC-UNIT-02
   - Входные данные: тот же файл `packages/mcp-server/src`, вход гейта сужен до `packages/core/src`
   - Ожидаемый результат: сужённый вход даёт «гейт прошёл»; тест закрепляет требование двух пакетов
4. **TC-UNIT-04:** неквалифицированный `CREATE TABLE` в миграции останавливает гейт
   - Входные данные: строка `CREATE TABLE IF NOT EXISTS diagnostics (` в `sql/migrations/*.sql`
   - Ожидаемый результат: гейт завершается с ошибкой; постусловие §10.2.1 требует `onchain.<name>`
5. **TC-UNIT-05:** список таблиц гейта берётся из миграции
   - Входные данные: таблица, добавленная в миграцию и не добавленная в код гейта
   - Ожидаемый результат: её неквалифицированная ссылка отвергается без правки кода гейта

### Регрессионные тесты
- `pnpm test`; сьюта не должна требовать поднятой базы

## Примечания

Тесты `TC-E2E-01` и `TC-E2E-02` требуют живого Postgres. Оба помечаются как интеграционные и
исключаются из прогона CI по R-21 канона: сеть в CI запрещена. По этой причине AC-46 в CI
подтверждается только офлайн-гейтом.

Миграцию задача не создаёт. Двенадцать таблиц `data-model.md` §4.4 — восемь по §4.5 плюс четыре
аналога §4.2.4 — создаёт задача 014-35. Гейт берёт список таблиц из файла миграции, поэтому порядок
задач на его работу не влияет.

Расхождение закрыто: задачи 014-29 и 014-30 приведены к пакету `mcp-server`. Файлы
`packages/mcp-server/src/engine/request-trace-store.ts` и
`packages/mcp-server/src/engine/pg-engine-store.ts` названы одним путём в задачах 014-02, 014-03,
014-29 и 014-30 — по `security.md` §7.5.1 и `deployment.md` §10.2.1.

Направление зависимости одно: эта задача берёт клиент записи задачи 014-39 и не правит ни одного её
файла. Задача 014-39 не правит `pg-engine-store.ts`.
