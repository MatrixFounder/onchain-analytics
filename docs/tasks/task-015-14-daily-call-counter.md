# Задача 015.14: суточный счётчик вызовов в той же транзакции `checkAndReserve` на обеих осях

## Связь со сценариями

- UC-3 — счётчик вызовов Blockscout переводит `entity.labels` на платный Nansen

<!-- contract:goal -->

## Цель задачи

Научить `checkAndReserve` читать и увеличивать `usage.calls_made` в той же транзакции, в которой он
уже сравнивает кредитный потолок.

**Why в той же транзакции.** Два процесса делят одну базу состояния. Раздельные чтение и запись
дали бы обоим пройти собственную проверку по устаревшему значению — тот же довод, которым SEC-1
свёл минутное окно в одну транзакцию (`packages/core/src/cache/budget-store.ts:57-61`).

**Why счётчик вызовов, а не кредитов.** `costOf` blockscout возвращает 0, и `used + 0 > ceiling`
ложно для всей жизни любой корзины при любом потолке (R-9.4,
`packages/core/src/cache/ddl.ts:98-102`).

### Оператор оси SQLite

Проверка стоит внутри тела `db.transaction(...)`, между суточной кредитной проверкой (`:343`) и
проверкой минутного окна (`:354`).

```ts
// PLANNED — packages/core/src/cache/budget-store.ts, внутри тела транзакции
if (dailyCalls !== undefined) {
  if (typeof usedCalls !== 'number' || !Number.isFinite(usedCalls)) {
    return { ok: false, reason: `daily call check failed closed for provider=${provider}: …` };
  }
  if (Number.isNaN(dailyCalls.ceiling) || usedCalls + 1 > dailyCalls.ceiling) {
    return { ok: false, reason: `${DAILY_CALL_EXHAUSTED_DETAIL}${provider}: …` };
  }
}
```

**Why fail-closed на неразрешимом сравнении.** `>` отвечает `false` при `NaN`, а `false` здесь
означает «разрешено». Тот же довод уже записан у двух соседних проверок (`:312-315`, `:359-360`).

**Why значение читается из той же строки, что и кредиты.** Один `SELECT` вместо двух: колонка
лежит на той же строке `(provider, day)`.

### Оператор оси Postgres

Вторая граница входит в тот же условный `INSERT … ON CONFLICT DO UPDATE`, повторяясь в обеих
ветвях — как это уже сделано для минутного окна (`packages/core/src/pg/budget-store.ts:330-340`).

```sql
-- PLANNED — packages/core/src/pg/budget-store.ts, суточный оператор
INSERT INTO onchain.usage (provider, day, credits_used, calls_made, updated_at)
SELECT $1, $2, $3, 1, $4 WHERE ($5 IS NULL OR $3 <= $5) AND ($6 IS NULL OR 1 <= $6)
ON CONFLICT (provider, day) DO UPDATE SET
  credits_used = onchain.usage.credits_used + $3,
  calls_made   = onchain.usage.calls_made + 1,
  updated_at   = $4
WHERE ($5 IS NULL OR onchain.usage.credits_used + $3 <= $5)
  AND ($6 IS NULL OR onchain.usage.calls_made + 1 <= $6)
RETURNING credits_used, calls_made;
```

Пустой `RETURNING` — отказ; `dailyRefusal` делает один дополнительный `SELECT` ради текста.

**Why отдельное чтение ради текста.** Нулевой результат не говорит, какая из двух границ отказала,
а операторские ответы на них разные: поднять потолок кредитов либо ждать следующих суток. Тот же
приём уже применён к окну (`:319-323`).

**Why `$6` допускает `NULL`.** `ceilingParam` (`:95-98`) переводит отсутствующую и бесконечную
границу в `NULL`, и ветвь `$6 IS NULL` оставляет вызов неограниченным по вызовам.

**Why сравнение стоит внутри оператора.** Под `READ COMMITTED` два соединения прочитали бы одно
значение и оба прошли бы проверку. Блокировка строки в ветви конфликта — единственная точка
сериализации (`:114-117`).

### Текст отказа

`daily calls spent for provider=<id>: <N> of <M> calls already made today (day starts <ts>)`

| Отказ                   | Начало текста                     | Источник                      |
| :---------------------- | :-------------------------------- | :---------------------------- |
| суточный по кредитам    | `budget exceeded`                 | `cache/budget-store.ts`       |
| минутный по кредитам    | `velocity limit reached`          | `cache/budget-store.ts`       |
| минутный по вызовам     | `call rate limit reached`         | `cache/budget-store.ts`       |
| **суточный по вызовам** | `daily calls spent for provider=` | `DAILY_CALL_EXHAUSTED_DETAIL` |

**Why текст не пересекается с соседями.** AC-25 проверяет класс отказа по значению, а не по факту
падения любого исключения.

**Маркер принадлежит классу, деталь — хранилищу (исправлено при исполнении 2026-08-28).** Первая
редакция этого раздела предписывала хранилищу начинать текст словами `daily call ceiling reached`,
а `ProviderCallCeilingExceededError` по объявлению §3.5.4 строит `daily call ceiling reached:
${reason}` поверх него. Измерено зондом на собранном гейте: оператор читал
`daily call ceiling reached: daily call ceiling reached for provider=blockscout: 625 of 625 …`.
Отсюда две стороны: хранилище отдаёт деталь без маркера через экспортируемую константу
`DAILY_CALL_EXHAUSTED_DETAIL`, обе оси читают одну эту константу, класс добавляет маркер один раз.
Метод 015-01, задачи 015-29 и 015-30 продолжают опираться на `daily call ceiling reached:` — они
читают текст КЛАССА, и правка их не затрагивает.

**Отказ, не решивший вопрос о потолке, не выдаёт себя за исчерпание.** Тем же измерением: обе ветви
fail-closed этого же `checkAndReserve` — нечитаемое значение `credits_used` или `calls_made`,
записанное посторонним процессом, ради чего ветви и заведены, — выходили наружу как
`daily call ceiling reached: budget check failed closed …`. `ensureCallBudget` теперь ветвится по
`DAILY_CALL_EXHAUSTED_DETAIL`: исчерпание даёт `ProviderCallCeilingExceededError`, всякий иной отказ
— `ProviderCallGateUnavailableError` с текстом `daily call gate unavailable: …`, не содержащим
маркера. Без этого десятый класс отказа задачи 015-15, чей признак `/daily call ceiling reached: /i`,
маршрутизировал бы испорченный леджер как исчерпанный потолок.

### `recordDelta` колонку не трогает

Ось SQLite связывает `calls: 0`. Ось Postgres присваивает `calls_made = onchain.usage.calls_made`.

**Why присваивание самой себе выписано, а не опущено.** «Этот оператор не трогает счётчик вызовов»
становится свойством текста, которое читатель или статический гейт проверяет, вместо отсутствия,
которое надо заметить (`packages/core/src/pg/budget-store.ts:471-476`).

**Why счётчик не возвращается.** Вендорский обход состоялся. Возврат вызова дал бы череде
дешёвых-и-возвращённых вызовов пройти мимо предела, который для них и заведён
(`data-model-billing-ledger.md:294-296`).

### Один код гейта на два провайдера

Внутри `checkAndReserve` имени провайдера нет: потолок приходит параметром, как уже приходят
`cost`, `ceiling` и `velocity` (`data-model-billing-ledger.md:313-316`).

**Why это и есть AC-20.** Провайдер-специфичная ветка внутри гейта повторила бы разбор для
следующего бесплатного провайдера — RISK-4 спецификации.

### Читатель `getDailyCalls`

Возвращает накопленное значение `usage.calls_made` для пары `(provider, dayBucketMs)`; ноль, когда
строки нет.

**Why читатель нужен.** Существующие читатели показывают кредиты за сутки и обе величины минутного
окна (`cache/budget-store.ts:86-92`). Суточных вызовов не читает ни один, а тесты и замер UC-7
обязаны их предъявить.

### Чего задача не делает

- Параметр `dailyCalls` в сигнатуру не вводит: его объявляет задача 015-13.
- Колонку не создаёт: ось SQLite — задача 015-02, ось Postgres — задача 015-03.
- В адаптер blockscout гейт не включает: задача 015-15.
- Ключ `BLOCKSCOUT_DAILY_CALL_CAP` не читает: задача 015-16.

## Примечания

Задача зависит от 015-02 (колонка на оси SQLite), 015-03 (колонка на оси Postgres) и 015-13
(параметр `dailyCalls` и класс отказа).

Читатель `getDailyCalls` объявляется здесь, а не в 015-13: контракт гейта — параметр
`checkAndReserve`, а сам счётчик вводит эта задача.

Минутный счётчик `usage_window.calls_made` остаётся образцом паттерна, а не механизмом суточного
потолка: строки старше часа выпалываются (`WINDOW_RETENTION_MS`,
`packages/core/src/cache/budget-store.ts:144`), поэтому суточную сумму из него не восстановить
(R-9.1).

Критерий AC-19 цитируется и сценарием UC-4. Маршрутная половина UC-4 — типизированный отказ на
`token.holders` и `chain.transactions` — принадлежит задачам 015-15 и 015-17.
