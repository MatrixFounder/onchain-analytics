# Задача 012-4 — манифест capability: тип, модуль, 20 строк с выводом чисел, валидация на конструировании

**Эпики:** E-2 (манифест, D3), E-4 (бюджет дедлайна) · **Требования:** R-136, R-137, R-148, R-149 ·
**Критерии приёмки:** AC-4, AC-13 (первая половина) · **Фаза:** 4 из 10 · **Зависимости:** 012-1, 012-2

## Use Case Connection

- **UC-1** — разработчик описывает манифест новой способности и забывает `deadlineMs`: компилятор
  отказывает, потому что поле обязательное, а не строка в таблице, которую можно не заметить.
  Провал, который надо исключить: способность собирается и работает без дедлайна, потому что поле
  «на всякий случай» опционально.
- **UC-3** (частично) — числа `deadlineMs`/`paidLegMs` для `entity.labels` рождаются здесь.
- **UC-7** (частично) — 15-секундный потолок ниже `MAX_WAIT_MS = 30_000`, поэтому насыщенный бакет
  теперь отказывает быстро вместо 30-секундного сна.

<!-- contract:goal -->

## Цель задачи

Завести `src/capability-manifest.ts` — один декларативный коммитнутый литерал, покрывающий все **20**
маршрутизируемых способностей, — сделать его **инжектируемым** параметром `CapabilityRegistry` с
проверкой полноты **на конструировании**, и написать каждое число дедлайна вместе с записью его
вывода.

## Описание изменений

### Новые файлы

#### `packages/core/src/capability-manifest.ts`

```ts
type CapabilityManifestBase = {
  ttlSeconds: number;
  deadlineMs: number; // ТОЛЬКО отменяемая часть вызова (OD-3)
  shareable?: boolean; // первый читатель — ADR-003 D5 (T-014); в T-012 нет ни одного
  paidLegMs?: number; // только там, где маршрут достаёт до tier:'paid' адаптера
};

export type CapabilityManifest =
  | (CapabilityManifestBase & { shape: 'point' })
  | (CapabilityManifestBase & { shape: 'set' | 'series' });

export const capabilityManifests: Readonly<Record<string, CapabilityManifest>>;
```

**Union, а не плоский интерфейс — но с точной оценкой того, что он даёт СЕГОДНЯ.**

Обе ветви сейчас различаются **только литералом `shape`**, поэтому структурно union взаимозаменяем
с плоской формой, и поле слияния, добавленное в **базу**, было бы легально и на `point`. Значит
union **не делает ограничение действующим** — он делает его **выразимым**. T-013 добавляет поле
слияния **в одну ветвь**, и «слияние на `point`» становится ошибкой компиляции в тот же момент,
без переписывания типа. Стоит это **нуля** новых полей сегодня.

Первая редакция говорила «union — это и есть весь механизм форвард-совместимости R-136(d)»; это
завышение снято.

**Отклонено (F-5, вариант «сделать ограничение действующим сразу»):** добавить в ветвь `point` поле
`mergeKey?: never`. Это пред-выбор **имени**, которого T-013 ещё не делала: назови она поле иначе —
и запрет охраняет несуществующий ключ: входа, на котором сторож падает, не существует. Сторож без
такого входа здесь запрещён тем же правилом, что и везде в этой задаче.

### Аудит `shape` (OQ-T012-1) — 12 из 20 способностей

**ADR-002 D3 уже назвал 8:** `point` — `token.price`, `chain.tvl`, `chain.supply`; `set` —
`entity.labels`, `token.holders`, `wallet.balances.native`; `series` —
`privacy.shielded_pool.history`, `platform.metrics.history`.

**Остальные 12 классифицируются чтением фактического типа возврата `normalize()`.** Правило: одно
значение об одном субъекте → `point`; неупорядоченная коллекция однородных элементов → `set`;
упорядоченный по `ts` ряд → `series`. Стартовые гипотезы (подтвердить чтением, расхождение — работа
аудита, а не ошибка плана):

| Способность                                                                  | Гипотеза    | Где смотреть                                                         |
| ---------------------------------------------------------------------------- | ----------- | -------------------------------------------------------------------- |
| `token.metadata`                                                             | `point`     | `adapters/coingecko/index.ts`                                        |
| `pairs.new`, `pool.info`                                                     | `set`       | `adapters/dexscreener/index.ts:125` — `normalize` → `Pool[]`         |
| `protocol.tvl`                                                               | `point`     | `adapters/defillama/index.ts` — `ProtocolTvlResult`                  |
| `dex.volume.history`                                                         | `series`    | `adapters/defillama/index.ts:66` — `DexVolumeResult.series[]`        |

### 20 строк с записью вывода (R-149)

- `ttlSeconds` переносятся **побайтово** из `cache/ttl.ts`'s `TTL_SECONDS` **вместе с их
  обоснованиями**. Ни одно значение TTL в этой задаче не меняется.
- `deadlineMs` и `paidLegMs` — по таблице ниже. **Каждый комментарий обязан назвать измеренную
  огибающую И применённое значение**, и, когда они расходятся, сказать, что применённое —
  **потолок владельца** (OD-2/OD-3), а не измерение, и что именно им срезается.

| Ярус (по составу маршрута)                    | `deadlineMs` | Способности                                                                                                                            | Измеренная отменяемая часть               | `paidLegMs` |
| --------------------------------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | ----------- |
| Один свободный адаптер, одна попытка          | ~15_000      | `token.price`, `token.metadata`, `pairs.new`, `pool.info`, `protocol.tvl`, `chain.tvl`, `dex.volume.history`, `wallet.balances.native` | `30 + 4×15` = 90 с                        | —           |
| То же, адаптер с `REQUEST_TIMEOUT_MS = 5_000` | ~15_000      | `token.holders`, `chain.supply`                                                                                                        | `30 + 4×5` = 50 с                         | —           |
| **ПЕРЕОПРЕДЕЛЕНИЕ** (см. ниже)                | ~15_000      | `privacy.shielded_pool`, `platform.{identities,contracts,documents,credits}`                                                           | 90 с; `dash-platform` даёт 0              | —           |
| ≤2 свободных адаптера последовательно         | ~30_000      | `privacy.shielded_pool.history`, `platform.metrics.history`                                                                            | 90 с + не-HTTP подвызов `pg-history`      | —           |
| Платный композит — только отменяемая часть    | ~60_000      | `entity.labels`                                                                                                                        | **140 с** = 50 (blockscout) + 90 (ресинк) | 270_000     |
| Платный композит — только отменяемая часть    | ~60_000      | `smart-money.flows`, `token.risk`                                                                                                      | 90 с (ресинк `/account`)                  | 180_000     |

**Деривации, записываемые отдельно.** HTTP-шаблон к ним не применим:

- **`pg-history`** ходит по протоколу Postgres, а не через `safeFetch`: хопов редиректа нет, есть
  только `MAX_WAIT_MS` лимитера (`capacity 2, refillPerSec 0.2`) и время запроса.
- **`dash-platform`** не ходит никуда (`isAvailable()` безусловно `{ok:false}`) и добавляет **ноль**
  к пяти парным маршрутам. Комментарий обязан сказать, что число вырастет в тот день, когда приедет
  живой gRPC-транспорт.

  **Why.** Без этой пометки будущая задача унаследует неверную границу без единой диагностики.

- **`paidLegMs`** — **худший случай по аргументам**, не фиксированное число подвызовов.
  `entity.labels` в дефолтном ярусе делает **2 ИЛИ 3** подвызова под одним резервом
  (`nansen/reconcile.ts:8`). Публикуется граница 3 × 90 = 270_000. `smart-money.flows` и
  `token.risk` — по два подвызова: 2 × 90 = 180_000.

### Одна строка — ПЕРЕОПРЕДЕЛЕНИЕ утверждённого числа, и оно объявляется

Строка таблицы «`deadlineMs`/`paidLegMs` by capability» в `system-architecture.md`, адресуемая
**списком способностей** (`privacy.shielded_pool`, `platform.identities/contracts/documents/credits`),
присваивает им
**~30_000** по ярусу «≤2 свободных адаптера».

**Адресовать эту строку номером строки нельзя.** Сразу под ней стоит **визуально идентичная**
строка `~30_000` для `privacy.shielded_pool.history` и `platform.metrics.history` (два свободных
адаптера последовательно — `platform-explorer` + `pg-history`), и её значение **верное, она не
трогается**. Строка адресуется списком способностей в колонке Capability.

План ставит **~15_000**: второй адаптер этих
маршрутов — `dash-platform` — имеет безусловно ложный `isAvailable()` и не выполняет **ни одной**
сетевой попытки, то есть маршрут фактически одноживо-адаптерный. Это признаёт и сама колонка
деривации архитектурной строки («`dash-platform` (unconditionally unavailable today)»), продолжая
при этом считать его за адаптер яруса.

**Порядок действий обязателен: иначе утверждённое число переписывается молча, а новый
WI-28-гейт пропускает такую правку как соответствующую — форма дефекта WI-24:**

1. здесь (012-4) число помечено **переопределением**, а не выравниванием;
2. в 012-5 правка документа вносится **как переопределение с однострочной деривацией**;
3. в 012-10 решение закрывается записью в `open-questions.md`.

**Выравнивание и переопределение не должны выглядеть одинаково в дифе.** Оговорка §0.2a — часть
деривации: с приездом живого gRPC-транспорта `dash-platform` число возвращается к двухадаптерному
ярусу, и это записано рядом с числом, а не только здесь.

**Числа — стартовое присвоение.** R-148(e) требует присвоения против измеренной огибающей именно
этой способности, а не механического округления к ближайшему ярусу; любая правка приезжает со своей
записью вывода.

**Следствие, которое надо назвать вслух:** 15-секундный потолок **ниже** `MAX_WAIT_MS = 30_000`,
поэтому на насыщенном бакете `point`-способность теперь отказывает вместо 30-секундного сна. Это
UC-7, а не регрессия. Обратная сторона: свободный вендор, успешно отвечающий дольше 15 с, начнёт
получать отказ. Реакция на такое наблюдение — **поднять `deadlineMs` этой способности с новой
записью вывода**, а не ослабить механизм.

### OQ-T012-5 — решение задачи

Исполняемого **падающего** тип-теста «слияние нельзя объявить на `point`» в T-012 **нет**: поля
слияния не существует, охранять нечего, а у такого теста нет входа, на котором он падает.
Вместо него:

1. дискриминированный union — сам механизм;
2. намерение записано в докстринге типа (кто и когда добавит поле слияния и почему оно будет
   валидно только на `set`/`series`);
3. **исполняемый сторож объявления**: тест читает исходник `capability-manifest.ts` и требует, чтобы
   `CapabilityManifest` оставался union'ом с двумя ветвями. Прецедент — `ttl-coverage.test.ts`,
   читающий свой источник. Схлопывание union'а в плоский интерфейс до T-013 роняет этот тест.
   **Что этот сторож НЕ доказывает:** он проверяет форму объявления, а не правило слияния — правила
   пока нет. Сказано прямо, чтобы гейт не читался сильнее, чем он есть.

## Тест-кейсы

### Юнит

- **TC-UNIT-01** (перечисляющий, R-136/R-138d) — для **каждой** `route.capability` из
  `providers.config.ts` есть запись манифеста. Guard: `routes.length > 10` и
  `Object.keys(capabilityManifests).length > 10`, иначе проверка вакуумна.
- **TC-UNIT-02** — обратная сторона: запись манифеста для capability, которую ничто не маршрутизирует,
  — падение (мёртвая строка читается следующим как обслуживаемая способность).
- **TC-UNIT-03** — каждая запись несёт `shape`, `ttlSeconds`, `deadlineMs`; `ttlSeconds` и
  `deadlineMs` — положительные числа.
- **TC-UNIT-04** (R-137) — ни одна запись не несёт ключей `chains`/`providers`/`price`/`cost`;
  плюс типовой `@ts-expect-error` на литерале манифеста с любым из них.
- **TC-UNIT-05** — `ttlSeconds` **побитово равны** прежней таблице: тест сверяет каждую из 20 записей
  со списком значений, зафиксированным до переезда. Правка TTL под видом переезда роняет этот тест.
- **TC-UNIT-06** (R-148/R-149) — каждая запись, у которой есть `paidLegMs`, лежит на маршруте,
  достающем до `tier: 'paid'` адаптера; и наоборот — способность без платного подвызова `paidLegMs`
  **не несёт** («на всякий случай» запрещено).
- **TC-UNIT-07** — сторож **объявления** union'а (OQ-T012-5). Докстринг обязан сказать, что он
  охраняет: тип остаётся **двухветвевым union'ом**, чтобы T-013 могла добавить поле слияния в одну
  ветвь. Он **не** охраняет правило слияния (правила нет) и **не** делает «слияние на `point`»
  ошибкой сегодня (обе ветви пока различаются лишь литералом `shape`). Формулировка вроде
  «гарантирует, что слияние нельзя объявить на `point`» была бы ложной.
- **TC-UNIT-08** (R-149, механизирует «оба числа») — сторож **записи вывода**. Тест читает
  исходник `capability-manifest.ts`. Каждая строка с `deadlineMs` (и с `paidLegMs`) обязана нести
  в прилегающем комментарии **два** числа: измеренную огибающую и применённое значение. Строка с одним числом роняет тест. Прецедент источника-как-предмета-проверки —
  `ttl-coverage.test.ts`. **Чего этот сторож не доказывает** (сказано в его докстринге): он не
  проверяет, что арифметика верна — верность числа против задокументированной деривации проверяет
  расширенный WI-28-гейт в 012-5. Здесь проверяется только то, что срез не выдан за деривацию.

## Критерии приёмки

- [ ] `CapabilityManifest` — дискриминированный union; `ttlSeconds` и `deadlineMs` обязательны;
      `shareable`/`paidLegMs` необязательны
- [ ] 20 записей покрывают все маршрутизируемые способности; ни одной лишней
- [ ] `shape` двенадцати способностей определён **чтением `normalize()`**, а не гипотезой плана;
      расхождения с таблицей гипотез записаны
- [ ] **Каждое `deadlineMs` и каждое `paidLegMs` несёт запись вывода, называющую ОБА числа:
      измеренную огибающую И применённое значение.** Запись прямо говорит, какое из них измерение,
      какое — потолок владельца (OD-2/OD-3), и что именно потолком срезается. Комментарий с одним
      числом не проходит приёмку, даже если число верное.

      **Why.** R-149 делает эти комментарии источником, откуда следующая правка кода их **копирует**; скопированный срез, выглядящий деривацией, воспроизводит происхождение самой цифры 410 с

- [ ] Строка `privacy.shielded_pool` + четыре `platform.*` помечена в коде **переопределением**
      архитектурного `~30_000`, с причиной и с условием возврата к двухадаптерному ярусу; передана
      в 012-5 как переопределение, а не как выравнивание
- [ ] **Атомарность:** если цикл затягивается, задача режется по объявленной границе — пункты плана 4.3/4.4
      (аудит `shape` + данные манифеста) отделяются от пункта плана 4.5 (конструктор и валидация).
      Это единственный допустимый разрез: он не разрывает пару «число ↔ запись вывода»
- [ ] Для `pg-history` и `dash-platform` запись вывода **не** переиспользует HTTP-шаблон
      (`адаптеры × попытки × таймаут × хопы`) и называет фактическую механику; у `dash-platform`
      сказано, что число вырастет с приездом живого gRPC-транспорта
- [ ] Ни один `ttlSeconds` не изменился (TC-UNIT-05)
