# Задача 014.10: посессионный `McpServer` поверх общих зависимостей `[LOGIC]`

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети
- UC-2 — две сессии делят вендорскую квоту

<!-- contract:goal -->

## Цель задачи

Создавать экземпляр `McpServer` на сессию, оставив `registry`, `budgetStore` и `CacheStore`
процессными.

**Why раскладка такая.** Кеш и бюджет разделяются между сессиями по определению: общий кеш — смысл
кеша, общий бюджет — смысл потолка. Экземпляр сервера несёт состояние протокола одной сессии, и его
разделение смешивает протокольные состояния двух клиентов. Раскладка подтверждена пробой 014-01.

## Тест-кейсы

### Сквозные тесты

1. **TC-E2E-01:** две сессии получают разные экземпляры `McpServer` и один `registry`
   - Ожидаемый результат: ссылки на серверы различны, ссылка на реестр одна (AC-18)

### Модульные тесты

1. **TC-UNIT-01:** экземпляр удаляется по завершении сессии
   - Ожидаемый результат: размер соответствия возвращается к исходному
2. **TC-UNIT-02:** общие зависимости собираются один раз
   - Входные данные: счётчик на конструкторе `CacheStore`
   - Ожидаемый результат: единица при трёх сессиях
3. **TC-UNIT-03:** `budgetStore` процессный
   - Входные данные: счётчик на конструкторе `SqliteBudgetStore` и три созданные сессии
   - Ожидаемый результат: конструктор вызван один раз; три вызова `createServer` получили одну и ту
     же ссылку на хранилище бюджета (R-2.2)

### Регрессионные тесты

- `e2e.stdio.test.ts` зелёный; stdio продолжает собирать один экземпляр

## Примечания

RISK-6 спецификации — рост памяти при невытесняемом соответствии `sessionId` → экземпляр. Удаление
по завершении сессии закрывает штатный путь; брошенная сессия закрывается задачей 014-13.

Задача 014-04 применяет сужение инвентаря в цикле `packages/mcp-server/src/server.ts:74` и ждёт
отсюда доставку прочитанного профиля в фабрику. Носителя архитектура не называет: §3.4.3 объявляет
одно новое необязательное поле `principals?: PrincipalResolver` в `CreateServerDeps`.
