# Задача 014.32a: покрытие сетей DexScreener измеряется генератором

## Связь со сценариями

- UC-1 — n8n вызывает способность по сети

<!-- contract:goal -->

## Цель задачи

Заменить литерал `DEXSCREENER_OBSERVED` генератором с закоммиченной уликой, чтобы `vendors.dexscreener`
называл сети, обслуживаемые вендором, а не сети, попавшие в один спот-чек.

**Требование.** R-33, критерий AC-51.

**Why.** Колонка не проставлена на 455 строках из 458, и рантайм читает `null` по первому из двух
определений — `docs/architectures/data-model.md:141`,
`` `null` = the vendor does not have the chain. ``. Замер 2026-08-18: вендор обслуживает 65 наших
сетей.
62 строки отказывают утверждением, которое вендор опровергает. Дефект зарегистрирован как
[L-18](../issues/l-18-the-registry-marks-62-dexscreener-served-chains-as-unsupported.md).

**Правило не меняется, меняется инструмент.** Докстринг генератора
(`packages/core/scripts/sync-chain-registry.ts:35-44`, `publishes no chain catalog, so this cannot be derived, only witnessed.`)
запрещает выдумывать идентификаторы. Запрет остаётся в силе. Каталога у вендора нет, а
пер-чейновый свидетель есть: маршрут пары отвечает HTTP 200 на известный сегмент сети и HTTP 400 на
неизвестный.

### Генератор

Контракт совпадает с `gen-defillama-dex-chains.ts` и `gen-nansen-coverage.ts`: **сам генератор** ни
из чего под `src/` не импортируется, он читает закоммиченную улику и пишет закоммиченный
`.ts`-модуль, ревью идёт по git-диффу. Эмитируемый модуль при этом лежит под `src/` и импортируется
рантаймом — ровно как `nansen/chain-coverage.ts`, который читает адаптер
(`packages/core/src/adapters/nansen/index.ts:9`,
`import { NANSEN_CHAIN_COVERAGE, NANSEN_EXHAUSTIVE_LABELS_CHAINS } from './chain-coverage.js';`).

1. Режим `--record` выполняет зонд и пишет улику. Кандидаты — `slug` и каждый `alias` каждой строки
   реестра. Улика записывает на каждого кандидата его `caip2`, HTTP-статус и, где ответ содержал
   строки, эхо-значение `pair.chainId`.
2. Режим по умолчанию читает улику и эмитит модуль.

**Оракул статуса.** `GET /latest/dex/pairs/{chainId}/{адрес}` отвечает 200 с телом `{"pairs":null}`
на маршрутизируемый сегмент сети и 400 с HTML-телом на немаршрутизируемый. Замер 2026-08-18:
`base` — 200, `seiv2` — 200, `sei` — 400, `zcash` — 400, `gnosis` — 400.

**Статус доказывает маршрутизируемость, а не тождество.** Значением колонки становится
**ответивший кандидат**, никогда не `slug`.

**Why.** `normalize()` фильтрует строки сравнением `pair.chainId === chain.vendors['dexscreener']`
(`packages/core/src/adapters/dexscreener/index.ts:182`,
`(pair) => pair.chainId === (chain.vendors['dexscreener'] ?? chain.slug),`) ⇒ записанный слаг вместо
вендорского идентификатора отбрасывает каждую строку, и способность отвечает пустой страницей.
Замер 2026-08-18: у 4 сетей слаг отвечает 400, а вендорский идентификатор отвечает 200 —
`op-mainnet` → `optimism`, `zksync-era` → `zksync`, `data-network` → `story`,
`robinhood-chain` → `robinhood`.

**Несколько ответивших кандидатов — отказ генератора, а не выбор.** Строка попадает в отчёт для
курирования, колонка остаётся `null`. Идиома совпадает с существующей записью — `packages/core/scripts/sync-chain-registry.ts:570`,
`'Ambiguous / rejected vendor joins — vendors.coingecko left null',`.

Замер 2026-08-18: ровно у одной сети из 65 ответили два кандидата. У `hyperliquid-l1` отвечают
`hyperevm` и `hyperliquid`, и это два разных сегмента вендора: пара
`0x6c9A33E3b592C0d65B3Ba59355d5Be0d38259285` резолвится под `hyperevm` и отвечает `pairs:null` под
`hyperliquid`. У остальных 64 ответил ровно один кандидат.

**`OQ-32a-2` закрыт решением владельца 2026-08-19: `hyperliquid-l1` → `hyperevm`.** Ответ выведен
из идентичности самой строки, а не выбран.

Строка реестра несёт `caip2: eip155:999` и `family: evm`, то есть по определению называет EVM-сеть,
а не книгу заявок.

Замер 2026-08-19 подтверждает, что это два разных предмета:

|                         | `hyperevm` | `hyperliquid`     |
| :---------------------- | :--------- | :---------------- |
| строк в выдаче          | 29         | 14                |
| различных `dexId`       | 8          | 1 — `hyperliquid` |
| строк с `liquidity.usd` | 29 из 29   | 0 из 14           |
| котировка               | разная     | всегда USDC       |

**Следствие для контракта.** Отсутствие `liquidity.usd` — вторая, независимая причина: `PoolSchema`
получил бы строки без `liquidityUsd` на способности, где это поле и есть ответ.

**Отказ генератора при двух кандидатах сохраняется.** Решение владельца снимает одну строку, а не
правило: `hyperevm` вносится курируемой записью, и второй кандидат по-прежнему обязан попасть в
отчёт.

**Эхо подтверждает тождество там, где тело ответа его содержит.** Кандидат, чей `pair.chainId`
никогда не наблюдался в теле ответа, записывается в улику как `unverified` и в колонку не попадает.

**Why.** Ответ 200 с телом `pairs:null` получает и сегмент, который держит данные, и сегмент, у
которого их нет ⇒ один статус не отличает их. Это распознавание пустого ответа как покрытия —
класс, зафиксированный в L-10.

**Порог правдоподобия.** Улика с числом сетей ниже 20 отвергается генератором.

**Why.** Число ниже порога означает смену формы маршрута или обрыв зонда ⇒ принятая улика сузит
покрытие до нуля, и результат неотличим от невыполненной задачи.

**Отказ вместо экранирования.** Идентификатор сети вне класса `/^[a-z0-9][a-z0-9-]*$/` не эмитится,
а роняет генератор. Доктрина `safeName` из `gen-defillama-dex-chains.ts`.

**Темп зонда.** Правило кандидатов даёт 854 строки. Замер 2026-08-18 покрыл 849 из них: зонд
отбрасывал кандидата вне класса `/^[a-z0-9-]+$/i`, и под это попали `shimmer_evm`, `titan_tkx`,
`lightlink_phoenix`, `tacchain_239-1` и `shiden network`.

**Пропуск заменяется отчётом.** Генератор зондирует все 854 и называет кандидата вне класса в
отчёте курирования. Молчаливый пропуск и измеренное отсутствие в улике неразличимы, а число 849
без названного фильтра делает замер невоспроизводимым.

Четыре параллельных запроса при паузе 220 мс дали 348 ответов 429 из 849. Пауза 320 мс без
параллелизма отработала за два круга без потерь. Генератор повторяет 429 и падает, если после
четырёх кругов остаётся хотя бы один.

### Три состояния колонки различимы (R-33.5)

Улика записывает на каждого кандидата исход зонда, а генератор переносит его в модуль третьим
значением рядом с идентификатором: `verified` — эхо наблюдалось; `excluded` — вендор ответил 400;
`unverified` — кандидат не зондировался или ответ не дал эха.

**Носитель третьего состояния — сгенерированный модуль, не колонка реестра.** Решение владельца
2026-08-19. Колонка `vendors.<id>` остаётся двузначной и описывает **именование**, а не покрытие:
`packages/core/src/chain/registry-core.ts:56`,
`Vendor NAMING only — "what this chain is called at vendor X". Never coverage: conflating the`.
Класть туда покрытие запрещено ровно тем дефектом, который чинит эта задача.

**Файл `packages/core/src/chain/coverage.ts`:**

- Тип `CoverageStatus = 'covered' | 'excluded' | 'unverified' | 'vendor-serves-chain-capability-absent'` —
  **четыре** значения, потому что исходов четыре, а не три

**Правило композиции: покрытие решает предикат, статус зонда — только текст отказа.** Исход зонда
**не** определяет покрытие. `coverageStatus` считается в два шага:

1. если булев предикат даёт `true` → `covered`, и статус зонда не спрашивается;
2. иначе спрашивается хук, и его ответ выбирает **исход и формулировку отказа**: `excluded` →
   `excluded`, «вендор не обслуживает эту сеть»; `unverified` → `unverified`, «зонд по этой сети не
   выполнялся»; `verified` → `vendor-serves-chain-capability-absent`, «вендор обслуживает эту сеть,
   но способность на ней не построена». Три формулировки, ни одна не совпадает с другой; четвёртый
   исход `covered` отказа не порождает вовсе.

**Why третья формулировка обязательна.** `verified` **не** влечёт покрытия: предикат адаптера требует
два условия, а зонд ставит одно —
`packages/core/src/adapters/dexscreener/index.ts:148`,
`chain.vendors['dexscreener'] != null && chain.nativeSymbol != null,`, и сверх того матрица
отбрасывает `deprecated` (`packages/core/src/chain/coverage.ts:89`,
`!chain.deprecated && routesFor(capability).some((route) => routeCoversChain(route, chain));`).
Пара (зонд подтвердил, покрытия нет) — не гипотетическая: она предписана этим же планом:
`docs/tasks/task-014-32c-pool-info-tool.md:159`,
`**TC-UNIT-02:** `chainSupport`возвращает`true`для`pool.info`на сети без`nativeSymbol``.
В реестре 23 строки несут `nativeSymbol: null`.
Без третьей формулировки такая сеть получила бы отказ «зонд не выполнялся» о сети, которую зонд
подтвердил, — то есть ложное утверждение в тексте, заведённом ради честности.

**Покрытие эта задача не расширяет.** Предикат остаётся прежним, `nativeSymbol` не смягчается;
смягчение для `pool.info` отгружает 014-32c.

- Функция `coverageStatus(capability, chain)` рядом с булевым предикатом
- Булев предикат становится `coverageStatus(...) === 'covered'`; ни один существующий вызывающий не
  меняет поведения (`packages/core/src/chain/coverage.ts:88`,
  `const computeCovered = (capability: string, chain: ChainInfo): boolean =>`)
- Третье состояние читается через необязательный хук адаптера `chainProbeStatus?(chain)`

**Файл `packages/core/src/adapters/registry.ts` — здесь строится отказ, и здесь выбирается текст:**

- Единственное место, где рождается обобщённый отказ по паре (способность, сеть):
  `packages/core/src/adapters/registry.ts:922`, `throw new CapabilityNotCoveredOnChainError({`. Оно
  вызывает `coverageStatus(...)` и передаёт `hint`, различающий **все три** исхода отказа —
  `excluded`, `unverified` и `vendor-serves-chain-capability-absent`

**Файл `packages/core/src/chain/errors.ts` — правки не требует, и это сказано, чтобы не искать:**

- Носитель текста уже есть и уже рендерится: `packages/core/src/chain/errors.ts:111`, `hint?: string;`,
  конкатенация на `:129`. Класс отказа не меняется, меняется вызывающий

**Why владелец назван поимённо.** Прежняя редакция ставила в список изменений `errors.ts` с правкой
нулевого объёма, и плечо «текст отказа» подпункта R-33.5 оставалось без исполнителя: поле есть,
заполнить его некому. Утверждение `«ни один существующий вызывающий не меняет поведения»` верно про
булев предикат и неверно про текст отказа — этот вызывающий обязан измениться, иначе TC-UNIT-08 не
на чем прогнать.

**Адаптер без хука отвечает `unverified`, и умолчание выбрано именно так.** Хук реализует один
адаптер, а предикат объявляют двенадцать; при умолчании `excluded` каждый из остальных одиннадцати
начал бы утверждать вендорское исключение там, где непокрытие имеет другую причину.

**Why умолчание `excluded` было бы воспроизведением L-18.** Непокрытие у соседей вендорским фактом
не является: `packages/core/src/adapters/rpc-evm/index.ts:150`, `chain.rpcHosts !== null &&`, а
`docs/architectures/data-model.md:142` читает этот `null` как нашу
кураторскую дыру, не как отсутствие сети у вендора; `packages/core/src/adapters/dune/index.ts:25`,
`chainSupport: (): boolean => false,` — сплошной отказ уровня M1, и «у вендора нет этой сети» ложно
про каждую сеть, которую Dune обслуживает. Правило прямое:
`packages/core/.AGENTS.md:1296`, `(R-58d): a false narrowing is as wrong as a false widening`.

**Обоснование через `nansen` снято как неверное.** Манифест перечисляет обслуживаемое, но предикат
адаптера отбрасывает сверх него: `packages/core/src/adapters/nansen/index.ts:160`,
`if (!hasAddressValidator(chain.family)) return false;`, и сам адаптер это записывает. То есть даже
у `nansen` «не покрыта» не равно «вендор её не обслуживает».

**Какой сломанный случай маскирует новое законное значение.** `unverified` — третий законный ответ
там, где раньше было два, и он снимает сеть с обвинения «вендор её не обслуживает», ничего не
утверждая взамен ⇒ он маскирует «зонд сломался и молча вернул пусто на всём каталоге». Поэтому
генератор падает при числе сетей ниже порога (TC-UNIT-02), а не эмитит каталог из одних
`unverified`. Это запись M6 памяти.

**Why.** Сегодня три состояния сходятся в один `null`, а `docs/architectures/data-model.md:141` читает `null` как
«вендор не имеет сети» ⇒ дефект L-18 воспроизводится внутри задачи, которая его чинит. R-58d требует
`unverified`, не `unsupported`.

## Примечания

**Перенос значения из предыдущего снимка.** Строка `packages/core/scripts/sync-chain-registry.ts:472`
(`dexscreener: DEXSCREENER_OBSERVED[caip2] ?? prev?.vendors.dexscreener ?? null,`) переносит
значение из предыдущего снимка. Правка `registry.data.json` руками переживает следующий `sync` при
литерале из трёх записей, и расхождение данных с генератором не обнаруживает ни один гейт. Чинить
надо генератор.

**Свежесть — обязанность оператора.** Сеть, появившаяся у вендора, становится доступной после
прогона `--record` и коммита снимка. Автоматически — никогда. Это тот же контракт, что у трёх
существующих генераторов.
